# 如何校验向量化的内容是否准确

> 本文档回答一个具体问题：把文档灌进 Dify 知识库后，**怎么证明「向量化后的内容」是准的**——不只是「切得对」，而是「检索时能命中正确的片段」。它是 `README.md` 与 `09_quality_gate.py` 的补充，重点补齐其中一直缺失的 **C 层（检索准确性）**，配套脚本 `10_validate_retrieval.py` 已落地。

---

## 一、先明确：什么叫「向量化内容准确」

一条 RAG 链路的准确，要分三层看，任何一层出错最终都表现为「检索不准」：

| 层 | 校验对象 | 回答的问题 | 工具 |
|----|---------|-----------|------|
| A 解析 | PDF → md 的文本 | 内容有没有丢、错、乱码 | `09_quality_gate.py parse` |
| B 分片 | md → 父段 / 子段 | 切的粒度对不对、切没切在句子里 | `09_quality_gate.py chunk` |
| **C 向量检索** | **embedding + 检索参数** | **向量化之后，检索能否命中正确片段** | **`10_validate_retrieval.py`（本文档）** |

**核心结论**：A、B 两层只保证「喂给 embedding 的文本是对的、切的单元是对的」，它们是 C 层的**必要非充分条件**。向量化是否准确，唯一终局判据是 C 层——**问它问题，看它命没命中**。所以「校验向量化内容是否准确」这件事，最终落在 C 层。

> 举例：就算 md 一字不差、分段也整齐，如果 embedding 模型对中文跨领域语义不敏感、或 `top_k`/`score_threshold`/重排权重配错，检索照样命中不了正确片段。A、B 层全都 PASS 也拦不住这类问题。

---

## 二、C 层原理：黄金测试集 + 召回指标

C 层不「猜」向量化对不对，而是直接测最终效果：

```
黄金测试集 { query_i -> 期望命中的相关片段 }
        │
        ▼
逐条调 Dify 检索接口 (hit-testing)
        │
        ▼
看 top-k 结果里命中哪些黄金片段 → Recall@k / Precision@k / MRR / nDCG@k
```

**判断「召回数据是否准确」要同时回答三个问题，缺一不可：**

| 维度 | 问的问题 | 指标 |
|------|---------|------|
| 召回全不全 | 正确片段有没有被召回来 | **Recall@k**（主指标） |
| 召回干不干净 | 召回来的片段是不是都相关 | **Precision@k** |
| 排对不对 | 最相关的有没有排最前 | **MRR**、**nDCG@k** |

- **Recall@k**：所有 query 里，正确片段落在 top-k 中的比例。衡量「能召回到」。
- **Precision@k**：top-k 结果里相关片段（唯一去重后）的占比。衡量「召回来的是不是都是对的」——只看 Recall 会漏掉「召回 8 条里 7 条是噪声」的情况。**注意：它要求黄金集每条 query 标多个相关片段才有意义**，只标 1 个时退化为 Recall 的缩放。
- **MRR**：正确片段第一次出现位置的倒数的平均值。衡量「能不能排到最前」。
- **nDCG@k**：把排序位置也折算进得分。衡量「排序质量」。

### 黄金测试集怎么造

这是 C 层唯一需要人工投入的地方，但规则简单：

1. **来源**：从切片后的 md（`sliced_output.md` / `1_1_new_process.md`）里，每个父分段（`@!@` 切出来的一段）抽 1 句能「唯一定位该段」的问题。
2. **规则**：
   - 问题应能从**该段唯一回答**，不能是跨段/泛化问题（如「全文讲了什么」不可用）；
   - 问题最好带原文档的**专有名词/编号**，避免歧义；
   - 每个问题标注相关片段：单相关用 `expected_anchor`（该段独有的一段原文子串）/`expected_id`（入库后 segment id）；**算 Precision@k 需用 `relevant` 数组标多个相关片段**。
3. **规模**：20~50 条起，覆盖全文档各章节；验收至少 30 条。

格式（JSONL，每行一条）：

```json
{"query": "制定本细则的依据是什么？", "expected_anchor": "制定目的"}
{"query": "3.2.1 条对结算周期有什么要求？", "expected_anchor": "结算周期"}
{"query": "结算周期与违约金分别怎么约定？", "relevant": [{"anchor": "结算周期"}, {"anchor": "违约金"}]}
```

## 三、如何判断召回数据是否准确（三种方式）

按「有无黄金集」从省事到严格逐级推进：

### 方式一：不靠黄金集，看 score 分布（最省事，先做这个）

直接看 `hit-testing` / `retrieve` 返回的每条 `score`，不用造黄金集就能发现明显问题：

- **分数塌陷**：所有结果 score 都在 0.3~0.4 挤成一团 → embedding 没区分度，或没开重排。
- **一刀切**：开了 `score_threshold_enabled` 但阈值设太高 → 大量 query 召回为空。
- **关键词倒挂**：纯关键词命中的片段分数远高于语义相关片段 → `keyword_weight` 设太高（`knowledge_base_uploader.py` 里是 0.3，若明显偏关键词命中就该调低）。

这个方法只能抓「明显不对」，判断不了「内容对不对」。

### 方式二：有黄金集，算自动指标（标准做法）

就是 `10_validate_retrieval.py` 的四件套（见第二节阈值表）。其中 **Precision@k 是关键补充**——它回答「召回来的是不是都是对的」，而 Recall 只回答「对的有没有进来」。三条一起看才能下结论。

### 方式三：人工判定相关性（终局尺子）

自动指标靠「标注」判断，标注本身可能不严谨。抽 20~30 条召回结果，人工对每条打分：

- **相关**（2 分）：内容直接回答 query 或包含其答案依据；
- **部分相关**（1 分）：沾边但答不全/答不精确；
- **无关**（0 分）：答非所问、跨章节、或只是同名词巧合。

判据：

- **Precision =（相关 + 部分相关）/ 召回总数**，< 0.6 说明噪声大（常见病：切分太粗、一个父段混了多个不相关小节）；
- **语义完整性**：相关片段能否「自足」地答对问题，还是要再跳转别处 → 对应 B 层的「子块只剩半句话」。

### 推荐顺序

```
1. 先看 score 分布          → 抓分数塌陷/阈值误设（5 分钟，零成本）
2. 跑 Recall/Precision/MRR/nDCG → python 10_validate_retrieval.py（判断全不全、干不干净、排对不对）
3. 补人工相关性打分          → 判断召回噪声（有噪声就回查 B 层切分粒度）
```

## 四、怎么跑

```bash
# 1. 先过 A/B 门禁（内容与分片都合法了，C 层结果才有意义）
python 09_quality_gate.py all --pdf 结算细则.pdf --md sliced_output.md

# 2. 造黄金集（JSONL），然后跑 C 层
python 10_validate_retrieval.py --golden golden.jsonl \
    --dataset-id <你的知识库ID> --api-key dataset-<你的KEY> \
    --base-url http://10.17.1.134:30001 --top-k 8
```

输出示例：

```
黄金集共 30 条，开始逐条检索（top_k=8）...
[1/30] 命中@#1   制定本细则的依据是什么？
[2/30] 命中@#3   3.2.1 条对结算周期有什么要求？
[3/30] 未命中    4.5 条关于违约金的约定？

=== C 层：向量化/检索准确性 ===
指标          实测      达标线    判定
Recall@k      0.900     0.850     PASS
Precision@k   0.625     0.600     PASS
MRR           0.783     0.700     PASS
nDCG@5        0.821     0.750     PASS
```

退出码：`0` = 达标，`1` = 存在不达标项（可接 CI 前置门禁）。报告写到 `quality_report_recall.md`。

### 阈值（默认，可 `--recall-min/--precision-min/--mrr-min/--ndcg-min` 覆盖）

| 指标 | 达标线 | 说明 |
|------|--------|------|
| Recall@top_k | ≥ 0.85 | 主指标；top_k 与知识库配置一致（本套默认 8） |
| Precision@k | ≥ 0.60 | 召回噪声；仅当黄金集标了多相关片段时才可信 |
| MRR | ≥ 0.70 | 正确片段平均排位 |
| nDCG@5 | ≥ 0.75 | 排序质量 |

## 五、不达标怎么归因（分层排查）

C 层只告诉你「结果不对」，归因要回到链路逐层对照：

| 现象 | 最可能的层 | 排查动作 |
|------|-----------|---------|
| 大量 query 召回为空 / 分数极低 | C（embedding/参数） | 检查 `embedding_model`、`search_method`、`score_threshold_enabled` 是否被误开（阈值过高会一刀切） |
| Precision 低、召回里混入噪声 | B（分片粒度） | 父段跨了多个不相关小节 → 回 `09_quality_gate.py chunk` 看「子块超限」「句尾完整性」 |
| 命中但永远排到第 3 名以后 | C（重排） | 检查 `reranking_enable` 是否真开、`bge-reranker-v2-m3` 是否可用；对比关重排前后 MRR |
| 召回了「相邻段」而非「目标段」 | B（分片粒度） | 目标段被切碎/跨段合并了 → 同上回查 chunk 门禁 |
| 召回内容里出现页眉/乱码/错字 | A（解析） | 回 `09_quality_gate.py parse` 看「页眉页脚残留」「乱码率」「字符保真度」 |
| 特定章节整体召不回 | A（漏页/漏段） | 看「页覆盖」「目录对齐率」是否 PASS |

**一句话**：C 层是「报警器」，A/B 层是「定位仪」。三层一起跑，才能把「检索不准」精确归因到某一步。

## 六、不靠检索的「直达核对」（可选，用于抽查）

C 层测的是端到端效果；如果怀疑「入库内容本身就不对」，可以直接拉取已入库的分段做对照，绕过检索：

1. **核对入库内容**：`GET /v1/datasets/{dataset_id}/documents/{document_id}/segments` 拉出全部父分段，与源 md 逐段 diff，确认上传时没有丢字、重复、错位。
2. **核对层级模型是否生效**：确认父段数 ≈ `@!@` 切出的段数、子块数 ≈ `@@` 切出的块数（可用 `09_quality_gate.py chunk` 的「父段/子块 token 分布」交叉验证）。
3. **核对检索参数落库**：确认 `embedding_model=qwen3-embedding-8b-vllm`、`hybrid_search`、`top_k=8`、`bge-reranker-v2-m3` 与 `knowledge_base_uploader.py` 里写的一致（上传时 payload 里的参数才真正生效）。

## 七、完整校验清单（Checklist）

| # | 步骤 | 命令 / 动作 | 通过标准 |
|---|------|------------|---------|
| 1 | A 层解析保真 | `python 09_quality_gate.py parse --pdf x.pdf --md x_norm.md` | 无 FAIL |
| 2 | B 层分片合法 | `python 09_quality_gate.py chunk --md sliced_output.md` | 无 FAIL |
| 3 | 造黄金集 | 每父段抽 1 句可唯一定位的问题，≥30 条；算 Precision 需标多相关片段 | 覆盖全章节 |
| 4 | C 层检索准确 | `python 10_validate_retrieval.py --golden golden.jsonl ...` | Recall@k ≥ 0.85 且 Precision@k ≥ 0.60 |
| 5 | 看 score 分布 | 抽 10 条召回看分数是否塌陷/倒挂 | 无硬伤 |
| 6 | 人工相关性终审 | 抽 20~30 条召回按相关/部分/无关打分 | Precision ≥ 0.6 |
| 7 | 不达标归因 | 按第五节对照排查 | 定位到 A/B/C 具体层 |
| 8 | 直达核对（抽查） | 拉 segments 与源 md diff | 内容一致 |

---

## 八、一句话总结

**A、B 层只能保证「喂进去的内容是对的」，要回答「向量化后准不准」，最终得靠 C 层：造一份黄金测试集，逐条问检索接口，Recall@k（全不全）+ Precision@k（干不干净）+ MRR/nDCG（排对不对）三件套一起看，达标才算向量化真正可用。三层门禁连起来跑，检索不准时才能从「结果不对」精确定位到「哪一层错了」。**
