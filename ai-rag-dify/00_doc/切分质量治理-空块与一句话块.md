# 知识库切分质量治理：空块与一句话块

> 记录一次 RAG 落地中遇到的问题：**Dify 知识库处理文档时不做内容清洗，直接按分隔符切分 → 向量化**，
> 结果库里出现大量空块（`---`、只剩标题行）和一句话块，直接影响检索质量。
> 本文给出实测数据、影响分级、根因分析、阈值判据与四级治理方案。
>
> 标注约定：**【实测】** 有数据/接口证据；**【推断】** 基于机制分析但未直接验证；**【待验证】** 需要可用环境或评估集才能定论。

---

## 一、问题现象

上传 Markdown 到 Dify 知识库，链路是：

```
原始 md  ──[按 segmentation.separator 做字符串 split]──> 父分段
         ──[按 subchunk_segmentation.separator 再 split]──> 子分段
         ──> embedding ──> 向量库
```

中间**没有"内容清洗 / 语义切块 / 短块合并"环节**，于是原文里的装饰行、列表项、短标题行都会被切成独立分段。

典型脏块：

| 类型 | 例子 | 成因 |
|---|---|---|
| 纯装饰符块 | `---`、`***`、`___` | Markdown 分隔线本身被空行包围，天然成为独立段 |
| 只剩标题行 | `## 三、故障定位` | 标题和正文之间有空行 |
| 一句话块 | `其上限为 200 条。` | 列表项 / 加粗要点被空行隔开，主语落在上一段 |
| 表格碎片 | `\| 3 \| 200ms \|` | 表格行被空行切开 |
| 断句块 | 段尾是"的 / 与 / 或" | `max_tokens` 硬截断，不按句号收敛 |

---

## 三、影响分级

### 3.1 危害小：空块 / 纯装饰符块【推断】

- **向量分支基本不会被召回**：`---` 的 embedding 几乎没有语义，与任意 query 的余弦相似度接近随机；
- **关键词分支也命中不了**：分词后为空；
- 真实代价仅：占向量库存储、把 `segment_count` / `average_segment_length` 撑大、
  让 `hit_count` 统计失真、人工评估时干扰视线。

结论：**该删，但不紧急**，且删除成本接近零。

### 3.2 危害大：一句话块 / 缺主语块

- **召回后不可用**。例如只有"其上限为 200 条"，谁的上限？模型只能猜或整段忽略。
  这比"没召回"更糟：白占上下文窗口，还可能误导生成。
- **被当前检索配置放大**：`top_k=3` + `score_threshold_enabled=false`，等于**命中即放行、没有相关性门槛**，
  一个废块直接吃掉 1/3 的上下文槽位。
- **父子分段叠加伤害**：父块若只有标题行，子块继承的上下文就是空的，层级结构等于失效。

### 3.3 不会有的事（避免过度焦虑）

- 不污染好块的向量：每个分段独立 embedding，互不影响；
- 不会显著拖慢检索；
- 不会让原本正确的知识"变错"，只是压低了检索精度的**上限**。

---

## 四、根因

1. **Dify 只做字符串 split**，不解析 Markdown 结构（标题层级、列表、表格、代码块）。
   `process_rule.rules.segmentation.separator` 就是一个字面量分隔符。
2. **预处理规则只有两个开关**：`remove_extra_spaces`、`remove_urls_emails`，
   **没有**"丢弃超短块""合并相邻短段""整块保留表格"这类能力。
3. **`max_tokens` 是硬截断**，不按句号收敛，尾部会出现"的 / 与 / 或"这类断句。
4. **默认分隔符不匹配文档形态**：网页上传默认给 `\n\n`，对"短行密集"的技术笔记切得过碎。

一句话：**不是 Dify 有 bug，而是"默认切分 + 无前置清洗"这个组合不适合短行密集的中文技术文档。**

## 五、判据阈值

| 指标 | 本次实测 | 可接受 | 必须治理 |
|---|---|---|---|
| 纯装饰符块占比 | 14.6% | 0（删除无成本） | > 5% |
| < 20 字块占比 | 30.5% | < 10% | > 20% |
| 父块 p50 | 34 字 | 200–500 字 | < 100 字 |
| 句尾断在 `，、；：的了吗和与` | 未统计【待验证】 | < 2% | > 5% |
| 代码围栏配对破坏 | 未统计【待验证】 | 0 | > 0 |

## 六、治理方案（按性价比排序）

### 方案 A：上传前清洗（首选）

切分之前对 md 做一遍结构化清洗，**不改正文语义**：

1. 删除**独立成行**的 `---` / `***` / `___`（整行替换为空行，不留残段）；
2. 连续空行压缩为一个空行；
3. **短段落合并**：长度 < N（建议 80 字）且不是标题 / 表格 / 代码块开头的段落，与相邻段落合并；
4. 代码块保护：三个反引号围栏内的内容不做清洗与断行处理；
5. 表格保护：连续的 `|` 开头行不拆开；
6. 页眉页脚去重：出现 ≥5 次的短行判定为页眉页脚并删除。

代价：一个一次性处理脚本；风险是规则过激会改变原意，因此需要**清洗前后 diff 抽查**。

### 方案 B：换父分隔符（改动最小）

不用 `\n\n`，改用标题锚点做父分隔符：

| 位置 | 建议 separator | 效果 |
|---|---|---|
| 父分段 | `## ` | 父块 ≈ 一节，天然有语义边界，不会产出装饰符块 |
| 子分段 | `\n` | 保留段内的细粒度 |
| 退化选择 | `\n\n` + 前置清洗 | 文档没有稳定的标题层级时用 |

注意：`separator` 是字面量字符串，`## ` 后面那个空格要带上；文档里标题格式不统一（有的用 `###`）时会漏切，需要先统一标题层级。

### 方案 C：客户端全权切块（控制力最强）

走「建空文档 + 手工推分段」路径（`POST /v1/datasets/{id}/documents/{doc_id}/segments`），
自己按 Markdown 结构切块、自己合并短块、自己给每块补 `# 主标题 / ## 小节` 前缀。
`dify_uploader_v120.py` 已实现该路径（分批提交 + 索引完成校验）。

代价：切分逻辑要自己维护，且每个文档多一次"建空文档 + 等索引"的往返（1.20.0 下空文档也必须先 `completed` 才能推分段）。

### 方案 D：检索侧兜底（治标）

| 参数 | 现在 | 建议 |
|---|---|---|
| `top_k` | 3 | 5 ~ 8 |
| `score_threshold_enabled` | false | true，阈值 0.3 起调 |
| `reranking_enable` | true | 保持（已是最有效的降噪手段） |
| hybrid 权重 | keyword 0.3 / vector 0.7 | 中文技术文档可试 0.2 / 0.8 |

能挡住部分噪音，但治不了"一句话块本身没信息"这个根本问题。

## 七、验证方法

复用仓库里已有的质量门禁 `01-minerU-block/09_quality_gate.py`：

```bash
cd ai-rag-dify/01-minerU-block

# 只查分片合法性（未切分检测 / 父块超限 / 子块超限 / 句尾完整性 / 代码块配对 / 标记误插 / 体量分布）
python 09_quality_gate.py chunk --md <清洗后的md>
```

判定重点：**体量分布 p50 / p95 / max**、句尾断句率、`未切分检测`。
建议对"治理前 / 治理后"各跑一次，把 p50 从 34 字提上来作为验收指标。

另需人工抽样：随机取 20 个父块自问"只看这一块能不能回答它对应的问题"，1–5 分打分，均值 < 3.5 说明粒度仍不对。
