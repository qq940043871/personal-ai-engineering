# 02 · 低代码编排与中台机制

> 定位：ownrag 的**"低代码业务中台"层**——管道 DSL、步骤注册表、应用模板，以及中台四件套（工具网关 / 权限分级 / 审计留痕 / 计量观测）的自研实现。
> 低代码的两层含义：**管道低代码**（数据接入全链路配置化）+ **应用低代码**（问答应用一份 YAML 即一个应用）。

---

## 一、管道 DSL（数据接入的低代码）

### 1.1 设计目标

新接入一类数据源（比如"又来一批 mp4 培训视频"）= **写一段 YAML，不写 Python**。代码只出现"步骤类型"这一层，步骤怎么串、参数怎么配、失败怎么降级全部在配置里。

### 1.2 DSL 结构（YAML）

```yaml
# configs/pipelines.yaml
pipelines:
  pdf_v1:                       # 管道名 = 任务类型路由键
    source: { type: upload, accept: [.pdf] }
    steps:
      - type: detect_pages      # 页级路由探测：电子版/扫描件/复杂版式
        params: { sample_pages: 3 }
      - type: parse_mineru
        params: { backend: auto, backend_vlm: glm-4v, lang: ch }
        fallback:               # 失败降级链（顺序执行，前败后继）
          - { type: parse_mineru, params: { backend: pipeline } }
          - { type: parse_pymupdf }        # 纯文本降级：结构丢了也要内容在
      - type: validate_parsed   # 空Markdown/表格破损/页数缺失 → fail
        params: { min_chars_per_page: 20 }
      - type: chunk_markdown
        params: { max_tokens: 512, overlap: 64, keep_tables_whole: true }
      - type: embed
        params: { model: bge-m3, batch: 32 }
      - type: index_upsert
        params: { vector: chroma, keyword: sqlite_fts5, replace_by_doc: true }

  av_v1:                        # 音视频管道
    source: { type: upload, accept: [.mp4, .mp3, .wav, .m4a] }
    steps:
      - type: ff_extract_audio
        params: { ac: 1, ar: 16000 }       # 单声道16k，ASR 标准输入
      - type: asr_transcribe
        params: { engine: faster-whisper, model: medium, vad: true }
        fallback:
          - { type: asr_transcribe, params: { engine: funasr, model: paraformer-zh } }
      - type: segment_by_time
        params: { max_sec: 60, anchor: "mm:ss" }   # 块带时间戳锚点，可回跳源视频
      - type: embed
        params: { model: bge-m3, batch: 32 }
      - type: index_upsert
        params: { vector: chroma, keyword: sqlite_fts5 }

  excel_v1:                     # Excel → 临时表管道
    source: { type: upload, accept: [.xlsx, .csv] }
    steps:
      - type: excel_stage                 # 落 staging 临时表（全 TEXT 保真）
        params: { db: sqlite, schema: staging }
      - type: schema_infer                # 列名/样本/空值率/类型推断
      - type: column_mapping              # 列语义映射（LLM 建议 + 人工确认）
        params: { suggest_by_llm: true }
      - type: textualize                  # 行级卡片 / 聚合摘要 两种策略
        params: { strategy: row_card, max_rows: 5000 }
      - type: embed
        params: { model: bge-m3, batch: 32 }
      - type: index_upsert
        params: { vector: chroma, keyword: sqlite_fts5, meta_extra: [table, sheet, row_range] }
```

### 1.3 DSL 能表达什么、不能表达什么（边界即设计）

| 能表达 | 不能表达（必须写代码） |
|---|---|
| 步骤串行 / 参数 / fallback 降级链 | 新的**步骤类型**（如接一个新解析器） |
| 按条件选分支（页级路由、策略选择） | 跨步骤的自定义数据变换 |
| 环境差异（同一管道 dev 用小模型 / prod 用大模型） | 复杂有向图（多入多出）——**刻意不做**，RAG 接入是线性流，画布是过度设计 |

> 这条边界直接回应复盘 §3.1"纯自研缺平台能力"论：**配置化的性价比只存在于 80% 的线性场景**，剩下 20% 承认要写代码——这是自研路线真实的样貌，不吹"零代码"。

## 二、步骤注册表（代码侧的约定）

```python
# core/registry.py —— 步骤类型注册表（示意）
STEP_REGISTRY: dict[str, type[Step]] = {}

def register(name: str):
    def deco(cls):
        STEP_REGISTRY[name] = cls
        return cls
    return deco

@register("parse_mineru")
class ParseMinerU(Step):
    def run(self, ctx: StepContext, params: dict) -> StepResult: ...
```

- **注册表是 DSL 与代码的唯一接缝**：YAML 里的 `type` 必须能在注册表里找到，启动时全量校验（配置错误在启动期爆，不在运行半夜爆）。
- 每个步骤实现统一接口：`run(ctx, params) -> StepResult`，StepResult 携带 `status / data / metrics / error`——**失败也是结果，不是异常**（Harness 报文铁律第 4 条的同构：工具失败也回一条结果）。
- 步骤无状态：所有中间数据走 ctx（含 trace_id、doc_id、检查点）。

## 三、应用模板（问答应用的低代码）

一个问答应用 = 一份 YAML，指向已建好的知识资产：

```yaml
# configs/apps.yaml
apps:
  policy_qa:
    knowledge_bases: [policy_v1, direct_hits]     # 直击库一并挂
    retrieval:
      vector_topk: 20
      bm25_topk: 20
      rrf_k: 60
      metadata_filter: { kb: auto, recency: true } # 权限过滤在中台执行，不在此配
      rerank: { enabled: false }                   # 无 rerank 服务时 RRF 兜底
    direct_hit: { enabled: true, levels: [L0, L1, L2], threshold_gate: true }
    generation:
      model: qwen:8b-q4
      prompt: policy_strict_v3        # 指向 configs/prompts/policy_strict_v3.yaml
      stream: true
      max_ctx_tokens: 6144            # 上下文预算：先算容量再拼装
    gates:
      pre:  [sufficiency_check]       # 生成前：候选充分性
      post: [citation_check, schema_check]   # 生成后：引用真实性 / 输出结构
```

**应用之间互不感知**；换模型 / 换 Prompt / 开关闸门都是改配置——对应 Dify"Prompt 与代码解耦、迭代从发版变改配置"的能力，自研版落点在此。

## 四、中台四件套（自研版）

> 对应公司中台四件套的**个人实现**。规模缩小一个量级（单机、单团队），但**职责划分一模一样**——这四件的职责边界是可迁移的工程认知，不是平台附属品。

### 4.1 工具网关（数据类问题的唯一入口）

- RAG 只答**知识类**；"我的单子到哪一步"这类**数据类**问题走工具网关查业务库，**不进向量检索**（意图分流前置，走错必然答错——复用公司智能客服两分岔口径）。
- 数据类 API 白名单：只读优先、逐动作登记（动作名 / 参数 schema / 返回裁剪）、网关统一鉴权后代理。
- ownrag 定位：网关机制 + 假业务 API 两个（供联调与演示），**不实现真实业务库**。

### 4.2 权限分级（过滤责任不交给 Prompt）

| 级别 | 控制点 | 实现 |
|---|---|---|
| 知识库级 | 哪些库可问 | 应用配置 + 请求侧校验（中台执行） |
| 元数据级 | 密级 / 部门 / 时间范围 | 检索前 where 过滤（先过滤后召回，防泄漏进上下文） |
| 工具级 | 只读 / 写 / 高危 | 注册表白名单；写操作一律拦下转"工单确认"（HITL 卡点） |

**铁律与公司平台同款**：权限跟用户身份走，不跟模型/应用走；Prompt 里的"请不要泄露"不是权限。

### 4.3 审计留痕

- `trace_id` 贯穿：上传 → 解析各步 → 切分 → 索引 → 检索 → 闸门 → 生成 → 推流，每步一行 trace 记录（步骤 / 状态 / 耗时 / 关键计数）。
- 问答侧另落 Q&A 日志（问题 / 命中块 id / 答案 / 用户反馈）——这是评测集与直击库回流的原料。

### 4.4 计量观测

- Ollama 本地无 token 计费，**但计量不能没有**：按调用记 token 数 / 耗时 / 并发排队时长——远程模型切进来时同一套计量直接可用。
- 指标口径对齐公司设计：解析成功率按文档类型分桶、检索命中率按固定问答集、token 成本按应用拆分——全部 `【待实测】`。

## 五、Harness 六机制承接表（★叙事咬合点）

> ownrag 不重新发明编排哲学——**六机制逐条承接**，差异只在承载形态。

| Harness 六机制 | ownrag 落点 | 形态差异 |
|---|---|---|
| ① 任务执行循环（终止闸门） | 管道执行器：线性步骤流 + 步数天然有限；问答侧 ReAct 若启用则带步数 / 预算 / 重复检测三闸门 | 接入管道是**确定性线性流**，比 Agent 循环简单——该简单就简单 |
| ② 状态管理（状态外置） | 任务表（SQLite）：任务状态机 + 步骤检查点，中断可续跑、可重入 | 同构：outbox 思想落在任务表 |
| ③ 权限分级 | §4.2 三级权限 + 工具注册表分级 | 同构：鉴权收口在网关/检索前 |
| ④ 异常恢复（失败补偿） | 步骤级 fallback 降级链 + 任务级重试（幂等键 = doc_id + 步骤名） | 同构：四层恢复链的管道版 |
| ⑤ 人工介入（HITL） | 失败入待办表（人工队列）；Excel 列映射人工确认；写操作转工单 | 同构：中断 + 恢复 |
| ⑥ 评测观测 | trace 表 + 评测集 + `eval_recall.py` + 指标口径 | 同构：trace_id 全链路 + 评测回归 |

**一句话承接**："Harness 保证每一步可靠可管可查可停；ownrag 把同一套机制从'Agent 执行循环'搬到'RAG 数据管道'——机制不变，对象换了。"
