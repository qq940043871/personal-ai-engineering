# 09 · 向量库标量过滤：过滤式检索（filtered ANN）的三种执行策略

## 一、先把问题说准：filtered ANN ≠ 检索完再筛

纯语义检索回答的是"哪块文本和问题最像"；但业务问题几乎总带约束：

| 约束类型 | 例子 | 过滤字段性质 |
|---|---|---|
| 时间 / 版本 | "只在 2025 年后的制度里找" | 范围谓词，高基数 |
| 归属 / 租户 | "只查我这个知识库" | 等值谓词，低基数但**决定越权** |
| 密级 / 权限 | "只查我有权看的密级" | 等值/集合，**必须前置** |
| 类型 / 状态 | "只看 tech_spec，不吃草稿" | 低基数枚举 |
| 数值区间 | "金额 > 100 万" | 范围谓词 |

形式化地讲，filtered ANN 要求解的是：

```
给定谓词 P（布尔表达式）与目标条数 n：
  top_n{ sim(q, v_i) | i ∈ { j : P(meta_j) = true } }
```

三个目标同时成立才算做对——**正确性**（返回的每一条都满足 P，且不漏到少于 n）、**性能**（不因 P 退化成全表扫描）、**可解释**（能说清本次用了哪条执行计划，而不是"它有时候慢"）。

> 注意谓词里混着两种性质完全不同的条件：**权限类**（漏一条就是泄漏）和**偏好类**（漏几条只是效果差）。它们不能用同一种策略兜底——权限类必须前置且不可降级，偏好类才允许"过采样 + 事后筛"。

## 二、三种执行策略

| 策略 | 执行顺序 | 核心机制 | 什么时候对 | 失效模式 |
|---|---|---|---|---|
| **预过滤** Pre-filtering | 标量 → 向量 | 先走标量索引出候选 ID 集合，再在这个集合上算距离 | 选择性高（过滤后只剩很少） | 选择性低时集合仍很大，距离计算量随 \|S\| 线性涨 |
| **后过滤** Post-filtering | 向量 → 标量 | 先 ANN 召回 K 条，再对 K 条过谓词 | 选择性低（几乎全满足） | **召回不足**：K 条里满足 P 的可能远少于 n，且静默 |
| **内联过滤** Inline / filtered ANN | 向量遍历中实时判定 | 谓词编译成 bitset，HNSW/IVF 每访问一个节点先查位图，不满足就跳过 | 中高选择性、且引擎改过索引 | 高过滤率下图被"剪断"，遍历大量空转、召回崩（见 §三） |

### 2.1 预过滤

```
谓词 P → 标量索引（B+Tree / 倒排 / Bitmap）→ 候选 ID 集合 S
S → 逐个算距离（或把 S 当 allowed-set 注入 ANN）→ 取 top-n
```

- **两种实现要分清**：`S` 很小（比如只占 1%）时，直接对 `S` 做暴力距离计算是**最优解**——此时"退化成暴力扫描"不是缺陷而是正确选择；`S` 仍很大时，必须把 `S` 作为允许集注入 ANN，否则代价就是 `|S| × d` 的全量计算。
- **前提是标量索引真实存在**。没有索引，第一步就是全表扫，后面再快也没用。
- **最适合的形态**：租户/知识库隔离、密级、状态这类"一次砍掉 99%"的条件；以及时间窗很窄的查询。

### 2.2 后过滤

```
ANN 取 top-K → 用 P 过滤 → 得到 m ≤ K 条（m 常常 < n）
```

- **算术上就不成立**：过滤后剩余数据占比为 `S`（选择性），均匀假设下 `E[m] ≈ K × S`。要保证得到 `n` 条，需要 `K ≈ n / S`（还只是**期望**，方差会继续吃掉尾部）。`S = 0.01`、`n = 10` 时 `K` 得开到 1000 量级——这时候 ANN 的成本已经翻了几十倍，等于用性能换了个"可能还不够"。
- **真正的坑是静默**：接口 `limit=10`，返回 8 条，调用方通常不校验条数，下游直接把这 8 条拼进 Prompt；闸门只看见"候选池非空"就放行。用户看到的是"资料不足"，工程师查半天以为是索引问题。
- **只在一种情况下可接受**：谓词几乎恒真（`S → 1`），或者调用方**显式做 over-fetch + 条数校验 + 不足时报可观测事件**。裸用后过滤 + 直接透传 `limit`，是 RAG 检索层最常见的隐性故障。

### 2.3 内联过滤（filtered ANN / 联合检索）

以 HNSW 为例，主流做法是把布尔表达式先在标量侧求值成 **bitset（位图）**，再让图遍历持有它：

```
build:  谓词 P --(倒排/B+Tree)--> bitset B（第 i 位 = 第 i 个实体是否满足 P）
search: 从入口点开始 BFS/贪心遍历
        每访问节点 u：if not B[u]: 跳过（不入候选堆，但仍需通过它继续寻路）
        否则：算距离、更新候选堆、按图边继续扩展
        终止：候选堆满 n 且已无法改进，或访问预算用尽
```

- **与后过滤的本质区别**：过滤不是"搜完再删"，而是"**不合格的节点不许进结果堆**"——所以最终 top-n 天然满足 P，正确性有保证。
- **与预过滤的本质区别**：不需要先物化整个候选 ID 集合，谓词判定摊在遍历过程中，内存与延迟更平滑。
- **仍然有代价**：被跳过的节点**依然要花一跳的路由开销**（否则图就断了）。过滤率越高，无效 hop 越多——这是 §三的主题。

---

## 三、内联过滤的死角：高过滤率下图会被剪断

这是"内联过滤 = 完美方案"叙事里最常被漏掉的一段。

- HNSW 的召回依赖**图连通性**：能进候选堆的节点，才能从它继续往外扩展。
- 谓词一旦把绝大多数节点标记为不合格，这些节点就变成"只可路过、不可停留"的中转站。极端情况（如只留 0.1%）下，满足条件的节点在图上**彼此不相邻、甚至互不连通**——遍历想从一个合格节点走到下一个合格节点，中间要连续跨过大量不合格节点，而 HNSW 的贪心策略只保证"沿着更近的方向走"，跨越多层空节点时极易**走进死胡同就终止**。
- 结果：**条数够但召回差**（返回的是"能走到的那几个"），或**条数也不够**（提前终止）。这种情况比后过滤更隐蔽，因为看起来"过滤生效了、也返回了"。

现代引擎的对策（方向一致，具体版本行为以官方文档为准）：

| 对策 | 思路 |
|---|---|
| 迭代式过滤 / 迭代搜索 | 候选不足时不终止，扩大访问预算、多轮扩展继续找，直到凑够 n 或触达预算上限 |
| 按代价回退暴力扫描 | 选择性极高（候选集足够小）时，直接对候选集做精确距离计算，放弃图遍历 |
| 基数估算驱动 | 先估过滤后规模，再决定走哪条路（这就是 §五 的 CBO） |
| 物理隔离 | 把租户/知识库做成独立 collection 或 partition，从"过滤问题"降级成"路由问题" |

**一句话结论**：过滤的条件越"狠"，越不应该指望图遍历自己扛——要么提高选择性的手段换成物理隔离，要么让引擎回退暴力扫，要么接受过采样。

## 四、底层依赖：标量索引决定过滤能不能便宜

| 索引结构 | 典型字段 | 支撑的算子 | 备注 |
|---|---|---|---|
| B+Tree / 有序索引 | 数值、时间戳、字符串（前缀） | `==` `!=` `>` `>=` `<` `<=` `in`、**前缀** `like 'x%'` | 范围查询的默认选择；顺序扫描 + 二分 |
| 倒排索引 | 低基数枚举、标签、关键词 | 等值、`in`、`not in`、分词后的 `like` | 布尔组合的位图求交天然快 |
| Bitmap | 状态、密级、布尔位 | 等值、多条件 AND/OR | 基数低时压缩率高；更新代价大 |
| Trie / 前缀树 | 编码、路径、前缀类 ID | 前缀匹配 | 字符串前缀本质上是范围问题 |
| Zone map / min-max 裁剪 | 大块存储上的时间、版本号 | 范围（粗筛） | 便宜但只做剪枝，不定位 |
| 哈希 | 精确等值（含主键） | `==` | 范围查询用不上 |

三个工程要点，比记住索引类型清单更重要：

1. **`like` 只有前缀能吃索引**。`'制度%'` 可以走有序索引；`'%制度'`、`'%制度%'` 用不上——除非引擎额外做了 n-gram 倒排。把"包含匹配"当免费功能写进查询条件，就是在给自己埋一次全扫。
2. **字段类型必须按查询语义存**。范围比较要求可比较的**数值/时间类型**；一旦存成字符串，`>= 2023` 就变成字典序比较（`"999" > "2023"`）。ISO8601 字符串字典序与时间序一致是**巧合可用**，而不是设计正确——跨格式（`2023/5/1` vs `2023-05-01`）立刻失效。
3. **索引跟着字段走**。新增一个过滤字段 = 建索引 + **回填历史数据**（只建索引不回填，历史行不算入索引，过滤结果会静默缺一段）。

## 五、CBO：按选择性挑执行计划

选择度（selectivity）`S = 满足 P 的行数 / 总行数`。`S` 越小（越"挑"），预过滤/暴力扫越占优；`S` 越接近 1，后过滤越省。

代价模型（示意，非实测）：

| 计划 | 代价近似 | 何时最优 |
|---|---|---|
| 预过滤 + 子集精确计算 | `T_scalar_index + S·N·d` | `S` 很小 |
| 内联过滤（bitset 遍历） | `(N·S)^{-1}` 相关的 hop 放大 × ANN 基础代价 | 中等 `S`，索引支持 |
| 后过滤 | `T_ann(K) , K ≈ n/S` | `S → 1` |

决策要点：

- **估算 `S` 的数据从哪来**：统计信息（直方图 / 基数 HyperLogLog / 采样），或直接对过滤条件做一次 count（贵但准）。**没有统计信息时，优化器只能靠猜**——多条件 AND 的相关性尤其容易估歪（`year>=2025 AND type='spec'` 的真实交集可能远小于两个 `S` 相乘）。
- **估算失真比没有优化器更可怕**：估 `S=0.5` 实际 `0.001` → 选了后过滤 → 召回不足；估 `S=0.001` 实际 `0.5` → 选了暴力扫 → 延迟爆。
- **RAG 场景的额外约束**：检索要进 Prompt，晚到的高延迟比略差的召回更伤——所以本工程的选择偏向**确定性优先**（见 §七）。

## 六、算子与语法

通用算子集（各引擎语法略有差异，语义一致）：

| 类别 | 算子 | 备注 |
|---|---|---|
| 比较 | `== != > >= < <=` | 数值/时间字段才说得上"范围" |
| 逻辑 | `and or not` / `&& \|\| !` | AND 顺序影响代价，别把最贵的放前面 |
| 集合 | `in` `not in` | 等价于多个等值的 OR，走倒排/Bitmap 最优 |
| 模糊 | `like`（前缀/后缀/包含） | 后缀与包含**通常用不上索引** |
| 存在/数组 | `exists` `contains` `array_length` | JSON/数组字段语义各引擎差异最大 |

典型调用（Milvus，`filter` 即谓词，与向量检索同一次请求）：

```python
results = client.search(
    collection_name="my_docs",
    data=[query_vector],
    filter="release_year >= 2023 and doc_type == 'tech_spec'",  # 谓词
    limit=5,
    output_fields=["text"],
)
```

同一件事在其它引擎里的形状（只记形状，不背 API）：

```python
# Chroma：metadata 谓词（我们自己用的这套）
col.query(query_embeddings=[q], n_results=5,
          where={"$and": [{"year": {"$gte": 2023}}, {"doc_type": "tech_spec"}]})

# Qdrant：payload filter + 条件组合
client.search("my_docs", query_vector,
              query_filter=Filter(must=[FieldCondition(key="year", range=Range(gte=2023))]))

# pgvector：谓词和排序写在同一条 SQL 里，进同一个执行计划
SELECT id, text FROM chunks
WHERE year >= 2023 AND doc_type = 'tech_spec'
ORDER BY embedding <=> %s LIMIT 5;

# Elasticsearch / OpenSearch：filter context 不打分，kNN 与 filter 组合
{"knn": {"field": "embedding", "query_vector": q, "k": 10,
         "filter": [{"range": {"year": {"gte": 2023}}}]}}
```

引擎性格（一句话，细节以官方文档为准）：

| 引擎 | 过滤与向量如何结合 |
|---|---|
| Chroma | metadata 索引 + `where` → **pre-filter 语义**，候选集小时等价暴力精确算 |
| Milvus | 谓词编译 bitset，倒排/B+Tree 加速；遍历内判定；高过滤率提供迭代式过滤 |
| Qdrant | payload 索引 + filter-aware HNSW，按**基数估算**在过滤遍历与全扫之间切 |
| pgvector | 谓词与 `<->`/`<=>` 同进 PG 优化器；扫描不足时靠 `ef_search` 或迭代扫描补 |
| ES / OpenSearch | filter context 走倒排，与 kNN 组合，常见 pre-filter |
| PolarDB / Vastbase 等 SQL 一体化 | 向量作为算子进优化器，按选择度在标量索引与向量索引间选路（各家实现差异大） |

## 七、ownrag 的落地：选"物理隔离 + 前置过滤"，缺口写清楚

### 7.1 现状（代码事实）

| 事项 | 现状 | 出处 |
|---|---|---|
| 知识库隔离 | **物理隔离**：每个 kb 一个 collection（`kb_{kb}`），FTS 侧 `WHERE ... AND kb=?` | `ownrag/ownrag/index/store.py:95`、`:55-74` |
| 向量检索的谓词 | **当前不带 `where`**：`col.query(...)` 只有向量与 `n_results` | `ownrag/ownrag/index/store.py:120-129` |
| 混合检索的过滤参数位 | `metadata_filter` 参数**已留位未接线**，注释写明 M2 接密级/时间，权限在中台 | `ownrag/ownrag/retrieve/hybrid.py:31-35` |
| 元数据写入 | 全部 `str(v)` 字符串化后落 Chroma metadata | `ownrag/ownrag/index/store.py:106-107` |
| 删除 | 按 `doc_id` 走 `where` 删除（这条是真在用的 where） | `ownrag/ownrag/index/store.py:112-117` |

### 7.2 三个决策及理由

1. **隔离用 collection，不用过滤条件**。租户/知识库这一层一旦靠 `where` 保证，就意味着"漏拼一个条件 = 一次越权"，而且漏拼不会报错。做成 `kb_{kb}` 之后，越权在**路由层就不可能发生**——过滤问题降级成路由问题，符合 §三"物理隔离"那条对策。
2. **权限类过滤前置，偏好类才允许事后筛**。这与 `04` §三"先过滤后召回"同一条纪律：**召回进上下文再被过滤 = 已泄漏**（模型已经看过了）。
3. **不自己实现过滤式遍历**。选 Chroma 的 `where` 就是买它的 pre-filter 语义；自己写 bitset 注入 HNSW 属于引擎侧工作，个人工程不碰——**但要知道它在什么条件下会退化成暴力扫**（`S` 很小时其实是好事）。

### 7.3 已知缺口（主动写，别等被问）

- **`str(v)` 字符串化与范围过滤冲突**：`release_year` 存成 `"2023"` 后，`>= 2023` 的语义取决于引擎的类型推断与字典序——**时间/数值字段必须保持数值类型落库**，否则 §四第 2 条那个坑原地生效。修法：写入侧按类型分流（数值/布尔保留原类型，时间统一 ISO8601 且**只在类型无法保留时才用字符串 + 字典序**，并在 schema 里注明）。
- **过滤字段还没建索引**：Chroma 的 metadata 索引与 collection 创建参数相关；新增过滤字段要按引擎要求建索引并回填，否则就是"写得对但扫得慢"。
- **`metadata_filter` 空转**：接口上像支持，实际不生效——这是"看起来有、其实没有"的配置项，比没有更危险（同 `07` C61 的诚实清单口径）。

### 7.4 M2 接线清单

- [ ] `hybrid.search` 把 `metadata_filter` 真正编译成 `where`，向量与 FTS 两路**同一套谓词**（两路过滤口径不一致 = 融合结果一半越权）。
- [ ] 写入侧保留数值/时间类型，历史数据按新 schema 重灌（与 `embed_version` 全量重建同一次操作完成，别做两遍）。
- [ ] 观测：过滤条件与命中条数进 trace / `retrieval_path`，把"被过滤掉"和"本来就没有"区分开——否则闸门一会把"过滤太紧"误判成"没有依据"。
- [ ] 评测集补"过滤 + 无答案"组合用例（`data/eval/` 现有无答案题可扩展），验证收紧过滤后拒答语义不走样。

## 八、坑清单（按踩中概率排序）

| # | 坑 | 现象 | 对策 |
|---|---|---|---|
| 1 | 后过滤直接透传 `limit` | 返回条数少于 limit，静默 | over-fetch（`K ≈ n/S`）+ 条数校验 + 可观测事件 |
| 2 | 元数据字符串化 | 范围比较变字典序，边界错、结果缺 | 数值/时间保留类型；时间统一 ISO8601 |
| 3 | 过滤字段没建索引 | 检索偶发慢一个数量级 | 建标量索引 + 回填历史 |
| 4 | `like '%x%'` | 全扫 | 改前缀匹配或加 n-gram 倒排 |
| 5 | NULL / 缺失字段语义 | `!= 'draft'` 把 NULL 行一起漏掉 | 显式 `exists` 或写入侧补默认值 |
| 6 | 多租户靠过滤条件 | 一次漏传 = 越权 | 物理隔离（collection / partition） |
| 7 | 两路召回过滤口径不一致 | 向量路干净、BM25 路泄漏 | 同一谓词编译，单点生成 |
| 8 | 过滤太紧被当成"无依据" | 闸门一误拒答 | 观测区分"过滤掉"与"没有"，评测集覆盖 |
| 9 | 数组/JSON 字段 `contains` 各引擎语义不同 | 换引擎行为突变 | 归一化成扁平标签字段再索引 |
| 10 | 只改 schema 不重灌历史 | 老文档永远过滤不到 | schema 变更 = 回填任务，不可省 |

## 九、面试三问（每问 30 秒）

**Q1 · 后过滤为什么危险，怎么修？**
> "算术上就不成立：过滤后剩余占比 S，均匀假设下要拿 n 条，得先召回 `n/S` 条。真问题不是慢，是**静默**——接口要 10 条返回 8 条，下游照拼进 Prompt，谁都发现不了。修法是两条：要么前置过滤（能建索引就让引擎先筛），要么显式 over-fetch 加条数校验，并把不足数落成可观测事件。"

**Q2 · 内联过滤已经"边遍历边判断"了，为什么还会召回不好？**
> "因为过滤会**把图剪断**。HNSW 靠合格节点之间的连通性扩展，过滤率一高，合格节点彼此不相邻，遍历只能路过大量不合格节点、走进死胡同就终止——条数可能够，召回是塌的。所以引擎在极端过滤率下会回退暴力扫或做迭代式过滤；工程上更彻底的办法是把租户这类高选择性条件做成物理隔离，根本不进过滤。"

**Q3 · 哪些字段该建标量索引，怎么判断？**
> "看三条：**进不进谓词**、**选择度高不高**、**运算符吃不吃索引**。进了谓词的才建；选择性低的（状态、密级）用倒排或 Bitmap，范围和时间的用有序索引；`like '%x%'` 这种吃不到索引的，要么改前缀要么别指望索引。另外两条纪律：类型按查询语义存，建了索引要回填历史。"
