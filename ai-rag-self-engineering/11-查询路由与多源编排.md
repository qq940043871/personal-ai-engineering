# 11 · 查询路由与多源编排（route-first）

> 定位：一次提问先判"该查哪类数据"，再决定走哪条通道，最后把**不同类型**的证据统一成同一批候选块，
> 交给现有的预算 / 闸门 / 生成 / 引用链路。本文是这套设计的权威口径。
> 本期范围：**RAG + SQL + MULTI**；WEB 通道只留接口与配置位，不实现联网（见 §九）。

---

## 一、结论先行

```
现状：/chat 是单轨硬编码 —— 直击库 → 改写 → 混合检索(RAG) → 重排 → 闸门一 → 生成
问题：没有"判定该用哪个数据源"这一层，Excel 数据只能靠向量召回（聚合必错）
改法：route-first，四段式；路由只负责分诊，不负责回答
```

四段式：

```
① 意图判定   QueryRouter：规则打分 →（可选）LLM 归类，规则命中即短路不花钱
② 可用性掩码  该数据源在本库到底有没有：staging_registry / chunks.source_type / search 配置
③ 通道执行   SQL | RAG | MULTI（本期），WEB（预留）
④ 证据装配   三类证据统一编号成 candidates，共用同一套预算/闸门/引用
```

**为什么是 route-first 而不是 retrieve-first**：聚合问题做向量检索纯属浪费；更糟的是"先召回再计算"
会让计算路径依赖一次不相关的召回（召回错了，SQL 的 WHERE 也跟着错），且延迟叠加。

---

## 二、① 意图判定

### 2.1 三级级联

| 层 | 做什么 | 何时短路 |
|---|---|---|
| L0 强制 | 请求体 `route: rag\|sql\|multi\|auto`；`apps.yaml` 的 `routing.allow` 白名单 | 显式指定 → 直接采纳（仍做可用性校验） |
| L1 规则 | 信号词打分（下表） | 最高分 ≥ 4 → 直接定案 |
| L2 结构 | 可用性掩码（§三） | 掩码后只剩一个通道 → 直接定案 |
| L3 LLM | 低置信时一次分类调用，JSON `{route, reason, confidence}` | 本期默认 **关闭**（`routing.llm_classify: false`），M2 再开 |

### 2.2 信号表（进 Git，可回归）

| 信号族 | 例词/结构 | 指向 | 权重 |
|---|---|---|---|
| 表/列显式指称 | 问题里出现 `staging_registry` 的 sheet 名、原始列名（≥2 字） | SQL | +3 |
| 聚合/统计 | 多少、总计、合计、平均、最大、最小、前 N、占比、环比、按月、汇总、一共、总共 | SQL | +2 |
| 明细+条件 | 地区/月份/金额大于…这类能落到 `WHERE` 的限定词 | SQL | +1 |
| 数字口径 | 元、万元、笔、条、单 | SQL | +1 |
| 知识型 | 为什么、怎么、流程、标准、规定、区别、原理、依据、方案 | RAG | +2 |
| 内部资料 | 我们公司、内部、制度、合同、纪要、政策 | RAG | +2 |
| 时效/外网 | 最新、今天、最近、新闻、官网、汇率、上网查 | WEB | +3（本期不可用 → 记信号但不选路） |
| 多轮继承 | history 上一轮通道 + 本轮"那/这个/再按…" | 继承 | +2 |
| 红线 | 命中 `redline_terms.txt` | 前置拒答 | 短路（已有逻辑，先于路由） |

打分：

```
sql_score = 3·表列命中 + 2·聚合词 + 1·明细条件 + 1·数字口径 − 2·知识型
rag_score = 1（基线） + 2·知识型 + 2·内部资料 − 2·聚合词
web_score = 3·时效 + 3·外网指称（本期：只记录，不参与选路）
```

### 2.3 定案规则

```
若 web_score 最高且 web 可用            → web（本期不可用，落到下一行）
若 sql_score ≥ 4                        → sql
若 sql_score ≥ 3 且 rag_score ≥ 3       → multi（跨源对比题）
若 sql_score >  rag_score 且 sql_score ≥ 2 → sql
否则                                    → rag
confidence = min(1, max(sql, rag, web) / 5)
若 confidence < routing.min_confidence（默认 0.4） → 按 routing.on_low_confidence（默认 rag）
```

`multi` 的触发条件值得单说：**"报销明细里 3 月华东的差旅总额，够不够政策里的标准？"** 这类题
一半要算、一半要读规定，单选任何一路都答不全。这就是原方案（"若 A 则 X，若 B 则 Y"）最缺的一格。

### 2.4 路由不改写问题

路由只读**原问题**（+ history 的通道记录），不做改写。改写仍由 `QueryRewriter` 负责，且只服务召回通道
——与现有口径一致（直击库始终用原问题精确匹配）。

## 三、② 可用性掩码（原方案最大的缺口）

判定"想查什么"和判定"有没有"必须分开。掩码作用：**不可用的通道直接 −∞，不允许"意图是 SQL 却没表"时
悄悄回落 RAG 假装回答。**

| 通道 | 可用条件 | 不可用时的行为 |
|---|---|---|
| SQL | `staging_registry` 中存在该 app/kb 可见的 doc，且 `documents.enabled=1` | 返回 `no_evidence{reason=no_table}`，明说"库里没有这类结构化数据" |
| RAG | 该 kb 存在 `source_type <> 'excel'` 的 chunks | 走现有降级播报（`vector_skipped_reason`） |
| WEB | `endpoints.search.base_url` 非空 + `OWNRAG_SEARCH_API_KEY` + app 允许 | 本期恒不可用；若 app 只允许 web → `no_evidence{reason=web_unavailable}` |

表级鉴权也在这一层做（`documents.sensitivity/topic` → 允许的 doc 集合），**先鉴权再生成 SQL**：
`staging_*` 表本身没有 sensitive 列，不先收窄 doc 范围，SQL 通道就是一条绕过现有 `metadataFilter` 的后门。

## 四、③ SQL 通道（六步）

### 4.1 流程

```
1. 定位目标表   读 staging_registry（+ PRAGMA table_info 校验表还在）→ 表名/sheet/列名与问题做匹配打分
2. schema 链接  问题里的实体词 → 列（原始名/物理名/枚举样本）→ 生成"列白名单 + 值提示"
3. 生成 SQL     一次 LLM 调用，输入 = 表结构（含 sql_expr）+ 值提示 + 问题；输出 JSON {sql, reason}
4. 校验         SELECT-only、单语句、无注释、表名 ⊆ 白名单、强制 LIMIT
5. 执行         只读连接（PRAGMA query_only=1）+ 超时 + LIMIT；失败回喂错误重写一次
6. 装配         结果集 → 证据块（含 SQL 全文口径）；空结果与无表分开报
```

### 4.2 SQL 白名单（硬约束，纯代码可测）

| 规则 | 实现 |
|---|---|
| 只允许一条 `SELECT`（可带 `WITH`） | 去注释后正则 + 分号计数 |
| 禁止关键字 | `insert update delete drop alter create attach detach pragma vacuum replace` |
| 禁止注释 | `--` / `/* */` 一律判非法（比"剥离注释"更安全） |
| 禁止 `sqlite_master` / `sqlite_` 前缀 | 关键字扫描 |
| 表名白名单 | 提取 `FROM/JOIN` 后的标识符，必须 ∈ 本次候选表集合 |
| 强制 LIMIT | 无 `LIMIT` 则追加 `LIMIT max_rows`；已有且超限则钳到 `max_rows` |

### 4.3 为什么必须走 `sql_expr`

staging 全列 TEXT，`SUM(金额)=0`、中文日期比较恒假。`schema_infer` 产出的 `sql_expr` 是唯一正确的聚合口径，
SQL 生成 prompt 里必须逐列给出（见 `10-Excel通道口径.md` §六）。

### 4.4 失败与降级阶梯

| 情形 | 行为 | 事件 |
|---|---|---|
| 无候选表 | 不进模型，直接拒答 | `no_evidence{reason=no_table}` |
| 无 LLM key / 调用失败 | 降级：把"表目录 + 前 3 行样本"作为证据块，让模型据实说明"无法统计" | `gate{stage=sql_degraded}` |
| SQL 校验不过（尝试 1） | 错误信息回喂重写一次 | `route.detail` 记录 |
| SQL 校验/执行仍失败 | 同上，降级为目录 + 样本；**绝不放行编造数字**；同时计数（见下） | `gate{stage=sql_failed}` |
| 同一题连续失败 ≥2 次 | 进 `todos`（人工队列），reason 以「SQL 通道连续失败」开头；成功一次自动关账并清零 | `gate{stage=sql_degraded, todo_id}` |
| 执行成功但 0 行 | 合法答案："按该条件没有记录"，必须带 SQL 口径 | `route.detail.rows=0` |

## 五、④ 证据装配与引用契约

### 5.1 统一候选结构

三类证据进同一批 `candidates`，新增两个字段：

| 字段 | 取值 | 用途 |
|---|---|---|
| `kind` | `chunk` \| `sql` \| `web` | 前端分区展示；闸门按类型放宽 |
| `trust` | `high`(sql) > `medium`(kb) > `low`(web) | 冲突时的取舍依据（不是自动取舍，是显式声明） |

SQL 证据块的 `text`：

```markdown
【SQL 查询结果｜来源：报销明细.xlsx / Sheet1｜1,204 行中被筛选 37 行（LIMIT 200 未截断）】
SQL: SELECT SUM(CAST(...)) AS 总额 FROM "staging_ab12cd34_Sheet1" WHERE ...
| 地区 | 总额 |
|---|---|
| 华东 | 128,400.00 |
执行耗时：12ms
```

`ordinal` 分配：SQL 块接在检索候选之后（`max(ordinal)+1` 起），保证"块 N"全文唯一。

### 5.2 闸门必须扩（否则正确回答被判违规）

`Gates.citationCheck` 现在的规则是"答案里的数字必须能在**被引用块原文**里找到"。SQL 结果的数字不在
任何 chunks 里 —— 不扩就会把正确回答判成幻觉。扩法：

| 证据类型 | 数字校验口径 |
|---|---|
| `chunk` | 原样（数字必须在块正文中） |
| `sql` | 数字必须能在该证据块的 **result 表格文本** 中命中（块 text 已包含表格） |
| `web` | 数字必须伴随 URL 引用（本期不涉及） |

即：校验对象从"chunks 正文"变成"该证据块自己的 text"，规则本身不变，只是允许证据块有多种 `kind`。
另外 SQL 块天然是"有据可查"，因此**必须带 SQL 全文**——没有 SQL 的数字等于没有出处。

## 六、SSE 契约（追加，不重排）

新增 `route` 事件，位置在 `rewrite` **之前**（`pre_redline` 之后）：

| 字段 | 说明 |
|---|---|
| `route` | `rag` \| `sql` \| `multi` |
| `layer` | `forced` \| `rule` \| `structure` \| `llm` \| `fallback` |
| `confidence` | 0~1 |
| `signals[]` | `{name, weight, route}`，前端画"为什么这么判" |
| `targets[]` | `{kb, doc_id, doc_name, table, sheet}`（SQL 才有） |
| `availability` | `{sql, rag, web}` 布尔三元组 |
| `detail` | SQL：`{sql, rows, ms, truncated, degraded_reason}` |
| `reason` | 一句话 |
| `ms` | 判定耗时 |

普通对话页（`debug=false`）也下发 `route`（体积小、且"走了哪条路"是用户能感知的关键信息）；
`detail.sql` 只在 `debug=true` 时下发（可能含业务字段）。

`no_evidence.reason` 枚举扩为：`no_table` / `sql_empty` / `sql_failed` / `no_hit` / `route_low_confidence` / `web_unavailable`。

## 七、配置（apps.yaml）

```yaml
apps:
  finance_qa:
    knowledge_bases: [kb_interview, kb_expense]
    routing:
      enabled: true
      allow: [rag, sql]          # 本期无 web
      default: rag
      llm_classify: false        # 低置信是否再花一次 LLM 归类（M2）
      min_confidence: 0.4
      on_low_confidence: rag     # rag | sql | multi | ask
      weights:
        table_hit: 3
        agg_word: 2
        detail_word: 1
        unit_word: 1
        knowledge_word: 2
      sql:
        max_rows: 200
        timeout_ms: 5000
        max_tables: 3            # 候选表上限，防 prompt 爆炸
```

`routing.enabled: false` 时行为与改造前完全一致（单轨 RAG）——用于回滚与 A/B。

## 九、WEB 通道（本期不实现，接口预留）

保留三件事，避免以后返工时改契约：

1. **配置位**：`models.yaml endpoints.search` + `OWNRAG_SEARCH_API_KEY`，缺任一 → `web` 恒不可用；
2. **枚举位**：`route=web` 与 `no_evidence.reason=web_unavailable` 已在契约里；
3. **安全位（实现时必须做）**：外发 query 先过红线词（客户名不进搜索引擎）；抓取仅 https、
   禁内网段/重定向到内网/超大响应（SSRF）；网页块必须带 `url + retrieved_at`，答案里的网页数字必须
   带 URL 才过闸门；网页内容不得被表述为"内部政策"。
