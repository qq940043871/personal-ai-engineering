1 什么是 Function Calling

Function Calling（函数调用）是大模型的一项关键能力，允许模型"调用"预定义的函数/API 来获取外部信息或执行操作。

核心思想

大模型本身只能基于训练数据生成文本，通过 Function Calling，模型可以：

  • 查询实时天气、股价等外部数据
  • 调用计算器进行精确数学运算
  • 操作数据库、发送邮件、创建文件
  • 与各类 API 服务交互

2 Function Calling 工作流程

工作流程: 用户: "北京今天天气怎么样？" │ ▼ ┌─────────┐ ①发送请求（含工具定义） ┌──────────┐ │ 客户端 │ ──────────────────────────→ │ LLM API │ └─────────┘ └──────────┘ ▲ │ │ ②模型返回 function_call │ │ { ▼ │ "name": "get_weather", ┌──────────┐ │ "arguments": { │ 模型判断 │ │ "city": "北京" │ 需要调用 │ │ } │ 函数 │ │ } └──────────┘ │ │ │ ③执行函数，获取真实天气数据 │ │ { ▼ │ "temperature": 25, ┌──────────┐ │ "condition": "晴" │ 执行函数 │ │ } └──────────┘ │ │ │ ④将函数结果发回模型 ▼ │ ... │ │ └──────────────────────────────────────────┘ ⑤模型根据函数结果生成最终回复: "北京今天天气晴朗，温度25°C。"

关键点：模型本身不执行函数，而是告诉客户端执行哪个函数以及参数是什么。

3 什么是 MCP 协议

MCP (Model Context Protocol) 是 Anthropic 提出的一种开放协议，旨在标准化 AI 模型与外部工具/数据源之间的通信。

类比理解

MCP 之于 AI Agent，就像 USB 之于外设 —— 提供了一个统一的"接口标准"，让任何 AI 应用都能方便地连接各种外部工具和数据源。

对比对象 MCP 类比
USB 协议统一的外设连接标准
HTTP 协议统一的 Web 通信标准
ODBC/JDBC统一的数据库连接标准
MCP统一的 AI 工具连接标准

4 MCP 架构设计

MCP 采用客户端-服务器架构，由三个角色组成：

┌──────────────────────────────────────────────────────┐ │ MCP 架构总览 │ ├──────────────────────────────────────────────────────┤ │ │ │ ┌──────────┐ MCP Protocol ┌──────────┐ │ │ │ │ ←───────────────────→ │ │ │ │ │ Host │ JSON-RPC 2.0 │ Server │ │ │ │ (宿主) │ │ (服务) │ │ │ │ │ │ │ │ │ │ - Claude│ │ - 工具 │ │ │ │ - IDE │ │ - 数据 │ │ │ │ - App │ │ - API │ │ │ └──────────┘ └──────────┘ │ │ │ │ │ │ │ ┌──────────┐ │ │ │ └────────→│ Client │←─────────────┘ │ │ │ (客户端) │ │ │ └──────────┘ │ │ │ └──────────────────────────────────────────────────────┘

Host (宿主)

AI 应用本身，如 Claude Desktop、VS Code、自定义 App。负责发起和管理 MCP 连接。

Client (客户端)

协议客户端实例，由 Host 创建，与 Server 建立 1:1 连接，负责协议层的通信。

Server (服务端)

提供具体能力的服务，如文件系统访问、数据库查询、API 调用等。轻量级、易于实现。

5 MCP 核心能力

MCP Server 可以向 AI 模型暴露三种类型的原语：

Tools (工具)

模型可控的执行功能，类似 Function Calling。模型通过工具来执行操作。

服务器暴露: search_web, calculate, send_email, create_file, read_database 模型调用: search_web(query="最新AI新闻") → 返回搜索结果 calculate(expression="2+3*4") → 返回 14

Resources (资源)

结构化的只读数据，类似 GET 请求。模型通过资源来获取上下文。

资源 URI: file:///project/README.md → 读取文件内容 db://users/table → 获取表结构 weather://beijing/current → 获取天气数据

Prompts (提示模板)

预定义的交互模板，用于引导模型执行特定任务。

/code-review → "请审查以下代码变更，关注安全性和性能" /summarize → "请用3句话总结以下内容" /explain-sql → "请解释以下SQL查询的执行计划"

6 Function Calling vs MCP

维度 Function Calling MCP
定位 模型能力（API 级别） 通信协议（架构级别）
提出者 OpenAI (2023) Anthropic (2024)
标准化 各家实现不统一 开放标准，统一接口
工具定义 JSON Schema 内嵌在请求中 Server 端动态暴露/发现
资源访问 需要手动编码集成 原生支持 Resources 原语
传输方式 HTTP API 请求 stdio / SSE / HTTP
生态复用 每个应用单独集成 一次开发，多客户端复用
提示模板 不支持 原生支持 Prompts 原语

关系理解：Function Calling 和 MCP 并非对立，而是不同层次的方案。

应用层: Claude / ChatGPT / 自定义 AI 应用 │ │ 协议层: │ ┌─────┴──────────────────────┐ │ │ MCP (Model Context │ │ │ Protocol) 统一标准 │ │ └─────┬──────────────────────┘ │ │ 能力层: Function Calling Tools / Resources / Prompts │ │ 执行层: 自定义函数 MCP Server (工具实现)

8 实战示例

配置 MCP Server

{ "mcpServers": { "filesystem": { "command": "npx", "args": [ "-y", "@modelcontextprotocol/server-filesystem", "/path/to/allowed/dir" ] }, "github": { "command": "npx", "args": [ "-y", "@modelcontextprotocol/server-github" ], "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_xxxxx" } }, "postgres": { "command": "npx", "args": [ "-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/mydb" ] } } }

Function Calling 示例 (OpenAI)

import openai response = openai.chat.completions.create( model="gpt-4", messages=[{"role": "user", "content": "北京天气怎么样？"}], tools=[{ "type": "function", "function": { "name": "get_weather", "description": "获取指定城市的天气", "parameters": { "type": "object", "properties": { "city": {"type": "string"} }, "required": ["city"] } } }] ) # 模型返回 tool_calls，而不是直接回答 tool_call = response.choices[0].message.tool_calls[0] # tool_call.function.name = "get_weather" # tool_call.function.arguments = '{"city": "北京"}' # 执行函数后，将结果返回给模型生成最终回复...

9 总结

Function Calling

  • 简单直接，易于上手
  • OpenAI/多家厂商支持
  • 缺乏统一标准，各平台不兼容
  • 工具定义需开发者手动维护

MCP

  • 开放标准，跨平台统一
  • 一次开发，多处复用
  • 原生支持 Tools + Resources + Prompts
  • 较新，生态仍在建设中

关键结论： MCP 并不是要取代 Function Calling，而是在更上层提供统一的工具集成标准。 可以理解为：MCP Server 内部也可以使用 Function Calling 来与模型交互，但对外提供标准化的 MCP 接口。 未来趋势是两者互补共存，MCP 成为 AI Agent 时代的"USB 标准"。

MCP 协议让 AI 真正"连接世界"，是通往 AI Agent 的关键基础设施！
