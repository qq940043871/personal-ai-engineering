1. Loop 是什么？

核心定义

Loop（主循环）是整个 AI Agent 的心脏。它是一个事件驱动的循环，持续地：

  • 接收用户输入（文本、文件、命令等）
  • 构建消息上下文（System Prompt + 历史消息 + 新输入）
  • 调用 LLM API 获取响应
  • 解析 LLM 响应（文本 + Tool Calls）
  • 通过 Harness 执行工具调用
  • 将工具结果注入下一轮循环
  • 管理上下文窗口大小，防止超出 Token 限制
Loop 状态机：
IDLE
等待输入
→
BUILD
构建上下文
→
CALL
调用 LLM
→
PARSE
解析响应
↑ ↓
EXECUTE
执行工具（如有）
←
CHECK
检查是否有 Tool Calls
没 Tool Calls → 返回 IDLE，输出给用户
与 Harness 的关系：
Loop
编排调度器
负责"什么时候做什么"
→ 调用 →
Harness
工具执行器
负责"怎么做"

Loop 调用 Harness 来执行工具，Harness 返回结果给 Loop，Loop 将结果送回 LLM。

2. 消息循环（Message Loop）

单次交互流程
Step 1: 接收用户输入
- 用户输入可能是文本、文件拖拽、命令（如 /commit）
- Loop 对输入进行预处理（如文件上传处理、命令解析）
- 将输入包装为 message { role: "user", content: "..." }
↓
Step 2: 构建上下文
- System Prompt（系统指令、工具定义）
- 历史消息（之前的对话和工具调用结果）
- 新的用户输入
- 如果上下文超过 token 限制 → 触发压缩
↓
Step 3: 调用 LLM
- 发送消息数组到 LLM API
- 携带工具定义（tool_definitions）
- 设置推理参数（temperature, max_tokens, top_p）
- 等待流式或非流式响应
↓
Step 4: 解析响应
- 提取 content（文本回复）
- 提取 tool_calls（工具调用请求）
- 处理流式输出（逐 token 渲染）
↓
Step 5: 决策分支
- 如果有 tool_calls → 交给 Harness 执行 → 回到 Step 2
- 如果没有 tool_calls → 输出给用户 → 回到 Step 1
这就是"循环"名字的由来！
只要 LLM 还在返回 tool_calls，Loop 就继续迭代，直到 LLM 给出最终回复。

3. 上下文管理（Context Management）

上下文内容结构
1. System Prompt（系统级，不可见用户）

- 角色定义："你是一个 AI 编程助手"

- 行为规范："不要在回答中提及你是一个 AI"

- 工具定义：所有注册工具的 Schema

- 环境信息：工作目录、操作系统、Git 状态

- 记忆信息：用户偏好、项目上下文

2. 消息历史（Message History）

- 用户消息 + AI 回复的交替序列

- 工具调用（tool_calls）和工具结果（tool_results）

- 上下文压缩后的摘要消息

3. 新输入（New Input）

- 用户最新的消息

- 或者本轮循环中工具调用的结果

上下文 Token 预算管理
Token 分配策略：
// 总预算 = 模型的最大上下文窗口 - 保留的余量
maxContextTokens = model.getMaxContextTokens() // 例如 200K
reservedTokens = 2000 // 保留给 API 响应
budget = maxContextTokens - reservedTokens // 198K
 
优先级分配：
1. System Prompt + Tool Definitions = 20K（固定）
2. 最新的用户输入 = 变量
3. 剩余预算 → 历史消息（从新到旧裁剪）

当历史消息超过预算时，Loop 从最旧的消息开始丢弃

消息类型与角色：
Role来源内容
system系统系统指令、工具定义
user用户用户的输入消息
assistantLLMAI 的回复（文本 + tool_calls）
toolHarness工具执行结果

4. 上下文压缩与总结

为什么需要压缩？

随着对话进行，消息历史不断增长。LLM 有最大上下文窗口限制（如 200K tokens），
当接近限制时，Loop 必须对历史进行压缩。

策略 1：滑动窗口裁剪
保留最新的 N 条消息，丢弃最旧的消息。
简单但会丢失早期上下文。
[msg1, msg2, msg3, ..., msg100] → 丢弃前50条 → [msg51, ..., msg100]
策略 2：摘要压缩
将早期的对话用 LLM 总结为一句话/一段话，
用摘要消息替换原始对话。
[msg1..msg50] → [summary: "用户询问了项目结构，然后要求实现一个功能..."] → [summary, msg51..msg100]
策略 3：工具结果降级（Truncation）
- 工具返回的内容太长（如大文件）
- 只保留前 N 个字符 + "（...省略...）"
- 文件内容可以被替换为文件路径
策略 4：选择性保留
- 保留所有 tool_calls 和 tool_results 的结构
- 但裁剪 tool_result 中的 content
- 或者只保留最后一次迭代的上下文
实际场景中的 Token 消耗示例：
// 一个典型的 10 轮交互会话
System Prompt: 15K tokens
用户消息: 5K tokens
AI 回复: 10K tokens
工具调用: 10K tokens
工具结果: 60K tokens ← 一般是最大的
总计: ~100K tokens

5. 重试与容错

错误处理策略
API 调用失败（网络错误、超时）
• 指数退避重试（Exponential Backoff）：1s → 2s → 4s → 8s
• 最大重试次数：3次
• 如果持续失败 → 降级为本地模式或报错
API 返回错误（400, 401, 429）
• 400 Bad Request：参数错误，需要调整请求
• 401 Unauthorized：认证失败，重新登录
• 429 Rate Limit：限流，等待后重试
• 500 Server Error：服务器问题，重试
截断（Cutoff）处理
LLM 响应可能因为 token 限制被截断：
• finish_reason === "length" → 表示被截断
• Loop 检测到截断后，将已生成的内容作为上下文，继续请求 LLM
• 递归调用直到完整生成或达到最大迭代次数
内容过滤（Content Filter）
• LLM 可能因为安全策略拒绝回答
• finish_reason === "content_filter"
• Loop 需要重新措辞后重试

6. 生命周期钩子（Hooks）

Loop 生命周期事件

Loop 在关键节点触发钩子（Hook），允许用户或插件介入自定义行为。

preProcessUserInput 在用户输入被处理前触发。可用于命令解析、文件上传预处理。
preBuildContext 在构建消息上下文前触发。可注入额外的系统指令或上下文。
postBuildContext 上下文构建完毕，即将发送给 LLM。可检查/修改消息列表。
preCallLLM 在调用 LLM API 前触发。可修改请求参数。
postCallLLM LLM 响应返回后触发。可检查/修改响应内容。
postProcessResponse 响应被解析后触发。决定是否继续循环或输出给用户。
onLoopIteration 每次循环迭代完成时触发。可用于进度报告或日志记录。
钩子配置示例（settings.json）：
{
"hooks": {
"preBuildContext": {
"command": "node scripts/inject-context.js"
},
"postCallLLM": {
"command": "node scripts/log-response.js"
}
}
}

钩子让用户可以在不修改核心代码的情况下，扩展 Loop 的行为

7. 完整伪代码

// ============================================
// Loop — 主循环与上下文管理 核心伪代码
// ============================================
 
class ConversationLoop {
 
config = {
model: "claude-sonnet-4-6",
maxTokens: 200_000,
maxIterations: 50, // 单次交互最大循环次数
retryCount: 3,
temperature: 0.7,
systemPrompt: "..."
}
 
messages = [] // 消息历史
hooks = {} // 生命周期钩子
harness = new ToolHarness() // 工具执行框架
 
// ---------- 主入口 ----------
async processUserInput(userInput) {
await this.runHook("preProcessUserInput", userInput)
 
// 包装用户输入为消息
userMsg = { role: "user", content: userInput }
this.messages.push(userMsg)
 
// 进入推理循环
iteration = 0
while (iteration < this.config.maxIterations) {
iteration++
 
// Step A: 构建上下文
context = await this.buildContext()
 
// Step B: 调用 LLM
response = await this.callLLM(context)
this.messages.push({
role: "assistant",
content: response.content,
tool_calls: response.tool_calls
})
 
// Step C: 检查是否有工具调用
if (response.tool_calls && response.tool_calls.length > 0) {
// 通过 Harness 执行工具
toolResults = await this.harness
.executeToolCalls(response.tool_calls)
 
// 将工具结果加入消息历史
this.messages.push(...toolResults)
 
// 检查是否达到预算限制
if (this.isNearTokenLimit()) {
await this.compressContext()
}
 
// 继续循环（把工具结果发给 LLM）
continue
 
} else {
// LLM 没有工具调用 → 返回文本给用户
await this.runHook("postProcessResponse", response)
return response.content
}
}
 
// 达到最大迭代次数 → 报错
throw new Error("达到最大循环迭代次数")
}
 
// ---------- 构建上下文 ----------
async buildContext() {
await this.runHook("preBuildContext")
 
systemMsg = {
role: "system",
content: this.config.systemPrompt
}
 
// 计算 token 数
totalTokens = countTokens(systemMsg) + countTokens(this.messages)
budget = this.config.maxTokens - 2000 // 预留余量
 
// 如果超出预算，压缩历史
while (totalTokens > budget) {
await this.compressContext()
totalTokens = countTokens(systemMsg) + countTokens(this.messages)
}
 
toolDefs = harness.getToolDefinitions()
 
await this.runHook("postBuildContext")
 
return {
messages: [systemMsg, ...this.messages],
tools: toolDefs
}
}
 
// ---------- 调用 LLM API ----------
async callLLM(context, retryCount = 0) {
try {
await this.runHook("preCallLLM", context)
 
response = await apiClient.createMessage({
model: this.config.model,
messages: context.messages,
tools: context.tools,
max_tokens: this.config.maxTokens,
temperature: this.config.temperature
})
 
await this.runHook("postCallLLM", response)
 
// 处理截断
if (response.finish_reason === "length") {
this.messages.push({
role: "assistant",
content: response.content
})
return await this.callLLM(this.buildContext())
}
 
return response
 
} catch (error) {
// 指数退避重试
if (retryCount < this.config.retryCount) {
waitMs = 1000 * Math.pow(2, retryCount)
await sleep(waitMs)
return await this.callLLM(context, retryCount + 1)
}
throw error
}
}
 
// ---------- 上下文压缩 ----------
async compressContext() {
// 策略：找到最旧的消息块，替换为摘要
if (this.messages.length < 20) {
return // 消息太少，不需要压缩
}
 
// 提取前10条消息
oldMessages = this.messages.slice(0, 10)
 
// 用 LLM 生成摘要
summary = await apiClient.createMessage({
messages: [
{ role: "system", content: "请总结以下对话，保留关键信息" },
...oldMessages
],
max_tokens: 500
})
 
// 替换为摘要消息
this.messages.splice(0, 10, {
role: "user",
content: `[上下文摘要] ${summary.content}`
})
}
 
// ---------- 钩子执行 ----------
async runHook(hookName, ...args) {
hook = this.hooks[hookName]
if (hook) {
await hook(...args)
}
}
 
// ---------- Token 预算检查 ----------
isNearTokenLimit() {
used = countTokens(this.messages)
limit = this.config.maxTokens
return used > (limit * 0.8) // 使用超过 80% 时触发压缩
}
}

8. 关键点总结

关键点 1：循环的本质是"推理-执行"交替

Loop 不是简单的"一问一答"，而是 LLM 推理 → 工具执行 → LLM 再推理 → ... → 最终回复 的多轮迭代。每次工具执行的结果都被喂回给 LLM，让它"看到"自己操作的结果。这就是 Agent 能自主完成复杂任务的根源。

关键点 2：上下文窗口是有限资源

LLM 的上下文窗口是有限的（如 200K tokens），但对话和工具结果会不断增长。Loop 必须主动管理上下文预算：裁剪、摘要、选择性丢弃。上下文管理的好坏直接决定了 Agent 的"记忆力"和表现。

关键点 3：工具结果是上下文膨胀的主要来源

工具执行返回的内容（文件内容、命令输出）往往是最大的 token 消耗者。读一个 2000 行文件 ≈ 50K tokens。Loop 需要对工具结果做截断（只保留前 N 行）、摘要（LLM 总结文件内容）、引用（用文件路径替代内容）等优化。

关键点 4：重试策略需要指数退避

API 调用总会失败（网络抖动、限流、服务器错误）。Loop 使用 Exponential Backoff（1s → 2s → 4s → 8s）重试，而不是固定间隔。同时要区分可重试错误（500、429、超时）和不可重试错误（400、401）。

关键点 5：截断恢复（Recovery from Cutoff）

当 LLM 响应被截断（finish_reason === "length"），Loop 不 panic。它将已生成的内容作为上下文的一部分，递归调用 LLM 继续生成。这让 Agent 能写出超出单次 max_tokens 限制的长内容。

关键点 6：生命周期钩子让 Loop 可扩展

Loop 不是封闭的黑盒。通过 pre/post 钩子系统，用户可以在每个关键节点注入自定义逻辑（日志、监控、上下文注入、行为修改）。这是 Loop 架构的扩展点设计。

关键点 7：安全终止（Guardrails）

Loop 必须有安全终止条件：最大迭代次数限制防止无限循环、最大 token 预算防止失控、用户取消信号允许手动中断。这些 guardrails 是生产级 Agent 的必要组件。
