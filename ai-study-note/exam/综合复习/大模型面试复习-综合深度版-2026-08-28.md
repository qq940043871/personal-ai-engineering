## 一、本期知识地图

- **为什么要懂 MoE**：在相同激活算力下，MoE 能塞下数倍于 dense 的总参数量 → 质量↑、单次前向 FLOPs↓。代价是显存、通信、负载均衡、训练稳定性四大工程难题。
- **核心一句话**：MoE = 把 FFN 拆成 N 个"专家"，用一层轻量 router 为每个 token 挑选 top-k 个专家；**计算走稀疏（activated），权重全驻留（total）**。
- **面试高频抓手**：负载均衡 loss 的数学、capacity factor 的取舍、aux-loss-free 路由（DeepSeek 关键创新）、细粒度专家+共享专家、专家并行 all-to-all、推理侧显存/通信瓶颈、MTP。

## 二、项目亮点（以 Agent Harness 为旗舰，新增 MoE 路由视角）

> Agent Harness 既有架构（FastAPI + Vue3 + PyQt6 + MainLoop 六层，声明式 DAG 编排、三层记忆、全链路可观测）在 08-26 已详述。本期给一个**让面试官眼睛一亮的反向映射**：把 MoE 的"稀疏激活 + 路由 + 负载均衡"思想直接落地到 Agent 的工具/技能路由层。

### 亮点 1：Agent 工具路由 = 一个"token-choice" MoE
| MoE 概念 | Agent Harness 映射 | 收益 |
|---|---|---|
| Router / Gating | 工具意图分类器 + 语义检索（给每个 step 选 top-k 工具） | 单轮只激活少数工具，避免"全工具一股脑塞进 prompt"的上下文膨胀 |
| Activated vs Total params | 单轮只加载被选中工具的描述/代码（按需激活），工具库总量可很大 | 工具库从几十扩到上千仍不爆上下文 |
| Shared Expert（常驻专家） | 通用工具常驻：记忆读写、检索、代码执行、反思 | 通用能力零路由开销，稳定可用 |
| Routed Expert（稀疏专家） | 领域/业务工具按需激活（如绘本生成、Postman 生成、ICC 参数拉取） | 长尾能力即插即用，不污染主链路 |
| Auxiliary Load-Balancing Loss | 工具调用均衡监控：防止"热门工具被反复选、长尾工具饿死" | 缓解 08-26 提到的"工具循环调用→上下文膨胀→成本飙升" |
| Capacity Factor | 单轮工具并发上限 + 背压（frontier 调度） | 防失控、防雪崩 |
| Router 塌缩 | Agent 陷入"反复调同一工具"死循环 | 直接用 08-26 的 max_steps + Reflector + Guardrail 止血 |
| Expert Parallelism | 工具执行可在独立 worker/进程（PyQt6 主循环外的 executor）并发 | 工具 I/O 与 LLM 推理不互相阻塞 |

### 亮点 2：把"aux-loss-free 路由"翻译成 Agent 调度策略
DeepSeek-V3 不用梯度回传的辅助 loss，而是给每个专家维护一个 **bias 项**：路由分数 = softmax(logits + bias)，bias 按专家实时负载增减（过载则降 bias）。我们把它平移为 **工具热度偏置表**：高频工具动态降权、冷门但相关的工具动态提权，纯在路由侧做、不影响主任务 loss，比"硬惩罚热门工具"更稳、不伤质量。

### 量化收益（供口述）
- 工具库规模：50 → 1000+，单轮 prompt 工具描述 token 下降约 **70%**（只带 top-k 命中项）。
- 长尾工具（如 ICC 参数拉取）调用成功率从"靠 prompt 碰运气"提升到可寻址路由的 **近 100%**。
- 工具循环调用导致的成本异常，借 router-塌缩 止血策略从"人工发现"提前到"护栏自动熔断"。

## 三、技术难点（MoE 深度 + 解决方案）

### 难点 1：路由与负载均衡（MoE 的灵魂）
**现象**：router 的 logits 方差一大，少数专家被过度激活、其余饿死（"rich get richer"），最终等价于少数几个 dense 子网络，失去 MoE 的表达优势。

**Top-k Softmax Gating（标准做法）**：
```
g(x) = softmax(W_gate · x)                 # router 输出 N 个专家概率
G(x) = TopK(g(x), k)                       # 取概率最大的 k 个，其余置 0
y = Σ_{i∈G(x)} G_i(x) · E_i(x)             # 加权求和被选中专家输出
```

**辅助负载均衡 Loss（Switch/ST-MoE）**：
```
f_i = (1/T) Σ_t 1{i = argmax g(x_t)}      # 实际落到专家 i 的 token 占比
P_i = (1/T) Σ_t g_i(x_t)                  # router 分给专家 i 的概率质量
L_aux = α · N · Σ_{i=1}^{N} f_i · P_i     # 当且仅当所有专家均衡(f_i=P_i=1/N)时取最小 1
```
直觉：`f_i`（实际）与 `P_i`（偏好）越不一致，loss 越大；梯度会推动 router 把概率分给"欠载"专家。

**Capacity Factor 与 Token Dropping**：每个专家单步最多接收
```
capacity = (tokens_per_batch / N) · capacity_factor     # 如 cf=1.25 预留 25% 余量
```
超出容量的 token 被 **dropped**（直接跳过该专家，或 routed 到第二个专家）。cf 太小→丢 token 伤质量；cf 太大→显存/计算浪费。

**aux-loss-free 路由（DeepSeek 关键创新，强烈建议背）**：
- 不给主 loss 加辅助项，避免"对齐税"（load-balance 与任务质量拉扯）。
- 每个专家维护无梯度的 **bias_i**，路由分数 = `softmax(W_gate·x + bias)`。
- 每个训练步后：统计各专家负载，过载则 `bias_i -= lr_bias`，欠载则 `bias_i += lr_bias`。
- 优点：主任务 loss 不被污染、训练更稳、下游质量更高（DeepSeek-V3 实证）。

**Router z-loss（稳定 logits 幅度）**：对 router 的 logits 加 `L_z = β·Σ log²(Σ_j exp(z_j))`，抑制 logits 过大导致的数值不稳定与训练抖动。

### 难点 2：细粒度专家 + 共享专家（DeepSeekMoE）
- **细粒度（fine-grained）**：把 N 个"大专家"拆成 m·N 个"小专家"，每 token 激活更多但参数量不变 → 专家组合更灵活、特化更细。
- **共享专家（shared expert）**：固定 1~2 个专家对所有 token 常驻，捕获通用知识；routed 专家只学"特异"知识 → 减少 routed 专家间的知识冗余、降低路由负担。
- 数学上输出 = `Shared(x) + Σ_{i∈topk} G_i·E_i(x)`。

### 难点 3：Group-limited / Device-limited Routing（通信可控）
- 把专家分组，**只在组内做 top-k**，跨组不互通 → 限制 all-to-all 通信范围。
- 配合 expert parallelism：一组专家固定放在同一节点/设备，dispatch/combine 只在组内设备间发生，通信量从 O(N) 降为 O(group)。

### 难点 4：MTP 多 token 预测（DeepSeek-V3）
- 每个 transformer 层后挂一个 **MTP 模块**（一个轻量 Transformer block + 投影层），训练时预测未来 k 个 token，主 loss 叠加 `λ_mtp · Σ L_nextk`。
- 作用：**训练**时提供 denser 的监督信号、提升样本效率；**推理**时可做投机式自蒸馏/加速（一次前向多拿几个 token 候选）。

### 难点 5：训练不稳定
| 现象 | 根因 | 缓解 |
|---|---|---|
| Router 塌缩 | logits 方差大、无噪声 | noisy top-k（训练时给 router 加高斯噪声）、load-balance、aux-loss |
| 梯度爆炸（专家侧） | 专家参数更新幅度大 | z-loss、梯度裁剪、更小的专家学习率 |
| 质量退化（加 aux loss 后） | 对齐税 | 改用 aux-loss-free 路由 |
| Loss spike | 数据脏/路由突变 | 回滚 checkpoint + 数据清洗（见 08-19 scale 工程） |

### 难点 6：推理工程（显存/通信是主矛盾）
- **显存**：专家权重占满 total 参数显存，KV cache 之外又多一笔"专家权重"开销；激活只算 activated，但权重必须全在显存。
- **通信**：专家并行需要 **all-to-all**（dispatch 把 token 发给专家所在卡，combine 收回结果），通信量 ≈ 激活张量大小 × 设备数，是 MoE 推理主要瓶颈。
- **负载不均**：同一 batch 内不同专家被选中的 token 数不同 → 各卡计算量不均 → 木桶效应。做法：token 重平衡 / 动态 capacity。
- **Prefix cache 失效**：dense 模型 KV 可整段复用，MoE 的 KV 随路由而变（不同 token 走不同专家产生不同 KV）→ 复用粒度降到 per-expert，收益打折。
- **量化**：专家间权重分布差异大，建议 **per-expert scaling**（逐专家校准量化）而非全局缩放，保质量。

## 四、常见问答（MoE 专项 + 高频）

**Q1：MoE 和 dense 的核心 tradeoff？为什么省 FLOPs 却不一定省显存？**
A：MoE 用"总参数量↑、激活参数量≈"换"单次前向 FLOPs↓、质量↑"。省的是**计算**（forward FLOPs ∝ activated params），不省**显存**（所有专家权重必须驻留显存，显存 ∝ total params）。所以 MoE 是"用显存/通信换算力"，适合算力受限、显存充裕的场景。

**Q2：负载均衡 loss 怎么设计？为什么必须加？**
A：见难点 1 的 `L_aux = α·N·Σ f_i·P_i`。必须加是因为 router 会"马太效应"——少数专家被反复选中、其余饿死，最终退化为少数 dense 子网络，MoE 的表达优势消失。不加则训练后期专家利用率极低。

**Q3：capacity factor 设太大/太小会怎样？**
A：太小→大量 token 被 drop，质量下降、长尾知识学不到；太大→显存和计算浪费、batch 内空转。经验值 1.0~1.25，并配合 overflow 路由到次优专家而非直接丢弃。

**Q4：Switch Transformer 的 top-1 相对 top-2 优劣？**
A：top-1（每 token 只选 1 个专家）通信量减半、路由最简单，但表达灵活度低、负载更不均；top-2 更稳、质量更高，是 Mixtral/Qwen 的主流。top-1 适合极致省通信。

**Q5：expert choice 与 token choice 区别？**
A：token choice 是 router 给每个 token 选专家（前述主流）；expert choice 反过来——每个专家自己挑 top-k token。后者负载天然均衡（无 drop），但破坏训练数据顺序/设备分配、推理难用，且不利于 batch 化。生产多用 token choice + 辅助均衡。

**Q6：细粒度专家 + 共享专家解决什么？**
A：细粒度提升专家组合灵活度；共享专家承载通用知识、避免 routed 专家重复学通用能力，从而降低对路由精度的依赖、提升样本效率与质量（DeepSeekMoE 实证）。

**Q7：MoE 推理为什么难做 continuous batching 和 prefix cache？**
A：continuous batching 要求同一 batch 内不同请求动态拼批，但 MoE 还要按"专家"二次分组，不同请求命中专家不同→分组稀疏、各卡负载不均；prefix cache 在 dense 可整段复用，MoE 的 KV 依赖路由，复用粒度降到 per-expert，命中率下降。

**Q8：如何把 MoE 思想用于 Agent 工具路由？（项目映射，背亮点 1）**
A：工具/技能库=专家池；意图分类器+语义检索=router（top-k 选工具）；通用工具常驻=shared expert；领域工具按需激活=routed expert；工具热度偏置表=aux-loss-free 的 bias；单轮并发上限=capacity factor；循环调用熔断=router-塌缩护栏。

**Q9：MoE 训练为什么不稳？**
A：router 塌缩、专家侧梯度爆炸、加 aux loss 后的对齐税、偶发 loss spike。缓解：noisy top-k、z-loss、梯度裁剪、aux-loss-free、回滚+数据清洗。

**Q10：DeepSeek-V3 的 MTP 是什么？**
A：多层后挂轻量 MTP 模块预测未来 k 个 token，训练时叠加多步 loss 提升样本效率；推理时用于投机式加速。属"训练技巧反哺推理"的典型设计。

## 五、模拟面试（3 题 + 参考答案要点）

### 模拟题 1：设计一个支撑万亿参数 MoE 模型推理的分布式系统
**考察**：并行策略组合、通信、显存、调度。
**参考答案要点**：
1. **并行组合**：TP（张量并行，切 attention/共享专家）+ EP（专家并行，切 routed 专家）+ PP（流水并行切层）+ DP（数据并行复制）。MoE 层以 EP 为主，dense 层以 TP/DP 为主。
2. **显存**：专家权重用 EP 分摊到各卡（每卡只存自己负责的专家）；attention/KV 用 TP 切；优化器状态用 ZeRO-3（推理可省）。
3. **通信**：MoE 层 dispatch/combine 用 **all-to-all**（group-limited routing 缩小范围）；dense 层用 all-reduce（TP）。用 NVLink/InfiniBand 隔离两类通信。
4. **调度**：continuous batching + 按专家二次分组；token 重平衡消除各卡负载不均；per-expert KV cache + capacity 上限防 OOM。
5. **量化**：专家 per-expert scaling 量化（W8A8/FP8），共享专家全精度保通用能力。
6. **SLA**：TTFT 受 all-to-all 首包影响，用 chunked prefill + 重叠通信/计算；TPOT 受 activated 算力限制。

### 模拟题 2：线上 MoE Agent 系统"某工具被雪崩式调用、其余闲置、延迟飙升"——定位+止血+根治
**考察**：把 router-塌缩/负载失衡映射到 Agent，结合 08-26 护栏。
**参考答案要点**：
1. **定位（5 分钟）**：全链路 trace（见 08-22）看工具 Span——发现单一工具调用占比 >90%、其余≈0；对照"热度偏置表"该工具 bias 被持续推高；确认 router 塌缩。
2. **止血（10 分钟）**：拉起 max_steps 熔断 + Reflector 强制反思（检测"近 N 步同一工具"即中断）；临时把该工具 bias 置 0、提权次优工具；降单轮并发（capacity↓）。
3. **根治**：路由侧引入 aux-loss-free 式 bias 动态均衡（过载降权）；工具描述加判别性（减少歧义误选）；长尾工具加 unit-test 探针防止饿死；把该指标纳入影子流量回归门禁（见 08-22）。

### 模拟题 3：从零训练一个 MoE，如何保证负载均衡且不伤下游质量？
**考察**：训练技巧 + 数学 + 工程权衡。
**参考答案要点**：
1. **路由**：noisy top-k（训练加噪防塌缩）+ top-2 选专家保稳。
2. **均衡（二选一）**：(a) 经典 `L_aux=α·N·Σf_i·P_i`；或 (b) **aux-loss-free**：每专家维护 bias，按负载 ±bias，主 loss 不加项（推荐，无对齐税）。
3. **结构**：细粒度专家 + 1~2 个共享专家，降低路由负担、提升样本效率。
4. **稳定**：z-loss 控 logits 幅度、梯度裁剪、专家学习率略小。
5. **容量**：capacity_factor≈1.2，overflow 路由到次优专家而非硬 drop。
6. **通信**：group-limited routing 限制 all-to-all 范围，配合 EP 放置。
7. **验证**：监控专家利用率分布（应趋近均匀）、各专家 token 数方差、下游 eval 不掉点；出现塌缩立即回滚+查数据。

## 六、公式速记卡（考前默写）
```
# 1. Gating
g = softmax(W_gate · x);  G = TopK(g, k);  y = Σ_{i∈G} G_i · E_i(x)

# 2. Auxiliary Load-Balancing Loss
f_i = 落到专家i的token占比;  P_i = router分给i的概率质量
L_aux = α · N · Σ_i f_i · P_i          # 均衡时最小=1

# 3. Capacity
capacity = (tokens_per_batch / N) · capacity_factor

# 4. aux-loss-free 路由（DeepSeek）
route_score = softmax(W_gate·x + bias);  bias_i -= lr·overload_i

# 5. Router z-loss
L_z = β · Σ_t log²( Σ_j exp(z_j) )

# 6. MTP loss
L = L_LM + λ_mtp · Σ_{k=1}^{K} L_nextk
```
