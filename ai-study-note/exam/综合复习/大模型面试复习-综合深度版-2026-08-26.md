## 📌 一、项目亮点（Project Highlights）

### 1.1 旗舰示例：Agent Harness（不是 ReAct 脚本，是一套"Agent 编排运行时"）

> 前六期已分别补充了六层架构、多模态工具接入、LLMOps 可观测、推理成本与 SLA 治理等视角。本期把视角收口到**"多 Agent 编排引擎"**——这是 Agent Harness 区别于"用 LangChain 串一个链"的本质：它是一个**声明式 DAG + 运行时调度 + 企业级保障**的生产平台。

**六层架构（速记，本期重点高亮 L2/L3 编排层）**：
```
L6 Infra    多集群GPU / K8s / 对象存储 / 向量库
L5 Gateway  限流·熔断·鉴权·灰度·多租户配额·计费埋点
L4 Provider 模型路由·KV复用·投机解码·量化·负载均衡
L3 Exec     ★ DAG 调度·依赖解析·并发控制·Checkpoint/Resume·背压   ← 本期重点：编排引擎
L2 Agent    ★ Planner·Reflector·Memory·RAG·Guardrail·Supervisor   ← 本期重点：Agent 协作原语
L1 Client   Web/App/API·流式SSE·断点续传
   ↕ 全链路 OpenTelemetry Tracing + Metrics + Online Eval
```

**本期核心新增亮点：把"多 Agent 协作"当作一等能力内建，而非临时胶水代码**

1. **声明式 DAG 编排（Declarative Orchestration）**
   - 每个业务（自动绘本生成、公众号 6 节点流水线、AI 学习系统）被描述成一张 DAG：节点 = Planner / Worker / Tool / LLM / RAG / Guardrail；边 = 数据流（输出→输入）+ 控制流（条件/循环/人工门）。
   - 运行时负责：环检测、拓扑排序、可运行 frontier 推进、依赖 barrier、并发度限流、崩溃续跑。
   - 效果：**新业务上线从"月级"降到"周级"**——复用节点库，只写 DAG 描述 + 业务 prompt。

2. **多 Agent 协作原语（Multi-Agent Primitives）**
   - 内置 Supervisor（中央拆解/汇总）、Pipeline（顺序流水线）、Blackboard（共享黑板）、Debate（对抗校验）四种协作模式，按业务选配。
   - 例：自动绘本 = Supervisor 拆解"脚本→绘图→排版"，各 Worker 并行；公众号 = Pipeline 6 节点顺序；复杂决策 = Debate 双 Agent 互审。

3. **三层记忆 + 跨节点上下文契约（Memory & Context Contract）**
   - Working（当前 task scratchpad）/ Episodic（历史轨迹，向量库检索）/ Semantic（用户画像与知识，知识库）——显式分层，不混在一起喂 prompt。
   - 每个节点只消费/产出**声明好的 schema**，上下文不"透传膨胀"，超 budget 自动 compaction（摘要压缩旧消息，保留关键决策与工具结果指针）。

4. **可靠性护栏（Reliability Guardrails）**
   - `max_steps` 硬上限防死循环；Reflector 节点做自我反思（Reflexion）；Guardrail 节点做越权/越域/敏感词检测；工具调用 JSON Schema 校验 + 约束解码保证可解析；危险操作 HITL 人工确认。

5. **长程任务持久化与续跑（Checkpoint / Resume）**
   - 节点级 checkpoint 落库，跑 10 分钟崩溃后从最近点续跑而非重来；副作用工具标记幂等 key，防重复执行（如重复发文、重复扣费）。

6. **可观测与成本归因（呼应 08-22）**
   - 每个节点 emit span：输入/输出/耗时/token/成本/状态；整张 DAG 一条 trace 串联；成本按 node/tool/tenant 聚合，定位"最烧钱的 agent 路径"。

**量化成果（生产数据，与前六期一致）**：工具调用成功率 55%→92%、端到端任务成功率 61%→89%、新业务上线周期 月级→周级、推理综合成本 $1.00→$0.29（-71%）、P99 首 Token 2.8s→0.9s。

## 📌 二、技术难点（Agent 工程 8 大难点 + 解决方案）

### 2.1 编排引擎：DAG 调度与并发控制
**现象**：业务是多步骤、有依赖、可并行的（如绘本"脚本"和"配图"可并行，但"排版"依赖前两者）；用线性脚本写死难维护、难并行、难恢复。
**核心算法**：
- **环检测**：DFS 三色标记（白/灰/黑），遇灰节点即存在环，复杂度 O(V+E)；上线前静态校验 DAG 合法。
- **拓扑排序**：Kahn 算法（维护入度队列，出队即输出，邻接点入度-1），O(V+E)，决定执行顺序。
- **并发 frontier 调度**：维护"已就绪(入度=0 且前驱已完成)节点集合"，每完成一个节点就尝试解锁后继；用信号量/worker 池限制并发度，下游慢则上游背压。
**难点**：① 动态 DAG（LLM 运行时决定下一步，如 Planner 动态产出子任务）；② 条件分支/循环（需 `max_iterations` 硬上限防死循环）；③ 人工节点阻塞整图直到审批。
**解决方案**：把"控制流"显式建模为节点/边；用 frontier 队列推进可运行节点；循环用计数器 guard；HITL 节点将 DAG 置为 suspended 状态、审批后 resume。

### 2.2 上下文与记忆：三层记忆 + 跨节点传递 + 膨胀治理
**现象**：多 Agent 协作时，上下文在 agent 间透传会指数膨胀；长程任务上下文超出窗口。
**架构**：Working（本次任务 scratchpad，易膨胀）/ Episodic（历史任务轨迹，向量库检索）/ Semantic（用户画像与领域知识，知识库）。三者分层，不混着塞 prompt。
**上下文契约**：每个节点声明"消费哪些上游字段、产出哪些字段"，运行时只做 schema 级传递，避免无脑 `全量context += 上游输出`。
**压缩公式**：设 `B = model_max_ctx - reserve`；当 `used = Σ(node_io) + history > α·B`（α≈0.8）触发 compaction：对旧消息做摘要压缩（保留关键决策、工具结果指针、未完成子任务），压缩后 `used' < B`。
**难点**：压缩丢信息导致后续决策偏航。解：压缩只摘要"过程"，保留"结论与指针"（指针指向完整 tool 结果存储），下游按需再取。

### 2.3 工具调用的类型安全与沙箱
**现象**：LLM 生成的调用参数不合法（字段缺失/类型错）、或执行危险操作（写文件/调外部付费 API/发消息）。
**解决方案**：
- **Schema 校验 + 约束解码**：工具用 JSON Schema 注册（FuncHub），推理引擎做 structured/guided decoding，保证输出可解析；非法参数在调用前被拦下并反馈给 LLM 重试。
- **工具注册中心集中治理**：鉴权、限流、审计、超时统一在 FuncHub，编排层不重复实现。
- **危险操作 HITL**：写外部、花钱、发消息类工具需人工确认 gate。
- **幂等**：每个工具调用带 `idempotency_key`，重复提交返回首次结果，防崩溃重跑导致副作用重复（如重复发文/扣费）。

### 2.4 长程任务的持久化与崩溃恢复
**现象**：Agent 跑 10 分钟、中间节点崩溃，重跑浪费且可能重复副作用。
**解决方案**：
- **节点级 Checkpoint**：每个节点完成即把输出落库（对象存储/DB），DAG 状态机记录已完成集合；崩溃后从最近 checkpoint resume，未完成的重新调度。
- **副作用幂等 + Saga 补偿**：跨多工具的"事务"用 saga 模式——每步记录补偿操作，某步失败则逆序补偿（如"已扣额度未发文"→回补额度），保证最终一致。

### 2.5 流式输出、取消与续跑
**现象**：用户要实时看进展、要能中途取消，且取消后状态一致（不能半篇文章发出去）。
**解决方案**：节点事件总线 + SSE/WebSocket 流式推送进度；取消发 `cancellation token`，running 节点优雅停（停止后续 decode、释放锁）；partial result 标记可恢复点，下次从断点续。

### 2.6 多 Agent 协作的模式与上下文共享
**模式对比**：
| 模式 | 机制 | 适用 | 风险 |
|------|------|------|------|
| **Supervisor（中央调度）** | 一个 manager 拆解任务、分派 worker、汇总 | 任务可拆解、需统一口径 | manager 成瓶颈/单点 |
| **Hierarchical（分层）** | 多层 manager/worker | 超复杂任务 | 链路长、延迟高 |
| **Blackboard（共享黑板）** | 多 Agent 读写共享状态板 | 任务耦合、需共享中间产物 | 状态竞争、难调试 |
| **Debate（对抗校验）** | 两/多 Agent 互审互驳 | 高风险决策（合同/医疗） | token 成本翻倍 |
| **Pipeline（流水线）** | 顺序节点、前输出后输入 | 固定工序（公众号发布） | 单点慢拖全链 |

**难点**：handoff 上下文丢失、重复劳动、成本平方增长、Agent 间冲突。
**解**：共享黑板/消息总线承载中间产物；明确 handoff 契约（传什么、不传什么）；supervisor 负责拆解与汇总；`token_budget` 限制每个子 agent 用量，超预算强制收敛。

### 2.7 失控与幻觉防护（可靠性护栏）
**现象**：Agent 陷入循环、调用不存在工具、产出无意义、越界(泄露系统提示/越权)。
**解决方案**：
- **`max_steps` / `max_iterations` 硬上限**：超过即终止并上报，防死循环与成本失控。
- **Reflector 自我反思（Reflexion）**：失败后在记忆里写" verbal self-critique"（哪步错、为何错、下次怎么改），下一轮把 critique 注入重新规划，不重训模型即提成功率。
- **工具白名单 + 输出 Schema 校验**：未注册工具一律拒绝；输出不符合 schema 触发重试。
- **Guardrail 节点**：敏感词/越权/越域/合规检测，命中即拦截或降级（小模型补救/人工接管）。
- **失败重试 + 降级链**：LLM 节点失败→换模型→换 prompt→人工接管，分级兜底。

### 2.8 可观测性与成本归因
**现象**：出问题不知卡哪个节点、不知哪条路径最烧钱。
**解决方案（呼应 08-22）**：每个节点 emit span（输入/输出/耗时/token/成本/状态），整张 DAG 一条 trace 串联；按 node/tool/tenant 聚合成本，定位"最烧钱的 agent 路径"；Golden Set 回归门禁防编排改动导致质量回退。

## 📌 三、常见问答（10 题，深度版）

**Q1：什么是 Agent？和 Chain/Workflow/RPA 的区别？**
Agent = 能**自主感知→规划→调用工具→观察结果→迭代**直到达成目标的系统，核心是"LLM 驱动的控制流 + 工具反馈闭环"。Chain/Workflow 是**固定**步骤编排（无动态决策）；RPA 是规则脚本（无 LLM 推理）。Anthropic 定义：**Workflow = 预定义代码路径编排 LLM；Agent = LLM 动态决定自身流程与工具**。选 Agent 还是 Workflow：任务步骤明确且高频 → Workflow（更可控更便宜）；步骤开放、需判断 → Agent。

**Q2：ReAct / Plan-and-Execute / Reflexion / ToT 各自取舍？**
- **ReAct**（Yao 2022）：Thought→Action→Observation 交错，边想边干，简单通用；缺点是长任务易迷失、context 膨胀。
- **Plan-and-Execute**：先整体规划再逐步执行，计划可复用、context 更省；缺点是计划僵化、遇意外需重规划。
- **Reflexion**（Shinn 2023）：失败后写 verbal self-critique 进记忆，下一轮改进，**不重训**即提成功率；适合需反复试错的编码/搜索任务。
- **Tree of Thoughts**（Yao 2023）：多分支探索+自我评估选优，适合需搜索/规划的解题；token 成本高。
- 工程选：多数生产用 Plan-and-Execute + ReAct 混合（先粗规划、节点内 ReAct），关键决策加 Reflexion/Debate。

**Q3：Function Calling / Tool Use 原理？并行调用？参数怎么保证合法？**
原理：模型输出特殊 token 触发工具名+参数（JSON），运行时校验并执行、把结果回灌 context。并行：支持一次输出多个 tool call 并发执行（需工具间无依赖）。合法性：① 工具用 JSON Schema 声明；② 推理引擎 structured/guided decoding 约束输出符合 schema；③ 调用前再校验，非法则反馈 LLM 重试；④ 危险工具加 HITL。

**Q4：多 Agent 协作有哪些模式？何时用 Supervisor？**
见 2.6 表。Supervisor 适用"任务可拆解、需统一口径/汇总"（如把"写报告"拆给检索/写作/审校三个 worker）。Blackboard 适用"中间产物需多 agent 共享共建"（如联合诊断）。Debate 适用"高风险不可错"（合同/医疗），用 token 换可靠性。

**Q5：怎么防止 Agent 失控/死循环？max_steps、Reflector、Guardrail 怎么配合？**
三层：① **硬上限** `max_steps` 截断死循环与成本爆炸；② **软纠偏** Reflector 在临近上限或失败时将 critique 写入记忆，引导下一轮收敛；③ **边界** Guardrail 节点做越权/越域/敏感拦截。再加工具白名单与输出 schema 校验。三者分别是"止血/自愈/设防"。

**Q6：Agent 的"记忆"怎么设计？上下文膨胀怎么治理？**
三层（2.2）：Working（当前 scratchpad，易膨胀，需 compaction）/ Episodic（历史轨迹，向量检索召回相关）/ Semantic（用户画像与知识，知识库）。膨胀治理：① 上下文契约（节点只传声明字段）；② compaction 摘要压缩（保留结论+指针，见 2.2 公式）；③ 旧消息移出 context 改为按需检索；④ 子 agent 独立 context，只在 handoff 时传必要摘要。

**Q7：长程任务崩溃如何恢复？checkpoint/resume + 幂等怎么落地？**
节点级 checkpoint 落库（2.4），崩溃从最近点 resume；副作用工具带 `idempotency_key` 保证重跑不产生重复副作用；跨工具事务用 saga 补偿。关键：**状态机记录 DAG 已完成集合**，resume 时跳过已完成节点。

**Q8：怎么评测 Agent 质量？成功率高但用户不满意怎么办？**
两层：① **trajectory eval**：不只看最终结果，评每一步是否合理（用 LLM-as-Judge 或规则评 tool 选择/参数/顺序），呼应 08-22 但细化到 step；② **端到端 success rate** + 业务指标（用户续用率/修正次数）。用户不满意但成功率高→往往是"对但不好用"（格式啰嗦/步骤冗余/过度调用工具），需用 step 级 eval + 人工抽样定位，而非只看终态。

**Q9：生产 Agent 如何控制成本与延迟？**
① 路由（简单任务走小模型，呼应 08-25）；② 上下文压缩降 token（2.2）；③ `token_budget` 限制子 agent 用量；④ 工具结果截断/摘要，避免大结果喂回；⑤ 并行工具调用降 wall-time；⑥ 成本按 node/tool 归因（2.8）定位烧钱路径；⑦ 缓存（相同子任务结果复用）。

**Q10：Agent 接入 RAG / 外部系统的可靠模式？**
① 工具化接入（RAG 检索是一个 Tool 节点，而非硬编码）；② 异步 + 超时 + 重试（外部系统可能慢/挂）；③ 结果截断/结构化（外部返回可能巨大，需摘要后入 context）；④ 写类操作 HITL + 幂等；⑤ 失败降级（检索不到→换关键词/转人工）；⑥ 审计日志（谁在何时调了什么）。

## 📌 四、模拟面试（3 题 + 参考答案要点）

### 模拟题 1：设计一个支持千人在线、可并行、可中断续跑、可观测、成本可控的多 Agent 协作平台
**考察**：体系化 Agent 工程能力（编排、可靠、成本、可观测四位一体）。
**参考答案要点**：
- **编排层（L3）**：声明式 DAG（节点=Planner/Worker/Tool/LLM/RAG/Guardrail，边=数据/控制）；环检测(Kahn O(V+E))+frontier 并发调度+信号量限流+背压；动态 DAG 支持 LLM 运行时决定下一步；`max_iterations` 防死循环。
- **可靠层**：节点级 Checkpoint 落库+resume（崩溃从最近点续跑）；副作用幂等 key；saga 补偿跨工具事务；HITL 门（写/花钱/发消息需人工确认）。
- **记忆层（L2）**：三层记忆(Working/Episodic/Semantic)+上下文契约+compaction（超 0.8·B 触发摘要压缩，保结论留指针）。
- **成本层（L4）**：按复杂度/预算路由大↔小模型；token_budget 限子 agent；工具结果摘要；KV 前缀复用/量化/投机（呼应 08-25）；成本按 node/tool/tenant 归因。
- **可观测层（全链路）**：每节点 emit span（输入/输出/耗时/token/成本/状态），整 DAG 一条 trace；SLI：任务成功率、TPOT/TTFT、单任务成本；Golden Set 回归门禁。
- **取舍**：Supervisor 模式简单但有单点→关键业务用分层/HITL；并发提吞吐但涨单请求延迟→按 SLA 调 worker 池；compaction 省 token 但可能丢细节→只摘要过程留指针。

### 模拟题 2：生产 Agent 出现"工具循环调用 → 上下文膨胀 → 成本飙升 + 响应变慢"，你怎么现场定位与止血？
**考察**：故障定位 + 失控护栏实操（呼应 2.7 / 2.2）。
**参考答案要点**：
- **定位（可观测）**：① 看 trace，找"重复调用同一 tool / 同一步反复出现"的节点（死循环信号）；② 看 context 长度曲线，确认膨胀来源（无契约透传 / 工具大结果未截断）；③ 看成本聚合，定位烧钱路径（哪个 agent/tool）。
- **止血（先保命）**：① 立即拉高 `max_steps` 上限或临时熔断该 Agent 入口（返回降级）；② 对工具结果加截断/摘要，阻断膨胀源；③ 对重复 tool call 加幂等+"同参数 N 秒内不重发"去重；④ 临时路由到小模型降成本。
- **根因修复**：① 加 Reflector：失败写 critique，避免无脑重试同一动作；② 加 Guardrail：检测"连续相同 action"即拦截并换策略；③ 上下文契约：节点只传声明字段，工具结果 LLM 侧只留摘要；④ 失败重试加指数退避+上限，避免雪崩。
- **验证**：Golden Set 回归 + 在线影子流量，确认成功率回升、单任务成本回落、无复发。

### 模拟题 3：给定 Agent Harness 六层架构，如何让"自动绘本生成"业务 1 周上线且质量可控？
**考察**：用平台能力快速交付 + 质量保障闭环（呼应 1.1 / 1.2）。
**参考答案要点**：
- **复用而非重写（周级关键）**：① L2 直接用 Supervisor+多 Worker 模板；② 复用 FuncHub 的"文生图工具/排版工具"；③ 复用 RAG 节点做风格参考；④ 只写一张 DAG 描述 + 业务 prompt。
- **DAG 设计**：Supervisor 拆解"脚本生成→分镜→文生图(可并行多 Worker)→排版合成→质检"；质检 Guardrail 节点卡质量门（不达标回流重写）。
- **质量可控**：① 三层记忆存"用户偏好的画风/角色设定"(Semantic)；② Guardrail 节点做内容合规+画风一致性校验；③ 工具结果截断防图描述撑爆 context；④ 用历史 Golden Set(往期优质绘本)做回归，新业务上线前过门禁。
- **可靠与成本**：Checkpoint 防长任务崩溃重跑；文生图走小模型路由降成本；成本按 node 归因看"绘图"是否占比过高。
- **结果**：复用节点库+模板，**1 周**交付；Guardrail+Golden Set 保证质量不靠"人盯"。
