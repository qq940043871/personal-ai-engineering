## 📌 二、技术难点速记（Technical Difficulties）

### 2.1 Transformer 注意力机制进化速记

**MHA → MQA → GQA → MLA**：

| 机制 | KV Cache 大小 | 质量损失 | 适用场景 |
|------|--------------|---------|---------|
| MHA | 1.0x（最大） | 0% | 高质量要求 |
| MQA | 0.52x（-48%） | 5-10% | 极长上下文 |
| GQA | 0.75x（-25%） | 2-5% | 平衡方案 |
| MLA | 0.174x（-82.6%） | <2% | DeepSeek-V3 |

**MLA 核心技巧**：
- 低秩 KV 压缩：K/V 投影到低维空间
- 解压时重构：推理时再投影回高维
- 显存占用：-95.5%（相比 MHA）

### 2.2 位置编码全面对比速记

**Sinusoidal → RoPE → ALiBi → YaRN**：

| 编码 | 核心思想 | 长度外推 | 工业应用 |
|------|---------|---------|---------|
| Sinusoidal | 正弦余弦 | 差 | 已淘汰 |
| RoPE | 旋转矩阵 | 中 | ⭐ 工业标准 |
| ALiBi | 注意力偏置 | 好 | 短上下文 |
| YaRN | NTK-aware 插值 | 极好（8x） | 长上下文 |

**RoPE 为什么成为工业标准？**
1. 相对位置编码（任意位置组合）
2. 旋转矩阵（保持内积不变）
3. 长度外推能力（训练 4K，推理 8K）

**YaRN 核心技巧**：
- NTK-aware 插值：高频保留，低频插值
- 温度缩放：Softmax 温度随位置调整
- 长度外推：8x 几乎无损

### 2.3 大模型训练稳定性——Loss Spike 速记

**六大根因与解决方案**：

| 根因 | 占比 | 解决方案 |
|------|------|---------|
| 学习率过大 | 40% | Warmup + Cosine Decay |
| 数据质量差 | 25% | 质量过滤 + 去重 |
| 梯度爆炸 | 15% | Gradient Clipping（1.0） |
| Embedding 不稳定 | 10% | Tied Embedding |
| 注意力崩溃 | 5% | Softmax 温度缩放 |
| 硬件故障 | 5% | 健康检查 + 回滚 |

**排查流程**（5 步）：
1. 检测 Spike（Loss 突增 10x）
2. 保存检查点（Spike 前 100 步）
3. 检查学习率（是否过高）
4. 检查数据（是否有异常 Token）
5. 回滚重试（从检查点恢复）

### 2.4 KV Cache 工程化速记

**三代技术对比**：

| 技术 | 显存利用率 | 核心思想 | 应用 |
|------|----------|---------|------|
| 传统管理 | ~60% | 连续显存分配 | 早期方案 |
| PagedAttention | 92% | 分页管理（类似 OS） | vLLM |
| MLA | 95.5% | 低秩压缩 | DeepSeek-V3 |

**PagedAttention 核心思想**：
- 将 KV Cache 分成固定大小的"页"
- 动态分配（按需申请）
- 共享机制（Prefix Caching）

**MLA 核心思想**：
- K/V 低秩压缩（投影到 512 维）
- 推理时解压（重构完整 K/V）
- 显存占用：-95.5%

## 📌 三、常见问答速记（Common Interview Q&A）

### Q1：Transformer 为什么用 Attention 而不是 RNN？

**五层答案速记**：

1. **序列建模演进**：RNN（梯度消失）→ LSTM（局部依赖）→ Attention（全局依赖）
2. **数学对比**：Attention 任意位置依赖 = 1 次矩阵乘法，RNN 需要连乘 t 次
3. **训练稳定性**：残差连接 + LayerNorm + 注意力稀疏性
4. **并行性**：Attention 可完全并行，RNN 必须串行
5. **归纳偏见**：Attention 无局部性偏见，数据驱动学习

**面试加分项**：
- 能手写 Attention 公式：$Attention(Q,K,V) = softmax(\frac{QK^T}{\sqrt{d_k}})V$
- 理解 Attention 的 O(n²) 复杂度与优化（Flash Attention）

### Q2：LoRA 的原理是什么？为什么比全量微调更高效？

**四层答案速记**：

1. **问题定义**：全量微调显存占用大（13B 模型需要 208 GB）
2. **核心思想**：低秩适配，ΔW = BA（参数量 0.4%）
3. **变体全景**：
   - QLoRA：量化 + LoRA（显存 -60%）
   - AdaLoRA：自适应秩（重要层用大秩）
   - DoRA：权重分解（方向 + 幅度）
4. **实战代码**：LoRALinear 实现（见综合精华版）

**面试加分项**：
- 理解 LoRA 的秩选择（通常 r=8~64）
- 知道 LoRA 的局限性（推理时额外计算）

### Q3：RAG 和 Fine-tuning 应该如何选择？

**决策框架速记**：

| 维度 | RAG | Fine-tuning |
|------|-----|-------------|
| 知识时效性 | 实时更新 | 静态（需重训） |
| 能力类型 | 知识密集型 | 能力密集型 |
| 可解释性 | 高（可溯源） | 低（黑盒） |
| 成本 | 低 | 高 |
| 定制化 | 中 | 高 |

**混合策略**：
- RAG + 轻量微调（质量 +10-15%）
- Fine-tuning + RAG（能力 + 知识）

### Q4：如何设计一个支持百万级用户的 LLM 服务？

**架构设计速记（五层）**：

1. **接入层**：负载均衡（Anycast + BGP）+ 认证（JWT）
2. **路由层**：模型选择（7B/13B/70B）+ 语义缓存（命中率 40%）
3. **推理层**：vLLM 集群 + PagedAttention + Prefix Caching
4. **监控层**：Prometheus + Grafana + 告警
5. **优化层**：模型路由（-80% 成本）+ 量化推理（-50% 成本）

**成本优化速记**：
- 模型路由：80% 流量用 7B（成本 -80%）
- 语义缓存：命中率 40%（成本 -40%）
- 量化推理：INT4/INT8（吞吐量 +100%）

### Q5：Flash Attention 的核心原理是什么？

**IO 感知计算速记**：

1. **标准 Attention 的 IO 瓶颈**：S 矩阵必须存在 HBM，读写速度慢（1.5 TB/s）
2. **Tiling**（分块计算）：每个 Block 完全放入 SRAM（20 MB，快 10x）
3. **Online Softmax**（在线 Softmax）：增量更新，无需存储整个 S 矩阵
4. **Kernel Fusion**（算子融合）：减少 HBM 访问次数 -94%

**性能数据速记**：
- 加速比：3.75x（A100）
- 显存占用：-66%
- 适用场景：长上下文（8K+）

### 模拟面试题 1：如何设计一个支持多模态输入的 LLM 应用系统？

**参考答案要点**：

**第1层：需求分析**
- 输入类型：文本 + 图像 + 音频 + 视频
- 输出类型：文本 + 图像（可选）
- 延迟要求：< 2s（实时）/ < 10s（批量）
- 成本要求：$0.01/请求（目标）

**第2层：系统架构设计（六层）**

```
┌─────────────────────────────────────────┐
│           Client Layer (Web/App)         │
├─────────────────────────────────────────┤
│        API Gateway (负载均衡/认证)        │
├─────────────────────────────────────────┤
│      Multimodal Router (多模态路由器)     │
├─────────────────────────────────────────┤
│  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
│  │ Vision  │ │ Audio   │ │ Video   │   │
│  │ Encoder │ │ Encoder │ │ Encoder │   │
│  └────┬────┘ └────┬────┘ └────┬────┘   │
├───────┼───────────┼───────────┼─────────┤
│      Multimodal Fusion (多模态融合)      │
├─────────────────────────────────────────┤
│         LLM (GPT-4V/Claude/Local)        │
├─────────────────────────────────────────┤
│      Output Layer (文本/图像/音频)        │
└─────────────────────────────────────────┘
```

**第3层：关键技术实现**

1. **多模态编码器**：
   - 视觉：CLIP ViT-L/14（图像 → 768 维向量）
   - 音频：Whisper Encoder（音频 → 1280 维向量）
   - 视频：TimesFormer（视频 → 时序向量）

2. **多模态融合策略**：
   - 早期融合：拼接所有模态特征（简单但低效）
   - 晚期融合：各模态独立编码，最后融合（高效）
   - 跨模态注意力：Q（文本） × K/V（图像）（推荐）

3. **跨模态注意力实现**：
```python
# 文本 Query × 图像 Key/Value
text_hidden = text_encoder(input_text)  # [B, T, D]
image_features = vision_encoder(input_image)  # [B, N, D]

# Cross-Attention
Q = text_hidden @ W_Q  # [B, T, D]
K = image_features @ W_K  # [B, N, D]
V = image_features @ W_V  # [B, N, D]

attention_scores = Q @ K.T / sqrt(D)  # [B, T, N]
attention_weights = softmax(attention_scores)  # [B, T, N]
output = attention_weights @ V  # [B, T, D]
```

**第4层：工程优化**

1. **模型选择策略**：
   - 简单任务（纯文本）：7B 模型（$0.001/请求）
   - 中等任务（文本+图像）：13B 模型（$0.01/请求）
   - 复杂任务（多模态理解）：70B 模型（$0.1/请求）

2. **缓存策略**：
   - 图像特征缓存（Redis）：避免重复编码
   - 文本特征缓存（内存）：加速相似请求

3. **批处理优化**：
   - 动态 Batching（持续收集请求，填满 Batch）
   - Padding 优化（去掉无效 Token）

**第5层：成本估算**

| 组件 | 成本/请求 | 优化后 |
|------|----------|--------|
| 视觉编码 | $0.005 | $0.002（缓存） |
| 音频编码 | $0.003 | $0.001（缓存） |
| LLM 推理 | $0.05 | $0.02（模型路由） |
| 存储 | $0.001 | $0.0005（压缩） |
| **总计** | **$0.059** | **$0.0235（-60%）** |

**面试加分项**：
- 理解多模态对齐问题（如何对齐不同模态的语义空间）
- 知道多模态模型的训练策略（对比学习/跨模态注意力）

### 模拟面试题 2：如何优化 LLM 在边缘设备上的部署？

**参考答案要点**：

**第1层：边缘设备约束分析**

| 约束 | 手机（iPhone） | 嵌入式（树莓派） | IoT 设备 |
|------|--------------|-----------------|---------|
| 算力 | 10 TOPS | 0.1 TOPS | 0.01 TOPS |
| 内存 | 8 GB | 4 GB | 512 MB |
| 存储 | 256 GB | 32 GB | 4 GB |
| 功耗 | 5W | 3W | 1W |
| 延迟 | < 500ms | < 2s | < 5s |

**第2层：模型压缩技术（四维）**

1. **量化（Quantization）**：
   - INT8 量化：模型大小 -75%，精度损失 <2%
   - INT4 量化：模型大小 -87.5%，精度损失 2-5%
   - 混合精度：敏感层用 FP16，其他用 INT8

2. **剪枝（Pruning）**：
   - 非结构化剪枝：去掉个别权重（稀疏度 50%）
   - 结构化剪枝：去掉整个神经元/层（加速比 2x）
   - 迭代剪枝：训练 → 剪枝 → 微调（重复）

3. **知识蒸馏（Knowledge Distillation）**：
   - Teacher（70B）→ Student（7B）
   - 蒸馏损失：KL 散度（Soft Target）
   - 效果：Student 达到 Teacher 90% 性能

4. **低秩分解（Low-Rank Factorization）**：
   - 权重矩阵分解：W ≈ U Σ V^T
   - 参数量：D×D → (D×r) + (r×D)（r << D）
   - 加速比：2-3x

**第3层：推理优化技术**

1. **算子融合（Operator Fusion）**：
   - LayerNorm + Attention + MLP 融合
   - 减少内存读写（加速比 1.5x）

2. **Flash Attention（移动端适配）**：
   - 分块计算（适配小显存）
   - Online Softmax（减少显存占用）

3. **Speculative Decoding（推测解码）**：
   - 小模型生成候选 → 大模型验证
   - 加速比：2-3x（接受率 70%）

4. **KV Cache 优化**：
   - PagedAttention（分页管理）
   - 共享 KV Cache（Prefix Caching）

**第4层：工程实践（以手机部署为例）**

**模型选择**：
- 7B 模型（量化后 3.5 GB，适合手机）
- 推理框架：llama.cpp / MNN / TFLite

**部署流程**：
1. 模型训练（云端 70B 模型）
2. 知识蒸馏（70B → 7B）
3. 量化（FP16 → INT4）
4. 算子优化（ONNX → TensorRT / CoreML）
5. 部署（App 集成）

**性能数据**：
- 模型大小：13B（FP16）→ 3.5B（INT4）（-73%）
- 推理速度：5 Token/s → 20 Token/s（+300%）
- 内存占用：8 GB → 2 GB（-75%）
- 功耗：5W → 2W（-60%）

**第5层：成本控制**

| 优化策略 | 成本节省 | 实施难度 |
|---------|---------|---------|
| INT4 量化 | -50% | 低 |
| 知识蒸馏 | -70% | 中 |
| 算子融合 | -30% | 高 |
| Speculative Decoding | -50% | 中 |

**总节省**：~80%（相比云端推理）

**面试加分项**：
- 理解量化误差的来源（截断误差/舍入误差）
- 知道如何选择合适的量化策略（Post-training vs Quantization-aware Training）

**参考答案要点**：

```
99.99% 可用性 = 每年停机时间 < 52.56 分钟
= 每月停机时间 < 4.38 分钟
= 每周停机时间 < 1.01 分钟

```

**第2层：高可用架构设计（七层）**

```
┌─────────────────────────────────────────┐
│        Global Load Balancer (全局负载均衡) │
│        (Anycast + BGP, 多区域)           │

│      区域 LB (DNS Round Robin)           │
├─────────────────────────────────────────┤
│    ┌──────────┐  ┌──────────┐          │
│    │ 区域 A    │  │ 区域 B    │          │
│    │(主)      │  │(备)      │          │
│    └────┬─────┘  └────┬─────┘          │
├─────────┼─────────────┼─────────────────┤
│    API Gateway (K8s Ingress)             │
├─────────────────────────────────────────┤
│    ┌──────────┐  ┌──────────┐          │
│    │ 推理集群  │  │ 推理集群  │          │

│    └────┬─────┘  └────┬─────┘          │
├─────────┼─────────────┼─────────────────┤
│        KV Cache 集群 (Redis)             │
├─────────────────────────────────────────┤
│        监控系统 (Prometheus + Grafana)    │
└─────────────────────────────────────────┘
```

**第3层：关键高可用技术**

1. **多区域部署**：
   - 主区域（Region A）：承载 80% 流量
   - 备区域（Region B）：承载 20% 流量 + 灾难恢复
   - 数据同步：Redis 主从复制（延迟 < 100ms）

2. **自动故障转移（Failover）**：
   - 健康检查：每 5 秒检查一次
   - 故障检测：连续 3 次失败 → 标记为不健康
   - 流量切换：DNS TTL = 60s（1 分钟内切换）

3. **优雅降级（Graceful Degradation）**：
   - 70B 模型不可用 → 13B 模型（质量 -10%，可用性 +20%）
   - 13B 模型不可用 → 7B 模型（质量 -20%，可用性 +30%）
   - 所有模型不可用 → 返回缓存结果（可用性 +10%）

4. **限流与熔断（Rate Limiting & Circuit Breaker）**：
   - 限流：令牌桶（1000 QPS/用户）
   - 熔断：错误率 > 50% → 打开熔断（30 秒）
   - 降级：返回默认响应（"系统繁忙，请稍后重试"）

**第4层：监控与告警**

**监控指标（四类）**：

1. **服务指标**：
   - QPS、延迟（P50/P90/P99）、错误率
   - 目标：P99 延迟 < 2s，错误率 < 0.1%

2. **资源指标**：
   - GPU 利用率、显存占用、HBM 带宽
   - 目标：GPU 利用率 > 80%，显存占用 < 90%

3. **业务指标**：
   - 任务成功率、用户满意度、Token 消耗
   - 目标：任务成功率 > 95%，满意度 > 4.5/5

4. **成本指标**：
   - 每请求成本、GPU 时成本、月度总成本
   - 目标：每请求成本 < $0.01

**告警策略**：
- P0（立即响应）：服务完全不可用、错误率 > 10%
- P1（5 分钟响应）：P99 延迟 > 5s、GPU 利用率 > 95%
- P2（30 分钟响应）：错误率 > 1%、显存占用 > 90%

**第5层：灾难恢复（Disaster Recovery）**

**备份策略**：
- 模型权重：每日备份（S3/GCS）
- 用户数据：实时备份（Redis AOF）
- 配置文件：Git 版本控制

**恢复流程**：
1. 检测故障（监控系统告警）
2. 定位故障（日志分析 + 链路追踪）
3. 切换流量（DNS 切换 + 负载均衡）
4. 修复故障（回滚代码/替换硬件）
5. 验证恢复（健康检查 + 冒烟测试）

**恢复时间目标（RTO）**：
- RTO < 5 分钟（自动故障转移）
- RPO < 1 分钟（数据丢失 < 1 分钟）

**第6层：成本估算**

| 高可用措施 | 成本增加 | 可用性提升 |
|-----------|---------|-----------|
| 多区域部署 | +100% | 99.9% → 99.99% |
| 自动故障转移 | +20% | 99.99% → 99.999% |
| 优雅降级 | +10% | 99.999% → 99.9999% |
| 限流与熔断 | +5% | 防止雪崩 |
| **总计** | **+135%** | **99% → 99.99%** |

**成本优化**：
- 备区域平时承载 20% 流量（不是完全闲置）
- 使用 Spot 实例（成本 -70%，但可用性 -5%）
- 混合部署（关键服务多区域，非关键服务单区域）
