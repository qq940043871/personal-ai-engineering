1. **多层模型路由（Model Routing）**
   - 按任务复杂度 / 延迟预算 / 成本预算动态路由：旗舰 70B ↔ 轻量 7B ↔ 专用小模型（如分类/抽取），失败自动回退到更大模型；

   - 效果：综合推理成本从 $1.00 → $0.29（**-71%**）。

2. **KV Cache 前缀复用（Prefix Caching）**
   - 多租户公共 system prompt、多轮对话历史、RAG 召回上下文作为可复用 prefix block，跨请求命中，**跳过重复 prefill**；
   - 命中率 ~60% → 首 Token 延迟显著下降，长上下文场景尤其明显。

3. **投机解码（Speculative Decoding）**
   - 草稿小模型快速生成 k 个候选，目标大模型单次前向并行验证，**无损**加速 2–3×；
   - 接受准则保证最终分布严格等于目标模型自回归分布。

4. **量化推理（Quantization）**
   - 长尾/高并发用 W4（AWQ）；通用服务用 W8A8（SmoothQuant）；新卡（H100/H200）用 FP8 近乎无损；端侧 EdgeLLM 用 INT4（AWQ + llama.cpp/MLC）。

5. **Prefill/Decode 分离（Disaggregated Serving）**
   - 长上下文 prefill 与 decode 解耦调度（不同实例池），避免长请求阻塞短请求，TTFT 降数十个百分点。

6. **并发与背压（Continuous Batching + 排队）**
   - iteration 级连续批处理 + PagedAttention，GPU 利用率从 ~20% 提到 ~90%+；
   - P99 首 Token 延迟 2.8s → **0.9s**。

## 📌 二、技术难点（推理服务与成本工程 8 大难点 + 解决方案）

### 2.1 显存墙：KV Cache 是推理的"内存黑洞"
**现象**：batch 一大、上下文一长，OOM；显存主要被 KV Cache 吃掉而非权重。
**显存估算**：单 token KV 占用 ≈ `2(layer) × n_kv_heads × d_head × dtype_bytes`；整序列 ≈ 该值 × seq_len；整 batch ≈ × batch_size。
- 例：7B（BF16, 32 层, GQA 8 KV-heads, d_head 128）→ 单 token KV ≈ 2×8×128×2 = 4KB；32k 上下文 × batch 64 ≈ **~8GB**，已超过很多卡的单卡余量。
- 70B 类模型在长上下文高并发下，KV Cache 可远超权重本身。
**根因**：自回归每生成一 token 需缓存全部历史 K/V；长上下文 × 高并发使 KV 成为显存主占用。
**解决方案**：
- **PagedAttention（vLLM）**：把 KV Cache 像 OS 虚拟内存一样**分页（block）**，非连续分配，消除内部/外部碎片，显存利用率从 ~20% → ~90%+，吞吐数倍提升。
- **KV Cache 量化**：KV 存 FP8/INT8 甚至 INT4（KVQuant），显存降 2–4×，精度损失可控。
- **GQA / MQA**：减少 K/V head 数（GQA 折中，Llama2/3、Mistral 采用），KV Cache 随 head 数线性下降。
- **前缀/会话 KV 复用（Prefix Caching）**：system prompt、多轮历史、RAG 上下文作可复用 prefix block，跨请求命中跳过 prefill。
- **滑动窗口/稀疏注意力**：超长但局部相关场景限制 KV 长度（Mistral 滑动窗口）。

### 2.2 吞吐墙：静态 Batching 浪费严重 → Continuous Batching
**现象**：传统静态 batching 要等 batch 内最长序列生成完才释放 slot，短请求被长请求拖死，GPU 利用率低。
**根因**：自回归生成序列长度不齐，静态 batch 的"木桶效应"（最长者决定释放时机）。
**解决方案 —— Continuous Batching（in-flight batching, Orca / TRT-LLM / vLLM）**：
- 以**每个 decode step（iteration）**为单位调度；某序列命中 EOS 或达 max 立刻腾出 slot，新请求随时插入；
- 把"整序列生成"拆成"逐 token 微批"，GPU 始终满负荷；
- 吞吐提升 **2–10×**，P99 延迟下降。
**注意**：Continuous Batching 与 PagedAttention 配合才能最大化收益（前者解决调度粒度，后者解决显存碎片）。

### 2.3 延迟墙：TTFT 被长 Prefill 拖垮
**现象**：长 prompt（RAG 注入、多轮历史）prefill 计算量大，用户等首 token 很久。
**TTFT 公式**：`TTFT ≈ queue_time + prefill_compute(seq_len) + first_decode`；prefill 注意力在 FlashAttention 下仍为 O(seq_len²/d)，是主要项。
**解决方案**：
- **Prefill/Decode 分离（DistServe / Splitwise）**：prefill 用高算力实例（吃算力不吃带宽），decode 用高带宽实例（吃带宽不吃算力），分池调度互不阻塞，TTFT 降数十%。
- **Chunked Prefill（vLLM）**：长 prefill 切块与 decode 请求穿插，避免一次 prefill 阻塞整批 decode。
- **前缀缓存命中**：命中 prefix cache 则跳过 prefill，TTFT 骤降。
- **投机解码**：加速 decode 阶段（见 2.4），缩短 TPOT/ITL。

### 2.4 加速无损耗：投机解码（Speculative Decoding）
**原理**：用小"草稿模型"（draft）快速自回归生成 k 个候选 token，再用大"目标模型"（target）**单次前向并行验证**这 k 个 token 是否接受。
**接受准则（保证无损）**：对第 i 个候选，接受概率 `min(1, p_target(x_i)/p_draft(x_i))`；若拒绝则在 target 修正处重新采样。
**为什么严格无损**：该准则下，最终每个位置的边缘分布**数学上等于 target 的自回归分布**（等价于对 target 分布做重要性采样），不改变输出质量，只改变采样路径。
**收益**：若草稿接受率 γ，有效 step 数约降为 `1/(1+γ·(k-1))` → 接近 k 倍（实测 2–3×）。
**工程变体**：Medusa（多头并行草稿）、EAGLE/Lookahead（用 target 特征加速草稿）、REST（retrieval-based）。
**面试追问**：与 beam search 区别？beam search 是搜索策略、不改分布；投机解码不改分布、只加速推理。

### 2.5 成本墙：量化部署的精度-速度-成本三角
**背景**：FP16/BF16 权重显存大、带宽需求高，量化是降本主手段。
**量化分类与选型**：
- **W8A8（INT8 权重+INT8 激活）**：SmoothQuant 解决激活离群，精度损失小，是通用服务主力选型。
- **W4（4bit 权重，GPTQ / AWQ）**：显存降 4×，适合显存受限/大 batch；AWQ 保护 ~1% 显著权重（activation-aware），比 GPTQ 更稳。
- **FP8（H100/H200 原生）**：训练/推理通用，几乎无损，是新一代性价比之王。
- **KV Cache 量化（FP8/INT8）**：单独量化 KV，省显存换吞吐。
- **端侧 INT4（EdgeLLM）**：AWQ + llama.cpp/MLC，手机/边缘跑 7B。
**三角权衡**：精度↑ ↔ 速度↑ ↔ 成本↓ 不可能三角。选型：高价值任务 FP8/W8A8，长尾/高并发 W4，端侧 INT4。
**陷阱**：量化后必须重新评测（呼应 08-22 Golden Set 门禁），W4 在少数任务掉点明显，需分层报告。

### 2.6 调度墙：高并发下的排队、背压与公平性
**现象**：流量尖峰请求堆积，尾部延迟（P99/P999）爆炸；个别大请求（长上下文）饿死小请求。
**解决方案**：
- **队列 + 背压**：请求入队，超容量返回 429/排队（不是无脑拒绝），保护后端不雪崩。
- **优先级/分类调度**：按用户等级、延迟预算、成本预算分级；短请求优先（SJF 近似）降低平均等待。
- **负载均衡 + 多副本**：多 GPU 节点，最少负载/一致性哈希路由；**prefix cache 亲和性路由**（同一会话/前缀路由到同节点提升命中）。
- **Prefill/Decode 分离**（见 2.3）缓解长请求阻塞短请求。
- **限流/熔断（Gateway L5）**：QPS 限流、模型不健康熔断降级到小模型。

### 2.7 Agent 场景的特殊推理挑战
- **多轮长上下文**：一回合可能含上万 token 的 tool 结果 + 多轮历史，KV 压力大；用 prefix caching 复用 system+历史，用滑动窗口/摘要压缩旧上下文。
- **工具调用的"中间态"**：约束解码（grammar-constrained，如 JSON/function-call schema）需引擎支持 structured output（Outlines / vLLM Guided Decoding），保证输出合法可解析。
- **并发 Agent 会话的 KV 复用**：同一 Agent 模板、同一知识库前缀可跨会话复用。
- **投机/量化对 Agent 的影响**：Agent 输出多为结构化指令，草稿模型难预测工具参数 → 投机接受率可能下降，需实测；W4 对结构化抽取偶有格式错误，需评测兜底。
- **成本归因**：每次 tool/LLM 调用计 token 与成本（呼应 08-22 可观测），定位"最烧钱的 agent 路径"。

### 2.8 SLA 指标定义与成本控制闭环
**核心 SLA 指标**：
- **TTFT（Time To First Token）**：首 token 延迟，影响"体感"，受 prefill + 排队主导。
- **TPOT（Time Per Output Token）**：每输出 token 延迟，受 decode 算力主导，决定流畅度。
- **ITL（Inter-Token Latency）**：token 间延迟，比 TPOT 更反映"卡顿"（受 batch 抢占影响）。
- **Throughput**：tokens/s/GPU，衡量利用率。
- **成本**：$/1M tokens（输入/输出分开计价）、单任务成本。
**SLO 示例**：TTFT P99 ≤ 0.9s、TPOT ≤ 40ms、ITL P99 ≤ 80ms、任务成功率 ≥ 89%、单任务成本 ≤ $0.29。
**降本闭环**：小模型路由（省）+ prefix cache（省 prefill）+ 量化（省显存提吞吐）+ 投机解码（提吞吐省时）→ 成本 -71%；用 08-22 的可观测 SLI 持续监控与回归门禁防质量回退。

## 📌 三、常见问答（10 题，深度版）

**Q1：推理显存主要消耗在哪？权重 vs KV Cache 怎么估算？**
模型权重 ≈ `params × dtype_bytes`（如 7B×BF16 = 14GB）；KV Cache ≈ `2 × layers × n_kv_heads × d_head × seq_len × batch × dtype_bytes`。长上下文高并发下 KV 常超过权重。降显存：GQA/MQA（减 head）、KV 量化（FP8/INT4）、PagedAttention（减碎片）、prefix cache（减重复）。

**Q2：PagedAttention 解决了什么？原理？**
解决 KV Cache 显存碎片与利用率低（静态连续分配下利用率仅 ~20%）。原理类比 OS 虚拟内存：把 KV 按固定 block 分页，序列的逻辑 block 映射到非连续物理 block，通过 block table 寻址；序列增长只分配新 block，释放即时回收，消除碎片，利用率 → ~90%+，吞吐数倍提升（vLLM 核心）。

**Q3：Continuous Batching 是什么？和静态 batching 区别？**
静态 batching 等整批最长序列生成完才释放，短请求被拖死。Continuous Batching 以每个 decode step 为调度单位，序列完成即腾 slot、新请求随时插入，GPU 始终满负荷；吞吐 2–10×，P99 下降。需与 PagedAttention 配合（连续批依赖分页显存管理）。

**Q4：Prefill 和 Decode 为什么分离？TTFT 怎么优化？**
Prefill 是算力密集（O(seq_len²) 注意力），decode 是带宽密集（每 step 只算 1 token 但要搬全部权重/KV）。二者资源画像相反，混部时互相阻塞（长 prefill 卡住 decode）。分离后分池调度，互不干扰；TTFT 降数十%。其他 TTFT 优化：prefix cache 跳过 prefill、chunked prefill 穿插、投机解码缩短 decode。

**Q5：投机解码为什么无损？接受准则？**
草稿模型生成 k 候选，目标模型单次前向并行计算 target 概率，按 `accept_i = min(1, p_target(x_i)/p_draft(x_i))` 接受、否则在 target 修正处重采样。该重要性采样准则使最终每个位置边缘分布严格等于 target 自回归分布 → 数学无损。收益约 `1/(1+γ(k-1))` 倍（γ=接受率）。

**Q6：GPTQ 和 AWQ 区别？W8A8 / FP8 / INT4 怎么选？**
GPTQ 用二阶信息逐层补偿量化误差；AWQ 保护 ~1% "显著权重"（按激活幅度），更稳更通用。选型：通用服务 W8A8（SmoothQuant，精度好）；显存受限/大 batch W4（AWQ 优先）；新卡用 FP8（近乎无损、性价比最高）；端侧 INT4（AWQ+llama.cpp）。量化后必须分层评测防掉点。

**Q7：GQA / MQA 怎么降显存？和 MHA 关系？**
MHA 每个注意力头独立 K/V，KV 最大；MQA 所有头共享一组 K/V，KV 最小但表达力降；GQA 把头分组、每组共享 K/V，是二者折中。KV Cache 随 K/V head 数线性下降，故 GQA 在长上下文/高并发下显存与延迟优势明显（Llama2/3、Mistral 采用）。

**Q8：TTFT / TPOT / ITL 含义？如何权衡？**
TTFT=首 token 延迟（体感启动快慢，受 prefill+排队）；TPOT=每输出 token 延迟（流畅度，受 decode 算力）；ITL=token 间延迟（比 TPOT 更反映卡顿，受 batch 抢占）。三者常冲突：提吞吐（加大 batch）会涨 TPOT/ITL 但降单位成本。设 SLO 时按场景定权重（对话重 TPOT，代码补全重 TTFT）。

**Q9：高并发推理如何调度、限流、保证公平？**
入队+背压（超容 429 而非雪崩）；按用户等级/延迟预算/成本预算优先级调度，短请求优先（SJF）；多副本最少负载/一致性哈希 LB，prefix cache 亲和路由；Prefill/Decode 分离防长请求饿死短请求；Gateway 层 QPS 限流+不健康熔断降级小模型。

**Q10：Agent 应用推理有哪些特殊工程问题？**
① 多轮长上下文 KV 压力大 → prefix cache + 滑动窗口/摘要；② 工具调用需约束解码（structured output）保证可解析；③ 并发会话 KV 复用（模板/知识库前缀）；④ 投机解码对结构化指令接受率可能下降，需实测；⑤ 成本归因到每次 tool/LLM 调用，定位烧钱路径（呼应可观测）。

## 📌 四、模拟面试（3 题 + 参考答案要点）

### 模拟题 1：设计一套生产级 LLM 推理服务，要求高吞吐、低成本、低延迟（SLA 达标）
**考察**：体系化工程能力（从网关到引擎到指标闭环）。
**参考答案要点**：
- **入口**：Gateway 限流/熔断/鉴权/配额；队列+背压保护后端。
- **路由（L4）**：按复杂度/延迟预算/成本预算多层路由（大↔小↔专用），失败回退链。
- **引擎层**：Prefill/Decode 分离池 + PagedAttention + Continuous Batching（vLLM/TRT-LLM）；prefix cache 跨请求复用；投机解码无损提速；量化（W8A8/FP8/W4）降本。
- **指标**：TTFT/TPOT/ITL/吞吐/成本 五大 SLI + 任务成功率；SLO 与错误预算告警。
- **保障**：多副本 LB + prefix 亲和路由；影子流量验证 → 灰度 → 全量；用可观测 SLI + Golden Set 门禁防质量/成本回退。
- **闭环**：评测结果→定位瓶颈（显存？prefill？batch？）→驱动路由/量化/分离优化→再评测。

### 模拟题 2：线上 128k 长上下文请求首 Token 延迟高、还偶发 OOM，你怎么排查与优化？
**考察**：定位能力（TTFT 拆解）+ 长上下文专项优化。
**参考答案要点**：
- **定位**：TTFT = 排队 + prefill(seq_len²) + decode。128k → prefill 巨大 + KV 巨大（显存估算定位 OOM 来源）。
- **优化（对症下药）**：① prefix cache 命中复用，跳过 prefill（最快）；② chunked prefill / Prefill-Decode 分离，避免阻塞短请求；③ GQA/MQA 降 KV 规模；④ KV FP8/INT8 量化省显存；⑤ 滑动窗口/上下文压缩/摘要，缩短有效 KV 长度；⑥ 必要时缩小批或扩显存（多卡 TP）。
- **验证**：可观测看 TTFT 分位与 KV 显存占用曲线；用 Golden Set 验证长上下文任务质量未掉点。

### 模拟题 3：怎么把推理成本降 70% 而不伤质量？（结合你的 Agent Harness 经历）
**考察**：成本工程落地 + 质量保障双线思维。
**参考答案要点**：
- **路由降本**：旗舰↔轻量↔专用小模型按复杂度/预算路由，失败回退，避免"杀鸡用牛刀"。
- **复用降本**：system/历史/RAG 前缀 KV 复用（命中率 ~60%），省重复 prefill。
- **量化降本**：长尾 W4(AWQ)、通用 W8A8、新卡 FP8、端侧 INT4，按任务分层选型。
- **提速降本**：投机解码无损 2–3×，提吞吐即降单位时间成本。
- **质量兜底**：每调用计 token 成本（可观测归因烧钱点）；Golden Set 回归门禁防量化/路由致质量回退；在线 A/B + 业务指标终判（非只看离线分）。
- **结果数据**：成本 $1.00→$0.29（-71%）、成功率 61%→89%、TTFT 2.8s→0.9s。

## 📌 五、本期速记卡（30 秒回顾）

- **一句话主线**：推理服务 = 路由 + PagedAttention + Continuous Batching + 量化 + 投机解码 + Prefill/Decode 分离，目标"高吞吐、低成本、低延迟"。
- **显存估算**：KV ≈ `2·layers·n_kv_heads·d_head·seq·batch·bytes`；长上下文高并发下 KV 常超权重。
- **三把斧**：PagedAttention（碎片）、Continuous Batching（调度粒度）、Prefix Caching（省 prefill）。
- **无损加速**：投机解码接受准则 `min(1, p_t/p_d)`，分布严格等于 target。
- **量化三角**：精度↑ ↔ 速度↑ ↔ 成本↓；W8A8 通用 / W4(AWQ) 省显存 / FP8 新卡神 / INT4 端侧。
- **SLA 三指标**：TTFT（首 token）/ TPOT（每 token）/ ITL（token 间卡顿）；SLO 示例 P99 TTFT≤0.9s、成功率≥89%、单任务成本≤$0.29。
- **与往期关系**：架构(08-18)/训练(08-19)/安全(08-20)/多模态(08-21)/LLMOps(08-22) 已覆盖；本期补"推理服务与成本"——把模型送到用户面前的最后一公里。
