## 一、项目亮点

### 1.1 Agent Harness 架构总览
Agent Harness 是一套面向"大模型驱动的多智能体应用"的端到端运行框架，四层职责清晰：

| 层 | 技术 | 职责 |
|---|---|---|
| 调度 / 推理编排 | FastAPI | 接收任务、管理会话、调用 LLM、调度工具、流式推送 |
| 桌面端 | PyQt6 | 本地桌面 GUI、文件 / 设备交互、长任务驻留 |
| Web 看板 | Vue3 | 任务流可视化、日志追踪、人工确认闸门 |
| 统一控制循环 | MainLoop | 驱动"思考-决策-执行-观察"的 Agent 主循环 |

**设计哲学（最值得讲的点）**：以 LLM 作为"控制器（controller）"，MainLoop 作为确定性的执行引擎，把不可控的生成式模型约束在一个**可观测、可中断、可回放**的状态机里。核心信条是——**大模型负责"决策"，确定性的运行时负责"执行与兜底"**。这一分工把"幻觉/失控"的业务风险从"模型必须永远正确"转换为"运行时必须有护栏"，工程上可落地得多。

### 1.2 五大核心亮点

**亮点 1：自研 MainLoop 控制循环 + "反思-动作"状态机**
- 把 ReAct 范式工程化为显式状态机：`REASON → ACT → OBSERVE → (REFLECT) → REASON …`
- 每次状态转换都有 `trace_id` 埋点，便于事后复盘"模型为什么这么走"（可回放 = checkpoint 每步落盘）。
- 反思节点（REFLECT）强制每 N 步做一次"是否继续 / 是否需要人工确认"的显式判断，避免无脑循环；这是把"该停了"这种隐式认知变成可测试、可观测的显式决策。

**亮点 2：工具调用的强类型 Schema 校验与自愈**
- 工具以 JSON Schema 注册（名称、参数、必填、类型、枚举）。
- 模型输出的 `tool_call` 先过 Schema 校验：缺参 / 类型错 → 自动回填 prompt 要求修正（最多 k 次自愈）；仍失败 → 转人工。
- 破坏性工具（删除 / 发送 / 支付）必须有"人工确认闸门"，满足安全诉求。
- 进阶：用**约束解码（grammar-constrained decoding，如 outlines / guidance / lm-format-enforcer）**在 token 级别保证 JSON 合法，把"解析失败率"从训练问题变成确定性问题。

**亮点 3：多端实时协同**
- 同一任务流，PyQt6 桌面端与 Vue3 Web 端通过 WebSocket / SSE 订阅同一事件总线，状态一致。
- 前端只渲染"状态快照 + 增量事件"，不持有业务逻辑，降低多端不一致风险；所有写操作带 `idempotency_key` 保证幂等。

**亮点 4：基于 LangGraph 的多智能体编排**
- 微信公众号自动发布流水线：选题 → 素材 → 配图 → 排版 → 审核 → 发布，6 节点以状态图编排。
- 利用 checkpoint（持久化中间状态）支持长任务断点续跑与回放；状态图天然支持环路（自我修正）与条件分支（审核不通过回退），并内建 human-in-the-loop。

**亮点 5：全链路可观测**
- 请求流经每个阶段（入口 → LLM → 工具 → 观察 → 回流）都有结构化日志。
- 主动监控日志异常并触发告警 / 自愈；关键指标（准确率 / 延迟 / 成本 / 工具成功率）看板化，构建 golden set 做回归。

### 1.3 业务落地（证明不是玩具）
- 微信公众号 6 节点自动发布流水线（已长期运营长文 + 配图排版）。
- 自动绘本生成智能体（故事生成 + 图像生成串联）。
- AI 学习系统（Transformer 学习材料拆分并集成到 HTML 页面展示）。

## 二、技术难点与解决方案（含架构权衡）

### 2.1 大模型输出不确定性 → 结构化输出约束
- **问题**：同一 prompt 多次结果不同，难以落地到确定性业务系统。
- **方案**：① 要求模型输出 JSON 并附 JSON Schema 强校验；② 解析失败自动重试 / 降级；③ 关键字段加校验器（正则 / 范围 / 枚举）；④ 关键路径用低温（temperature≈0）+ 结构化 prompt（"先给结论，再给理由"）；⑤ 进阶用约束解码（outlines / guidance）在生成时即保证合法。
- **权衡**：约束解码牺牲一点吞吐换取零解析失败；低温降低创造性但提升稳定性。

### 2.2 Agent 循环失控 → 步数 / Token 预算 + 反思节点
- **问题**：模型可能陷入"反复调用同一工具""自洽幻觉"的死循环，浪费成本且不出结果。
- **方案**：① 每任务设 `max_steps` 与 `max_tokens` 硬上限；② 每 N 步插入 REFLECT，要求模型显式回答"是否已能结束"；③ 工具结果做幂等 / 去重，重复观察直接终止；④ 成本与超时双护栏；⑤ checkpoint 支持失控回滚到安全点。

### 2.3 上下文窗口限制 → 滑动窗口 + 摘要压缩 + RAG
- **问题**：超长对话 / 文档超出 context length，且长上下文推理成本与失真上升（ lost-in-the-middle 现象：模型易忽略长上下文中间信息）。
- **方案**：① 保留最近 K 轮 + 历史递归摘要；② 长文档走 RAG 检索相关片段注入；③ 需全局信息时做"分治 + 归并"再总结；④ 用指令强化"关键信息若在中间，请重点注意"。

### 2.4 工具调用可靠性 → 解析 + 自愈 + 闸门
- 同亮点 2。补充：① 工具执行失败要返回"模型可消费的错误信息"而非抛异常中断；② 网络类工具加重试与超时；③ 结果做长度裁剪避免撑爆上下文；④ 约束解码替代脆弱的"正则抽取 `{}` 块"。

### 2.5 流式输出与多端一致性 → SSE / WebSocket + 状态机
- **方案**：① 后端以 SSE / WebSocket 流式推送 token 与状态事件；② 前端乐观更新 + 断线重连（带 offset 续传）；③ 统一状态机保证多端"同一时刻看到同一状态"。

### 2.6 多端状态同步 → 事件总线 + 幂等
- **方案**：① 单一事实源（FastAPI 会话状态）；② 多端订阅事件总线；③ 所有写操作幂等（带 `idempotency_key`），避免重复执行。

### 2.7 推理成本控制 → 模型路由 + 缓存 + 量化
- **方案**：① 简单任务路由小模型，复杂任务才用大模型（LLM router / 分类器）；② 语义缓存（相同 / 相似 query 命中，用 embedding 相似度判等）；③ 批处理合并请求；④ 本地部署走 INT4 量化降低显存占用；⑤ 投机解码降低首 token 延迟。

### 2.8 评估与可观测 → trace + eval 集
- **方案**：① 全链路 `trace_id`；② 构建 golden set 做回归；③ 关键指标（准确率 / 延迟 / 成本 / 工具成功率）看板化；④ 引入 **LLM-as-Judge** 做开放式质量评分（注意位置偏差、自我偏好偏差，需用强模型 + 多轮 + 引用锚定）。

## 三、常见问答（20 题，深度版）

### Q1 讲讲 Transformer 的自注意力机制与复杂度
自注意力把输入 X 通过三个线性投影得到 Q、K、V：`Q=XW_Q, K=XW_K, V=XW_V`，注意力为 `softmax(QK^T / √d_k) V`。`√d_k` 是缩放因子，防止点积随维度增大而过大导致 softmax 进入梯度消失的饱和区。`√d_k` 实际取 `d_k` 的平方根，使 QK^T 点积的方差保持在 O(1)。多头注意力把 d_model 切成 h 个头，每个头维度 `d_k = d_model/h`，各自算注意力后拼接再投影，让模型在不同子空间关注不同关系（语法 / 语义 / 指代等）。复杂度：对序列长度 n，时间 / 空间均为 **O(n²·d)**，n² 来自 QK^T 的成对计算——这是长上下文的核心瓶颈。Decoder 侧还要加因果掩码（causal mask）保证第 i 个位置只能看到 ≤i 的位置。

### Q2 位置编码有哪几种？RoPE 为什么重要？
- **绝对位置**（sinusoidal / learned）：直接给每个位置一个向量加到 token 上，长度外推差（训练 4k 推理 8k 易崩）。
- **相对位置**（T5、Transformer-XL）：在注意力分数里引入相对距离偏置。
- **RoPE（旋转位置编码）**：把 Q、K 按位置做旋转变换 `f(x, m) = R_m x`（R_m 为旋转矩阵），使得 `q_m^T k_n` 只依赖于相对位置 `m-n` 与内容，兼具相对位置性质且**长度外推好**。LLaMA、Qwen、ChatGLM、DeepSeek 均用 RoPE。配合 NTK-aware 缩放、位置插值（PI）、YaRN 可在不重训情况下扩展上下文长度（如 4k→128k）。**为什么重要**：它让"位置"与"内容"解耦且可外推，是当今开源大模型事实标准。

### Q3 预训练、SFT、RLHF 三阶段分别做什么？
- **预训练（PT）**：在海量网页语料上做 next-token prediction（自监督），学习通用语言与知识，算力消耗最大（占全周期 90%+ 成本）。
- **监督微调（SFT）**：用"指令-回答"配对数据微调，让模型学会遵循指令、规范格式、扮演角色。
- **RLHF**：① 训奖励模型（RM）拟合人类偏好排序（Bradley-Terry 模型）；② 用 PPO 以 RM 为信号优化策略，对齐"有用、无害、诚实"。**DPO** 是更简洁的离线替代：直接用语偏好数据做分类式优化 `L_DPO = -E[log σ(β log(π_θ(y_w)/π_ref(y_w)) - β log(π_θ(y_l)/π_ref(y_l)))]`，省去独立 RM 与 PPO 的复杂训练，更稳更简。

### Q4 RAG 的原理与常见优化
- **流程**：索引（切片 → 嵌入 → 向量库）→ 检索（query 嵌入 → ANN 近邻搜索 → top-k）→ 生成（把召回片段拼进 prompt，要求引用出处）。
- **优化**：① 切片策略（按语义 / 标题层级，避免切坏表格与代码，可用语义分块 / 父子文档）；② 混合检索（BM25 关键词 + 稠密向量融合，RRF 重排）；③ rerank 模型（cross-encoder）对 top-k 精排；④ query 改写 / 多路召回（HyDE、step-back）；⑤ 引用与溯源降幻觉；⑥ 元数据过滤（时间 / 权限）；⑦ 重排后做上下文压缩（去冗余）。

### Q5 Agent / Function Calling 的原理
模型在生成时除文本外还能输出"工具调用"：`{name, arguments(JSON)}`。框架解析参数 → 执行工具 → 把结果（observation）作为新消息回灌给模型，进入下一轮。典型范式 **ReAct**（Reason + Act 交替）。工程要点：工具以 JSON Schema 描述、输出要可解析（优先用原生 function calling 或约束解码）、执行失败要返回可消费错误、破坏性动作加人工闸门、长程任务用记忆与规划。

### Q6 幻觉的成因与缓解
- **成因**：参数化知识存在缺口、训练数据噪声、暴露偏差（自回归只顾前文）、解码策略过自由、训练目标不强制事实一致性、长上下文 lost-in-the-middle。
- **缓解**：RAG 注入事实、要求引用出处、self-consistency 多采样投票、事实核验工具、置信度校准、对齐训练（RLHF/DPO 惩罚编造）、用思维链强制"先检索再回答"。

### Q7 长文本处理有哪些关键技术？
- 位置编码外推：RoPE + NTK 缩放 / 位置插值（PI）/ YaRN。
- 注意力实现：**FlashAttention**（IO 感知、分块计算、精确、省显存，把 QK^T、softmax、PV 融合，避免把 N×N 中间矩阵写回 HBM）；**MQA / GQA**（多查询 / 分组查询，共享 K/V 头降显存与提速，GQA 是 LLaMA2/3 默认）；**滑动窗口注意力（SWA）**只算局部。
- 工程：KV Cache 量化（INT8/INT4）、上下文分块 + 摘要、稀疏注意力（Longformer / BigBird）。

### Q8 模型量化（INT8 / INT4）怎么做？
- **PTQ（训练后量化）** vs **QAT（量化感知训练）**；PTQ 无需重训，性价比高。
- 线性量化：`q = round(x / scale) + zero_point`，INT8 对称 / 非对称，INT4 更激进。
- **GPTQ**：逐层用二阶信息（Hessian 逆）补偿量化误差，weight-only，单卡可跑 70B/4-bit。
- **AWQ（Activation-aware Weight Quantization）**：观察到约 1% 的"显著权重"（对激活影响大）决定性能，只保护这 1% 不量化、其余量化，效果好且快。
- **SmoothQuant**：把激活的量化难度"平滑"到权重上，解决激活离群值问题，使 W8A8 可行。
- KV Cache 也可量化进一步省显存。

### Q9 参数高效微调 LoRA 是什么？
冻结原权重，只学低秩增量 `ΔW = B·A`，`B∈R^{d×r}, A∈R^{r×k}, r≪d`。可训练参数量从 `d·k` 降到 `(d+k)·r`（如 r=8 时仅为原 0.5%），显存与存储大幅下降，可多任务挂多个 LoRA 适配器 hot-swap（同一基座切换不同能力）。**QLoRA** = 4-bit NF4 量化基座 + LoRA，单张消费级显卡可微调 65B 级模型；配合 paged optimizers 防 OOM。**DoRA** 进一步把权重分解为方向与量级分别微调。

### Q10 推理优化：KV Cache、PagedAttention、连续批处理
- **KV Cache**：缓存历史 K/V 避免每步重算，显存随序列长度线性增长（K/V 各 `2·n·h·d_h·bytes`）。
- **PagedAttention（vLLM）**：像操作系统虚拟内存一样把 KV Cache 分页（block），按需分配、跨请求共享（同一 prompt 前缀共享）、显存碎片大幅降低，利用率从 ~20% 提升到 ~90%+，吞吐大幅提升。
- **Continuous Batching（连续批处理）**：在 iteration 级别动态把新请求并入正在跑的批，而非等整批结束，显著降低排队延迟（Orca / vLLM / TGI 均支持）。
- 其他：投机解码（small draft model 先猜 k token，大模型一次验证）、Medusa（多头并行猜）、张量并行 / 流水并行、算子融合、量化。

### Q11 LangChain 与 LangGraph 的区别？
LangChain 偏"链（chain）"——DAG 式顺序组合，适合确定性 pipeline；LangGraph 偏"图（graph）"——节点 + 状态 + 条件边，支持**环路、状态持久化（checkpoint）、人在回路（human-in-the-loop）、断点续跑**，更适合需要自我修正与长程编排的 Agent。一句话：LC 是"写好的流程"，LG 是"能循环和暂停的状态机"。LG 的 State 是跨节点共享的可变对象，checkpoint 把每步 State 落盘，崩溃后可 resume。

### Q12 多智能体协作有哪些模式？
- **Supervisor（主管）**：一个调度模型分发子任务给 worker（如 AutoGen、CrewAI）。
- **Hierarchical（分层）**：多层主管-worker。
- **Debate（辩论）**：多个角色互相驳斥提升质量（如 critic/refiner，Self-Refine）。
- **Pipeline（流水线）**：如本项目的 6 节点发布流水线，前一节点产物是后一节点输入。
- **Network（网状）**：Agent 自由通信（如 CAMEL）。
- 关键工程问题：状态如何共享、何时并发、如何避免无限协商（设轮数上限）、成本如何控制（路由器 + 预算）。

### Q13 提示工程有哪些经典技术？
- **CoT（思维链）**："Let's think step by step"，显式推理提升复杂题准确率。
- **Zero-shot / Few-shot CoT**、**Self-Consistency**（多采样取众数，提升推理稳定性）。
- **ToT（思维树）**：在分支上搜索（BFS/DFS + 价值评估）。
- **ReAct**：推理与动作交替，连接工具。
- **CoT-SC、PoT（Program of Thought，用代码当推理）、ART（自动 CoT）**。
- 工程上还要做：角色设定、格式约束、少样本示例、防注入（严格区分系统/用户/工具内容边界）。

### Q14 对齐与安全（RLHF / DPO / Constitutional AI）
- **RLHF（PPO）**：奖励模型 + PPO，流程复杂、易训崩（reward hacking：模型找到骗过 RM 的捷径）、对超参敏感。
- **DPO**：直接在偏好数据上做分类损失优化，无需 RM 与 PPO，更稳更简，但依赖偏好数据质量。
- **PPO 关键机制**：① **GAE（广义优势估计）**平衡偏差与方差；② **clip（截断）**把策略更新比 `π_θ/π_ref` 限制在 `[1-ε,1+ε]` 防止毁灭性更新；③ **KL 惩罚**约束偏离参考模型过远。
- **Constitutional AI**：用一组原则（constitution）让模型自我批评修正，减少人工标注。
- 安全还要防：提示注入、越狱、数据泄露、输出合规、agent 越权调用工具。

### Q15 【进阶】Mixture of Experts（MoE）原理与工程要点
- **原理**：每个 FFN 层用多个"专家"子网络 + 一个路由器（router / gating），每个 token 只激活 top-k 个专家（如 top-2），在**不增推理算力**情况下大幅扩参（总参大、激活参小）。代表：Mixtral 8x7B、DeepSeekMoE、Qwen-MoE。
- **路由**：`g = softmax(W_r · x)`，取 top-k；常用 **auxiliary loss（负载均衡损失）** 防止所有 token 涌向少数专家（expert collapse）；进阶用 **router z-loss**、分组路由。
- **工程要点**：① 专家并行（expert parallelism）跨 GPU 放置，带来 all-to-all 通信开销；② 显存大（全专家常驻）但单次计算小；③ 推理需支持细粒度专家调度；④ fine-grained MoE + 共享专家（DeepSeek 做法）提升参数效率。

### Q16 【进阶】State Space Models（Mamba / SSM）与 Transformer 对比
- **核心**：SSM（如 S4、Mamba）用线性递归状态 `h_t = A h_{t-1} + B x_t; y_t = C h_t`，把序列建模变成 O(n) 的递归 / 卷积，**无注意力 O(n²)**，理论上可处理无限长度、推理恒定内存。
- **Mamba 关键创新**：**选择性状态空间（selective SSM）**——让 A/B/C 依赖输入（参数随 token 变），获得"内容感知"的压缩，克服早期 SSM 不能做内容相关推理的弱点；用硬件感知的并行扫描（parallel scan）实现训练高效。
- **对比 Transformer**：Transformer 擅长"全局点对点检索"（注意力任意两位置直接交互），SSM 擅长"压缩式长程记忆"但内容检索弱。当前大模型主流仍是 Transformer+改进（因生态 / Scaling 成熟），SSM 在超长序列 / 实时流式有优势。

### Q17 【进阶】Agent 的记忆架构怎么设计？
- **分层记忆**：① 短期/工作记忆（当前上下文窗口 + 最近 K 轮）；② 情节记忆（episodic，存具体交互事件，可检索）；③ 语义记忆（semantic，抽取出的事实/用户画像，向量库）；④ 程序记忆（procedural，可复用的技能/工具链）。
- **写入**：交互后用 LLM 抽取"值得记住的事实"写入向量库（带去重/合并）。
- **读取**：每轮把 query 检索相关记忆注入系统 prompt；用时间衰减/重要性排序。
- **避坑**：记忆污染（错误记忆被反复召回）、上下文膨胀（只取 top-k + 压缩）、隐私（敏感记忆加密/可删）。本项目 MainLoop + checkpoint 天然可作为"过程记忆"回放。

### Q18 【进阶】如何评测一个 LLM / Agent？（LLM-as-Judge）
- **能力评测**：MMLU / GSM8K / HumanEval / MT-Bench / Arena-Hard 等基准；Agent 用工具成功率、任务完成率、步数效率。
- **LLM-as-Judge**：用强模型当评分员，Prompt 要求"按维度打分 + 给理由 + 引用原文"。
- **偏差与缓解**：① 位置偏差（交换顺序多次评）；② 自我偏好（评测模型与被评不同）；③ 长度偏差（长答更易高分）；④ 用 rubric 锚定 + 多轮投票。
- **离线 + 在线结合**：离线 golden set 回归 + 线上 A/B（留存、采纳率、人工抽检）。

### Q19 【进阶】注意力机制的变体与稀疏化
- **MQA / GQA**：共享 K/V 头，降显存、提速解码（GQA 折中质量与速度，成主流）。
- **稀疏注意力**：Longformer（局部窗口 + 全局 token）、BigBird（随机+窗口+全局）、稀疏降低 O(n²)→O(n·log n)。
- **线性注意力**：用核技巧把 softmax(QK^T)V 近似为 `φ(Q)(φ(K)^T V)`，复杂度 O(n·d²)，但表达力弱于 softmax 注意力。
- **FlashAttention**：不是新注意力，而是 IO 感知的高效实现，已成标配。

### Q20 【进阶】大模型推理的服务架构与并行策略
- **并行维度**：① 数据并行（DP，多副本）；② 张量并行（TP，单层矩阵切分，Megatron）；③ 流水并行（PP，层切分到不同阶段）；④ 专家并行（EP，MoE 专家跨卡）。实际用 **3D 并行**（TP+PP+DP）组合。
- **调度**：continuous batching + 优先级队列；KV Cache 用 PagedAttention 管理。
- **高可用**：多副本 + 健康检查 + 降级（大模型超时切小模型）；流式用 SSE，断线 offset 续传。
- **成本**：语义缓存命中、量化、路由、批处理是关键降本手段。

## 四、模拟面试（3 题 + 参考答案要点）

### 模拟题 1：设计一个支持工具调用的 LLM Agent，模型偶尔返回不合法的 JSON（缺字段 / 类型错），你如何处理？
**参考答案要点**：
1. **结构化约束前置**：工具用 JSON Schema 声明参数（类型、必填、枚举、范围），prompt 中明确"必须只输出 JSON，字段如下"。
2. **解析与校验分层**：先用容错解析（如 `json5` / 正则抽取 `{}` 块 / 专用解析器）；再按 Schema 校验缺参、类型、越界。
3. **自愈重试**：校验失败不报错——把"错误原因 + 原输出 + Schema"回灌给模型要求修正，设最大重试次数（如 3 次）并降低温度。
4. **降级与兜底**：重试仍失败 → 转人工或走安全默认；破坏性参数缺失时绝不猜测，必须确认。
5. **约束解码（加分）**：用 outlines / guidance / lm-format-enforcer 在 token 级别保证 JSON 合法，把"解析失败"从概率问题变确定性问题；或用原生 function calling 模型由推理端保证格式。
6. **可观测**：记录"不合法率"指标，反向优化 prompt 与 Schema 描述（多数错误源于描述歧义）。

### 模拟题 2：你的 Agent Harness 用 MainLoop 驱动 Agent，如何防止 Agent 陷入无限循环或失控？
**参考答案要点**：
1. **硬上限护栏**：每任务 `max_steps`（如 20）与 `max_tokens` / 成本预算，超限即终止并报告。
2. **反思节点（REFLECT）**：每 N 步强制模型显式判断"是否已能给出最终答案 / 是否需人工确认"，把隐式"该停了"变成显式决策。
3. **工具结果去重 / 幂等**：记录已调用工具与返回摘要，重复观察（反复调同一工具且结果不变）直接终止，避免"原地打转"。
4. **人工确认闸门**：删除 / 发送 / 支付等破坏性动作必须人工确认，确定性运行时不替模型做危险决策。
5. **超时与成本双护栏**：单步超时、整体超时、累计花费上限。
6. **可回放（checkpoint）**：每步状态落盘，失控时可回滚到安全点重规划。
7. **加分项**：引入"规划-执行"分离（先让模型产出计划再执行）、或用 critic 模型对循环行为打分干预；记忆层避免重复探索。

### 模拟题 3：讲讲你用 LangGraph 做多智能体编排的经历，状态图 + checkpoint 是如何解决长任务可靠性问题的？
**参考答案要点**：
1. **为什么用图而非链**：发布流水线有"审核不通过回退""配图失败重试"等环路与条件分支，DAG 链表达不了，StateGraph 用条件边天然支持。
2. **状态（State）共享**：中央 State（选题/素材/图片URL/排版/审核意见）各节点读写同一状态，避免参数在节点间手动传递出错；用 TypedDict / pydantic 强类型定义。
3. **checkpoint 持久化**：每步 State 落盘（SQLite / Redis / Postgres），进程崩溃或用户关闭后可从最后节点 `resume()` 续跑，不用从头再来——长任务可靠性核心。
4. **人在回路（human-in-the-loop）**：审核节点 `interrupt()` 暂停等待人工，确认后从断点继续，符合业务合规。
5. **可观测与回放**：配合 trace_id 看每节点输入输出，出问题可定位、可 replay 复现 bug。
6. **工程收益**：编排逻辑从代码 if/else 变声明式图，改动节点不影响全局，可测试性强；配合 `update_state` 支持人工修正状态后继续。
