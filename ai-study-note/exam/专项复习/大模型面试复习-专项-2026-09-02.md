## 一、项目亮点（Project Highlights）

> 面试策略：用「背景痛点 → 技术方案 → 量化结果 → 可追问点」四段式讲每个项目，避免流水账。每个亮点都能被深挖到算法/系统层。

### 1.1 Agent Harness —— 企业级 LLM 应用框架（锚点项目）

**技术栈**：FastAPI（后端编排）+ Vue3（Web 前端）+ PyQt6（桌面端）+ MainLoop（核心调度循环）

**背景痛点**：企业内部 LLM 应用开发混乱——Prompt 硬编码、工具调用成功率低（仅 55%）、无评估体系、线上问题 7 天后才发现。

**六层架构**（分层解耦，职责清晰）：

```
Client 层  (FastAPI + WebSocket/SSE 流式接入)
   ↓
Agent 层   (DAG 动态调度器，依赖感知 + 并行)
   ↓
Execution 层 (工具执行 + 可靠性工程：重试/超时/降级)
   ↓
Provider 层  (多模型统一路由：7B/13B/70B/本地)
   ↓
Gateway 层   (鉴权 + 限流 + 租户隔离)
   ↓
Infra 层     (OpenTelemetry 可观测 + Redis 记忆/缓存)
```

**六大核心亮点**（逐条可展开）：

| # | 亮点 | 关键技术 | 量化收益 |
|---|------|---------|---------|
| 1 | **DAG 动态调度器** | 拓扑排序 + 分层并行执行 | 3 个独立工具 3.6s → 1.2s（-67%） |
| 2 | **三层记忆系统** | 工作记忆(Session) + 短期(Redis滑动窗口) + 长期(向量库) | 64K 上下文压缩至 4K，信息保真 >90% |
| 3 | **全链路可观测** | OpenTelemetry Tracing + TraceId 透传 | 线上问题发现 7天 → 2小时（-98.8%） |
| 4 | **评估体系** | 离线(LLM-as-Judge) + 在线(A/B) + 对抗(红队) | 评测覆盖率 30% → 95% |
| 5 | **工具调用可靠性** | Structured Output(JSON Schema 强制) + 双模式降级 | 工具调用成功率 55% → 82% |
| 6 | **多模型适配** | 统一 Provider 接口 + 成本路由 | 推理成本 -80%（70% 流量走 7B） |

**亮点 1 深挖——DAG 调度核心算法（面试常让手推）**：
```python
def topological_sort(dag: Dict[str, List[str]]) -> List[List[str]]:
    """返回可并行的分层列表：同一层内的工具调用可并发执行"""
    in_degree = {n: 0 for n in dag}
    for n, deps in dag.items():
        for d in deps:
            in_degree[n] += 1
    queue = deque([n for n in dag if in_degree[n] == 0])
    layers = []
    while queue:
        layer = list(queue); queue.clear()
        layers.append(layer)
        for node in layer:
            for neigh, deps in dag.items():
                if node in deps and (in_degree[neigh] := in_degree[neigh] - 1) == 0:
                    queue.append(neigh)
    return layers
```
> 可追问：并行执行用 ThreadPool 还是 AsyncIO？→ IO 密集型（调外部工具/API）用 AsyncIO 更优；CPU 密集型才用线程池。

**亮点 3 深挖——为什么用 OpenTelemetry 而非自定义日志？**
OTel 是行业标准，支持 HTTP/DB 自动埋点注入，且天然对接 Prometheus/Grafana；跨服务用 `traceparent` Header 串联 TraceId，定位「哪次工具调用慢、哪次推理失败」。

**亮点 5 深挖——双模式降级**：
JSON Mode 准确率 94% 但依赖模型支持；Prompt Engineering（Few-shot + 正则解析）兼容性强但准确率 75%。双模式保障可用性。幻觉工具名用「Embedding + BM25 + Rerank」混合检索抑制，幻觉率 8% → 0.5%。

**一句话锚点**：Agent Harness 是我的「能力基座」，下面所有的注意力/KV Cache/流式/RAG/量化原理，都能在这里找到对应的工程决策（路由→Provider 层、记忆→Infra 层、可靠性→Execution 层）。

### 1.2 微信公众号 6 节点内容流水线（LangChain / LangGraph）

**亮点**：将「选题 → 资料检索 → 大纲 → 正文 → 配图 → 排版发布」建模为 **LangGraph 有状态图（StateGraph）**，人工审核节点作为 human-in-the-loop 中断点。

**关键技术**：
- **StateGraph + Checkpointer**：支持断点续跑、失败重试（节点级而非全链路）。
- **条件边（Conditional Edge）**：长度/质量不达标自动回环重写（最多 3 次，防死循环）。
- **5 套预定义视觉主题**：样式与内容解耦，发布前注入主题 Token。
- **五段式结构约束**：概念介绍 → 核心原理 → 应用场景 → 最新进展 → 总结展望，800–1200 字。

**量化收益**：单篇成文时间 2h → 15min；人工仅需审核 1 次。

### 1.3 RAG 系统 —— 三代演进（大模型落地第一条高速公路）

| 版本 | 核心技术 | Recall@10 | 关键突破 |
|------|---------|-----------|---------|
| V1 | ChromaDB + OpenAI Embedding | 42% | 基础可用 |
| V2 | Milvus + BGE-M3 + BM25 混合 | 68% | 多路召回 + RRF 融合 |
| V3 | GraphRAG + 自适应 Chunking | 85% | 知识图谱 + 查询自适应路由 |

**GraphRAG 核心思想**：实体抽取 → 关系建模 → 子图检索（PageRank 排序路径）。解决传统 RAG「只会语义相似、不会关系推理」的缺陷（如"通策医疗的竞争对手是谁？"）。

## 二、技术难点（Technical Difficulties）

### 2.1 Agent 长程编排与状态管理
**难点**：多轮对话 + 多工具调用链路长，状态易丢失、上下文易溢出。  
**方案**：
- **DAG 调度**：把工具调用依赖关系图化，自动并行无依赖节点。
- **三层记忆**：长期记忆（向量库，语义检索 + 时间衰减）解决「跨会话遗忘」；短期记忆（Redis 滑动窗口 + LLM 摘要压缩）解决「上下文窗口溢出」；工作记忆（当前窗口）装 System + 摘要 + 输入。
- **记忆一致性**：写入前用 LLM 做冲突检测（"新记忆是否与已有矛盾？"）。

### 2.2 多模型统一抽象与动态降级
**难点**：不同厂商（OpenAI/Gemini/Claude/本地）接口、鉴权、流式格式各异。  
**方案**：统一 `Provider` 抽象 + 基于成本的路由策略（简单请求走 7B，复杂请求走 70B）。优雅降级链：70B → 13B → 7B → 缓存兜底，保障可用性。

### 2.3 流式输出与多端实时渲染
**难点**：TTFT（首 Token 延迟）、背压（生产过快压垮前端）、断线重连、Web(Vue3)/桌面(PyQt6) 一致性。  
**方案**：
- **SSE（Web）/ WebSocket（桌面）**：增量 token 推送。
- **背压**：前端按渲染帧率消费，缓冲上限触发服务端暂停。
- **断线重连**：用 `request_id` + Offset 续传，避免重复生成。
- **一致性**：渲染层与编排层解耦，同一份流式事件驱动两终态。

### 2.4 工具调用可靠性
**难点**：模型输出 JSON 格式错、类型错、幻觉工具名。  
**方案**：JSON Schema 强制（structured output）+ 双模式降级（见 1.1 亮点 5）+ 工具选择混合检索抑幻。

### 2.5 RAG 召回质量
**难点**：纯向量检索召回低、长尾知识缺失、Chunk 粒度难定。  
**方案**：Dense+Sparse+Rerank 混合；GraphRAG 补关系；自适应 Chunking（按语义边界而非固定长度切分）。

### 2.6 长上下文 KV Cache 与成本
**难点**：128K 上下文下 KV Cache 显存爆炸（标准 MHA 理论需 2560GB）。  
**方案**：GQA（KV Head 由 40 → 8，显存 -87.5%）+ INT4 量化（-75%）+ PagedAttention（碎片 40% → 8%）+ Prefix Caching（共享 System Prompt）。组合后单卡 A100 80GB 可承载（详见模拟题 2）。

### 2.7 多智能体协作一致性（进阶难点）
**难点**：多个子 Agent 分工后，中间结果格式不统一、上下游口径漂移、失败无法定位到具体 Agent。  
**方案**：用「结构化消息契约（Typed Message Schema）」约束 Agent 间输入输出；中心 Orchestrator 持有全局状态机；每个子 Agent 输出带 `agent_id + 置信度 + 引用来源`，便于回放与审计（呼应 1.2 的 StateGraph 思想）。

### 2.8 评测体系设计（LLM-as-Judge 的工程坑）
**难点**：人工评测成本高、不可规模化；纯规则评测覆盖窄；用 LLM 当裁判又有位置偏见与自我偏好。  
**方案**：离线 LLM-as-Judge（多裁判投票 + 去位置偏见：正反序各评一次取均值）+ 在线 A/B（业务指标兜底）+ 对抗红队（注入攻击样例）。评测覆盖率 30% → 95%（呼应 1.1 亮点 4）。

## 三、常见问答（Common Interview Q&A）

### Q1：Transformer 为什么用 Attention 而不是 RNN？
1. **梯度传播**：RNN 需连乘 t 次 ∂h_t/∂h_1 → 梯度消失；Attention 任意位置依赖 = 1 次矩阵乘，梯度稳定。
2. **并行性**：Attention 可完全并行；RNN 必须串行，训练慢 10–100×。
3. **归纳偏见**：RNN 隐含「相邻更强」偏见；Attention 无局部性偏见，数据驱动更灵活。
4. **加分**：能手写 `Attention(Q,K,V)=softmax(QKᵀ/√d_k)V`；理解 O(n²) 与 Flash Attention 优化。

### Q2：MHA / MQA / GQA / MLA 的区别与选型？
| 机制 | KV Cache 占比(13B/FP16) | 质量损失 | 适用 |
|------|------------------------|---------|------|
| MHA | 100% | 0% | 高质量要求 |
| MQA | ~50% | 5–10% | 极长上下文 |
| GQA | ~62.5% | 2–5% | 平衡（LLaMA-3） |
| MLA | ~15% | <0.5% | DeepSeek-V3 |

**MLA 技巧**：低秩 KV 压缩（投影到 512 维潜空间），推理时再上投影重构；显存 -82.6%。

### Q3：RoPE 为什么成为工业标准？YaRN 如何实现长度外推？
- **RoPE**：对 Q/K 施加旋转矩阵，使内积仅依赖相对位置 m−n，保持长度外推能力（训练 4K 推理 8K）。
- **YaRN**：NTK-aware 插值——高频维度保留、低频维度插值，配合温度缩放，实现 8× 几乎无损外推。

### Q4：LoRA 原理与变体？
- **核心**：ΔW=BA（低秩分解），参数量从 d×d 降到 d×r+r×d（r≪d，约 0.4%）。
- **变体**：QLoRA（4-bit 量化+LoRA，消费级 GPU 微调 65B）、AdaLoRA（自适应秩）、DoRA（方向+幅度分解）。
- **局限**：推理时多一次低秩计算；需选好 target_modules 与秩 r（8–64）。

### Q5：RAG 与 Fine-tuning 如何选择？
| 维度 | RAG | Fine-tuning |
|------|-----|-------------|
| 知识时效 | 实时 | 静态(需重训) |
| 能力类型 | 知识密集 | 能力密集 |
| 可解释性 | 高(可溯源) | 低 |
| 成本 | 低 | 高 |

混合策略：RAG 补知识 + 轻量微调补能力，质量 +10–15%。

### Q6：Flash Attention 核心原理？
1. **Tiling**：Q/K/V 分块放入 SRAM（A100 片上 40MB，比 HBM 快 10×），避免 S 矩阵落 HBM。
2. **Online Softmax**：增量更新（记录全局 max 与 running sum），无需存整个 S。
3. **Kernel Fusion**：QKᵀ/Softmax/PV 融合为单 Kernel，HBM 访问 -94%。
性能：加速 3.75×（A100），显存 -66%，长上下文收益最大。

### Q7：KV Cache 工程化（PagedAttention / MLA）？
- **PagedAttention（vLLM）**：借鉴 OS 虚拟内存，KV 切固定「页」(16 token)，按需分配 + 引用计数共享（Prefix Caching），显存利用率 60% → 92%。
- **MLA（DeepSeek-V3）**：低秩压缩，显存再降 82.6%。

### Q8：训练稳定性 —— Loss Spike 怎么排查？
五大根因：学习率过大(40%)、数据脏(25%)、梯度爆炸(15%)、Embedding 不稳(10%)、硬件故障(5%)。
SOP：保存检查点 → 查学习率(Warmup+Cosine) → 查数据(异常 Token) → 梯度裁剪(1.0) → 查硬件(ECC)。

### Q9（进阶）：MoE（混合专家）为什么能又省又强？路由与负载均衡怎么做？
- **核心**：每层只有部分「专家」FFN 被激活（稀疏激活）。DeepSeek-V3 总参数 671B，但每 token 仅激活 37B（~5.5%），推理算力接近 37B 稠密模型，知识容量是 671B。
- **路由**：Top-K 门控 `g=softmax(W_gate·x)`，取分数最高的 K 个专家；噪声项(`noise=StandardNormal·softplus(W_noise·x)`) 辅助探索。
- **负载均衡（必考）**：若不加约束，少数专家会被「赢者通吃」→ 退化成稠密。解法：
  1. **辅助损失（auxiliary loss）**：`L_aux = α·Σ_i f_i·P_i`（`f_i`=专家 i 被选中频率，`P_i`=路由概率均值），迫使两者对齐。
  2. **无辅助损失路线（DeepSeek）**：对路由分数加 `bias_i`，每步按负载增减 bias，无需辅助损失即均衡，避免主任务被 aux loss 拖累。
- **工程**：专家并行（Expert Parallelism）跨 GPU 放置；all-to-all 通信是瓶颈，需与 attention 的 TP 协同。

### Q10（进阶）：量化——GPTQ 与 AWQ 的核心区别？INT4 为什么常用？
- **GPTQ（二阶/Hessian 驱动）**：基于 OBQ（Optimal Brain Quantization），按列顺序量化，用逆 Hessian 把量化误差补偿到未量化的权重上；对校准集敏感，但压缩率高。
- **AWQ（激活感知）**：发现「少数权重（~1%）对激活影响极大（salient weights）」，只保护这些权重量化、其余可激进量化；不依赖反向传播、更稳。
- **INT4 为何常用**：权重显存直接 -75%（FP16→INT4），配合 KV Cache INT4 后，长上下文场景端到端显存可降一半以上；70B INT4 可由 2×A100 80G 承载。
- **坑**：weight-only 量化省显存但不省算力；要省算力需 weight-activation 联合量化（如 FP8），但 FP8 需 Hopper 架构。

### Q11（进阶）：推测解码（Speculative Decoding）为什么能加速？接受率怎么算？
- **思想**：用一个小 draft 模型快速「猜」若干 token，再交大 target 模型**并行验证**（一次前向验证 k 个），accept 的继续、首个 reject 后在修正分布下重采样。
- **接受率**：每个位置接受概率 ≈ `min(1, p_target(x)/p_draft(x))`；若 draft 与目标分布接近（同族小模型），接受率高。
- **加速比**：理论 `Speedup ≈ (k·t_draft_串行节省 + 验证成本节省)`；当 draft 远快于 target 时，吞吐接近 `k` 倍（受限于首个分歧点）。解密点：它**不改变输出分布**，是无损加速（与 distillation 不同）。

### Q12（进阶）：Agent 的 LLM-as-Judge 评测有哪些坑？Prompt Injection 怎么防？
- **Judge 坑**：
  1. **位置偏见**：把候选 A 放前面时 A 总是分高 → 正反序各评一次取均值（self-consistency）。
  2. **自我偏好**：裁判模型偏好「和自己风格像」的回答 → 用异源裁判或规则兜底。
  3. **长度偏见**：越长分越高 → 加「简洁性」约束项。
- **Prompt Injection 防护（Agent 上线必考）**：
  - 把**指令（System）与数据（用户/工具返回）显式隔离**，工具返回值标记为不可信、禁止其改写系统指令。
  - 引入「权限边界」：Agent 调敏感工具需二次确认；输出做关键词/语义越权检测。
  - 最小化上下文暴露：只把必要字段塞进 Prompt，长文档走 RAG 检索而非全量注入。

### Q13（进阶）：除了 Softmax Attention，还有哪些序列建模路线？（Linear / SSM）
- **Linear Attention**：用 `φ(Q)φ(K)ᵀV` 核技巧，把 O(n²) 降为 O(n)，但表达能力弱于 softmax（缺数据依赖门控）。
- **Mamba / SSM（状态空间模型）**：用选择性状态空间（input-dependent A/B/C）做线性时序压缩，推理时恒定内存、吞吐高；短板是并行的训练效率与长程「精确回忆」不如 Transformer。
- **答题姿态**：工业主流仍是 Transformer（生态/精度最优），Linear/SSM 是「长上下文成本」压力下的补充路线，按需选型（实时流式、超长文档）。

### 模拟题 2：请深入讲解 KV Cache 工程优化演进（MHA→GQA→PagedAttention→MLA），并手推 MLA 低秩压缩为何能把显存降 80%+。

**考查点**：推理系统底层深度（高频且易区分候选人层次）。

**参考答案要点**：
1. **演进主线**：MHA 每头独立 K/V（KV 最大）→ MQA 所有头共享 1 份 K/V（质量掉 5–10%）→ GQA 分组共享（8 组，平衡）→ PagedAttention 解决「管理碎片」而非「单头大小」→ MLA 从「表示维度」压缩。
2. **GQA 计算**：40 Query Head / 8 KV Head，KV Cache ∝ 8 而非 40 → -80%（约）。
3. **PagedAttention**：连续分配碎片 40%，分页 + 共享前缀 → 利用率 92%，等效再省 ~35%。
4. **MLA 手推（重点）**：
   - 标准 MHA：KV 形状 `[2, n_heads, S, d_h]`，缓存大小 ∝ n_heads·d_h。
   - MLA：将 K/V 投影到低维潜空间 `c_kv ∈ ℝ^{S×d_c}`（d_c=512 ≪ n_heads·d_h=4096），只缓存 `c_kv`。
   - 推理时上投影 `W_UK·c_kv` 重构 K，再算 Attention。
   - 显存比：`d_c / (n_heads·d_h) = 512/4096 ≈ 12.5%`，即 -87.5%；叠加后综合相对 MHA 降 82.6%，质量损失 <0.5%（深层结构补偿信息损失）。
5. **综合算例（128K 上下文）**：MHA 理论 2560GB → GQA(-87.5%)→320GB → INT4 量化(-75%)→160GB → PagedAttention(60%→92%)→104GB → Prefix Caching(-20GB)→84GB，单卡 A100 80GB 可承载（7B 权重 14GB + KV 10.5GB ≈ 24.5GB ✓）。

**可追问**：① MLA 上投影会不会增加推理计算（→ 会，但只在attention时重构，且被显存节省覆盖）？② PagedAttention 怎么支持 beam search（→ 引用计数 + 写时复制）？

### 模拟题 3：如何为百万级用户的 LLM 应用设计流式输出架构，并解决「首 Token 延迟、背压、断线重连、多端一致性」？

**考查点**：把你的全栈（FastAPI/Vue3/PyQt6）背景与大模型结合，区分「纯算法」与「能落地」的候选人。

**参考答案要点**：
1. **接入与协议选型**：Web 用 **SSE**（简单、自带重连）；桌面用 **WebSocket**（双向、需自己管心跳）。统一后端 `request_id`。
2. **首 Token 延迟（TTFT）优化**：模型路由（简单请求走 7B，TTFT <200ms）；Prefix Caching 复用 System Prompt；预取 + 推测解码（Speculative Decoding）加速前几 token。
3. **背压（Backpressure）**：服务端不能无脑狂推。前端按渲染帧率消费，超过缓冲上限（如 4KB）发 `pause` 信号，服务端暂停生成（AsyncIO 可挂起协程）；缓冲排空再 `resume`。避免「前端卡死、token 堆积内存」。
4. **断线重连**：客户端带 `request_id` + 已接收 `offset` 重连；服务端从 KV/Redis 中该请求的流式缓冲续传，避免重复生成（流式结果先落环形缓冲）。
5. **多端一致性（Web/Vue3 + 桌面/PyQt6）**：渲染层与编排层解耦——同一份「流式事件流（delta token / tool_call / done）」驱动不同终端渲染器；状态以服务端的「对话快照」为准，终端只做展示，保证两端看到的内容一致、可回溯。
6. **成本与高可用收尾**：语义缓存命中 40%（成本 -40%）；优雅降级链（70B→13B→7B→缓存）；多区域 + 自动故障转移保障 99.99%。

**可追问**：① 语义缓存怎么保证答案一致（→ 对 query 做语义聚类 + 版本化 System Prompt）？② 多端断线后 offset 乱序怎么处理（→ 服务端按 request 维护有序 buffer + monotonic offset）？

- `softmax(QKᵀ/√d_k)V`；O(n²)

- MHA(100%)→MQA(50%)→GQA(62.5%)→MLA(15%，低秩压缩 -82.6%)

**推理系统**
- Flash Attention：Tiling + Online Softmax + Kernel Fusion（HBM -94%）

- 推测解码：draft 猜 k 个 + target 一次验证，**无损**加速

**训练 / 微调**
- LoRA：ΔW=BA，参数量 ~0.4%；QLoRA=4bit+LoRA
- Loss Spike 五因：LR(40%)/脏数据(25%)/梯度爆炸(15%)/Embedding(10%)/硬件(5%)
- 量化：GPTQ(Hessian 补偿) vs AWQ(激活感知保护显著权重)；INT4 显存 -75%

**RAG / Agent**
- RAG 三代：Chroma+OpenAI(42%)→Milvus+BGE+BM25(68%)→GraphRAG(85%)
- RAG vs FT：实时性/可解释 vs 能力密度
- MoE：稀疏激活(671B 中激活 37B)；aux loss 防赢者通吃
- Judge 三坑：位置偏见(正反序)/自我偏好(异源)/长度偏见(简洁约束)
- Prompt Injection：指令-数据隔离 + 权限边界 + 最小暴露
