**亮点 A：生产级 DAG 动态调度器**（环检测 + 分层并行 + 熔断降级，含代码）

```python
from collections import defaultdict, deque
import asyncio

class DAGScheduler:
    def __init__(self):
        self.nodes = {}; self.deps = defaultdict(set)
        self.status = {}; self.max_retry = 3; self.circuit_open = set()

    def add(self, name, fn, depends_on=None, fallback=None):
        self.nodes[name] = (fn, fallback); self.deps[name] = set(depends_on or [])

    def _detect_cycle(self):                      # 入度法 O(V+E)
        indeg = {n: len(self.deps[n]) for n in self.nodes}
        q = deque([n for n in self.nodes if indeg[n] == 0]); seen = 0
        adj = defaultdict(list)
        for n, ds in self.deps.items():
            for d in ds: adj[d].append(n)
        while q:
            u = q.popleft(); seen += 1
            for v in adj[u]:
                indeg[v] -= 1
                if indeg[v] == 0: q.append(v)
        if seen != len(self.nodes): raise RuntimeError("DAG 存在环，无法调度")

    async def _run_node(self, name):
        if name in self.circuit_open: return await self._fallback(name)
        fn, fallback = self.nodes[name]
        for attempt in range(self.max_retry + 1):
            try:
                self.status[name] = 'running'; return await fn()
            except Exception:
                if attempt == self.max_retry:
                    if fallback: return await self._fallback(name)
                    self.circuit_open.add(name); self.status[name] = 'failed'; raise
                await asyncio.sleep(2 ** attempt)  # 指数退避
```

> 面试亮点：环检测防 Planner 自引用死循环；分层并行使整体时延≈最长链而非链和；**重试治瞬时故障，熔断治持续故障，防雪崩**。

## 二、技术难点（Technical Difficulties · 跨项目六大共性难点 + 解决方案）

### 2.1 多 Agent 编排的"任务发散 / 循环"

**现象**：Planner 反复生成相似子任务，A→B→A 打转，token 爆炸、任务不结束。  
**根因**：缺"已完成"状态约束 + 缺最大步数硬限。  
**方案**：DAG 化（产出有依赖的任务图）+ 状态机 `done` 标记 + `max_steps=12` 硬限触发 Reflector 兜底。

### 2.2 大规模推理 KV Cache 与显存墙

**现象**：百万并发下 KV Cache 显存成瓶颈。  
**根因公式**（MHA）：`KV_bytes = 2 × L × n_kv_heads × seq_len × head_dim × bytes_per_elem`。7B(MHA, 4K) ≈ 2.1GB。  
**方案**：模型侧换 GQA/MLA（KV head 32→8，显存 -82%）；服务侧 PagedAttention（利用率 60%→92%）+ Prefix Caching；业务侧上文压缩（LLMLingua 压到 30%）。

### 2.3 工具调用可靠性（让模型吐 100% 合法 JSON）

**根因**：自回归采样天然可能输出残缺 JSON。  
**根本解——约束解码**（token 级掩码，概率重标定公式）：

```
P_masked(x_t|x_<t) = P(x_t|x_<t)·1[x_<t x_t ∈ L(G)] / Σ P(x'|x_<t)·1[x_<t x' ∈ L(G)]
```

凡使前缀脱离文法 G 的词概率直接置 0，输出必可解析。兜底三档：严格 JSON → 宽松修复（截到平衡括号/去前缀）→ 错误回灌自愈（≤2 次）。

**自愈解析代码**：

```python
import json, re
def robust_json_parse(raw: str):
    raw = re.sub(r'^```(?:json)?', '', raw.strip()).strip()
    raw = re.sub(r'```$', '', raw).strip()
    try: return json.loads(raw), None
    except json.JSONDecodeError: pass
    for end in (raw.rfind('}'), raw.rfind(']')):
        if end > 0:
            try: return json.loads(raw[:end+1]), "truncated"
            except json.JSONDecodeError: continue
    return None, f"JSONDecodeError at pos {e.pos}"
```

### 2.4 幻觉与可控性工程化（四层堵死）

1. 工具返回值 schema 校验，非法即判失败重试；
2. RAG 回答强制"引用约束生成"（每论断挂 citation，无引用句扣分）；
3. Guardrail 层对事实性断言做轻量一致性检查；
4. Online Eval 持续监控幻觉率，>阈值自动告警 + 回滚 Prompt。  
**心法**：幻觉不能靠"提示词让它别编"解决，必须靠"系统把编造空间堵死"。

### 2.5 成本工程（推理成本 -71% 的数学拆解）

`成本 = Σ(路由单价 × token) × (1 - 缓存命中率)`。杠杆：

- **模型路由**：80% 简单流量走 7B，仅 20% 走 70B → 单价 -80%；
- **语义缓存 + KV 复用**：重复计算降到最低（命中 ~35%）；
- **量化（INT8/FP8）**：吞吐 +100%，单价 -50%；
- **上文压缩**：长文档 -70% token。三者叠加（非简单相加，有重叠）综合 -71%。

### 2.6 规模化 SRE（多租户隔离 + 故障止血）

- **隔离**：每租户令牌桶限流 + 独立推理队列 + 优先级调度，防头号租户占满 GPU；
- **重试 vs 熔断**：重试治瞬时故障，熔断治持续故障（连续失败开 `circuit_open` 走 Fallback，防雪崩）；
- **可观测前提**：全链路 `trace_id` 串联，否则 30 分钟定位不可能；
- **Fallback 金字塔**：70B 挂 → 13B → 7B → 缓存结果，逐级保可用。

### 2.7 延伸技术难点速查（常考深挖）

**注意力进化 MHA→MQA→GQA→MLA**：

| 机制 | KV Cache 大小 | 质量损失 | 适用 |
|------|--------------|---------|------|
| MHA | 1.0x | 0% | 高质量 |
| MQA | 0.52x | 5-10% | 极长上下文 |
| GQA | 0.75x | 2-5% | 平衡（端侧甜点） |
| MLA | 0.174x | <2% | DeepSeek-V3 |

**位置编码 Sinusoidal→RoPE→ALiBi→YaRN**：RoPE 因"相对位置 + 旋转矩阵保内积 + 长度外推"成工业标准；YaRN 用 NTK-aware 插值实现 8x 无损外推。

**Flash Attention**：Tiling（分块入 SRAM）+ Online Softmax（增量更新，不存整 S 矩阵）+ Kernel Fusion，HBM 访问 -94%，A100 提速 3.75x、显存 -66%。

**Loss Spike**：六大根因（学习率过大 40% / 数据质量 25% / 梯度爆炸 15% / Embedding 10% / 注意力崩溃 5% / 硬件 5%）；排查 5 步：检测→存检查点→查 LR→查数据→回滚。

## 三、常见问答（Common Q&A · 12 个高频深度问题）

**Q1：Agent Harness 与普通 RPA / 工作流（Airflow）的本质区别？**
① 决策：RPA 静态图（节点边写死），Agent 动态图（Planner 运行时实时决定，LLM 当软控制器）；② 容错：工作流按节点重试，Agent 能反思改路径；③ 接口：Agent 原生接 LLM 理解非结构化输入。代价：不确定性/可解释差，故生产用"DAG+状态机"收敛自由度。

**Q2：如何保证大模型输出 100% 合法 JSON / 工具参数？**
由浅入深：① prompt 约束（最弱，小模型仍失败）→ ② 后处理修复（兜底，耗 token）→ ③ **Grammar-Constrained Decoding（根本解，把 schema 编译成 CFG，token 掩码置 0 非法词，合法率 99.6% 且不改语义）→ ④ schema 校验 + 类型自愈 + 错误回灌。

**Q3：KV Cache 显存公式与压缩手段？**
`KV = 2·L·n_kv·T·head_dim·2(bytes)`。压缩：GQA/MQA（降 n_kv，-82%）、KV 量化（INT8/INT4，-50%）、PagedAttention（利用率 92%）、Prefix Caching（共享前缀）、H2O 淘汰（按注意力得分淘汰 70~90%）。

**Q4：RAG 召回率上不去怎么系统排查？**
分层：① 召回层（换 BGE-M3 Embedding、上混合检索、加重排 Cross-Encoder）② 切分层（布局感知 + 父子文档）③ 索引层（IVF-PQ 的 nprobe 是否过小）④ 评测层（用 nDCG@10/Recall@10 量化而非体感）。

**Q5：推理成本如何优化 70%+？**
成本模型驱动：`路由单价 × token × (1-缓存命中率)`。模型路由(-80%) + 语义缓存/KV 复用(-30%~) + 量化(-50%) + 上文压缩(-70%)，叠加综合 -71%。

**Q6：如何把幻觉率压到可控范围？**
四层堵死：工具 schema 校验 + RAG 引用约束 + Guardrail 事实检查 + Online Eval 监控回滚。"提示词让它别编"无效，必须堵死编造空间。

**Q7：ReAct 与 Function Calling 本质区别？何时用哪个？**
ReAct 是 prompt 范式（自然语言 Thought→Action，正则解析，脆弱）；FC 是模型原生能力（训练出结构化 tool_calls，可靠/可并行/可控）。生产一律 FC；ReAct 适合快速原型/无 FC 训练数据的小模型（配宽松解析兜底）。

**Q8：为什么 GQA 是端侧 KV 压缩的最佳折中？**
MHA（KV 最大）vs MQA（1 个 KV head，KV 最小但质量降）vs GQA（32Q:8KV，KV=1/4、质量近 MHA）。端侧要压 KV 又不想牺牲质量 → GQA 甜点（LLaMA-3/Mistral/Qwen2 均用）。且 K 用 INT8、V 用 INT4（Key 定分布、Value 被平均稀释）。

**Q9：端云协同路由如何避免"路由错误导致质量崩塌"？**
① 路由器用云端大模型质量做标签训练（非拍脑袋）；② 置信度阈值，低于一律走云；③ 云端兜底（端侧答完低置信→云二次答）；④ 在线评估监控路由后质量，下降自动回退全云；⑤ A/B 验证。RouteLLM 质量不变下省 ~50% 云端调用。

**Q10：多 Agent 系统如何防循环发散？**
DAG 化（Planner 产出有依赖的任务图）+ 状态机 `done` 标记（禁重复调度）+ `max_steps` 硬限（超限进 Reflector 输出"无法完成+部分结果"）。核心是给 LLM 自由度加约束，否则不可运维。

**Q11：MoE 为什么比稠密模型更高效？路由与负载均衡怎么做？**
稠密：所有参数参与计算；MoE：每个 token 仅激活 Top-K Expert（DeepSeek-V3 671B→37B，仅 5.5%）。负载均衡早期用 Auxiliary Loss（鼓励均匀路由），但会损伤主任务，DeepSeek 用 **Auxiliary-Loss-Free**（动态调整 bias 项，无额外损失）。训练不稳定常因路由震荡，需 warmup + 稳定 router。

**Q12：Test-Time Compute（o1/DeepSeek-R1）的原理与工程代价？**
显式 CoT（o1，生成思考过程）+ 隐式 CoT（R1，RL 自我验证）。关键技术：PRM（过程奖励模型）、MCTS（探索多推理路径）、Long CoT（1000+ token）。代价：推理算力 ×N（算力换质量），需配合采样/重排序（Best-of-N）与预算控制；线上靠"难度分级路由"只在难题启用。

## 四、模拟面试（Mock Interview · 3 道深度针对性题）

> 三题均为**跨项目综合级全新题**，不与历史 46 道重复，聚焦"长上下文 / 容量与长尾延迟 / 评测体系"三大高频深挖方向。

### 🎯 模拟题 1：128K+ 长上下文场景下，如何做 KV Cache 显存与调度优化？

**题干**：业务要求单请求支持 128K token 上下文，且并发 1 万。请系统说明：KV Cache 显存如何估算、会撞什么墙、从模型结构 / 推理框架 / 业务三层分别怎么优化，并给出调度侧"分块预填充 + 上下文压缩"的落地思路。

**参考答案要点（估算 → 模型 → 框架 → 业务 → 调度）**：
1. **显存估算**：`KV = 2·L·n_kv·T·head_dim·bytes`。以 7B(GQA 8 KV head, head_dim 128, FP16) 为例，单请求 128K ≈ 2×1×8×131072×128×2 ≈ **4.3 GB**；1 万并发若不优化需 43 TB → 撞墙。
2. **模型侧（降 n_kv）**：GQA/MLA 把 KV head 压到 8/1，MLA 再低秩压缩（KV 仅 0.174x），单请求 128K 降到 ~0.75 GB；KV 量化（K INT8/V INT4）再 -50%。
3. **框架侧（提利用率）**：PagedAttention 把 KV 分页、按需分配（利用率 60%→92%）；Prefix Caching 让同源系统提示共享前缀，省重复计算；H2O/StreamingLLM 按注意力得分淘汰 70~90% 历史 KV（保留"重点 token"）。
4. **业务侧（降 token）**：上文压缩 LLMLingua 压到 30%；分层记忆（把长文档摘要进长期记忆，推理时只带摘要 + 检索片段）；RAG 替代全量注入。
5. **调度侧**：分块预填充（Chunked Prefill）把长 prompt 拆块与 decode 混合批处理，避免单请求占满；**分离式架构（Prefill/Decode  disaggregation）** 让 prefill 集群算完 KV 再卸载给 decode 集群，KV 走 CPU/SSD 或 RDMA（如 Mooncake），解耦长上下文的算力与显存瓶颈。
**加分项**：点出"长上下文真正的成本不在单请求，而在并发放大 ×并发数"，所以必须模型+框架+业务三层同时动手；并提到"外推≠免费"——YaRN/NTK 扩展后仍要评测远端位置衰减。

### 🎯 模拟题 2：推理服务从 0 到百万 QPS，如何做容量规划与长尾延迟（P99）治理？

**题干**：你的 Agent 平台要支撑百万 QPS 的 LLM 推理。请给容量规划方法、核心吞吐优化手段，并重点说明"为什么平均延迟好看但 P99 爆炸"，以及工程上如何治理长尾。

**参考答案要点（容量 → 吞吐 → 长尾根因 → 治理）**：
1. **容量规划**：先按 `GPU数 = 目标QPS × 单请求平均耗时(s) / 单卡吞吐(req/s/卡) / 利用率目标(0.8)` 估算；用 Continuous Batching 把 GPU 利用率拉到 90%+（传统静态 batch 仅 30~50%）。单卡 7B 约 1k~3k tok/s，需按请求长度建模。
2. **吞吐优化**：Continuous Batching（请求动态进批，不等齐）+ PagedAttention（KV 不碎片化）+ 模型路由（简单走小模型省算力）+ 投机解码（小模型 draft + 大模型 verify，接受率 70% 提速 2~3x）。
3. **长尾根因（P99 爆炸）**：① 队列排队（瞬时突发 + 批内最长请求拖累同批所有人，"队头阻塞"）；② 长请求占卡（一个 128K 预填充拖垮整批）；③ KV Cache 抢占/换页（内存不够触发换出）；④ 下游工具 RPC 抖动；⑤ 重试放大（失败重试叠流量）。
4. **治理手段**：
   - **Prefill/Decode 分离**：预填充是算力密集、decode 是访存密集，分离后互不拖累，P99 显著降；
   - **优先级队列 + 抢占**：付费/高优请求插队，长请求可抢占让短请求先走；
   - **SLO 分桶路由**：按延迟目标把请求分档，超长上下文走独立池；
   - **KV 卸载 + 分级缓存**：热点前缀常驻，冷 KV 落 CPU/SSD；
   - **限流 + 熔断 + 重试预算**：限制单用户并发，重试带退避与上限防爆量；
   - **可观测**：按 (模型, 路由, 租户) 拆 P50/P90/P99，定位长尾来源。
**加分项**：强调"平均延迟是骗局，面试官看 P99/P999"；并说明分离式架构下 KV 传输成为新瓶颈，需用 RDMA/高速互联。

### 🎯 模拟题 3：如何设计 Agent 评测体系，证明"新版 Agent 比旧版更好"？

**题干**：你迭代了一版 Agent（新 Planner + 新工具路由）。老板问"凭什么说新版更好？"请设计一套评测体系，覆盖离线 / 在线 / 自动化评测，并解释 LLM-as-Judge 的偏置与缓解，最后说明如何防止"评测通过但线上翻车"。

**参考答案要点（分层 → Judge 偏置 → 防翻车）**：
1. **三层评测体系**：
   - **离线基准**：固定任务集（工具选择准确率 / 多步成功率 / 合法 JSON 率 / 端到端任务成功率），新旧版跑同集比 AST 匹配率 + 执行成功率；
   - **在线 A/B**：小流量灰度（5%），比业务指标（任务成功率、用户满意度、token 成本、P99）；
   - **Online Eval**：采样 3%~8% 真实流量，LLM 自动打分 + 规则校验（引用约束、schema 合规），实时监控回归。
2. **LLM-as-Judge 三坑 + 缓解**：
   - 坑① **位置偏置**（偏好先出现的答案）→ 双盲交换顺序取平均；
   - 坑② **长度/Verbosity 偏置**（偏爱更长）→ 改用 rubric 打分 + 控制长度；
   - 坑③ **自我偏好**（偏爱同模型输出）→ 用第三方强模型 + 多 judge 投票；加人类校准集（Judge 分 vs 人分相关性 ≥0.8 才可信）。
3. **防"评测通过但线上翻车"**：
   - **回归护栏**：每次发版自动跑回归集，指标掉超阈值自动阻断；
   - **影子模式（Shadow）**：新版本镜像流量但不返回用户，先比行为一致性；
   - **金丝雀 + 自动回滚**：灰度看板异常（成本×3 / 成功率掉 / P99 翻倍）自动回滚；
   - **长尾覆盖**：评测集必须含失败/异常/对抗样本，不能只测 happy path；
   - **成本与质量联合 SLI**：不只看质量，成本/延迟同步纳入上线门槛。
**加分项**：点出"评测集污染"风险（训练数据含评测题），需独立 held-out 集；并说明"成功率 89% vs 61%"这类数字必须可复现、有置信区间。
