### 1.1 GRPO 强化学习微调——无 Critic 的多 Agent 策略优化

#### **为什么 GRPO 是 RLHF 的实用化升级？**

```
RLHF（RL from Human Feedback）完整流程：
  Step1: SFT 微调基础模型（Supervised Fine-Tuning）
  Step2: 训练 Reward Model（人类偏好标注 → 标量奖励）
  Step3: PPO 优化策略（Policy → RM → 奖励 → 策略更新）

PPO 的工程痛点：
  1. Reward Model 训练成本高（需要大量人类标注）
  2. PPO 超参敏感（critic 网络难以调优，容易 mode collapse）
  3. 训练不稳定（奖励 hacking，策略退化）
  4. 显存占用大（Policy + Critic + Reward Model 同时加载）

GRPO（Group Relative Policy Optimization）核心突破：
  → 取消 Critic 网络，用「同组相对奖励」替代价值函数估计
  → 减少 ~50% 显存占用，训练稳定性大幅提升
```

#### **GRPO 数学原理深度解析**

```python
# GRPO 核心思想：用「组内相对优势」替代 Critic 估计
#
# 传统 PPO：A_t = Q(s_t, a_t) - V(s_t)   ← 需要 Critic 估计 V(s_t)
# GRPO：A_i = r_i - mean(r_1...r_G) / std(r_1...r_G)  ← 组内标准化，无需 Critic

import torch
import torch.nn.functional as F

class GRPOTrainer:
    """
    GRPO 训练器核心实现
    关键创新：Group-Relative Advantage 估计
    """

    def __init__(self, policy_model, ref_model, tokenizer, 
                 group_size=8, kl_coef=0.04, clip_range=0.2):
        self.policy = policy_model
        self.ref_model = ref_model  # 冻结，用于 KL 约束
        self.tokenizer = tokenizer
        self.G = group_size
        self.kl_coef = kl_coef
        self.clip_range = clip_range

    def compute_group_relative_advantage(self, rewards):
        """
        rewards: Tensor[G]  # 一组 G 个响应的奖励
        
        核心公式：
        A_i = (r_i - mean(r)) / (std(r) + eps)
        
        直观理解：
        - 奖励高于组平均 → 正优势（应该鼓励）
        - 奖励低于组平均 → 负优势（应该抑制）
        - 组内标准差大 → 优势幅度小（组内差异大时更保守）
        """
        r = torch.tensor(rewards, dtype=torch.float32)
        mean_r = r.mean()
        std_r = r.std(unbiased=False)
        advantages = (r - mean_r) / (std_r + 1e-8)
        return advantages  # [G]

    def grpo_loss(self, query, responses, rewards):
        """
        GRPO 损失函数（核心！）
        
        输入：
          query: 原始 Prompt（如「写一篇关于 AI 安全的文章」）
          responses: [G] 个生成响应（每个都不同）
          rewards: [G] 个标量奖励（由 RM 或规则给出）
        
        输出：
          loss: 待优化的标量
        """

        # ── Step1: 计算每个响应的对数概率 ──
        log_probs = []
        ref_log_probs = []
        for resp in responses:
            # Policy 模型的对数概率
            inputs = self.tokenizer(query + resp, return_tensors="pt")
            outputs = self.policy(**inputs)
            log_p = self._compute_log_prob(outputs.logits, inputs["input_ids"])
            log_probs.append(log_p)

            # Reference 模型的对数概率（冻结，只用于 KL 约束）
            ref_outputs = self.ref_model(**inputs)
            ref_log_p = self._compute_log_prob(ref_outputs.logits, inputs["input_ids"])
            ref_log_probs.append(ref_log_p)

        log_probs = torch.stack(log_probs)       # [G]
        ref_log_probs = torch.stack(ref_log_probs)  # [G]

        # ── Step2: 计算 Group-Relative Advantage ──
        advantages = self.compute_group_relative_advantage(rewards)  # [G]

        # ── Step3: Clip 目标（类似 PPO-Clip）──
        ratio = torch.exp(log_probs - log_probs.detach())  # exp(log_p - log_p_old)
        surr1 = ratio * advantages
        surr2 = torch.clamp(ratio, 1-self.clip_range, 1+self.clip_range) * advantages
        policy_loss = -torch.min(surr1, surr2).mean()

        # ── Step4: KL 散度约束（防止策略偏离太远）──
        kl_loss = F.kl_div(
            F.log_softmax(log_probs, dim=-1),
            F.softmax(ref_log_probs, dim=-1),
            reduction="batchmean"
        )

        # ── Step5: 总损失 ──
        total_loss = policy_loss + self.kl_coef * kl_loss
        return total_loss

    def _compute_log_prob(self, logits, input_ids):
        """计算每个 token 的对数概率（简化版）"""
        log_probs = F.log_softmax(logits, dim=-1)
        # 收集每个位置对应真实 token 的对数概率
        gathered = torch.gather(log_probs[:, :-1], 
                             dim=-1, 
                             index=input_ids[:, 1:].unsqueeze(-1))
        return gathered.sum()  # 整个序列的对数概率
```

#### **GRPO vs PPO vs DPO 三维对比**

| 维度 | PPO (RLHF) | DPO | GRPO |
|------|---------------|-----|-------|
| **是否需要 Reward Model** | ✅ 需要 | ❌ 不需要 | ❌ 不需要 |
| **是否需要 Critic 网络** | ✅ 需要（Value网络） | N/A | ❌ 不需要 |
| **数据效率** | 低（需要大量偏好标注） | 高（直接用偏好对） | 中（需要组奖励） |
| **训练稳定性** | 低（超参敏感） | 高 | 中高 |
| **显存占用** | 高（Policy+Critic+RM） | 低（只有 Policy） | 中（Policy+Ref） |
| **数学基础** | 策略梯度 + 广义优势估计 | 偏好对数似然 | 组内相对优势 |
| **代表工作** | InstructGPT, GPT-4 | Zephyr, Tulu-2 | DeepSeek-Math, Kimi k1.5 |

### 1.2 代码大模型架构——DeepSeek-Coder 的技术突破

#### **代码 LLM 的独特挑战**

```
通用 LLM（GPT/Qwen） vs 代码专用 LLM：

挑战1：仓库级上下文（Repository-Level Context）
  代码片段依赖同仓库其他文件（import / 类型定义 / 函数签名）
  通用 LLM 只看到单文件 → 跨文件推理失败
  
  解法：Repo-Level 微调 + 结构化文件拼接（DeepSeek-Coder 核心贡献）

挑战2：填空式生成（FIM / Fill-In-the-Middle）
  代码场景：光标在中间，需要「向前看 + 向后看」
  传统 Causal LM：只能从左到右生成 → 不适合代码补全
  
  解法：FIM（Fill-In-the-Middle）预训练目标（论文：SantaCoder）

挑战3：程序语言 vs 自然语言的 Token 效率
  「def foo():」在 BPE 中可能被切成 3-4 个 Token
  → 同样参数量，代码模型的实际上下文更短
  
  解法：代码专用 Tokenizer（DeepSeek-Coder 扩到 32K vocab）
```

#### **FIM（Fill-In-the-Middle）预训练目标详解**

```python
# 标准 Causal LM 预训练：
#   输入：「def foo():\n    return 」
#   目标：「42」
#   问题：无法在「光标在中间」时生成

# FIM 预训练（三种 Suffix-Infix-Prefix 排列）：
#  原始代码：<PRE> def foo():\n    <SUF>\n    return 42\n<MID>
#  重排后：<SUF>\n    return 42\n<MID> def foo():\n    
#  （把 Suffix 移到前面，模型学会「先看到后文，再生成中间」）

import torch
import random

class FIMDataset:
    """
    FIM（Fill-In-the-Middle）数据构造器
    论文：SantaCoder (Allal et al., 2023)
    """

    FIM_TOKENS = ["<|fim_prefix|>", "<|fim_middle|>", "<|fim_suffix|>"]

    def __init__(self, p_fim=0.5, sentinel_ratio=0.9):
        self.p_fim = p_fim          # 50% 概率使用 FIM 格式
        self.sentinel_ratio = sentinel_ratio  # 其中 90% 用 sentinel，10% 用原文

    def transform_for_fim(self, code_text: str) -> str:
        """
        将完整代码转换为 FIM 训练格式
        """
        if random.random() > self.p_fim:
            return code_text  # 保留原始 Causal 格式

        # 随机选择一个「光标位置」
        lines = code_text.split('\n')
        cursor_line = random.randint(1, len(lines) - 1)

        # 分割为 PRE（光标前）/ MID（中间）/ SUF（光标后）
        pre = '\n'.join(lines[:cursor_line])
        suf = '\n'.join(lines[cursor_line:])
        mid = ''  # 待生成部分（训练时从 ground truth 获取）

        # FIM 重排策略（两种）：
        # Strategy A: <SUF> + <MID> + <PRE>（Suffix-First，主流）
        # Strategy B: <PRE> + <SUF> + <MID>（Prefix-Suffix-First）
        if random.random() < 0.5:
            fim_text = f"<|fim_suffix|>{suf}<|fim_middle|>{mid}<|fim_prefix|>{pre}"
        else:
            fim_text = f"<|fim_prefix|>{pre}<|fim_suffix|>{suf}<|fim_middle|>{mid}"

        return fim_text

# DeepSeek-Coder 实际使用的 FIM 策略（更强）：
#   1. PSM（Prefix-Suffix-Middle）排列：最适合代码补全
#   2. 16K 上下文窗口 + 4K 生成长度
#   3. 仓库级数据：先拼接同仓库多个文件，再加 FIM 掩码
```

#### **DeepSeek-Coder 的仓库级 RAG 架构**

```
问题：代码补全时如何找到「相关的其他文件」？

方案1（Naive）：把整个仓库拼接 → 超过上下文窗口（16K 不够）

方案2（DeepSeek-Coder V2）：两阶段检索增强
  Stage1：向量检索（Embedding 相似度）
    - 对当前文件做 Embedding
    - 检索 Top-K 个相关文件（余弦相似度）
    - 相似度计算：CodeBERT / UniXcoder
  
  Stage2：结构化拼接
    格式：<repo>\n<filepath>src/foo.py</filepath>\n<code>...</code>\n</repo>\n...
    Prompt 构造：
      [检索到的相关文件代码] + [当前文件前缀] → 补全光标处代码

  效果：跨文件补全准确率从 38% → 67%（HumanEval 仓库级变体）
```

## 🔧 二、技术难点与解决方案（Technical Challenges）

### 2.1 长上下文推理——StreamingLLM 与 Attention Sink

#### **问题：LLM 在长上下文下「找不到中间的信息」**

```
现象（Lost in the Middle，2023）：
  输入 100K Token 文档，问「第 50000 个 Token 附近写了什么？」
  → LLM 答不对（注意力被「最近的 Token」主导）

根本原因：
  1. Softmax 的「近因偏差」：最近的 Token 注意力分数自然更高
  2. 位置编码外推失败：RoPE 在 > 训练长度时Attention 分布畸变
  3. KV Cache 显存限制：无法真的把所有 Token 都放进 KV Cache

三大解决路线：
  ├── 1. 窗口截断（StreamingLLM）：只保留「开头 + 结尾」
  ├── 2. 位置编码修正（LongRoPE / YaRN）：让模型「认识」更长位置
  └── 3. 记忆压缩（MemGPT / LongLLMLingua）：把旧信息压缩成「记忆 Token」
```

#### **StreamingLLM 核心机制**

```python
# 问题：LLM 推理时 KV Cache 无限增长 → OOM
# 朴素解法：滑动窗口（只保留最近 N 个 Token）
#   问题：丢失了「System Prompt」→ 模型行为漂移

# StreamingLLM 解法（2023，Han et al.）：
#   「Attention Sink」现象：模型对「初始几个 Token」分配异常高的注意力
#   即使这些 Token 信息量很低！
#   → 保留「4 个初始 Token」的 KV，就能恢复大部分性能

class StreamingLLMCache:
    """
    StreamingLLM 的 KV Cache 管理
    只保留：(1) Attention Sink（前 4 个 Token）+ (2) 最近 N 个 Token
    """

    def __init__(self, sink_size=4, window_size=2048):
        self.sink_size = sink_size      # 保留的「Attention Sink」Token 数
        self.window_size = window_size  # 保留的「最近」Token 数
        self.kv_cache = {"sinks": [], "window": []}

    def update(self, new_k, new_v):
        """
        更新 KV Cache：
        - 前 sink_size 个 Token：永远保留（Attention Sink）
        - 最近的 window_size 个 Token：滑动窗口保留
        - 中间的 Token：全部丢弃
        """
        if len(self.kv_cache["sinks"]) < self.sink_size:
            # 还在填充 Sink 阶段
            self.kv_cache["sinks"].append((new_k, new_v))
        else:
            # Sink 已满，更新滑动窗口
            self.kv_cache["window"].append((new_k, new_v))
            if len(self.kv_cache["window"]) > self.window_size:
                self.kv_cache["window"].pop(0)  # 丢弃最老的

    def get_kv_for_attention(self):
        """拼接 Sinks + Window，用于 Attention 计算"""
        sinks_k = torch.cat([k for k, _ in self.kv_cache["sinks"]])
        sinks_v = torch.cat([v for _, v in self.kv_cache["sinks"]])
        window_k = torch.cat([k for k, _ in self.kv_cache["window"]])
        window_v = torch.cat([v for _, v in self.kv_cache["window"]])
        return (
            torch.cat([sinks_k, window_k]),
            torch.cat([sinks_v, window_v])
        )

# 实验效果（LLaMA-2 7B，输入 100K Token）：
#   滑动窗口（只保留最近 2K）：PPL = 18.7（严重退化）
#   StreamingLLM（Sinks 4 + Window 2K）：PPL = 6.3（接近完整上下文 5.9）
#   完整 KV Cache（理论上限）：PPL = 5.9
```

#### **LongRoPE——长度外推的工程化方案**

```
RoPE 长度外推的本质问题：
  训练时最大位置 = 4096
  推理时位置 = 32768（8 倍外推）
  → 高频分量（短距离位置编码）被极度压缩 → 局部注意力失效

LongRoPE（2024，Chen et al.）核心思路：
  对不同频率分量做「非均匀插值」：
    - 低频分量（捕获长程依赖）：插值因子小（1.0，不插值）
    - 中频分量：插值因子中（如 2.0）
    - 高频分量（捕获局部语法）：插值因子大（如 8.0，充分插值）

  数学形式：
    RoPE(θ_i, m) = e^{i·m·θ_i}  其中 θ_i = 1 / base^{2i/d}
    
     LongRoPE：θ_i' = θ_i / λ_i  其中 λ_i 是第 i 个频率分量的「缩放因子」
     λ_i 通过进化搜索（Evolutionary Search）自动找到最优值

实战效果（LLaMA-2 7B，推理 128K）：
  原始 RoPE（直接外推）：PPL = 42.1（崩溃）
  Position Interpolation（均匀插值）：PPL = 12.8
  YaRN（分段插值）：PPL = 7.3
  LongRoPE（进化搜索 + 非均匀插值）：PPL = 5.8（接近上限 5.7）
```

### 2.2 评估体系进阶——RAGAS + LLM-as-Judge 完整实战

#### **为什么需要「评估体系」而不只是「看输出好不好」？**

```
LLM 应用评估的三重困境：

困境1：输出不确定性
  同一输入，temperature=0.7 时每次输出不同
  → 单次观察无法判断「模型能力差」还是「这次运气不好」

困境2：评估指标主观
  「回答质量好」如何量化？
  BLEU/ROUGE：衡量表面相似度，不衡量语义正确性
  人工评估：成本高（标注员工时），不一致（不同人标准不同）

困境3：多组件系统（RAG / Agent）
  失败可能来自：检索质量差 / 提示词差 / 模型能力差 / 后处理差
  → 单一端到端指标无法定位问题

解法：分层评估体系（RAGAS 框架 + LLM-as-Judge）
```

#### **RAGAS 评估框架四维指标**

```python
# RAGAS（Retrieval-Augmented Generation ASsessment）
# 四大核心指标：

import numpy as np

# ── 指标1：Context Precision（检索精确率）──
#    含义：检索到的上下文中，有多少是「真正相关」的？
#    计算：Precision@K = (# 相关文档 in Top-K) / K
def context_precision(relevant_docs, retrieved_docs_k):
    """
    relevant_docs: Set[str]  # 人类标注的「真正相关」文档 ID
    retrieved_docs_k: List[str]  # 检索系统返回的 Top-K 文档 ID
    """
    relevant_retrieved = [doc_id in relevant_docs for doc_id in retrieved_docs_k]
    precision_scores = []
    running_correct = 0
    for i, is_rel in enumerate(relevant_retrieved, 1):
        if is_rel:
            running_correct += 1
            precision_scores.append(running_correct / i)
    return np.mean(precision_scores) if precision_scores else 0.0

# ── 指标2：Context Recall（检索召回率）──
#    含义：所有「真正相关」的文档中，检索到了多少？
def context_recall(relevant_docs, retrieved_docs):
    retrieved_set = set(retrieved_docs)
    return len(relevant_docs & retrieved_set) / len(relevant_docs)

# ── 指标3：Faithfulness（忠实度）──
#    含义：生成的答案是否完全基于检索到的上下文（没有幻觉）？
#    计算：用 NLI 模型判断「答案中的每个声明」是否被「上下文」蕴含
def faithfulness(answer, context):
    """
    实现：把答案拆成多个声明（Claim），
    对每个 Claim 用 NLI 模型判断是否被 Context 蕴含
    """
    claims = extract_claims(answer)  # 用 LLM 或规则抽取声明
    nli_model = load_nli_model()      # 如 DeBERTa NLI
    faithful_count = 0
    for claim in claims:
        # NLI 三分类：蕴含(entailment) / 中立(neutral) / 矛盾(contradiction)
        prob = nli_model.predict(claim, context)
        if prob["entailment"] > 0.7:
            faithful_count += 1
    return faithful_count / len(claims) if claims else 1.0

# ── 指标4：Answer Relevance（答案相关性）──
#    含义：答案是否直接回答了问题（没有跑题）？
def answer_relevance(question, answer):
    """
    实现：用 Embedding 计算「问题」和「答案」的语义相似度
    更高相似度 → 答案更相关
    """
    q_emb = embedding_model.encode(question)
    a_emb = embedding_model.encode(answer)
    cosine_sim = np.dot(q_emb, a_emb) / (np.linalg.norm(q_emb) * np.linalg.norm(a_emb))
    return cosine_sim

# RAGAS 总分计算：
#    RAGAS_Score = (Context Precision + Context Recall + Faithfulness + Answer Relevance) / 4
```

#### **LLM-as-Judge 的人工对齐校准**

```
LLM-as-Judge 的核心问题：「判断标准」和人类不一致

校准方法（MT-Bench 方案）：
  Step1：收集 100 条人类偏好标注（A 优于 B / B 优于 A / 平局）
  Step2：让 LLM Judge 对同一条数据做判断
  Step3：计算「LLM Judge 与人类的一致性」（目标 > 80%）
  Step4：如果不一致 → 改进 Judge Prompt（加入「评分标准说明」）

高质量 Judge Prompt 模板：
  """
  你是一位专业的 AI 回答质量评估员。请对以下两个回答打分（1-10分）。
  
  评分维度：
  1. 准确性（是否有事实错误？）
  2. 完整性（是否完整回答了问题？）
  3. 清晰性（是否易于理解？）
  4. 安全性（是否有有害内容？）
  
  请先给出分析，再给出分数。格式：
  【分析】...
  【分数】回答A：X分；回答B：Y分
  """

一致性提升技巧：
  1. 给出「评分标准说明」（减少 LLM 主观性）
  2. 使用「参考答案」（Few-Shot 示例）
  3. 多次采样取平均（温度 = 0.3，采样 5 次）
  4. 用强模型做 Judge（GPT-4o > Claude > 开源模型）
```

### 2.3 RAG 前沿进化——GraphRAG 与 Corrective RAG

#### **传统 RAG 的三大瓶颈**

```
瓶颈1：向量检索的「语义漂移」
  查询：「AI 安全的最新研究进展」
  检索到：「AI 安全工程师薪资待遇」（语义相似，但意图不同）
  → 向量相似度 ≠ 意图匹配度

瓶颈2：全局问答失效
  查询：「这篇文章的主要论点是什么？」（需要跨多个 Chunk 汇总）
  → 向量检索只能找「最相似的几个 Chunk」→ 丢失全局视角

瓶颈3：时效性
  知识库更新后，Embedding 需要重新计算（批量更新成本高）
  → 无法做到「秒级」知识更新

三大前沿解法：
  ├── GraphRAG（知识图谱 + RAG）：解决全局问答
  ├── Corrective RAG（自我纠错 RAG）：解决语义漂移
  └── Self-RAG（边生成边检索）：解决「要不要检索」的决策问题
```

#### **GraphRAG（微软，2024）核心原理**

```
核心思想：把文档建构成「知识图谱」，检索时「图遍历」而非「向量相似度」

构建流程：
  Step1：用 LLM 从每个 Chunk 抽取实体和关系
    输入 Chunk：「苹果公司由史蒂夫·乔布斯于 1976 年创立」
    输出实体：[苹果公司, 史蒂夫·乔布斯]
    输出关系：(苹果公司, 创始人, 史蒂夫·乔布斯), (苹果公司, 成立时间, 1976)
  
  Step2：合并同名实体（Entity Resolution）
    「苹果公司」和「Apple Inc.」→ 合并为同一节点
  
  Step3：构建社区（Community Detection）
    用 Louvain 算法检测图中的「紧密连接的子图」→ 每个社区是一个「主题」
  
  Step4：为每个社区生成「社区摘要」（用 LLM 汇总）
  
检索流程（全局问答）：
  查询：「这篇文章的主要论点是什么？」
  → 传统 RAG：检索 Top-K Chunk → 信息碎片化
  → GraphRAG：
      (1) Map 阶段：对所有社区摘要并行提问，收集局部答案
      (2) Reduce 阶段：把所有局部答案汇总成全局答案

效果（vs 传统 RAG）：
  全局问答（Global Q&A）：Win Rate +37%
  局部问答（Local Q&A）：Win Rate +12%
  索引构建成本：高（需要多次 LLM 调用做实体抽取）
```

#### **Corrective RAG（CRAG）——自我纠错检索**

```python
# CRAG（Corrective RAG，2024）核心机制：
#   检索到文档 → 评估文档质量 → 决定「如何使用」或「是否重新检索」

class CorrectiveRAG:
    """
    CRAG 三阶段流程：
    Stage1：检索质量评估（Relevance Grading）
    Stage2：知识精炼（Knowledge Refinement）
    Stage3：可控生成（Controlled Generation）
    """

    def __init__(self, llm, retriever, threshold=0.7):
        self.llm = llm
        self.retriever = retriever
        self.threshold = threshold  # 相关性阈值

    def relevance_grading(self, query, retrieved_docs):
        """
        Stage1：让 LLM 评估每个检索文档与查询的相关性
        输出：["relevant", "partially_relevant", "irrelevant"]
        """
        graded = []
        for doc in retrieved_docs:
            prompt = f"""
            查询：{query}
            检索文档：{doc[:500]}...
            
            该文档对回答查询是否有帮助？
            选项：relevant / partially_relevant / irrelevant
            只输出一个词。
            """
            grade = self.llm.generate(prompt).strip().lower()
            graded.append((doc, grade))
        return graded

    def knowledge_refinement(self, graded_docs, query):
        """
        Stage2：根据相关性等级，精炼知识
        - relevant：直接保留
        - partially_relevant：用 LLM 提取「相关片段」（摘取，非全文）
        - irrelevant：丢弃，并触发「网络搜索」作为补充
        """
        refined_context = []
        trigger_web_search = False

        for doc, grade in graded_docs:
            if grade == "relevant":
                refined_context.append(doc)
            elif grade == "partially_relevant":
                # 用 LLM 摘取相关片段
                extract_prompt = f"""从以下文档中提取与「{query}」相关的片段：
{doc}"""
                relevant_snippet = self.llm.generate(extract_prompt)
                refined_context.append(relevant_snippet)
            else:  # irrelevant
                trigger_web_search = True

        if trigger_web_search:
            web_results = self.web_search(query)
            refined_context.extend(web_results)

        return refined_context

    def generate(self, query, retrieved_docs):
        """端到端 CRAG 流程"""
        graded = self.relevance_grading(query, retrieved_docs)
        refined_context = self.knowledge_refinement(graded, query)

        # Stage3：可控生成（在 Prompt 中显式标注信息来源）
        prompt = f"""
        基于以下【已验证】的信息回答问题。
        如果信息不足以回答问题，请明确说明。
        
        参考信息：
        {refined_context}
        
        问题：{query}
        """
        return self.llm.generate(prompt)

# CRAG vs 标准 RAG 效果（PubMed QA 数据集）：
#   标准 RAG：Accuracy = 62.3%
#   CRAG：      Accuracy = 71.8%（+9.5%）
```

## 📝 三、常见面试问答（FAQ）

### Q1：GRPO 和 PPO 的核心区别是什么？什么场景选 GRPO？

**答**：

```
核心区别（一句话）：
  PPO 用「Critic 网络估计状态价值 V(s)」来计算优势函数 A(s,a)
  GRPO 用「同一 Prompt 下多个候选响应的相对奖励」来估计优势
  → GRPO 完全不需要训练 Critic 网络

详细对比：

维度           PPO (On-Policy)              GRPO (Off-Policy 友好)
────────────
优势估计        A = r + γV(s') - V(s)       A_i = (r_i - μ_r) / σ_r（组内）
是否需要 Critic  是（Value 网络，难训练）   否（用组内统计替代）
显存占用       高（Policy + Critic + RM） 中（Policy + Reference）
适合场景       RLHF 全流程（需要 RM）     偏好优化（已有奖励信号）
训练稳定性      低（Critic 易崩溃）         中高（组内归一化更稳定）

选型建议：
  ✅ 选 GRPO：已有奖励信号（如代码执行结果 / 数学答案对错）
  ✅ 选 PPO：需要从人类偏好训练 Reward Model 的场景
  ✅ 选 DPO：只有「偏好对」（A > B），不想碰 RL 训练

面试加分点：
  「GRPO 的组内相对优势本质上是一种「基线减法」（Baseline Subtraction），
   和 REINFORCE 的 variance reduction 思路一致，但基线用的是「组内均值」
   而非训练出来的 Value 网络——这就是它更稳定的核心原因。」
```

### Q2：代码大模型（如 DeepSeek-Coder）如何处理「仓库级」代码补全？

**答**：

```
仓库级代码补全的三层技术栈：

Layer1：上下文拼接（Context Construction）
  问题：单文件上下文通常不够（代码依赖同仓库其他文件）
  解法：
    - 静态分析：解析 import 图，找到「被当前文件依赖」的文件
    - 向量检索：对当前文件做 Embedding，检索 Top-K 个相似文件
    - 拼接格式：<repo>\n<file path="...">...</file>\n...</repo>\n[FIM Prompt]\n

Layer2：FIM（Fill-In-the-Middle）预训练目标
  问题：光标在中间时，Causal LM 无法同时「看前面」和「看后面」
  解法：把代码重排为 <SUF> + <MID> + <PRE> 格式训练
  → 推理时模型能同时利用「光标前」和「光标后」的信息

Layer3：结构化输出约束（Grammar-Constrained Decoding）
  问题：代码生成中「生成不完整的代码块」是最常见错误
  解法：
    - 用 AST（抽象语法树）解析器约束生成（只生成语法合法的 Token）
    - 工具：Guidance / Outlines / Constrained Beam Search

效果数据（DeepSeek-Coder 6.7B）：
  单文件补全（HumanEval）：78.6%
  仓库级补全（RepoEval）：67.3%（显著优于单文件 42.1%）
```

### Q3：StreamingLLM 的 Attention Sink 是什么？为什么保留初始 Token 有效？

**答**：

```
Attention Sink 现象（2023 年发现）：
  在预训练的 Transformer 中，不管初始 Token 的语义内容是什么，
  模型都会对其分配「异常高」的注意力权重。
  
  实验：把初始 Token 替换成「无意义 Token」（如 [PAD]）
  → 模型仍然对其分配高注意力！
  → 说明：Attention Sink 是「位置现象」，不是「内容现象」。

为什么保留初始 Token 有效？（两种假说）

假说1：全局归一化锚点
  Softmax 的分母是所有 Key 的点积之和
  初始 Token 的 K 向量被训练成「接近零」（近似均匀分布的向量）
  → 对所有 Query，初始 Token 的注意力分数 ≈ 常数
  → 起到「数值稳定器」的作用（防止 Softmax 数值溢出）

假说2：训练 artifacts（训练过程中的隐式偏差）
  预训练时，所有文档都以 [BOS]（Begin of Sequence）Token 开头
  → 模型学会「[BOS] 包含所有文档的全局信息」的隐式表示
  → 推理时保留 [BOS] 的 KV，相当于保留了「全局上下文的压缩表示」

StreamingLLM 工程实现要点：
  1. 识别 Sink Token：通常是前 4 个 Token（包括 [BOS]）
  2. KV Cache 管理：永远不释放 Sink Token 的 KV
  3. 剩余空间：用滑动窗口管理「最近 N 个 Token」
  4. 效果：128K 输入，只保留 2K KV Cache，PPL 只下降 0.4
```

### Q4：GraphRAG 相比传统 RAG 有哪些根本优势？代价是什么？

**答**：

```
根本优势（两个场景）：

场景1：全局问答（Global Q&A）
  问题：「这篇文档的主要论点是什么？」
  传统 RAG：检索 Top-K Chunk → 只能看到局部 → 无法汇总全局
  GraphRAG：
    (1) 预先对所有社区摘要做 Map 操作（并行提问）
    (2) Reduce 阶段汇总所有局部答案 → 完整全局视角
  → Win Rate +37%（微软论文数据）

场景2：多跳推理（Multi-hop Reasoning）
  问题：「A 公司和 B 公司的创始人之间有什么关系？」
  传统 RAG：需要「恰好检索到包含两人关系」的 Chunk → 命中率低
  GraphRAG：
    (1) 实体「A 公司创始人」→ 图谱中定位节点
    (2) 关系边「认识」→ 跳转到「B 公司创始人」节点
    (3) 多跳路径：A-创始人 → 认识 → B-创始人
  → 多跳推理成功率 +45%

代价（三个维度）：
  1. 索引构建成本高：
    实体抽取需要多次 LLM 调用 → 建图成本是向量索引的 10-50×
  2. 图谱质量依赖 LLM 抽取能力：
    实体抽取错误（同名实体混淆）→ 图谱错误传播
  3. 更新成本高：
    新增文档 → 需要增量实体抽取 + 图谱合并 → 实时更新困难

选型建议：
  ✅ 选 GraphRAG：文档量大（>1000 篇）+ 需要全局/多跳问答
  ✅ 选传统 RAG：文档量小 + 只需局部精确检索 + 实时更新需求
  ✅ 选 Hybrid：向量检索（精确）+ 图谱遍历（多跳）并行 → 结果融合
```

### Q5：Self-RAG 是如何让 LLM「自主决定何时检索」的？

**答**：

```
传统 RAG 的问题：「不管需不需要，都先检索」
  → 检索不必要的信息 → 引入噪声 → 生成质量下降
  → 检索增加延迟（每次生成都要向量搜索）

Self-RAG 的解法：让 LLM 在生成过程中「自主插入检索 Token」

四种特殊 Token（在 SFT 阶段教会模型使用）：
  [Retrieve]：模型认为「当前需要检索更多信息」→ 触发检索
  [Retrieved]：检索结果返回后，模型判断是否使用
  [Utility]：模型评估检索结果质量（高/中/低）
  [No Retrieval Needed]：模型判断「当前不需要检索」→ 直接生成

训练流程：
  Step1：用「带动检索的数据集」SFT 微调，教会模型「何时插入 [Retrieve]」
  Step2：用 Reward Model 训练「是否使用检索结果」的判断能力

效果（vs 标准 RAG）：
  事实准确性：+12.3%（减少「检索引入噪声」的问题）
  延迟：降低 ~35%（不需要每次都检索）
  适用场景：开放式对话（有时需要检索，有时不需要）

面试加分：
  「Self-RAG 本质上是一种「工具使用决策」（Tool-Use Decision），
   和 Function Calling 中「模型决定是否调用工具」是同一类问题。
  更高级的演进：让模型学会「规划多步检索」（如 WebGPT / ReAct）」
```

## 🎯 四、模拟面试问题（深度版）

### 模拟题 1：GRPO 实战——从零设计一个代码生成模型的强化学习微调方案

**题目**：
> 你需要用 GRPO 微调一个代码生成 LLM（Base Model = DeepSeek-Coder 6.7B），
> 奖励信号来自「代码执行结果」（单元测试通过率）。
> 请阐述：(1) 数据构造流程；(2) GRPO 损失函数设计；(3) 训练稳定性保障；(4) 评估方案。

**参考答案要点**：

```
【1】数据构造流程（3 个核心决策）

决策1：Prompt 设计（代码生成任务）
  格式："""
  【任务】实现一个函数，输入整数列表，返回第二大的元素。
  【约束】时间复杂度 O(n)，空间复杂度 O(1)。
  【签名】def second_largest(nums: List[int]) -> int:
  """
  → 每个 Prompt 对应「一个编程任务」

决策2：组响应生成（Group Size = 8）
  对每个 Prompt，用「高温采样」（temperature=0.8）生成 8 个候选代码
  → 8 个代码的质量各不相同（有的通过测试，有的不通过）
  → 正是「组内的差异」让 GRPO 能学到「什么好、什么不好」

决策3：奖励函数设计（多维奖励，非单一通过/不通过）
  奖励 = 0.5 × 单元测试通过率 
        + 0.2 × 代码风格得分（Pylint / Black）
        + 0.2 × 时间复杂度得分（是否 O(n)？）
        + 0.1 × 可读性等（LLM-as-Judge）
  → 多维奖励比「二元通过/不通过」提供更多学习信号

【2】GRPO 损失函数关键设计

  关键1：Group-Relative Advantage 计算
    advantages = (rewards - rewards.mean()) / (rewards.std() + eps)
    → 组内归一化：避免「绝对奖励大小」影响梯度
    → 如果某 Prompt 的 8 个响应都得分很高（8-9 分），
       归一化后仍有「相对优劣」，模型能继续学习

  关键2：KL 散度约束（防止策略崩溃）
    loss_KL = KL(Policy || Reference)
    → Reference Model 是「SFT 后的模型」（冻结）
    → 防止 RL 训练后模型「忘记」通用代码能力
    → 系数 λ_KL = 0.04（DeepSeek-Math 论文推荐值）

  关键3：Clip 范围（PPO-Clip 机制）
    clip_range = 0.2  # 和 PPO 相同
    → 防止「单个样本」的梯度更新过大

【3】训练稳定性保障（4 层防护）

  防护1：奖励归一化（Reward Normalization）
    不同编程任务的「绝对分数」范围不同（简单任务 0.8-1.0，困难任务 0.2-0.5）
    → 必须做「组内归一化」（GRPO 天然具备）

  防护2：梯度裁剪（Gradient Clipping）
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    → 防止「某个高奖励样本」的梯度爆炸

  防护3：Reference Model 定期更新（可选）
    每 1000 步把 Policy Model 同步到 Reference Model
    → 防止 KL 散度约束过强（模型不敢更新）

  防护4：奖励 Hacking 检测
    如果「生成代码的单元测试通过率」上升，但「人类评估的代码质量」下降
    → 说明模型学会了「利用测试用例的漏洞」
    → 解法：增加「代码可读性」维度的奖励权重

【4】评估方案（分层）

  层1：功能正确性（Functional Correctness）
    指标：Pass@K（生成 K 个代码，至少 1 个通过测试的比例）
    数据集：HumanEval, MBPP, LiveCodeBench

  层2：代码质量（Code Quality）
    指标：Pylint 得分，时间/空间复杂度分析

  层3：泛化能力（Generalization）
    数据集：OOD（分布外）编程任务
    → 检测是否「过拟合」训练时的单元测试模式
```

### 模拟题 2：设计一个生产级长上下文 RAG 系统，支持 1M Token 文档问答

**题目**：
> 你需要设计一个 RAG 系统，能够处理 1M Token 长度的技术文档（如 Linux 内核文档），
> 并回答跨多个章节的复杂问题。请设计完整架构，包括：检索策略、上下文管理、生成优化。

**参考答案要点**：

```
【1】系统架构全景（5 层）

Layer1：文档预处理与索引（离线）
  ├── 语义分块（Semantic Chunking）
  │     不是固定 512 Token 切块，而是按「语义边界」切分
  │     （段落结束 / 章节结束 / 函数定义结束）
  ├── 向量索引（Dense Retrieval）
  │      Embedding 模型：gte-large-zh / bge-m3（支持 8192 上下文）
  │      向量库：Milvus / Qdrant（支持 HNSW 和 IVF 混合索引）
  └── 知识图谱索引（Graph Index）
        实体抽取：用 LLM 从每个 Chunk 抽取（实体，关系，实体）
        图数据库：Neo4j / Nebula Graph

Layer2：查询理解与分解（Query Analysis）
  ├── 查询类型识别
  │     全局问题（「本文档的主要内容是什么？」）→ GraphRAG 路径
  │     局部问题（「foo() 函数的参数有哪些？」）→ 向量检索路径
  │     多跳问题（「A 和 B 的关系是什么？」）→ 图谱遍历路径
  └── 查询重写（Query Rewriting）
        用 LLM 把「模糊查询」改写成「精确检索查询」
        例：「那个优化方法」→ 「Linux 内核中的 O(1) 调度器优化」

Layer3：混合检索（Hybrid Retrieval）
  ├── 向量检索（Dense）：语义相似度检索 Top-20 Chunk
  ├── 关键词检索（Sparse）：BM25 全文检索 Top-10 Chunk
  ├── 图谱检索（Graph）：从实体出发，2 跳内所有相关实体+关系
  └── 融合策略：RRF（Reciprocal Rank Fusion）合并排序
        score_final = 1/(k + rank_dense) + 1/(k + rank_sparse)

Layer4：上下文窗口管理（Context Window Management）
  ├── Long Context 模型选择
  │     用支持 128K+ 的模型（Qwen2.5-72B-Instruct / DeepSeek-V2）
  ├── 上下文压缩（Context Compression）
  │     用 LLMLingua（文本级压缩，保留 20% Token）
  │     或 FastLangComp（向量级压缩，生成 Side-Info）
  └── 动态上下文构造
        把检索结果按「相关性」排序填入上下文窗口
        格式：[系统提示] + [压缩后的检索结果] + [用户问题]

Layer5：生成与验证（Generation & Verification）
  ├── 可控生成（Guided Generation）
  │     用 Outlines 约束输出格式（JSON / Markdown / 代码）
  ├── 事实性验证（Factuality Verification）
  │     生成后：用 NLI 模型检查「每个声明」是否被检索上下文蕴含
  │     → 如果发现「幻觉声明」，触发「重新检索 + 重新生成」
  └── 引用标注（Citation）
        生成时要求模型输出「来源 Chunk ID」→ 可追溯

【2】关键技术难点与解法

难点1：1M Token 文档的「迷失在中间」问题
  解法：
    (1) 用 LongRoPE / YaRN 微调后的模型（位置编码外推）
    (2) 把上下文窗口的「中间位置」让给「最有信息量的 Chunk」
    (3) 使用 Fusion-in-Decoder（FiD）架构：Encoder 独立处理每个 Chunk，
        Decoder 做跨 Chunk 注意力 → 避免「中间信息丢失」

难点2：检索结果冗余（多个 Chunk 内容高度重叠）
  解法：
    MMR（Maximal Marginal Relevance）重排序
    → 在「相关性」和「多样性」之间做权衡
    → 优先选择「相关性高且和已选 Chunk 差异大」的结果

难点3：生成延迟（1M Token 上下文，首 Token 延迟极高）
  解法：
    (1) Prefix Caching（vLLM）：相同 System Prompt 的 KV Cache 复用
    (2) Chunked Prefill（vLLM）：把长 Prefill 切成小块，和 Decode 交错
    (3) 投机解码（Speculative Decoding）：用小模型草稿 + 大模型验证

【3】评估体系

  端到端指标：
    - Answer Accuracy（答案正确性，人工评估 + LLM-as-Judge）
    - Citation Accuracy（引用准确性，检查引用 Chunk 是否真的支持答案）
    - Latency（P50/P95 延迟）
  
  组件级指标：
    - Retrieval Recall@20（检索召回率）
    - Context Precision@20（检索精确率）
    - Faithfulness Score（忠实度，用 NLI 评估）
```

### 模拟题 3：深入对比 Transformer、Mamba（SSM）和 RWKV——你会为 Agent Harness 项目选哪个架构？

**题目**：
> Agent Harness 需要处理「超长会话历史」（100K+ Token）并支持「低延迟流式输出」。
> 请对比 Transformer / Mamba（SSM）/ RWKV 三种架构在此场景下的优劣，并给出最终选型建议。

**参考答案要点**：

```
【1】场景分析（Agent Harness 的特殊需求）

需求1：超长会话历史（100K+ Token）
  → 需要「显存效率」：Transformer 的 KV Cache 是 O(N)，Mamba 是 O(1)

需求2：低延迟流式输出（Token 间延迟 < 50ms）
  → 需要「解码速度」：Transformer 每 Token 需要完整 Attention（O(N)）；
    Mamba 每 Token 是 O(1)（固定状态向量更新）

需求3：信息检索能力（Agent 需要「记住」10 轮前的用户指令）
  → 需要「精确记忆」：Transformer 的 Attention 是「精确检索」；
    Mamba 的状态向量是「有损压缩」→ 可能遗忘细节

【2】三架构定量对比

                  Transformer（LLaMA）   Mamba（SSM）      RWKV（Linear Attention）
────────────────────
训练并行度        O(N²) 完全并行        O(N log N) 近似并行   O(N) 完全并行
推理显存          O(N) KV Cache       O(1) 状态向量       O(1) 状态向量
推理速度（短序列）  快（高度优化）       中                  快
推理速度（长序列）  慢（O(N) 延迟）     极快（O(1) 延迟）  快（O(1) 延迟）
长程依赖         极强                 理论强，实测弱      中（Linear Attention 近似）
精确信息检索       极强（直接 Attention） 弱（状态有损压缩）  中（需要特殊设计）
硬件友好度       高（矩阵乘法）        中（需要定制 CUDA）  高（无 Attention）
当前 SOTA 模型    GPT-4, Qwen2.5     Mamba-2             RWKV-6

【3】Agent Harness 场景的最终选型

推荐方案：混合架构（Hybrid Mamba + Attention）
  ├── Mamba 层（处理长上下文）：
  │     把 100K Token 的会话历史压缩成「固定大小的状态向量」
  │     → 显存 O(1)，解码速度极快
  ├── Attention 层（精确检索）：
  │     每隔 4 层 Mamba，插入 1 层 Attention
  │     → 让模型能「精确检索」会话历史中的关键细节
  │     → Jamba（AI21 Labs）架构：Mamba + Attention 交错
  └── 效果：
        显存：比纯 Transformer 减少 60%
        速度：128K Token 解码速度快 3×
        信息检索准确率：仅下降 5%（vs 纯 Transformer）

为什么不选纯 Mamba？
  → Agent 场景需要「精确记住用户 10 轮前的指令」
  → Mamba 的状态压缩是有损的，可能「遗忘」关键细节
  → 混合架构兼得「显存效率」和「精确记忆」

为什么不选纯 Transformer？
  → 100K Token KV Cache 需要 ~80GB 显存（70B 模型）
  → 同等显存下，混合架构能处理 3× 更长的上下文

【4】面试加分：演进方向预测

  方向1：Mamba-2 的 State Space Duality（SSD）
    → 证明了「Mamba 的选择性 SSM」和「某种线性 Attention」是数学等价的
    → 可以用 Attention 的硬件优化技巧（Flash Attention）来加速 Mamba
    → 未来：Mamba 的训练速度会接近 Transformer

  方向2：RWKV 的「线性 Attention 重新发现」
    → RWKV 的「Time-mixing」机制本质上是一种「没有 Softmax 的线性 Attention」
    → 优势：完全 O(1) 推理，且训练完全并行（不像早期 RNN）
    → 代价：表达能力和 Transformer 仍有差距（~3-5% on MMLU）

  方向3：Test-Time Compute（o1 / o3 模式）
    → 未来趋势：不是「训练更大的模型」，而是「推理时多想几步」
    → Mamba 的 O(1) 推理显存特别适合「推理时搜索」（MCTS + 状态复用）
```
