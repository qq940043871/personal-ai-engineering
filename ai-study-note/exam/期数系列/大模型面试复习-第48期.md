**亮点 A：统一协议接入层（OpenAI-compatible，协议归一，含代码）**

对外只暴露一套 API 形状，内部把各厂商差异吞掉。业务方只认"逻辑模型名"，网关决定背后物理模型。

```python
# 以 OpenAI Chat Completions 为事实标准，内部归一为统一 Request/Response
from dataclasses import dataclass
from enum import Enum

class Provider(str, Enum):
    SELF_VLLM = "vllm"; OPENAI = "openai"
    CLAUDE = "claude"; QWEN = "qwen"; WENXIN = "wenxin"

@dataclass
class UnifiedRequest:
    model: str            # 逻辑模型名，如 "router-pro" / "gw-7b"
    messages: list        # 统一 messages 格式
    temperature: float = 0.7
    max_tokens: int = 1024
    stream: bool = False
    user: str = None      # 租户/用户标识，用于配额与隔离
    route_hint: str = None  # 业务可给路由偏好: "quality"/"cost"/"latency"

# 各厂商 SDK 返回结构不同 -> 适配为统一 Response
def adapt(provider: Provider, raw: dict) -> dict:
    if provider == Provider.OPENAI:
        return raw  # 已是标准
    if provider == Provider.CLAUDE:
        # 把 Anthropic 的 content[].text 折回 choices[].message.content
        return {"choices": [{"message": {"role": "assistant",
                "content": "".join(c["text"] for c in raw["content"])}}],
                "usage": raw["usage"]}
    # qwen / wenxin 类似归一 ...
    return raw
```

> 面试亮点：**逻辑模型名 vs 物理模型名解耦**——业务方只认 `router-pro`，网关决定背后路由到 70B 还是 7B；灰度 / 回滚只改路由表，业务零改代码。这是后面"智能路由"能成立的前提。

**亮点 B：智能路由（质量 / 成本 / 延迟感知，含代码 + 公式）—— 本期最核心**

问题：100+ 模型里很多简单 query 用 7B 就够，盲目上 70B 浪费 ~10× 成本；但用错小模型会掉质量。

RouteLLM 思路：用"大模型当评委"构造偏好数据，训练一个轻量路由器（用 embeddings 做特征），预测"小模型回答是否可被接受"。

```python
import numpy as np
# ---------- 1) 偏好数据构造：用强模型(A)给弱模型(B)打分 ----------
# 对一批 query，分别让 A、B 回答，再让 Judge(更强) 判断 B 是否"不逊于"A
def build_preference(q, ans_a, ans_b, judge):
    # judge 返回 1 表示 B 可接受(不逊于 A)，0 表示明显更差
    return 1 if judge(f"判断B是否不逊于A。Query:{q}\nA:{ans_a}\nB:{ans_b}") == "yes" else 0

# ---------- 2) 路由器：用 embedding 特征 + sigmoid 预测可接受概率 ----------
class Router:
    def __init__(self, w, b): self.w = w; self.b = b   # 可训练参数(embedding 维度)
    def accept_prob(self, q_emb):
        return 1 / (1 + np.exp(-(self.w @ q_emb + self.b)))   # sigmoid
    def route(self, q_emb, cost_budget):
        p = self.accept_prob(q_emb)
        # p 高且成本预算紧 -> 走小模型；否则走大模型
        return "small" if p >= cost_budget else "big"

# 训练(逻辑回归)：label=可接受(1)/不可接受(0)
def train(X, y):  # X: query embeddings, y: 偏好 label
    from sklearn.linear_model import LogisticRegression
    return LogisticRegression().fit(X, y)
```

路由决策的数学本质（成本-质量 Pareto 约束优化）：

$$C(q) = p_{\text{small}}(q)\,C_{\text{small}} + \big(1-p_{\text{small}}(q)\big)\,C_{\text{big}}$$
$$Q(q) \approx p_{\text{small}}(q)\,Q_{\text{small}} + \big(1-p_{\text{small}}(q)\big)\,Q_{\text{big}}$$

路由目标：在 $Q(q)\ge Q_{\min}$ 约束下最小化 $C(q)$。等价于对每个 query 求"质量门限下的最便宜模型"。

> 面试亮点：路由不是"随机 / 轮询"，而是**把路由建模成受约束的优化问题**；偏好数据用 LLM-as-Judge 自动构造（无需人工标注），路由器本身是毫秒级推理的小模型（embedding + sigmoid），不引入额外延迟。

**亮点 C：多级缓存（Exact + Semantic，含代码 + 命中率公式）**

```python
import hashlib, time

class Cache:
    def __init__(self):
        self.exact = {}        # key -> (value, ts, ttl)
        self.sem_index = []    # (emb, value, ts)

    def exact_key(self, req):  # 归一化后 hash；视场景忽略 temperature 等不影响结果的字段
        s = f"{req.model}|{req.messages}|{req.max_tokens}"
        return hashlib.md5(s.encode()).hexdigest()

    def get_exact(self, req):
        k = self.exact_key(req); e = self.exact.get(k)
        if e and time.time() - e[1] < e[2]: return e[0]
        return None

    def get_semantic(self, req, q_emb, tau=0.92):
        best, best_s = None, -1
        for emb, val, ts in self.sem_index:
            s = cos(q_emb, emb)
            if s > best_s: best_s, best = s, val
        return best if best_s >= tau else None   # 语义相似度超阈值才命中
```

语义缓存命中率：

$$\text{HitRate} = \mathbb{P}\big(\exists\, q' : \text{sim}(q,q') \ge \tau \;\big|\; q \text{ 是真实流量}\big)$$

阈值 $\tau$ 的权衡：高 $\tau$（如 0.97）误命中低但命中率低；低 $\tau$（0.85）命中率高但易"答非所问"。生产常用 **0.90–0.93**，并对"高风险 / 强时效"query 强制跳过缓存。

**亮点 D：成本治理与配额（含公式 + 代码）**

```python
# 单位请求成本 = Σ 各段 token 数 × 单价
def request_cost(usage, price_table):
    return (usage["prompt_tokens"]   * price_table["in"]
          + usage["completion_tokens"] * price_table["out"])

# 租户月度预算熔断
def check_budget(tenant, cost, budgets):
    budgets[tenant]["used"] += cost
    if budgets[tenant]["used"] > budgets[tenant]["cap"]:
        raise BudgetExceeded(tenant)
```

成本模型（月度）：

$$C_{\text{month}} = \sum_{m\in \text{models}} \big( N_m^{\text{in}}\cdot p_m^{\text{in}} + N_m^{\text{out}}\cdot p_m^{\text{out}} \big)$$

其中 $N$ 为 token 数，$p$ 为单价。路由 + 缓存让 $N_{\text{big}}^{\text{in/out}}$ 大幅下降 → 整体 **-71%**。

## 🔧 二、技术难点（根因 + 方案 + 代码 / 公式）

**① 路由决策延迟与一致性（幂等）—— 同请求必须落到同模型**
- **根因**：网关是同步链路，路由若多一次 LLM 调用 = 多几百 ms；且重试时若路由结果变，会造成"半路换模型"的诡异输出。
- **方案**：路由器用 embedding + sigmoid（<5ms），**非 LLM**；请求带 `route_hint` + 一致性哈希（同 user+query hash → 固定模型），重试复用同一路由结果；路由结论随请求上下文透传。

```python
import hashlib
def consistent_route(user, query, model_map):
    h = int(hashlib.md5(f"{user}:{query}".encode()).hexdigest(), 16)
    return model_map[h % len(model_map)]   # 同 user+query 永远同模型
```

**② 多模型输出不一致（同 prompt 不同模型结果漂移）**
- **根因**：不同厂商训练 / 后训练不同，temperature 采样也放大差异；业务方若依赖"某模型风格"，换模型会行为漂移。
- **方案**：路由表按"**能力画像**"分组（不是按厂商）；输出归一化层（统一 JSON Schema 校验 + 统一错误码）；对一致性敏感业务（如金融话术）锁定强模型 + 评估兜底；用户可选"钉死模型"。

**③ 语义缓存脏命中 / 失效**
- **根因**：相似 query 但语义不同（"翻译英→中" vs "翻译中→英"），或答案随时效变（股价 / 天气）。
- **方案**：缓存 key 编码意图与方向；对强时效 / 高风险 query 设 TTL=0 或跳过；命中后用"答案新鲜度"二次校验（如股票类缓存只存 30s）。

**④ 限流与配额公平性（多租户 burst）**
- **根因**：某租户突发把网关打满，挤掉其他租户；VIP 与免费用户要不同 SLA。
- **方案**：分层令牌桶（租户级 + 全局级）+ 优先级队列；VIP 走高优桶。

```python
import time
class TokenBucket:
    def __init__(self, rate, cap): self.rate=rate; self.cap=cap; self.tok=cap; self.ts=time.time()
    def allow(self, n=1):
        now=time.time(); self.tok=min(self.cap, self.tok+(now-self.ts)*self.rate); self.ts=now
        if self.tok>=n: self.tok-=n; return True
        return False   # 触发 429 + 重试退避(Retry-After)
```

**⑤ 厂商故障与优雅降级（fallback 链 + 熔断）**
- **根因**：三方 API 偶发 5xx / 限流，直连会雪崩。
- **方案**：每厂商健康探测 + 熔断（错误率超阈值切走）；fallback 链（主→备→更小模型 + 缓存兜底）；降级时返回部分结果与降级标记。

```python
def call_with_fallback(req, chain, cache):
    for provider in chain:
        try:
            if healthy(provider): return invoke(provider, req)
        except (Timeout, Upstream5xx):
            record_fail(provider); continue
    return cache.get_exact(req) or (_ for _ in ()).throw(Degraded("all providers down"))
```

**⑥ 安全合规透传（PII 脱敏 / 审计不落敏感）**
- **根因**：网关看到全部明文，日志若落库即合规风险。
- **方案**：入站 PII 检测脱敏后再转发（可选 Tokenization 还原）；审计日志只存 hash + 元数据，不存明文；输出合规扫描（接第25期安全系统）。

## ❓ 三、常见问答（深度）

**Q1 智能路由为什么比 round-robin / 规则路由好？偏好数据怎么来？路由器怎么训练？**
A：round-robin 不考虑 query 难度，简单题也上大模型浪费；规则（关键词 / 长度）粗糙易错。RouteLLM 用"强模型 A 答 + 弱模型 B 答 + 更强 Judge 判 B 是否可接受"自动造偏好数据(0/1)，训练 embedding + sigmoid 路由器，预测"小模型可接受概率" $p$，在质量门限下选最便宜模型。本质是**受约束优化**：$\min C(q)\;\text{s.t.}\;Q\ge Q_{\min}$。偏好数据用 LLM-as-Judge 造，无需人工标注。

**Q2 语义缓存命中率怎么量化？怎么避免脏命中？阈值怎么定？**
A：$\text{HitRate}=\mathbb{P}(\exists q':\text{sim}(q,q')\ge\tau)$。避免脏命中：① 缓存 key 编码意图 / 方向（翻译方向、任务类型）；② 强时效 / 高风险 query 跳过缓存或 TTL 极短；③ 命中后做"新鲜度 / 相关性"二次校验。$\tau$ 常用 0.90–0.93，越高越准但命中越低，需按业务调。

**Q3 网关如何保证同请求同模型（幂等）？**
A：路由器不用 LLM（用 embedding + sigmoid <5ms）；请求带 `route_hint`；用**一致性哈希**(user+query)→固定模型，重试复用同一路由结果；路由结论随上下文透传，避免重试换模型。

**Q4 多模型输出不一致怎么治理？**
A：① 路由按"能力画像"分组而非厂商；② 输出归一化（统一 JSON Schema + 错误码）；③ 一致性敏感业务锁强模型 + 评估兜底；④ 用户可"钉死模型"。核心是"**网关对上承诺稳定语义，对下屏蔽厂商差异**"。

**Q5 限流算法怎么选（令牌桶 vs 漏桶 vs 滑动窗口）？多租户配额？**
A：令牌桶允许突发（适合 LLM 偶发 burst），漏桶平滑恒定（保护下游），滑动窗口最精确但贵。网关用"**租户令牌桶 + 全局令牌桶**"双层 + 优先级队列；VIP 走高优。超桶返回 429 + Retry-After 退避。

**Q6 网关层怎么做成本治理？单位成本怎么压？**
A：计量每个租户 / 模型 token（in/out × 单价）→ showback / chargeback；路由把简单题导到小模型（-71% 主要来自这里）；缓存拦截重复 query；预算熔断 + 成本看板。$C_{\text{month}}=\sum(N_{\text{in}}\cdot p_{\text{in}}+N_{\text{out}}\cdot p_{\text{out}})$，杠杆在降低 $N_{\text{big}}$。

## 🎯 四、模拟面试（3 题 + 参考答案要点）

**题1：设计支撑千万 QPS、100+ 模型、跨云厂商的 LLM 网关端到端架构**
- **接入层**：OpenAI-compatible 单一入口，逻辑名 / 物理名解耦，协议归一适配各厂商
- **路由层**：embedding + sigmoid 路由器（<5ms），质量门限约束下选最便宜模型；一致性哈希保证幂等
- **缓存层**：exact（query hash）+ semantic（emb + τ），命中率 41%，强时效跳过
- **安全层**：PII 脱敏、注入检测、输出合规、审计只存 hash
- **容灾层**：厂商健康探测 + 熔断 + fallback 链，降级返回部分结果 + 降级标记
- **治理层**：双层令牌桶限流、预算熔断、成本 showback、A/B、可观测（接第39期 LLMOps）
- **性能**：网关自身 P99 < 8ms，无状态水平扩展，配置中心热更；用一致性哈希做亲和，避免路由抖动

**题2：故障复盘——某核心业务 P99 从 800ms 飙到 12s、成本 ×5 的 30 分钟止血**
- **快速止血**：① 发现某厂商突发限流 429（健康探测触发熔断，自动切 fallback 链）；② 但 fallback 全切大模型导致成本 ×5、延迟飙 → 临时把路由预算门限调紧、优先小模型 + 缓存；③ 缓存击穿（热点 query 未命中）→ 开启 exact cache 兜底；④ 限流误伤：临时扩租户令牌桶
- **根因**：路由偏好数据陈旧（小模型质量漂移导致 router 误判 → 不敢用小模型）+ 主厂商限流 + 缓存 TTL 配错
- **修复**：重训 router（新偏好数据）、修正缓存 TTL、加主厂商限流预检；上线"路由质量漂移监控"（小模型接受率周环比告警）

**题3：用 7B 小模型 + 路由把 70B 调用量降 80%，质量损失 <2% 的方案**
- **路由**：RouteLLM 式偏好数据（Judge 判 7B 是否可接受）+ embedding + sigmoid router；$p\ge$ 门限走 7B
- **门限调优**：用 MT-Bench / 业务集离线扫 $p$ 阈值，找"质量损失 <2% 时最大 7B 占比"
- **兜底**：7B 不可接受时自动升级 70B；缓存拦截重复
- **评估闭环**：线上采样评测 7B 质量，漂移即重训 router
- **预期**：简单题（问候 / 抽取 / 分类）占比高 → 7B 承接 80%+，质量损失可控 <2%，成本 -71%
