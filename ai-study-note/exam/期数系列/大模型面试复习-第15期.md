### 2.1 Scaling Laws——理解大模型的「物理定律」

#### **Kaplan Scaling Laws（OpenAI，2020）**

```
核心论文：Kaplan et al., "Scaling Laws for Neural Language Models"

五大核心结论：

┌─────────────────────────────────────────────────────────────────┐
│ 结论1：模型性能与模型大小、数据集大小、计算量呈幂律关系            │
│                                                                   │
│   L(N, D, C) = a·N^(-α) + b·D^(-β) + c·C^(-γ) + L_∞             │
│                                                                   │
│   其中 L = 测试Loss,  N = 参数量,  D = Token数,  C = 计算量       │
│   α ≈ 0.076, β ≈ 0.095, γ ≈ 0.050                                │
│                                                                   │
│   ⚠️ 解读：Loss 的对数 与 规模的对数 呈线性关系                     │
│   每次将参数量翻倍，Loss 下降约 5%                                 │
│   每次将数据量翻倍，Loss 下降约 6.4%                               │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 结论2：模型大小比数据量更重要（Kaplan的观点——后被Chinchilla修正）  │
│                                                                   │
│   Kaplan: 给定固定计算预算 C，最优分配是：                         │
│     N_opt ∝ C^0.73   （模型大小增长更快）                         │
│     D_opt ∝ C^0.27   （数据量增长更慢）                           │
│                                                                   │
│   → 这导致了很多"大模型小吃数据"的现象（如 GPT-3 175B 只训了 300B  │
│     tokens）                                                      │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 结论3：大模型更「数据高效」                                       │
│                                                                   │
│   大模型比小模型在相同数据量下收敛更快（以训练步数为单位）           │
│   但以计算量为单位，小模型更高效                                   │
│                                                                   │
│   例：训练 10B 模型到 Loss 1.5 需要 100B tokens                   │
│        训练 1B 模型到 Loss 1.5 需要 200B tokens（但更便宜）       │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 结论4：Batch Size 也存在幂律关系                                  │
│                                                                   │
│   L(B) = L_∞ + k·B^(-δ)                                          │
│   δ ≈ 0.2~0.3                                                    │
│   临界 Batch Size 随训练 loss 降低而增大                          │
│                                                                   │
│   → 训练初期可以用大 Batch Size 加速                               │
│   → 训练后期需要小 Batch Size 充分利用数据                         │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 结论5：架构细节（宽度/深度）在很大范围内不影响 Scaling            │
│                                                                   │
│   Transformer 的深度和宽度在宽广范围内按等比缩放时，               │
│   Scaling Law 主要取决于总参数量 N，而非具体架构                   │
│   （只要大致遵循 depth×width² = const 的缩放模式）                │
└─────────────────────────────────────────────────────────────────┘
```

#### **Chinchilla Scaling Laws（DeepMind，2022）——修正Kaplan**

```
核心论文：Hoffmann et al., "Training Compute-Optimal Large Language Models"

🎯 核心修正：Kaplan低估了数据的重要性！

┌─────────────────────────────────────────────────────────────────┐
│ Chinchilla 最优 Scaling Law：                                    │
│                                                                   │
│   N_opt(C) ∝ C^0.50                                              │
│   D_opt(C) ∝ C^0.50                                              │
│                                                                   │
│   模型大小和数据量应该等比增长！                                   │
│   给定计算预算 C，最优策略是：                                      │
│     tokens ≈ 20 × 参数量                                         │
│                                                                   │
│   例：训练一个 70B 模型，需要 1.4T tokens                          │
│        训练一个 7B 模型，需要 140B tokens                          │
└─────────────────────────────────────────────────────────────────┘

具体案例：Chinchilla 实验
  · 模型大小：70B 参数
  · 训练数据：1.4T tokens（20× 参数量）
  · 结果：在相同计算预算下，性能大幅超越 Gopher 280B
  · 训练数据只有 Gopher 的 4.7 倍，但性能更好
  → 证明了"更多数据 + 更小模型"比"更少数据 + 更大模型"更高效

为什么 Kaplan 错了？
  1. Kaplan 在拟合时没有学习率衰减到最后 → 低估了训练的最终效果
  2. Kaplan 的分析范围受限 → 没有充分探索「大模型+小数据」的区间
  3. Chinchilla 做了更系统的搜索（400+ 模型配置 × 广泛的 C 范围）

面试时的关键洞察：
  "Kaplan 说模型比数据重要，Chinchilla 说同等重要。深层原因是：
   Kaplan 没有充分训练（early stopping），所以大模型看起来更优；
   Chinchilla 训练到收敛，发现数据量才是决定性能的关键。
   这个教训说明——'有没有喂饱模型' 和 '模型多大' 一样重要。"
```

#### **Scaling Laws 的实践指导意义**

```
┌─────────────────────────────────────────────────────────────────┐
│ 如果给你 10^24 FLOPs（≈ 1000 个 A100-80GB 跑 1 个月）            │
│                                                                   │
│ 按 Chinchilla 最优方案：                                         │
│  模型大小：约 20B 参数                                            │
│  数据量：约 400B tokens                                           │
│                                                                   │
│ 按 Kaplan 方案（早已过时，仅作对比）：                              │
│  模型大小：约 60B 参数                                            │
│  数据量：约 200B tokens                                           │
│                                                                   │
│ 现实中的权衡：                                                    │
│  · 更大的模型 → 推理成本更高（部署限制）                          │
│  · 更多数据 → 数据工程成本更高（但通常是划算的）                   │
│  · 大多数公司选择「稍微偏大模型 + 稍微偏少数据」                   │
│    因为推理时可以使用量化/蒸馏降低部署成本                         │
└─────────────────────────────────────────────────────────────────┘

超越 Chinchilla：
  · LLaMA 的发现（Meta）：用比 Chinchilla 更多的数据（2T → 1.4T for 7B）
    → 小模型 + 超多数据 = 惊人的性能
  · DeepSeek 的做法：高质量数据 + MoE 架构 → 绕过 Scaling Law 约束
  · 数据质量 > 数据数量的说法越来越被接受
```

### 2.2 分布式训练——「3D并行」深度解析

```
┌─────────────────────────────────────────────────────────────────┐
│ 分布式训练的三种并行策略（3D Parallelism）                         │
│                                                                   │
│   ┌──────────────────┐                                            │
│   │  Data Parallelism │  DP/FSDP                                 │
│   │  (数据并行)        │  每个GPU有完整模型副本，处理不同batch      │
│   │                    │  AllReduce梯度                            │
│   │  批数据→GPU0→梯度  │                                           │
│   │  批数据→GPU1→梯度─→AllReduce→更新                             │
│   │  批数据→GPU2→梯度  │                                           │
│   │  批数据→GPU3→梯度  │                                           │
│   └──────────────────┘                                            │
│                                                                   │
│   ┌──────────────────┐                                            │
│   │Tensor Parallelism │  TP (如Megatron)                          │
│   │ (张量并行)         │  单层权重切分到多个GPU，同时计算           │
│   │                    │                                           │
│   │  权重矩阵W → 切分为 [W₁|W₂|W₃|W₄] → 4个GPU同时计算            │
│   │  Y₁ = X·W₁  Y₂ = X·W₂  Y₃ = X·W₃  Y₄ = X·W₄                 │
│   │  → AllGather → Y = [Y₁,Y₂,Y₃,Y₄]                             │
│   │                                                               │
│   │  通信模式：f(AllReduce) 或 g(AllReduce)                        │
│   │  每次前向/反向都需要通信 → 需要 NVLink/NVSwitch 高速互联      │
│   └──────────────────┘                                            │
│                                                                   │
│   ┌──────────────────┐                                            │
│   │Pipeline Parallelism│ PP (如GPipe/PipeDream)                   │
│   │ (流水线并行)       │  不同层放到不同GPU，batch微分成micro-batch │
│   │                    │                                           │
│   │  GPU0: Layer 1-8  ──→ GPU1: Layer 9-16 ──→ GPU2: Layer 17-24 │
│   │  [MicroBatch1]       [MicroBatch1]       [MicroBatch1]        │
│   │  [MicroBatch2]       [MicroBatch2]       [MicroBatch2]        │
│   │  ...                                                          │
│   │                                                               │
│   │  通信：只传激活值和梯度（层间） → 通信量小                     │
│   │  Bubble问题：填充和排空阶段GPU空闲                             │
│   │  Bubble Size = (PP_size - 1) / micro_batches                 │
│   └──────────────────┘                                            │
└─────────────────────────────────────────────────────────────────┘
```

#### **3D并行的协同——千亿参数模型如何训练？**

```python
"""
训练一个 175B 参数模型（GPT-3 规模）的 3D 并行方案

假设：
  · 模型 175B 参数 → FP16 约 350GB
  · 优化器状态（Adam）+ 梯度 → 约 1.4TB
  · 总计需要约 1.75TB 显存
  · 单卡 A100-80GB → 需要至少 22 张卡（纯显存计算）
  · 实际需要更多（激活值/临时变量）

3D并行方案：
  TP = 8（张量并行，切分到 NVSwitch 域内 8 张卡）
  PP = 4（流水线并行，分 4 个 stage）
  DP = 64（数据并行，64 组完整模型副本）
  总共：8 × 4 × 64 = 2048 张 GPU

显存分析（单张 GPU）：
  · 模型参数：350GB / (TP × PP) = 350 / 32 ≈ 11GB
  · 优化器状态：1.4TB / (TP × PP × DP) ... 等等，DP 不切分优化器
  · 实际上 FSDP/ZeRO 会在 DP 维度切分优化器状态

更实际的方案：ZeRO-3 + TP + PP
  · ZeRO-3 在 DP 维度切分参数/梯度/优化器状态
  · TP=2~4（NVLink域内）
  · PP=4~8（跨节点）
  
典型配置（Meta LLaMA 65B 训练）：
  · 2048 × A100-80GB
  · FSDP (ZeRO-3) + Tensor Parallelism
  · 序列长度 2048，Global Batch Size 4M tokens
  · 训练时间：约 21 天
"""

# ========================================
# 3D并行通信量分析（面试重点）
# ========================================

"""
通信瓶颈分析（按通信量排序）：

1. Data Parallelism (AllReduce梯度)
   通信量：2(N-1)/N × |model|  per step
   例：2 × 174GB ≈ 348GB per step (64卡时)
   瓶颈：卡间带宽（PCIe/NVLink/IB）

2. Tensor Parallelism (每层 f 和 g 操作)
   通信量：每次前向/反向 2 × batch_size × hidden_size × sequence_length
   例：8 × 2048 × 12288 × 2048 × 2 ≈ 800MB per layer per step
   32层 → 约 25GB per step (但可以pipeline化)
   瓶颈：NVLink 带宽（900GB/s for A100）→ 可以承受

3. Pipeline Parallelism (层间激活值传递)
   通信量：micro_batch × hidden_size × sequence_length
   例：4 × 12288 × 2048 ≈ 100MB per micro-batch per boundary
   只有 PP-1 个边界 → 总通信量很小
   瓶颈：不重要

关键设计原则：
  · TP 放在单节点内（NVLink）
  · PP 跨节点（IB/RoCE），通信量小
  · DP 可以跨集群（IB），使用梯度累积减少通信频率
  · ZeRO-3 的通信量和 DP 的 AllReduce 合并优化
"""
```

### 2.3 训练稳定性——Loss Spike 的根因与对策

```
┌─────────────────────────────────────────────────────────────────┐
│ 大模型训练中的「最大噩梦」—— Loss Spike                           │
│                                                                   │
│ 现象：训练百万步后，Loss 突然从 1.8 跳到 12.3，然后恢复不了         │
│                                                                   │
│   Loss                                                            │
│    ↑                                                              │
│  12│           ╱╲                                                  │
│    │          ╱  ╲________                                        │
│    │    _____╱           ╲_____   ← 永远回不去了                   │
│    │___╱                    ╲___                                  │
│    └──────────────────────────────→ Steps                         │
│                                                                   │
│ 根因分析（六大常见原因）：                                         │
│                                                                   │
│ 1. 梯度爆炸（Gradient Explosion）                                 │
│    原因：某层权重的梯度范数快速增长                                  │
│    检测：||g|| > threshold（如 10.0）                              │
│    修复：Gradient Clipping (max_norm=1.0)                          │
│                                                                   │
│ 2. 注意力Logit爆炸                                                 │
│    原因：Q·K^T 的值随序列长度和维度增长                             │
│    修复：合理的初始化 + QK Layernorm（如 LLaMA 的做法）            │
│                                                                   │
│ 3. 优化器状态损坏（Adam的 ε 和 β）                                │
│    原因：Adam 的二阶矩估计在高维稀疏梯度下失效                      │
│    修复：调整 β2（0.999 → 0.95），增大 ε（1e-8 → 1e-6）          │
│                                                                   │
│ 4. 数据质量问题                                                    │
│    原因：训练数据中有异常样本（如超大文本、重复模式）                │
│    修复：数据清洗 + 异常检测 + 跳过异常batch                       │
│                                                                   │
│ 5. 混合精度训练的数值不稳定                                        │
│    原因：FP16 的动态范围不足（6.5e-5 ~ 65504）                    │
│    修复：Loss Scaling（动态调整 scale factor）                     │
│          BF16 替代 FP16（动态范围更大）                            │
│          Critical ops 用 FP32                                     │
│                                                                   │
│ 6. 学习率与 Batch Size 不匹配                                      │
│    原因：过大的 LR 在 Loss Plateau 后突然发散                      │
│    修复：Warmup + Cosine Decay + 合理 LR schedule                 │
└─────────────────────────────────────────────────────────────────┘

实战：Loss Spike 后的恢复策略

# 标准恢复流程（Meta OPT 训练实践）
def recover_from_spike(checkpoint_manager, spike_step):
    """
    Step 1: 回滚到最近的健康 Checkpoint
    Step 2: 跳过导致 Spike 的数据 Batch（可选）
    Step 3: 调整超参数（降低 LR，增大 gradient clip）
    Step 4: 从回滚点继续训练
    """
    # Step 1: 回滚
    healthy_step = checkpoint_manager.find_last_healthy(spike_step)
    model, optimizer, scheduler = checkpoint_manager.restore(healthy_step)

    # Step 2: 降低学习率
    for param_group in optimizer.param_groups:
        param_group['lr'] *= 0.5  # 学习率减半

    # Step 3: 更严格的梯度裁剪
    max_grad_norm = 0.5  # 从 1.0 降到 0.5

    # Step 4: 调整 Adam β2
    for param_group in optimizer.param_groups:
        param_group['betas'] = (0.9, 0.95)  # 从 0.999 降到 0.95

    return model, optimizer, scheduler
```

#### **LoRA 深度原理——面试高频考点**

```python
"""
LoRA (Low-Rank Adaptation) —— 2021 微软

核心思想：
  预训练权重 W ∈ R^(d×k) 在微调时不需要完全更新
  只需要学习一个低秩增量 ΔW = B·A

  其中 B ∈ R^(d×r), A ∈ R^(r×k), r ≪ min(d, k)

  前向传播：
    h = W·x + ΔW·x = W·x + B·(A·x)

  为什么 Low-Rank 有效？
    1. Aghajanyan et al. (2020) 证明：预训练语言模型具有低"内在维度"
       → 实际可优化的自由度数远小于参数数
    2. 过参数化模型的梯度矩阵也是低秩的（Li et al., 2018）
    3. 微调只是"小幅调整"，不需要动所有权重

  LoRA 的初始化技巧：
    · A: 高斯初始化 N(0, σ²)
    · B: 零初始化
    → 初始时 ΔW=0，不会干扰预训练权重

  关键参数：
    · r (rank)：通常在 4~64 之间
    · α (scaling)：控制 LoRA 更新的强度
    · target_modules：通常选 Q, K, V, O 投影矩阵
"""

import torch
import torch.nn as nn

class LoRALayer(nn.Module):
    """标准 LoRA 实现（面试可手写）"""

    def __init__(self, base_layer: nn.Linear, r: int = 8, alpha: float = 16.0):
        super().__init__()
        self.base_layer = base_layer  # 冻结的原始权重
        d_in, d_out = base_layer.in_features, base_layer.out_features

        # 低秩矩阵
        self.lora_A = nn.Parameter(torch.randn(r, d_in) * 0.02)  # 高斯初始化
        self.lora_B = nn.Parameter(torch.zeros(d_out, r))         # 零初始化

        self.scaling = alpha / r  # 缩放因子

        # 冻结基础权重
        for param in base_layer.parameters():
            param.requires_grad = False

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        # 基础输出（冻结）
        base_out = self.base_layer(x)  # [batch, d_out]

        # LoRA 增量
        delta = (x @ self.lora_A.T) @ self.lora_B.T  # [batch, d_out]
        # 等价于: x → A → B

        return base_out + self.scaling * delta


# ========================================
# QLoRA —— 4-bit 量化的 LoRA
# 论文：Dettmers et al., "QLoRA", NeurIPS 2023
# ========================================

"""
QLoRA 的核心创新——NF4 (NormalFloat4) 数据格式

为什么不用 INT4？
  · 模型权重通常近似正态分布
  · INT4 均匀量化 → 浪费精度在高范围（尾部分布）
  · NF4 → 按正态分布的 CDF 分位点来划分区间

NF4 的 16 个量化值（近似）：
  [-1.0, -0.696, -0.525, -0.395, -0.284, -0.188, -0.101, -0.020,
    0.020,  0.101,  0.188,  0.284,  0.395,  0.525,  0.696,  1.0]

量化过程：
  Step1: 归一化权重 w_norm = (w - μ) / σ
  Step2: 找到最近的 NF4 值
  Step3: 存储 4-bit 索引
  Step4: 训练时需要反问量化（dequantize）

QLoRA 的三重技巧：
  1. NF4 量化：比 INT4 更好利用正态分布特性
  2. 双重量化：量化常数本身也量化（省 0.37 bit/参数）
  3. 分页优化器：把优化器状态 offload 到 CPU，需要时再加载
     → 单卡 48GB 可以微调 65B 模型

为什么 QLoRA 性能不下降？
  · 关键 insight：量化误差对预训练权重的扰动 ＜ LoRA 更新的信号
  · LoRA 在「纠正」量化误差时顺便完成了微调
  · 相当于用学习到的低秩修正来补偿量化误差
"""

# ========================================
# DoRA —— 权重分解的 LoRA
# 论文：Liu et al., "DoRA", ICML 2024
# ========================================

"""
DoRA (Weight-Decomposed Low-Rank Adaptation)

核心改进：
  LoRA 把增量 ΔW 全部加入 W
  但研究发现，微调时主要是方向 changes，幅度 changes 很小

  DoRA: W' = m · (W + ΔW_dir) / ||W + ΔW_dir||
          ↑                           ↑
        幅度（可学习）              方向（LoRA+归一化）

  将权重矩阵分解为「幅度」和「方向」两部分：
  · 幅度 m：标量，用 LoRA 更新
  · 方向：用 LoRA 更新后归一化

  效果：比 LoRA 好 0.5~1.0 个点（在各种 benchmark 上）
  代价：训练速度慢 20~30%（需要额外的归一化和分解）
"""
```

### Q1：Scaling Laws 对实际大模型训练有什么指导作用？

```
核心答案（分四层）：

第一层：确定模型和数据大小的关系
  · Chinchilla: tokens = 20 × params（最优）
  · LLaMA 实践：tokens ≈ 100-200 × params（更进一步）
  · 实际策略：通常选择「稍微偏大数据量」的方案
  · 原因：推理时可以用量化降低部署成本，但训练时数据不足无法补救

第二层：指导计算预算分配
  · 给定计算预算 C：
    - 按 Chinchilla:  N ≈ k·C^0.5,  D ≈ k·C^0.5
    - 训练总时间 ≈ C / (GPU数量 × GPU算力 × 利用率)
  · 例：C = 10^24 FLOPs, 1000 A100 (312 TFLOPS, 50% 利用率)
    → 训练时间 ≈ 10^24 / (1000 × 312×10^12 × 0.5) ≈ 6.4×10^6 秒 ≈ 74 天

第三层：指导超参数选择
  · Batch Size：按 Scaling Law 增长（loss 降低 → critical batch size 增加）
  · 学习率：通常随模型增大而减小（LLaMA 65B: LR=1.5e-4; 7B: 3e-4）
  · Sequence Length：需要根据目标应用确定，太长会严重影响训练效率
    → Flash Attention 使长序列训练成为可能

第四层：Scaling Law 的局限性（面试加分点）
  · 数据质量未被建模 → 高质量数据可能打破 Scaling Law
  · 架构差异（MoE vs Dense）→ Scaling 曲线不同
  · 评估指标单一（只预测 Perplexity）→ 下游能力没有被 Scaling Law 捕获
  · 涌现能力未被 Scaling Law 预测
  · 数据重复的影响（epoch 数 > 1）→ Chinchilla 假设单 epoch
```

### Q2：分布式训练中 3D 并行（DP/TP/PP）如何协同工作？各自的优缺点？

```
答案（结构化回答）：

1. 三维并行的职责分工：
   · DP（数据并行）：处理「吞吐量」问题 → 同时处理更多样本
   · TP（张量并行）：处理「单层显存」问题 → 把大矩阵切小
   · PP（流水线并行）：处理「显存总量」问题 → 层间切分

2. 通信特点对比：

   ┌──────┬────────────┬──────────────┬─────────────┐
   │ 策略  │ 通信频率    │ 通信量        │ 通信模式     │
   ├──────┼────────────┼──────────────┼─────────────┤
   │  DP   │ 每步1次    │ 2×模型大小    │ AllReduce   │
   │  TP   │ 每层每步   │ 大            │ AllReduce/g │
   │  PP   │ 每micro-b  │ 小（激活值）  │ P2P Send    │
   └──────┴────────────┴──────────────┴─────────────┘

3. 适用场景：
   · 小模型（<1B）：纯 DP 就够
   · 中等模型（1B~10B）：DP + FSDP (ZeRO-3) + 少量 TP
   · 大模型（10B~100B）：DP + TP(2~4) + PP(4~8)
   · 超大模型（>100B）：DP + TP(8) + PP(8~16) + ZeRO-3

4. 面试加分回答——组合策略的设计原则：
   · TP 放在 NVLink 域内（单机8卡内）→ 高带宽低延迟
   · PP 跨机器 → 通信量小，适合跨网络
   · DP 跨集群 → ZeRO 切分减少通信
   · 通信和计算 overlap → 使用 CUDA Stream
```

### Q3：LoRA 为什么有效？QLoRA 怎么做到的 4-bit 微调不掉点？

```
答案（双重原理）：

LoRA 为什么有效——三个层次：

第一层：内在维度假设
  Aghajanyan et al. (2020) 证明预训练模型的"内在维度"远小于参数量
  → 微调不需要更新所有权重，只需要在低秩子空间调整
  → 这解释了为什么 r=8 就能在 4096 维的矩阵中有效

第二层：微调本质是「小幅修正」
  · Full fine-tuning 更新的总变化量其实也很小（相对预训练权重）
  · 用 SVD 分解微调前后的 ΔW 矩阵 → 发现仅有少数奇异值很大
  · LoRA 刚好用低秩矩阵 B·A 逼近了这个变化

第三层：正则化效应
  · 低秩约束相当于一种隐式正则化
  · 防止过拟合到下游任务的小数据集
  · 在某些少样本场景下 LoRA 甚至超越 Full Fine-tuning

QLoRA 为什么 4-bit 不掉点——关键技术创新：

1. NF4 数据格式
   按正态分布分位点量化 → 比均匀 INT4 精度高
   对于正态分布权重，NF4 的信息损失仅 ~0.1%

2. 双重量化（Double Quantization）
   量化常数的 FP32 → FP8 → 省 0.37 bit/参数
   65B 模型可省约 3GB

3. 分页优化器（Paged Optimizers）
   优化器状态 offload 到 CPU
   仅在更新时 CPU→GPU 传输（使用统一内存）
   显存占用从 4×模型大小降到几乎 0

4. LoRA 的「纠错」效应
   量化引入的误差 ≈ 噪声
   LoRA 在学习时不仅微调任务 → 也在补偿量化误差
   两者恰好同向！
```

### Q4：训练过程中遇到 Loss Spike 怎么办？给出完整的排查和处理流程？

```
答案（系统性回答——体现工程素养）：

Step 1: 紧急止损（5分钟内）
  1. 立即暂停训练（不保存当前step的checkpoint）
  2. 检查 Loss 是否持续增长：
     · 如果单步 spike → 可能是某个 batch 的问题 → 跳过继续
     · 如果持续不降 → 回滚

Step 2: 回滚恢复（10分钟内）
  1. 回滚到最近健康 checkpoint
  2. 降低学习率（×0.5 或 ×0.3）
  3. 收紧梯度裁剪阈值
  4. 重新启动，观察 100 步

Step 3: 根因分析（30分钟+）
  按概率排序逐个排查：

  排查清单：
  □ 梯度范数：||g|| > 10? → 梯度爆炸
  □ 激活值范数：某层激活值异常？→ 注意力问题
  □ 数据 batch：检查 spike 前的 batch → 是否有异常样本
  □ 学习率：当前 step 的 LR 值是否过大？
  □ 混合精度：Loss Scale 值是否在持续下降？
  □ 优化器状态：Adam 的 v（二阶矩）是否出现 NaN？
  □ 权重值：某层权重是否出现 NaN 或极大值？

Step 4: 预防措施（整改）
  · 启用 FP32 Master Weights（BF16 训练 + FP32 权重副本）
  · 添加中间层激活值监控（WandB histogram）
  · 梯度裁剪阈值根据历史数据设定（如 max_norm = 99分位数 × 1.5）
  · 实施滚动 checkpoint（保留最近 N 个，自动清理旧的）
  · 数据 pipeline 添加异常检测

关键教训：
  "Loss Spike 从来不是意外，它只是你之前没监控到的必然事件"
  "发现一个 Spike 不值钱，建立一套不会漏掉 Spike 的监控体系才值钱"
```

```
· 自动恢复: Loss Spike检测(3σ异常) → 回滚 → 降LR → 重训
· 硬件容错: K8s job自动重建, NCCL超时自动重试

第5层：时间与成本估算（体现全局思维）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 模拟面试题 2：深入解释 Scaling Laws 并讨论其实际应用与局限性

> **面试官**："请详细解释大模型的 Scaling Laws，包括 Kaplan 和 Chinchilla 的核心结论差异，以及在实际训练中如何应用。另外，Scaling Laws 有哪些被证伪或修正的地方？"

**参考答案要点**：

```
第1层：Scaling Law 的基本形式（数学推导）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
幂律关系：
  L(N) = (N_c / N)^α_N   其中 N_c ≈ 8.8×10^13, α_N ≈ 0.076
  L(D) = (D_c / D)^α_D   其中 D_c ≈ 5.4×10^13, α_D ≈ 0.095
  L(C) = (C_c / C)^α_C   其中 C_c ≈ 3.1×10^8,  α_C ≈ 0.050

含义：
  · 每次将参数量翻倍 → Loss 减少约 5%
  · 每次将数据量翻倍 → Loss 减少约 6.8%
  · 每次将计算量翻倍 → Loss 减少约 3.4%

第2层：Kaplan vs Chinchilla 的差异及原因（体现批判思维）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
核心分歧：N_opt(C) 的指数

  Kaplan:  N_opt ∝ C^0.73  → 模型比数据重要
  Chinchilla: N_opt ∝ C^0.50  → 同等重要

根本原因：
  1. Kaplan 的学习率调度不完整
     · Kaplan 使用固定步数的 cosine decay，大模型没有充分训练
     · Chinchilla 训练到接近收敛 → 发现小模型+多数据更好
  2. 分析范围的差异
     · Kaplan 的 N 范围不够大，外推不可靠
     · Chinchilla 做了更系统的网格搜索 (400+ 模型)
  3. 对 "compute-optimal" 的定义不同
     · Kaplan: min L s.t. C fixed → 在给定计算下的最小 Loss
     · Chinchilla: per-token loss → 更直接的定义

第3层：实际应用（体现工程经验）
━━━━━━━━━━━━━━━━━━━━━━━━━━
给定计算预算 C = 10^24 FLOPs：

  Chinchilla method:
    N ≈ C^0.5 × k ≈ 20B
    D ≈ C^0.5 × k' × N ≈ 20B × 20 ≈ 400B tokens

  实际选择的考量：
    · 如果推理部署受限 → 可以选更小的 N，更大 D
      例：N=7B, D=1.5T (类比 LLaMA)
    · 如果训练时间受限 → 可以选更大的 N，更小 D
      例：N=30B, D=300B
    · MoE 模型打破了常规 Scaling → N_effective ≪ N_total

第4层：Scaling Laws 的局限性（面试高分区）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 数据质量未被建模
   · Scaling Law 假设数据是同质的
   · 实际上：高质量 100B > 低质量 500B
   · Phi 系列（微软）：3.8B 模型用「教科书质量」数据训练 → 性能惊人

2. 涌现能力未被捕获
   · Scaling Law 只预测 Perplexity
   · 下游能力（推理/代码/数学）的涌现是阶梯式的，不是平滑的
   · Wei et al. 2022: 某些能力在特定规模「突然出现」

3. 数据重复（多 Epoch）的影响
   · Chinchilla 假设单 epoch（数据不重复）
   · LLaMA 实践：2~4 epoch 仍然有效
   · 过多 epoch（>4）→ 过拟合风险

4. 不同领域的 Scaling 不同
   · 代码能力 vs 语言能力的 Scaling 曲线不同
   · 推理能力的 Scaling 更陡峭
   · 数据配比（code/math比例）影响 Scaling 曲线形状

5. 推理阶段的 Scaling（Test-time Compute）
   · 传统 Scaling Law 只考虑训练
   · o1/o3 证明：推理时的计算也可以 Scaling
   · 「推理时 Scaling Law」是新的研究方向

面试结尾总结：
  "Scaling Laws 是训练大模型的导航图——它告诉你方向，
   但不会告诉你路上有没有坑。真正的训练决策需要考虑：
   数据质量、部署约束、MoE vs Dense、多语言需求等，
   这些是 Scaling Law 无法告诉你的。"
```

### 模拟面试题 3：设计一个支持 1000 QPS 的大模型推理服务系统

> **面试官**："公司有一个 70B 参数的大模型，需要部署成在线服务，目标 QPS 达到 1000（平均输入 500 tokens，输出 200 tokens）。请给出完整的系统设计方案，包括硬件选型、推理优化、服务架构和高可用设计。"

**参考答案要点**：

```
第1层：需求分析与硬件估算（体现计算思维）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Load 计算：
  每秒 tokens = 1000 QPS × (500 input + 200 output) = 700,000 tokens/s
  如果 4×A100-80GB 单节点推理速度 ≈ 2000 tokens/s（未优化）
  需要 700,000 / 2,000 ≈ 350 个 A100（未优化方案，不可行）

优化后的目标：
  单卡优化后推理速度 ≈ 8000 tokens/s (70B 4bit量化)
  需要 700,000 / 8,000 ≈ 90 张 A100
  使用 8卡节点 → 约 12 个节点

第2层：推理优化技术栈（体现技术深度）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  1. 量化: INT4 (AWQ/GPTQ) → 模型从 140GB → 35GB
  2. Tensor Parallelism: TP=4 (4卡跑一个模型副本)
  3. Continuous Batching: 动态攒batch → 吞吐量 3-5×
  4. PagedAttention (vLLM): KV Cache 内存管理 → 显存利用率 2×
  5. Flash Decoding: 长序列解码加速
  6. Prefix Caching: 相同 System Prompt 复用 KV Cache
  7. Speculative Decoding: 小模型预测 + 大模型验证 → 延迟降低 2-3×

第3层：服务架构设计（体现系统能力）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

第4层：核心组件设计（体现细节）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  流量调度：
    · Consistent Hashing → 同 session 同 GPU → KV Cache 命中
    · 或者：无状态 + Prefix Caching → 灵活调度
    · 过载保护：Rate Limiting (Token Bucket) + 排队

  KV Cache 管理：
    · 淘汰策略: LRU + 时间窗口
    · 预分配: 根据 system prompt 和常见 pattern 预计算
    · 跨请求复用: Prefix Caching (相同 system prompt 的请求共享)

  优先级调度：
    · Priority Queue: 交互式请求 > 批处理请求
    · Preemption: 高优先级可以抢占低优先级的 batch slot

第5层：高可用与容灾（体现生产经验）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

    · 错误率: 5xx / 4xx / timeout

   2. 负载低谷时：用 Spot Instance → 成本 -60%

   4. 请求级 batching 优化：Dynamic batching + 请求打包

   比折腾其他任何优化都有效。"
```
