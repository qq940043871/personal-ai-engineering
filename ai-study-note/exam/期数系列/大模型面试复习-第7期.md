### 1.2 Continuous Batching + 投机解码

#### **Continuous Batching（持续批处理）**

```
传统 Static Batching 问题：
  请求1: [..........]（10步完成）
  请求2: [..............]（14步完成）
  → 等最长的完成后才释放资源，短请求的 GPU 白等了

Continuous Batching 解法：
  请求1: [..........]✓  请求3: [..........]  ← 立即插入新请求
  请求2: [..............]
  → 随时插入完成 & 新请求，GPU 利用率从 40% 提升到 85%+
```

#### **投机解码（Speculative Decoding）**

```python
"""
原理：用小模型"猜"，大模型"验"
- 小模型（Draft Model, 7B）一次生成 4-8 个候选 Token（速度快）
- 大模型（Target Model, 70B）一次性验证这些候选 Token（并行验证）
- 命中的 Token 直接采用，未命中的重新生成
- 文本生成速度提升 2-3x（语言模式越规律，加速效果越好）

适合场景：
  - 长文本生成（代码、文章）
  - 输出较为确定的场景（FAQ、模板填充）
不适合：
  - 高创意性、随机性强的输出（投机命中率低，收益小）
"""

# HuggingFace Transformers 实现投机解码
from transformers import AutoTokenizer, AutoModelForCausalLM
import torch

# 加载大模型（Target）和小模型（Draft）
target_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-72B-Instruct")
draft_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-72B-Instruct")

inputs = tokenizer("请写一段冒泡排序的 Python 代码", return_tensors="pt")

# 启用投机解码（num_assistant_tokens 即每次投机的 Token 数）
outputs = target_model.generate(
    **inputs,
    assistant_model=draft_model,
    num_assistant_tokens=5,      # 小模型一次投机 5 个 Token
    max_new_tokens=256,
)
```

### 1.3 LLM in Production：灰度发布与 A/B Testing

#### **Prompt 版本灰度发布**

```python
class PromptVersionManager:
    """Prompt 版本管理 + 灰度发布"""

    def __init__(self):
        self.versions = {
            "v1": {
                "prompt_template": "你是一个客服助手。用户问题：{query}\n",
                "weight": 0.7,    # 70% 流量
                "status": "stable"
            },
            "v2": {
                "prompt_template": "你是一个专业的客服助手，请简洁、准确地回答。\n问题：{query}\n",
                "weight": 0.3,    # 30% 流量（灰度中）
                "status": "canary"
            }
        }

    def get_prompt(self, user_id: str, query: str) -> tuple[str, str]:
        """基于用户 ID 哈希做流量分配（确保同一用户体验一致）"""
        user_hash = hash(user_id) % 100
        cumulative = 0

        for version_name, config in self.versions.items():
            cumulative += config["weight"] * 100
            if user_hash < cumulative:
                prompt = config["prompt_template"].format(query=query)
                return prompt, version_name

        # 兜底返回最后一个版本
        last_version = list(self.versions.keys())[-1]
        config = self.versions[last_version]
        return config["prompt_template"].format(query=query), last_version

    def record_feedback(self, version: str, feedback: dict):
        """记录反馈，供 A/B 测试分析使用"""
        # 存入数据库
        db.insert("ab_test_logs", {
            "version": version,
            "rating": feedback["rating"],
            "latency_ms": feedback["latency_ms"],
            "timestamp": time.time()
        })

    def analyze_ab_test(self) -> dict:
        """分析 A/B 测试结果"""
        results = {}
        for version in self.versions:
            logs = db.query(
                "SELECT AVG(rating) as avg_rating, "
                "AVG(latency_ms) as avg_latency, COUNT(*) as n "
                "FROM ab_test_logs WHERE version = ?",
                [version]
            )
            results[version] = logs[0]

        # 统计显著性检验（T-test）
        from scipy import stats
        v1_ratings = db.query("SELECT rating FROM ab_test_logs WHERE version='v1'")
        v2_ratings = db.query("SELECT rating FROM ab_test_logs WHERE version='v2'")
        t_stat, p_value = stats.ttest_ind(v1_ratings, v2_ratings)

        return {
            "version_stats": results,
            "p_value": p_value,
            "significant": p_value < 0.05,  # 置信度 95%
            "recommendation": "v2 significantly better" if p_value < 0.05 and results["v2"]["avg_rating"] > results["v1"]["avg_rating"] else "keep v1"
        }
```

**面试表达**：
> "我们的 Prompt 更新不是直接全量发布，而是先灰度 10%→30%→50%→100%。用用户 ID 的哈希值分流，保证同一个用户体验一致。每个版本收集满意度、延迟等指标，用 T-test 做显著性检验，确认新版本显著更好后才全量推送。"

### 2.2 多 Provider 兼容性工程

#### **核心挑战（Agent Harness 真实踩坑）**

在 Agent Harness 项目中，我们接入了 OpenAI、DeepSeek、火山引擎（Doubao）等多个 Provider，遇到了严重的兼容性问题：

```python
# ❌ 问题：Doubao 不支持 base_url 和 model_kwargs
# OpenAI 兼容写法（对大多数 Provider 有效）：
client = openai.AsyncOpenAI(
    api_key=api_key,
    base_url="https://api.doubao.com/v1",  # ❌ Doubao 不支持这个参数！
)

# ✅ 解决方案：策略模式 + 适配器层
from abc import ABC, abstractmethod

class BaseLLMProvider(ABC):
    @abstractmethod
    async def chat(self, messages: list, **kwargs) -> str:
        pass

class OpenAIProvider(BaseLLMProvider):
    def __init__(self, api_key: str, model: str):
        self.client = openai.AsyncOpenAI(api_key=api_key)
        self.model = model

    async def chat(self, messages: list, **kwargs) -> str:
        response = await self.client.chat.completions.create(
            model=self.model,
            messages=messages,
            **kwargs
        )
        return response.choices[0].message.content

class DoubaoProvider(BaseLLMProvider):
    """火山引擎 Doubao：不支持 base_url，必须使用官方 SDK"""

    def __init__(self, api_key: str, endpoint_id: str):
        # ✅ 必须使用 volcenginesdkarkruntime，不能用 openai 库
        from volcenginesdkarkruntime import AsyncArk
        self.client = AsyncArk(api_key=api_key)
        self.endpoint_id = endpoint_id  # Doubao 用 endpoint_id，不是 model name

    async def chat(self, messages: list, **kwargs) -> str:
        # ✅ 过滤掉 Doubao 不支持的参数
        supported_kwargs = {k: v for k, v in kwargs.items()
                          if k in {"temperature", "max_tokens", "top_p"}}

        response = await self.client.chat.completions.create(
            model=self.endpoint_id,
            messages=messages,
            **supported_kwargs
        )
        return response.choices[0].message.content

class ProviderFactory:
    """工厂模式：根据配置创建对应 Provider"""

    @staticmethod
    def create(config: dict) -> BaseLLMProvider:
        provider_type = config["provider"]

        if provider_type == "openai":
            return OpenAIProvider(config["api_key"], config["model"])
        elif provider_type == "deepseek":
            return DeepSeekProvider(config["api_key"], config["model"])
        elif provider_type == "doubao":
            return DoubaoProvider(config["api_key"], config["endpoint_id"])
        else:
            raise ValueError(f"不支持的 Provider: {provider_type}")
```

**面试表达**：
> "在多 Provider 兼容问题上，最难处理的是火山引擎 Doubao。它不走标准的 OpenAI 兼容接口，必须用官方 SDK，还不支持 base_url、model_kwargs 等参数。我们用策略模式 + 适配器层解决：每个 Provider 实现统一的 BaseLLMProvider 接口，Doubao 在适配器内部做参数过滤和 SDK 切换。上层代码完全不感知 Provider 的差异。"

```python
# ─────────────────────────────────────────────────
import asyncio

class StreamController:
    """流式输出背压控制器"""

    def __init__(self, max_queue_size: int = 100):
        self.queue = asyncio.Queue(maxsize=max_queue_size)

    async def producer(self, llm_response):
        """生产者：LLM 输出流"""
        async for chunk in llm_response:
            try:
                # put_nowait 在 Queue 满时抛出 QueueFull 异常（背压触发）
                await asyncio.wait_for(
                    self.queue.put(chunk),
                    timeout=5.0  # 等待 5 秒，超时则丢弃或降速
                )
            except asyncio.TimeoutError:
                # 消费者太慢，记录日志并丢弃（或触发限流）
                logger.warning("Stream backpressure: consumer too slow")

        await self.queue.put(None)  # 生产结束标记

    async def consumer(self):
        """消费者：推送给前端"""
        while True:
            chunk = await self.queue.get()
            if chunk is None:
                break
            yield chunk
```

### Q1: vLLM 的核心技术是什么？与 HuggingFace Transformers 相比优势在哪？

**答**：

vLLM 的核心创新是 **PagedAttention**，借鉴操作系统虚拟内存的分页机制：

| 维度 | HuggingFace Transformers | vLLM |
|------|--------------------------|------|
| **KV Cache 分配** | 提前分配最大长度的显存（利用率 20-40%） | 按需动态分配（利用率 85%+） |
| **批处理** | Static Batching（等最长请求完成） | Continuous Batching（实时插入新请求） |
| **吞吐量** | 基准值 1x | 10-20x |
| **显存效率** | 低（预分配浪费大） | 高（碎片化极低） |
| **适用场景** | 研究/开发 | 生产部署 |

**面试表达**：
> "vLLM 的 PagedAttention 把 KV Cache 拆成固定大小的 Page（类似内存分页），每个请求按需申请 Page，不再一次性占满最大长度的显存。这样同等显存下可以支撑更多并发，加上 Continuous Batching，整体吞吐量提升 10-20 倍。"

### Q2: 如何做大模型的量化（Quantization）？原理是什么？

**答**：

```
量化原理：用更少的 bit 表示模型参数
FP32（32位浮点） → INT8（8位整数） → INT4（4位整数）
模型大小：FP32 140GB（70B模型）→ INT4 35GB（减少4x）
推理速度：提升 2-4x（内存带宽瓶颈减少）
精度损失：INT8≈0%损失，INT4≈1-3%损失
```

### Q3: Transformer 的 KV Cache 是什么？为什么能加速推理？

**答**：

```
自回归生成过程：
  生成第1个Token：计算所有 Token 的 K、V 矩阵
  生成第2个Token：重新计算所有 Token 的 K、V → ❌ 重复计算！
  生成第N个Token：重新计算前 N-1 个 Token 的 K、V → ❌ O(N²) 计算

KV Cache 解法：
  生成第1个Token：计算 K1, V1 → 存入缓存
  生成第2个Token：K1, V1 从缓存读 + 计算 K2, V2 → O(1) 增量计算
  生成第N个Token：K1...N-1 从缓存读 + 计算 KN → O(N) 空间，O(1) 增量计算

内存开销（以 70B 模型为例）：
  每层 KV Cache = 2 × seq_len × d_head × num_heads × FP16
  70B 模型，4096 序列长度 → 约 40GB KV Cache
  → 这就是为什么长上下文对显存要求极高！
```

**面试要点**：
- KV Cache 解决了自回归推理的重复计算问题，将时间复杂度从 O(N²) 降到 O(N)
- 代价是显存占用随序列长度线性增长
- vLLM 的 PagedAttention 正是为了解决 KV Cache 的显存利用率问题

```python
    async def auto_rollback(self, version: str):
        """自动回滚：关键指标恶化时触发"""
        recent_metrics = self.metrics[version][-100:]  # 最近100次请求
        avg_rating = sum(m["rating"] for m in recent_metrics) / len(recent_metrics)
        error_rate = sum(1 for m in recent_metrics if m["error"]) / len(recent_metrics)

        # 触发回滚条件
        if avg_rating < 3.5 or error_rate > 0.05:
            logger.warning(f"版本 {version} 触发自动回滚: rating={avg_rating:.2f}, error_rate={error_rate:.1%}")

            # 将流量权重清零（立即停止灰度）
            self.versions[version]["weight"] = 0
            self.versions[version]["rollback_triggered"] = True

            # 告警通知
            await alert_team(f"LLM 版本 {version} 已触发自动回滚，请检查原因")
            return True

        return False
```

**面试表达**：
> "我们的灰度发布有三道防线：第一，按用户 ID 哈希分流，同一用户始终用同一版本；第二，配置自动回滚阈值（满意度低于 3.5 或错误率超过 5% 立即回滚）；第三，每次灰度配合人工 A/B 分析，显著性检验通过后再全量。"

### Q5: 什么是 LoRA？它相比全量微调的优势在哪里？

**答**：

```
LoRA（Low-Rank Adaptation）核心思想：
  大模型的参数更新矩阵 ΔW 是低秩的（low-rank）
  ΔW (d×d) ≈ A (d×r) × B (r×d)，其中 r << d

  全量微调：更新 d×d = 10亿个参数（假设d=1000）
  LoRA 微调：只更新 d×r + r×d = 2×1000×4 = 8000 个参数（r=4）
  参数量减少：99.2%！
```

```python
from peft import LoraConfig, get_peft_model, TaskType

# LoRA 配置
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,                    # 秩（rank），越大参数越多，效果越好
    lora_alpha=32,           # 缩放系数（通常是 r 的 2 倍）
    lora_dropout=0.1,
    target_modules=[         # 对哪些层做 LoRA（Q、V 通常效果最好）
        "q_proj", "v_proj",  # 注意力的 Query 和 Value
        "k_proj", "o_proj",  # 也可以加上 Key 和 Output
    ]
)

# 只有 0.1-1% 的参数是可训练的！
model = get_peft_model(base_model, lora_config)
model.print_trainable_parameters()
# trainable params: 8,388,608 || all params: 7,000,000,000 || trainable%: 0.12%
```

| 维度 | 全量微调 | LoRA 微调 |
|------|---------|----------|
| **可训练参数量** | 100% | 0.1-1% |
| **显存需求** | 极高（70B需 1.4TB） | 低（70B仅需 16-80GB） |
| **训练时间** | 极长 | 短（快 10-100x） |
| **效果** | 最好 | 接近全量（差距<5%） |
| **适用场景** | 充足资源，根本性能力提升 | 资源受限，领域适配 |

### 问题 2：你的团队准备将 LLM 从 GPT-4 迁移到自部署的 Qwen-72B，如何保证质量不下降？

**场景**：
- 出于成本和数据安全考虑，将 GPT-4 替换为自部署的 Qwen-72B
- 现有 1000+ 条历史问答（用于质量基准）
- 如何验证迁移后效果，并平滑切换？

**参考答案要点**：

#### **迁移质量保证方案**

```python
class ModelMigrationValidator:
    """模型迁移质量验证器"""

    async def run_regression_tests(self):
        """回归测试：对比新旧模型在基准集上的表现"""

        test_cases = db.query("SELECT * FROM qa_benchmark LIMIT 200")
        results = {"gpt4": [], "qwen72b": []}

        for case in test_cases:
            # 两个模型都跑一遍
            for model_name, model in [("gpt4", gpt4), ("qwen72b", qwen72b)]:
                output = await model.chat(case["question"])
                score = await evaluate_with_llm(
                    question=case["question"],
                    reference=case["reference_answer"],
                    candidate=output
                )
                results[model_name].append({
                    "case_id": case["id"],
                    "score": score,
                    "output": output
                })

        # 统计对比
        gpt4_avg = sum(r["score"] for r in results["gpt4"]) / len(results["gpt4"])
        qwen_avg = sum(r["score"] for r in results["qwen72b"]) / len(results["qwen72b"])

        print(f"GPT-4 平均分：{gpt4_avg:.3f}")
        print(f"Qwen-72B 平均分：{qwen_avg:.3f}")
        print(f"差距：{(qwen_avg - gpt4_avg) / gpt4_avg * 100:.1f}%")

        # 找出 Qwen 显著弱于 GPT-4 的 Case（需要针对性优化）
        weak_cases = [
            r for r1, r2 in zip(results["gpt4"], results["qwen72b"])
            for r in [r2] if r1["score"] - r2["score"] > 0.2
        ]
        return weak_cases
```

#### **迁移三步走**

```
Step 1：基准测试（迁移前）
  ├── 收集 200 个典型问题作为 Benchmark
  ├── GPT-4 全跑一遍，建立"基线分数"
  └── 确定可接受的分数下降区间（例如：整体 ≤5%，关键场景 0容忍）

Step 2：差距修复（迁移前）
  ├── 找出 Qwen-72B 显著弱于 GPT-4 的 Case（差距 > 0.2 分）
  ├── 针对这些 Case 优化 Prompt（Few-shot 补充、格式约束）
  └── 如果部分能力差距无法通过 Prompt 弥补 → LoRA 微调补齐

Step 3：灰度验证（迁移中）
  ├── 第1周：5% 流量切 Qwen-72B
  ├── 第2周：观察指标（满意度、错误率、延迟）
  ├── 无异常 → 逐步放量：30%→70%→100%
  └── 出现异常 → 立即回滚，回归分析原因
```

### 问题 3：解释 Transformer 注意力机制的计算复杂度问题及改进方案

**场景**：
- 面试官问："你说用了长上下文，但 Self-Attention 的复杂度是 O(N²)，怎么解决的？"

**参考答案要点**：

#### **标准 Self-Attention 复杂度分析**

```
Self-Attention 计算：
  Q、K、V 矩阵：每个 shape = [batch, seq_len, d_model]

  注意力分数：Attention(Q,K,V) = softmax(QK^T / √d_k) × V

  计算 QK^T：[batch, seq_len, d_model] × [batch, d_model, seq_len]
            → [batch, seq_len, seq_len]

  时间复杂度：O(N² × d)，其中 N = 序列长度
  空间复杂度：O(N²)（注意力矩阵）

  问题：N=1000 → 100万 × d 次计算
       N=100000 → 100亿 × d 次计算（基本不可行！）
```

#### **主流改进方案对比**

| 方案 | 时间复杂度 | 思路 | 适用场景 |
|------|----------|------|---------|
| **标准 Self-Attention** | O(N²) | — | seq_len ≤ 4K |
| **Sparse Attention** | O(N√N) | 只计算局部+全局Token的注意力 | seq_len 4K-32K |
| **FlashAttention** | O(N²) 但 IO 优化 | GPU 分块计算，减少 HBM 访问 | 所有场景（工程加速） |
| **Linear Attention** | O(N) | 核函数近似 softmax | 超长序列（理论） |
| **RoPE+滑动窗口** | O(N×W) | W=窗口大小 | Mistral 等模型 |
| **MLA (Multi-head Latent Attention)** | O(N²) KV 压缩 | KV Cache 压缩为低秩表示 | DeepSeek-V2/V3 |

```python
# FlashAttention 使用示例（最实用的优化，无精度损失）
from flash_attn import flash_attn_qkvpacked_func, flash_attn_func

# 标准注意力（速度慢，显存高）
attention_output = F.scaled_dot_product_attention(q, k, v)

# FlashAttention（速度快 2-4x，显存低 5-10x，精度完全相同）
# 原理：将注意力矩阵分块计算，避免 O(N²) 的中间矩阵存储到 HBM
attention_output = flash_attn_func(q, k, v, causal=True)
```

**DeepSeek MLA（前沿考点）**：
> "DeepSeek-V2/V3 引入了 MLA（Multi-head Latent Attention），将 KV Cache 压缩为低秩的潜在向量（latent vector）。KV Cache 从原来的 d_head × num_heads 压缩到 d_latent（远小于前者），大幅减少了 KV Cache 的显存占用，支持更大的批处理和更长的上下文。"
