## 📌 一、项目亮点（Project Highlights）

### 1.1 LLM 应用框架选型决策——从"会用"到"会选"

#### **三大框架深度对比**

在 Agent Harness 项目中，我们系统性地评估了 LangChain、LlamaIndex 和自研框架三种方案，最终选择了**混合架构**：核心编排自研 + 检索链路用 LlamaIndex + 工具集成用 LangChain。

```
框架选型决策树：

需求：快速原型验证？
  ├── 是 → LangChain（开箱即用，链式调用简单）
  └── 否 → 继续

需求：核心是 RAG / 知识检索？
  ├── 是 → LlamaIndex（检索优化极致）
  └── 否 → 继续

需求：高度定制化 + 生产级稳定性？
  ├── 是 → 自研框架（完全控制，但开发成本高）
  └── 折中方案 → 自研核心 + 框架模块混合

我们的选择：
  Agent 核心循环（MainLoop）→ 自研（事件驱动、背压控制）
  RAG 检索链路 → LlamaIndex（Query Rewrite + Rerank + 压缩）
  工具调用生态 → LangChain（预置工具库 + 格式化）
```

#### **框架深度对比表**

| 维度 | LangChain | LlamaIndex | 自研框架 |
|------|-----------|------------|---------|
| **核心定位** | 通用 LLM 应用框架 | RAG/知识检索专用 | 完全定制 |
| **抽象层级** | 高（Chain/Agent/Tool） | 中（Index/Query/Retriever） | 自定义 |
| **学习曲线** | 中等（概念多） | 较低（RAG 场景直觉） | 高（全部自己写） |
| **RAG 能力** | 基础（需自配） | 极强（内置多级检索） | 自定义 |
| **工具调用** | 丰富（200+预置Tool） | 一般 | 自定义 |
| **生产稳定性** | ⚠️ 曾有频繁Breaking Change | 较好 | 完全自主 |
| **Token 可观测** | LangSmith（付费） | 基础日志 | 自定义埋点 |
| **社区生态** | 最大 | RAG领域最强 | 无 |
| **适合团队** | 快速验证 / 工具密集型 | 知识密集型 | 大厂 / 深度定制 |

**面试表达**：
> "我们的选型不是'选一个框架'，而是分层选型。核心的 Agent 编排循环自研，因为我们需要精确控制事件驱动、背压和流式输出；RAG 检索用 LlamaIndex，因为它在 Query Rewrite、Hybrid Search 和 Rerank 方面的抽象最成熟；工具集成用 LangChain 的 Tool 接口，省去重复造轮子。这种混合架构让每个模块都用最合适的工具，同时避免了单一框架的锁定风险。"

### 1.2 Function Calling 工程化实践

#### **从"能调用"到"可靠调用"——工具调用全链路**

```
Function Calling 工程化全景：

用户输入 → LLM 判断是否需要调用工具 → 生成工具调用指令
  ↓
参数校验（Schema验证） → 工具执行 → 结果处理 → LLM 继续推理
  ↓
重试机制 → 超时控制 → 降级策略 → 审计日志
```

```python
from pydantic import BaseModel, Field
from typing import Optional
import asyncio
import json

# ─────────────────────────────────────────────────
# Step 1：结构化工具定义（Pydantic 保证 Schema 校验）
# ─────────────────────────────────────────────────

class SearchInput(BaseModel):
    """搜索工具输入参数"""
    query: str = Field(description="搜索关键词")
    top_k: int = Field(default=5, ge=1, le=20, description="返回结果数量")
    date_range: Optional[str] = Field(default=None, description="时间范围，如'7d'表示最近7天")

class CalculatorInput(BaseModel):
    """计算器工具输入参数"""
    expression: str = Field(description="数学表达式，如'2+3*4'")

# ─────────────────────────────────────────────────
# Step 2：工具注册中心（统一管理工具的生命周期）
# ─────────────────────────────────────────────────

class ToolRegistry:
    """工具注册中心——函数调用的"交通指挥""""

    def __init__(self):
        self.tools = {}          # name → tool_fn
        self.schemas = {}        # name → JSON Schema
        self.retries = {}        # name → max_retries
        self.timeouts = {}       # name → timeout_seconds

    def register(self, name: str, description: str, input_model: type[BaseModel],
                 fn: callable, max_retries: int = 2, timeout: float = 10.0):
        """注册工具（自动生成 OpenAI Function Calling 格式的 Schema）"""
        self.tools[name] = fn
        self.schemas[name] = {
            "type": "function",
            "function": {
                "name": name,
                "description": description,
                "parameters": input_model.model_json_schema()
            }
        }
        self.retries[name] = max_retries
        self.timeouts[name] = timeout

    def get_openai_tools(self) -> list[dict]:
        """生成 OpenAI API 所需的 tools 参数"""
        return list(self.schemas.values())

# ─────────────────────────────────────────────────
# Step 3：可靠的工具调用执行器
# ─────────────────────────────────────────────────

class ToolExecutor:
    """工具执行器——带重试、超时、降级的"安全执行""""

    def __init__(self, registry: ToolRegistry):
        self.registry = registry

    async def execute(self, tool_call) -> dict:
        """执行单个工具调用"""
        name = tool_call.function.name
        args = json.loads(tool_call.function.arguments)

        # 参数校验（Pydantic 自动验证类型、范围、必填项）
        schema = self.registry.schemas[name]["function"]["parameters"]
        try:
            validated_args = self._validate_args(name, args)
        except Exception as e:
            return {"error": f"参数校验失败: {e}", "tool": name}

        # 带重试的执行
        max_retries = self.registry.retries.get(name, 2)
        timeout = self.registry.timeouts.get(name, 10.0)

        for attempt in range(max_retries + 1):
            try:
                result = await asyncio.wait_for(
                    self.registry.tools[name](**validated_args),
                    timeout=timeout
                )
                return {"result": result, "tool": name, "attempts": attempt + 1}

            except asyncio.TimeoutError:
                if attempt < max_retries:
                    await asyncio.sleep(0.5 * (attempt + 1))  # 指数退避
                    continue
                return {"error": f"工具 {name} 执行超时（{timeout}s）", "tool": name}

            except Exception as e:
                if attempt < max_retries:
                    await asyncio.sleep(0.5 * (attempt + 1))
                    continue
                return {"error": f"工具 {name} 执行失败: {str(e)}", "tool": name}

    async def execute_parallel(self, tool_calls: list) -> list[dict]:
        """并行执行多个独立工具调用（关键优化！）"""
        tasks = [self.execute(tc) for tc in tool_calls]
        return await asyncio.gather(*tasks)

# ─────────────────────────────────────────────────
# Step 4：完整的 Agent 工具调用循环
# ─────────────────────────────────────────────────

class AgentWithTools:
    """带工具调用的 Agent 完整循环"""

    def __init__(self, llm_client, tool_registry: ToolRegistry, max_turns: int = 5):
        self.llm = llm_client
        self.executor = ToolExecutor(tool_registry)
        self.registry = tool_registry
        self.max_turns = max_turns

    async def run(self, user_message: str) -> str:
        """完整的工具调用循环：LLM ↔ Tools ↔ LLM"""

        messages = [{"role": "user", "content": user_message}]
        tools = self.registry.get_openai_tools()

        for turn in range(self.max_turns):
            # LLM 决策：是否调用工具
            response = await self.llm.chat.completions.create(
                model="gpt-4o",
                messages=messages,
                tools=tools,
                tool_choice="auto"   # auto = LLM 自主决定
            )

            msg = response.choices[0].message

            # 无工具调用 → 返回最终答案
            if not msg.tool_calls:
                return msg.content

            # 有工具调用 → 执行工具
            messages.append(msg)

            # 关键优化：并行执行多个独立工具调用
            results = await self.executor.execute_parallel(msg.tool_calls)

            # 将工具结果返回给 LLM
            for tc, result in zip(msg.tool_calls, results):
                messages.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": json.dumps(result, ensure_ascii=False)
                })

        return "达到最大工具调用轮次，请简化您的问题。"
```

**面试表达**：
> "Function Calling 的工程化不只是'调个 API'。我们做了四层保障：第一，Pydantic 做参数校验，防止 LLM 生成的参数类型或范围错误；第二，每个工具配置独立的超时和重试策略，指数退避；第三，多个独立工具调用并行执行（asyncio.gather），延迟从串行的 6s 降到并行的 2s；第四，限制最大工具调用轮次（5轮），防止 LLM 陷入无限工具调用循环。"

## 🔧 二、技术难点与解决方案（Technical Challenges）

### 2.1 Function Calling 的六大陷阱与解法

#### **陷阱1：LLM 幻觉工具名或参数**

```python
# ❌ 问题：LLM 可能"编造"不存在的工具或参数
# LLM 输出：调用 "search_web" 工具，参数 {"query": "...", "language": "zh"}
# 但实际上注册的工具名是 "web_search"，且没有 "language" 参数

# ✅ 解法：工具名白名单 + 参数严格校验
class StrictToolExecutor:
    async def execute(self, tool_call):
        name = tool_call.function.name

        # 校验1：工具名是否存在
        if name not in self.registry.tools:
            return {
                "error": f"工具 '{name}' 不存在。可用工具：{list(self.registry.tools.keys())}",
                "tool": name
            }

        # 校验2：参数 Schema 验证（Pydantic 自动抛出 ValidationError）
        try:
            args = json.loads(tool_call.function.arguments)
            validated = self.registry.input_models[name](**args)
        except json.JSONDecodeError:
            return {"error": "参数 JSON 格式无效", "tool": name}
        except Exception as e:
            return {"error": f"参数校验失败: {e}", "tool": name}

        # 校验3：执行结果格式检查
        result = await self.registry.tools[name](**validated.model_dump())
        if not isinstance(result, (str, dict, list)):
            result = str(result)

        return {"result": result, "tool": name}
```

#### **陷阱2：并行工具调用的依赖冲突**

```
问题场景：
  LLM 同时调用：
    Tool A: get_user_balance(user_id="123")     → 需要读取余额
    Tool B: transfer_money(from="123", to="456") → 需要修改余额
  → 并行执行会导致数据竞争！

解法：工具依赖图（DAG）分析
  1. 标注每个工具的读写资源（如 balance 表）
  2. 构建依赖图：写-写冲突、读-写冲突 → 必须串行
  3. 无冲突的工具才并行执行
```

```python
class DependencyAwareExecutor:
    """依赖感知的工具执行器"""

    def __init__(self, registry: ToolRegistry):
        self.registry = registry
        # 每个工具声明的资源依赖
        self.resource_map = {
            "get_user_balance": {"read": ["balance"]},
            "transfer_money":   {"write": ["balance"]},
            "search_products":  {"read": ["product_catalog"]},
            "get_weather":      {"read": []},  # 无依赖，可完全并行
        }

    def _has_conflict(self, tools: list[str]) -> bool:
        """检测工具间是否有资源冲突"""
        write_resources = set()
        read_resources = set()

        for tool_name in tools:
            deps = self.resource_map.get(tool_name, {"read": [], "write": []})
            write_resources.update(deps.get("write", []))
            read_resources.update(deps.get("read", []))

        # 读写冲突 或 写写冲突
        return bool(write_resources & read_resources) or len(write_resources) > 1

    async def execute_group(self, tool_calls: list) -> list[dict]:
        """分组执行：无冲突并行，有冲突串行"""
        if not self._has_conflict([tc.function.name for tc in tool_calls]):
            # 无冲突 → 并行执行
            return await asyncio.gather(*[self.execute(tc) for tc in tool_calls])
        else:
            # 有冲突 → 串行执行
            results = []
            for tc in tool_calls:
                result = await self.execute(tc)
                results.append(result)
            return results
```

#### **陷阱3：工具调用的无限循环**

```
问题：LLM 反复调用同一工具，陷入循环
  Turn 1: 调用 search("Python tutorial")
  Turn 2: 调用 search("Python tutorial for beginners")
  Turn 3: 调用 search("Python beginner guide")
  ...  20轮后仍在搜索

解法：三层防护
  1. 硬限制：max_turns = 5（最多5轮工具调用）
  2. 去重检测：相同工具+相似参数 → 直接复用上次结果
  3. 退化策略：连续2轮调用同类工具 → 强制输出当前结果
```

#### **陷阱4-6速览**

| 陷阱 | 根因 | 解法 |
|------|------|------|
| **工具返回结果过长** | LLM 上下文被塞满 | 结果摘要（LLM压缩/截断）+ Token 预算分配 |
| **工具调用延迟过高** | 外部 API 不稳定 | 超时控制 + 缓存 + 降级（返回兜底结果） |
| **多工具调用顺序错误** | LLM 未理解工具间依赖 | System Prompt 中声明工具执行顺序约束 |

### 2.2 Agent 记忆系统——从"金鱼记忆"到"长期记忆"

#### **三类记忆架构**

```
人类记忆模型 → Agent 记忆映射：

  感觉记忆（Sensory）    → 工作记忆（Working Memory）
    当前对话的上下文窗口      最近 N 轮对话 + System Prompt

  短期记忆（Short-term）  → 短期记忆（Short-term Memory）
    今天发生的事             当前会话的对话历史（完整）
                            ├── 存储介质：内存 / Redis
                            └── 生命周期：会话结束即清除

  长期记忆（Long-term）   → 长期记忆（Long-term Memory）
    多年的知识和经验         跨会话的用户偏好、知识库
                            ├── 存储介质：向量数据库 / 关系数据库
                            └── 生命周期：永久保存

  情景记忆（Episodic）    → 情景记忆（Episodic Memory）
    "上次对话我们讨论了X"     历史会话摘要 + 关键决策点
                            ├── 存储介质：向量数据库（按语义检索）
                            └── 生命周期：按重要性衰减
```

```python
import hashlib
from dataclasses import dataclass, field
from datetime import datetime

# ─────────────────────────────────────────────────
# 记忆条目数据结构
# ─────────────────────────────────────────────────

@dataclass
class MemoryItem:
    """一条记忆"""
    content: str                          # 记忆内容
    memory_type: str                      # short_term / long_term / episodic
    importance: float = 0.5               # 重要性（0-1）
    embedding: list[float] = field(default_factory=list)  # 向量表示
    created_at: datetime = field(default_factory=datetime.now)
    access_count: int = 0                 # 访问次数（LRU 淘汰参考）
    last_accessed: datetime = field(default_factory=datetime.now)

# ─────────────────────────────────────────────────
# 完整的记忆管理系统
# ─────────────────────────────────────────────────

class AgentMemorySystem:
    """Agent 三层记忆系统"""

    def __init__(self, embedding_model, vector_db):
        self.embedding_model = embedding_model
        self.vector_db = vector_db

        # 工作记忆：当前对话上下文（直接放进 messages）
        self.working_memory: list[dict] = []

        # 短期记忆：当前会话（内存）
        self.short_term: list[MemoryItem] = []
        self.max_short_term = 50  # 最多保留50条

        # 长期记忆：跨会话（向量数据库）
        self.long_term_collection = "agent_long_term"

    # ── 存入记忆 ──

    async def store(self, content: str, memory_type: str = "auto",
                    importance: float = 0.5):
        """存入记忆（自动判断类型）"""

        # 生成向量
        embedding = await self.embedding_model.embed(content)

        # 自动判断记忆类型
        if memory_type == "auto":
            memory_type = self._classify_memory(content, importance)

        item = MemoryItem(
            content=content,
            memory_type=memory_type,
            importance=importance,
            embedding=embedding
        )

        if memory_type == "short_term":
            self.short_term.append(item)
            # 淘汰最旧的记忆
            if len(self.short_term) > self.max_short_term:
                evicted = self.short_term.pop(0)
                # 重要的短期记忆升级为长期记忆
                if evicted.importance > 0.7:
                    await self._promote_to_long_term(evicted)

        elif memory_type == "long_term":
            await self.vector_db.insert(
                collection=self.long_term_collection,
                vector=embedding,
                metadata={"content": content, "importance": importance}
            )

        elif memory_type == "episodic":
            # 情景记忆：存入向量数据库，带时间戳和会话ID
            await self.vector_db.insert(
                collection="agent_episodic",
                vector=embedding,
                metadata={
                    "content": content,
                    "timestamp": datetime.now().isoformat(),
                    "session_id": self.current_session_id
                }
            )

    def _classify_memory(self, content: str, importance: float) -> str:
        """自动分类记忆类型"""
        # 高重要性 → 长期记忆（用户偏好、关键决策）
        if importance > 0.8:
            return "long_term"

        # 包含"上次""之前""之前讨论" → 情景记忆
        episodic_keywords = ["上次", "之前", "上次讨论", "上次提到", "previously"]
        if any(kw in content for kw in episodic_keywords):
            return "episodic"

        # 默认 → 短期记忆
        return "short_term"

    # ── 检索记忆 ──

    async def recall(self, query: str, top_k: int = 5) -> list[MemoryItem]:
        """检索相关记忆（三层融合）"""
        query_embedding = await self.embedding_model.embed(query)
        results = []

        # 1. 工作记忆（当前上下文，最高优先级）
        results.extend([
            MemoryItem(content=str(m), memory_type="working", importance=1.0)
            for m in self.working_memory[-5:]  # 最近5轮
        ])

        # 2. 短期记忆（语义检索）
        short_term_hits = self._semantic_search_in_memory(
            query_embedding, self.short_term, top_k=3
        )
        results.extend(short_term_hits)

        # 3. 长期记忆 + 情景记忆（向量数据库检索）
        long_term_hits = await self.vector_db.search(
            collection=self.long_term_collection,
            vector=query_embedding,
            top_k=3
        )
        results.extend([
            MemoryItem(
                content=hit["metadata"]["content"],
                memory_type="long_term",
                importance=hit["metadata"].get("importance", 0.5)
            )
            for hit in long_term_hits
        ])

        # 按重要性排序
        results.sort(key=lambda x: x.importance, reverse=True)
        return results[:top_k]

    # ── 记忆遗忘（模拟人类遗忘曲线）──

    def decay_memories(self):
        """记忆衰减——模拟 Ebbinghaus 遗忘曲线"""
        now = datetime.now()
        for item in self.short_term:
            age_hours = (now - item.created_at).total_seconds() / 3600
            # 艾宾浩斯遗忘曲线：R = e^(-t/S)，S=稳定性
            stability = 24 * (1 + item.importance)  # 高重要性记忆更稳定
            retention = math.exp(-age_hours / stability)

            # 保留概率 = 记忆保留率 × 重要性加权
            if retention * item.importance < 0.1:
                self.short_term.remove(item)

    # ── 记忆升级 ──

    async def _promote_to_long_term(self, item: MemoryItem):
        """短期记忆升级为长期记忆（重要的短期记忆不应被遗忘）"""
        await self.vector_db.insert(
            collection=self.long_term_collection,
            vector=item.embedding,
            metadata={"content": item.content, "importance": item.importance}
        )
```

**面试表达**：
> "我们的 Agent 记忆系统分三层：工作记忆是当前对话上下文，短期记忆是当前会话的完整历史，长期记忆是跨会话的用户偏好和知识。关键设计有三点：第一，短期记忆满时，重要的记忆自动升级到长期记忆（向量数据库），不重要的按遗忘曲线衰减淘汰；第二，检索时三层融合，按重要性排序；第三，情景记忆单独存储'上次讨论了什么'这类跨会话引用，用语义检索而非关键词匹配。"

### 2.3 大模型应用可观测性（Observability）

#### **为什么 LLM 应用需要可观测性？**

```
传统软件：输入确定 → 输出确定 → 日志 + 指标 + 链路追踪 够用
LLM 应用：输入非结构化 → 中间过程不透明 → 输出不确定

核心挑战：
  1. LLM 是黑盒：为什么生成了这个回答？不知道
  2. 成本不可预测：一次请求花了多少 Token？多少费用？
  3. 质量难以度量：回答质量好吗？怎么量化？
  4. 链路复杂：RAG → LLM → Tool → LLM → 输出，哪一步出了问题？

可观测性三支柱（ adapted for LLM）：
  Logging    → 每次请求的完整输入输出、Token 用量、延迟
  Metrics    → 成功率、平均延迟、Token 消耗趋势、工具调用频率
  Tracing    → 完整的调用链路追踪（RAG检索 → LLM推理 → 工具调用 → 输出）
```

```python
import time
from dataclasses import dataclass, field
from datetime import datetime
from contextlib import asynccontextmanager

# ─────────────────────────────────────────────────
# LLM 调用追踪（Tracing 核心）
# ─────────────────────────────────────────────────

@dataclass
class LLMSpan:
    """一次 LLM 调用的完整追踪"""
    trace_id: str
    span_id: str
    parent_span_id: str | None = None
    operation: str = ""              # chat / rag_search / tool_call
    model: str = ""
    input_tokens: int = 0
    output_tokens: int = 0
    latency_ms: float = 0
    status: str = "success"          # success / error / timeout
    error_message: str | None = None
    metadata: dict = field(default_factory=dict)
    start_time: datetime = field(default_factory=datetime.now)

    @property
    def total_tokens(self) -> int:
        return self.input_tokens + self.output_tokens

    @property
    def cost_usd(self) -> float:
        """估算费用（以 GPT-4o 价格为例）"""
        price_per_1k = {
            "gpt-4o": {"input": 0.0025, "output": 0.01},
            "gpt-4o-mini": {"input": 0.00015, "output": 0.0006},
            "qwen-72b": {"input": 0.0004, "output": 0.0012},
        }
        prices = price_per_1k.get(self.model, {"input": 0.001, "output": 0.003})
        input_cost = (self.input_tokens / 1000) * prices["input"]
        output_cost = (self.output_tokens / 1000) * prices["output"]
        return input_cost + output_cost


class LLMObservability:
    """LLM 可观测性系统"""

    def __init__(self):
        self.spans: list[LLMSpan] = []
        self.metrics = {
            "total_requests": 0,
            "total_tokens": 0,
            "total_cost": 0.0,
            "error_count": 0,
            "latencies": [],
        }

    @asynccontextmanager
    async def trace(self, operation: str, model: str = "", **metadata):
        """追踪一次 LLM 调用的上下文管理器"""
        span = LLMSpan(
            trace_id=self._generate_trace_id(),
            span_id=self._generate_span_id(),
            operation=operation,
            model=model,
            metadata=metadata,
            start_time=datetime.now()
        )

        start = time.time()
        try:
            yield span  # 调用方填充 token 等信息
        except Exception as e:
            span.status = "error"
            span.error_message = str(e)
            self.metrics["error_count"] += 1
            raise
        finally:
            span.latency_ms = (time.time() - start) * 1000
            self.spans.append(span)
            self._update_metrics(span)

    def _update_metrics(self, span: LLMSpan):
        """更新实时指标"""
        self.metrics["total_requests"] += 1
        self.metrics["total_tokens"] += span.total_tokens
        self.metrics["total_cost"] += span.cost_usd
        self.metrics["latencies"].append(span.latency_ms)

        # 只保留最近 1000 条延迟数据
        if len(self.metrics["latencies"]) > 1000:
            self.metrics["latencies"] = self.metrics["latencies"][-1000:]

    def get_dashboard(self) -> dict:
        """可观测性仪表盘数据"""
        latencies = self.metrics["latencies"]
        return {
            "total_requests": self.metrics["total_requests"],
            "error_rate": self.metrics["error_count"] / max(self.metrics["total_requests"], 1),
            "total_tokens": self.metrics["total_tokens"],
            "total_cost_usd": round(self.metrics["total_cost"], 4),
            "avg_latency_ms": sum(latencies) / max(len(latencies), 1),
            "p50_latency_ms": self._percentile(latencies, 50),
            "p95_latency_ms": self._percentile(latencies, 95),
            "p99_latency_ms": self._percentile(latencies, 99),
        }

    @staticmethod
    def _percentile(data: list, p: int) -> float:
        if not data:
            return 0
        sorted_data = sorted(data)
        idx = int(len(sorted_data) * p / 100)
        return sorted_data[min(idx, len(sorted_data) - 1)]
```

### Q1: LangChain 的核心抽象有哪些？它为什么被批评"过度抽象"？

**答**：

```
LangChain 核心抽象层级：

Layer 1：Model I/O
  ├── Prompts：Prompt 模板（PromptTemplate / ChatPromptTemplate）
  ├── LLMs / ChatModels：模型调用接口
  └── Output Parsers：输出解析（JSON / List / Pydantic）

Layer 2：Retrieval
  ├── Document Loaders：文档加载（PDF / Web / DB）
  ├── Text Splitters：文本分块
  ├── Embeddings：向量化
  └── VectorStores：向量存储

Layer 3：Chains
  ├── LLMChain：最基础的链（Prompt → LLM → Parser）
  ├── SequentialChain：串行链
  └── RouterChain：路由链（根据输入选择子链）

Layer 4：Agents
  ├── Tool：工具定义
  ├── AgentExecutor：Agent 执行器
  └── 各种 Agent 类型：ReAct / OpenAI Functions / Plan-and-Execute

被批评的原因：
  1. 抽象层级太多：简单功能需要理解 5+ 层抽象
  2. Breaking Change 频繁：v0.1 → v0.2 大量 API 不兼容
  3. 调试困难：报错信息嵌套层级深，难以定位
  4. 性能开销：抽象层引入额外延迟

建议：
  - 小项目/快速验证：LangChain 开箱即用
  - 生产项目：只用的 LangChain 的 Tool 和 Output Parser，
    核心编排逻辑自研（避免被框架绑架）
```

### Q2: Function Calling 和 Tool Use 有什么区别？ReAct 模式是什么？

**答**：

```
概念澄清：

Function Calling（OpenAI 术语）
  = LLM 输出结构化的工具调用指令（JSON 格式）
  = OpenAI 的专有实现

Tool Use（通用术语）
  = LLM 调用外部工具的能力
  = 包括 Function Calling，但不限于

ReAct（Reasoning + Acting）模式：
  Agent 的思考-行动循环

  Thought: 用户想查询北京天气，我需要调用天气工具
  Action: get_weather(city="北京")
  Observation: 北京今天晴，25°C
  Thought: 已经获取到天气信息，可以回答用户了
  Answer: 北京今天晴天，气温25°C，适合出行

ReAct vs Function Calling：
  ReAct：LLM 生成自然语言的思考和行动（通用但解析不稳定）
  Function Calling：LLM 生成结构化 JSON（解析稳定，但依赖模型支持）

实际工程：两者结合
  LLM 用 Function Calling 做工具调用（结构化、可靠）
  同时在 System Prompt 中引导 ReAct 思考模式（提升推理质量）
```

### Q3: Agent 的记忆系统如何设计才能避免"上下文窗口爆炸"？

**答**：

```
核心矛盾：
  记忆越多 → 上下文越丰富 → 回答质量越高
  记忆越多 → Token 消耗越大 → 成本越高 + 延迟越高

解法：分层记忆 + 智能压缩

策略1：记忆预算分配（Token Budget）
  总预算：4096 Token（以 8K 上下文为例）
  ├── System Prompt: 512 Token（12.5%）
  ├── 工作记忆: 1024 Token（25%）——最近对话
  ├── 检索记忆: 1536 Token（37.5%）——RAG / 长期记忆检索结果
  └── 预留: 1024 Token（25%）——LLM 输出空间

策略2：记忆压缩
  ├── 对话摘要：每10轮对话压缩为1段摘要（~100 Token）
  ├── 关键信息提取：用 LLM 从长文本中提取关键事实
  └── 渐进式压缩：新信息详细，旧信息逐步压缩

策略3：记忆淘汰
  ├── LRU（最近最少使用）：淘汰最久未访问的记忆
  ├── 重要性加权：低重要性的记忆优先淘汰
  └── 遗忘曲线：模拟人类记忆衰减

策略4：检索增强（按需加载）
  不是把所有记忆塞进上下文，而是：
  1. 根据当前问题，检索最相关的 Top-K 条记忆
  2. 只把检索结果放进上下文
  3. 类似 RAG，但检索的对象是"记忆"而非"文档"
```

**量化效果**：
> "通过记忆预算分配 + 对话摘要，我们将平均上下文长度从 6000 Token 降到 2800 Token，成本降低 53%，同时通过智能检索保证了关键信息不丢失，回答质量下降不到 3%。"

### Q4: 如何评估一个 LLM 应用的质量？除了准确率还看什么？

**答**：

```
LLM 应用评估五维模型：

维度1：正确性（Correctness）
  回答是否事实正确？
  方法：黄金数据集 + LLM-as-Judge + 人工抽检

维度2：相关性（Relevance）
  回答是否切题？
  方法：RAGAS 的 Answer Relevancy 指标

维度3：完整性（Completeness）
  回答是否覆盖了所有要点？
  方法：要点覆盖率（参考答案的 N 个要点，命中几个）

维度4：安全性（Safety）
  回答是否包含有害内容？
  方法：安全分类器 + 红队测试

维度5：效率（Efficiency）
  Token 消耗、延迟、成本
  方法：可观测性系统实时监控

实战：评估流水线
  每次更新 → 自动跑 200 条基准测试 → 五维评分
  任一维度下降 >5% → 阻止上线
  正确性下降 >2% → 紧急回滚
```

### Q5: LangGraph 和 LangChain 是什么关系？为什么要引入 LangGraph？

**答**：

```
LangChain 的局限：
  Chain 是线性的：A → B → C → D
  Agent 是循环的：LLM ↔ Tool ↔ LLM ↔ Tool...
  LangChain 的 AgentExecutor 对复杂 Agent 编排力不从心

LangGraph 解决的问题：
  用图（Graph）来表达 Agent 的状态机

  普通对话 Agent：
    START → llm_call → should_use_tool?
                        ├── yes → tool_call → llm_call（循环）
                        └── no → END

  多 Agent 协作：
    START → router → researcher → writer → reviewer
                    ↗                         ↓
                  (需要更多资料) ←─────────── 修改

核心概念：
  State：图的状态（消息列表、工具调用结果等）
  Node：图的节点（LLM 调用、工具执行、条件判断）
  Edge：图的边（状态转移规则）
  Conditional Edge：条件边（根据 LLM 输出决定下一步）

对比：
  LangChain：适合线性 Pipeline
  LangGraph：适合复杂状态机、多 Agent 协作、人机交互循环
```

#### **系统架构**


```python
class SmartScheduler:
    """智能调度器：依赖感知 + 并行优化"""

    async def schedule(self, tool_calls: list[ToolCall]) -> list[ToolResult]:
        # 1. 分析依赖关系
        groups = self._group_by_dependency(tool_calls)

        results = []
        for group in groups:
            if len(group) == 1:
                # 单个工具 → 直接执行
                result = await self._execute_with_retry(group[0])
                results.append(result)
            else:
                # 多个无冲突工具 → 并行执行
                group_results = await asyncio.gather(
                    *[self._execute_with_retry(tc) for tc in group],
                    return_exceptions=True
                )
                for r in group_results:
                    if isinstance(r, Exception):
                        results.append(ToolResult(error=str(r)))
                    else:
                        results.append(r)

        return results

    def _group_by_dependency(self, tool_calls):
        """将工具调用分组：无冲突的归为一组（可并行）"""
        groups = []
        current_group = []
        current_write_resources = set()

        for tc in tool_calls:
            resources = self.resource_map.get(tc.name, {"read": [], "write": []})
            write_set = set(resources.get("write", []))

            if write_set & current_write_resources:
                # 冲突 → 当前组结束，新开一组
                if current_group:
                    groups.append(current_group)
                current_group = [tc]
                current_write_resources = write_set
            else:
                current_group.append(tc)
                current_write_resources.update(write_set)

        if current_group:
            groups.append(current_group)

        return groups
```

**STAR 答题**：
> "**S**（情境）：我们的 AI 助手需要调用 5+ 个工具，但并行调用出现过数据竞争（余额查询和转账同时执行导致不一致）。**T**（任务）：设计可靠的多工具调用系统，支持并行加速但不牺牲一致性。**A**（行动）：四层架构——Schema 校验层、依赖感知调度层、重试执行层、循环控制层。调度器用 DAG 分析读写冲突，无冲突并行、有冲突串行。**R**（结果）：并行场景延迟从 8s 降到 2.5s，串行一致性 100%，工具调用成功率从 92% 提升到 99.3%。"

### 问题 2：请设计一个 Agent 的记忆系统，要求支持跨会话记忆、记忆衰减、和按需检索，同时控制上下文窗口不超过预算

#### **关键算法：记忆预算控制器**

```python
class MemoryBudgetController:
    """记忆 Token 预算控制器"""

    def __init__(self, total_budget: int = 4096):
        self.budget = {
            "system_prompt": 512,    # 12.5%
            "working": 1024,         # 25%
            "short_term": 512,       # 12.5%
            "long_term_recall": 1536, # 37.5%
            "output_reserve": 1024,   # 25%
        }
        self.tokenizer = tiktoken.encoding_for_model("gpt-4o")

    def count_tokens(self, text: str) -> int:
        return len(self.tokenizer.encode(text))

    async def build_context(self, query: str, memories: AgentMemorySystem) -> list[dict]:
        """构建符合预算的上下文"""

        messages = []

        # 1. System Prompt（固定预算）
        system_prompt = self._build_system_prompt()
        messages.append({"role": "system", "content": system_prompt})

        # 2. 长期记忆检索（按预算截断）
        recalled = await memories.recall(query, top_k=10)
        recall_text = self._format_recalled_memories(recalled)
        recall_text = self._truncate_to_budget(recall_text, self.budget["long_term_recall"])

        if recall_text:
            messages.append({
                "role": "system",
                "content": f"[相关历史记忆]\n{recall_text}"
            })

        # 3. 短期记忆（摘要）
        short_term_summary = memories.get_short_term_summary()
        short_term_summary = self._truncate_to_budget(
            short_term_summary, self.budget["short_term"]
        )
        if short_term_summary:
            messages.append({
                "role": "system",
                "content": f"[近期对话摘要]\n{short_term_summary}"
            })

        # 4. 工作记忆（最近对话原文）
        working = memories.working_memory[-5:]
        for m in working:
            messages.append(m)

        return messages

    def _truncate_to_budget(self, text: str, budget: int) -> str:
        """截断到预算内"""
        tokens = self.tokenizer.encode(text)
        if len(tokens) <= budget:
            return text
        truncated_tokens = tokens[:budget]
        return self.tokenizer.decode(truncated_tokens) + "\n[...已截断]"
```

#### **面试加分点**

```
1. 记忆升级策略：
   短期记忆满时 → 按重要性排序 → Top 20% 升级为长期记忆 → 其余按遗忘曲线衰减

2. 记忆冲突处理：
```

### 问题 3：你如何为一个自研的 LLM 应用框架搭建可观测性系统？需要监控哪些指标？如何做异常检测？

**场景**：
- 你从零开发了一套 Agent 框架（没用 LangChain），包括 RAG、Tool Calling、多轮对话
- 上线后发现偶尔出现回答质量下降、Token 消耗异常增高、工具调用超时等问题
- 如何设计可观测性系统来快速定位和解决这些问题？

**参考答案要点**：

#### **可观测性三层架构**

```
Layer 1：数据采集（Instrumentation）
  每次请求的完整追踪：
  ├── 请求级：trace_id、user_id、timestamp、总延迟、总 Token、总费用
  ├── RAG 级：检索 query、检索结果数、Rerank 分数、检索延迟
  ├── LLM 级：model、input/output tokens、延迟、finish_reason
  ├── Tool 级：tool_name、参数、返回值、执行时间、重试次数
  └── 输出级：完整输出、安全检测结果、用户反馈

Layer 2：指标聚合（Metrics）
  核心仪表盘指标：
  ├── 延迟：P50/P95/P99 延迟分位数
  ├── 吞吐量：QPS、并发请求数
  ├── 成本：每日 Token 消耗、每日费用、单请求平均费用
  ├── 质量：用户满意度、幻觉率（抽检）、安全拦截率
  ├── 工具：调用频率 Top10、失败率 Top5、平均执行时间
  └── 异常：4xx/5xx 错误率、超时率、重试率

Layer 3：异常检测与告警（Alerting）
  三级告警：
  ├── P0（紧急）：错误率 >5% 或服务不可用 → 即时通知
  ├── P1（重要）：P95 延迟 >10s 或单日费用超预算 50% → 15分钟内通知
  └── P2（关注）：Token 消耗趋势异常上升 → 每日报告
```

#### **异常检测算法**

```python
class LLMAnomalyDetector:
    """LLM 应用异常检测"""

    def __init__(self):
        self.baselines = {}  # 指标基线

    def update_baseline(self, metric: str, values: list[float]):
        """更新指标基线（滑动窗口均值±2σ）"""
        import numpy as np
        self.baselines[metric] = {
            "mean": np.mean(values[-100:]),      # 最近100个值的均值
            "std": np.std(values[-100:]),         # 标准差
            "threshold_upper": np.mean(values[-100:]) + 2 * np.std(values[-100:]),
            "threshold_lower": np.mean(values[-100:]) - 2 * np.std(values[-100:]),
        }

    def check_anomaly(self, metric: str, value: float) -> dict:
        """检测单个指标是否异常"""
        if metric not in self.baselines:
            return {"is_anomaly": False, "reason": "无基线数据"}

        baseline = self.baselines[metric]
        is_anomaly = (
            value > baseline["threshold_upper"] or
            value < baseline["threshold_lower"]
        )

        return {
            "is_anomaly": is_anomaly,
            "value": value,
            "baseline_mean": round(baseline["mean"], 2),
            "threshold_upper": round(baseline["threshold_upper"], 2),
            "deviation_sigma": round(abs(value - baseline["mean"]) / max(baseline["std"], 0.01), 2),
            "severity": "high" if abs(value - baseline["mean"]) / max(baseline["std"], 0.01) > 3 else "medium"
        }

    def detect_cost_anomaly(self, daily_cost: float, history: list[float]) -> dict:
        """成本异常检测（特殊的，因为成本只关心上升）"""
        self.update_baseline("daily_cost", history)
        baseline = self.baselines["daily_cost"]

        if daily_cost > baseline["threshold_upper"]:
            # 成本异常上升 → 进一步分析原因
            return {
                "is_anomaly": True,
                "daily_cost": daily_cost,
                "expected_range": f"{baseline['threshold_lower']:.2f} ~ {baseline['threshold_upper']:.2f}",
                "possible_causes": [
                    "RAG 检索返回了过多文档（上下文过长）",
                    "工具调用重试次数增加（API 不稳定）",
                    "用户输入变长（输入 Token 增加）",
                    "模型被替换为更贵的版本"
                ],
                "recommendation": "检查 Token 用量分布（input vs output）、工具调用频率、RAG 检索结果数量"
            }

        return {"is_anomaly": False}
```

**面试表达**：
> "我们的可观测性系统分三层。采集层：每次请求记录完整 Trace（RAG→LLM→Tool→Output 四个 Span），包括 Token、延迟、费用。指标层：实时聚合延迟分位数、成本趋势、工具失败率。异常层：用滑动窗口均值±2σ 做基线，超出即告警。最关键的是成本异常检测——一旦日费用超基线上限，自动分析可能原因（RAG 返回过多文档？工具重试？模型被替换？），并给出排查建议。这套系统帮我们把平均故障定位时间从 2 小时降到 15 分钟。"
