### 1.3 核心亮点 1：生产级 DAG 动态调度器

不是简单的"串行执行"，而是**依赖感知 + 分层并行 + 失败隔离 + 熔断降级**的工业调度。

```python
from collections import defaultdict, deque
import json

class DAGScheduler:
    def __init__(self):
        self.nodes = {}          # name -> callable
        self.deps  = defaultdict(set)   # name -> set(前置依赖)
        self.status = {}         # name -> 'pending'|'running'|'done'|'failed'
        self.max_retry = 3
        self.circuit_open = set()  # 熔断的节点

    def add(self, name, fn, depends_on=None, fallback=None):
        self.nodes[name] = (fn, fallback)
        self.deps[name] = set(depends_on or [])

    # ---- 环检测：有向图入度法，O(V+E) ----
    def _detect_cycle(self):
        indeg = {n: len(self.deps[n]) for n in self.nodes}
        q = deque([n for n in self.nodes if indeg[n] == 0])
        seen = 0
        adj = defaultdict(list)
        for n, ds in self.deps.items():
            for d in ds: adj[d].append(n)
        while q:
            u = q.popleft(); seen += 1
            for v in adj[u]:
                indeg[v] -= 1
                if indeg[v] == 0: q.append(v)
        if seen != len(self.nodes):
            raise RuntimeError("DAG 存在环，无法调度")

    # ---- 分层并行：同层无依赖可并发 ----
    def _topo_layers(self):
        indeg = {n: len(self.deps[n]) for n in self.nodes}
        layers, done = [], set()
        while len(done) < len(self.nodes):
            layer = [n for n in self.nodes if n not in done and indeg[n] == 0]
            if not layer: raise RuntimeError("DAG 死锁")
            for n in layer:
                for c in self.nodes:
                    if n in self.deps[c]: indeg[c] -= 1
                done.add(n)
            layers.append(layer)
        return layers

    async def run(self):
        self._detect_cycle()
        for layer in self._topo_layers():
            # 同层并发执行
            tasks = [self._run_node(n) for n in layer]
            await asyncio.gather(*tasks)

    async def _run_node(self, name):
        if name in self.circuit_open:        # 已熔断→直接走 fallback
            return await self._fallback(name)
        fn, fallback = self.nodes[name]
        for attempt in range(self.max_retry + 1):
            try:
                self.status[name] = 'running'
                return await fn()
            except Exception as e:
                if attempt == self.max_retry:
                    if fallback: return await self._fallback(name)
                    self.circuit_open.add(name)   # 连续失败→熔断
                    self.status[name] = 'failed'
                    raise
                await asyncio.sleep(2 ** attempt)  # 指数退避
```

**面试亮点**：能讲清"为什么需要环检测（防止 Planner 自我引用死循环）"、"分层并行的收益（无依赖节点并发，整体时延≈最长链而非链和）"、"熔断 vs 重试的边界（重试解决瞬时故障，熔断解决持续故障，避免雪崩）"。

### 1.4 核心亮点 2：百万用户的三层记忆系统

| 层级 | 存储 | 容量 | 时效 | 命中率 | 典型用途 |
|------|------|------|------|--------|---------|
| 工作记忆 | 进程内 / Session | KB | 单次会话 | 100% | 当前多轮上下文 |
| 短期记忆 | Redis（TTL 7d） | GB | 跨会话周级 | 38% | 用户偏好、最近任务 |
| 长期记忆 | 向量库（Milvus） | TB | 永久 | 22% | 历史知识、经验沉淀 |

**关键设计**：记忆写入走"异步双写 + 去重 + 重要性打分"，避免无脑灌入导致噪声。重要性打分用一个轻量分类器（是否含决策/偏好/事实）。

```python
async def write_memory(user_id, text, emb_model, vec_db, redis):
    imp = importance_score(text)           # 0~1，轻量本地模型
    if imp < 0.3: return                    # 低重要→直接丢弃，防噪声
    vec = emb_model.encode(text)
    # 异步双写：Redis 短期 + 向量库长期
    await asyncio.gather(
        redis.set(f"mem:{user_id}:{hash(text)}", text, ex=604800),
        vec_db.upsert(user_id, vec, text, importance=imp),
    )

def retrieve_memory(query_vec, user_id, vec_db, top_k=5):
    # 只召回重要性>0.5 的，降低幻觉源
    return vec_db.search(query_vec, user_id, top_k=top_k, min_imp=0.5)
```

### 1.5 核心亮点 3：工具调用可靠性工程

工具调用是 Agent 失败的高发区（JSON 非法、参数缺失、外部超时）。我们用三板斧把成功率从 55% 拉到 92%：

1. **Grammar-Constrained Decoding（约束解码）**：在 token 级用 JSON Schema 掩码，保证 99.6% 输出合法 JSON（而非事后修复）。
2. **双通道 + 自愈**：主通道结构化输出；失败时走"宽松解析 + 字段补齐"自愈通道。
3. **Fallback 链**：外部 API 超时时，自动降级到缓存结果 / 简化工具 / 人工兜底。

```python
def safe_parse(tool_schema, raw_text):
    # 第一板斧：严格 JSON
    try:
        return json.loads(raw_text)
    except Exception:
        pass
    # 第二板斧：容错修复（去尾逗号、补引号、抽 {...}）
    cleaned = repair_json(raw_text)
    try:
        obj = json.loads(cleaned)
        validate_against_schema(obj, tool_schema)  # 字段/类型校验
        return obj
    except Exception:
        # 第三板斧：兜底——返回空参数并触发 Fallback 工具
        return {"__fallback__": True, "raw": raw_text}
```

### 1.6 核心亮点 4：全链路可观测性

每个请求注入 `trace_id`，跨 Agent / 工具 / 模型调用串联；关键埋点：

- **Tracing**：每跳耗时、token 数、调用了哪个工具、哪层记忆命中。
- **Metrics**：P50/P90/P99 延迟、工具成功率、幻觉率（Online Eval 采样 5%）。
- **Online Eval**：对 5% 流量用轻量 Judge 打分（满意度 / 事实一致性），偏差校正（位置/长度偏置）。

→ 质量问题从"用户投诉后 7 天发现"变成"监控告警 30 分钟内定位"。

### 1.7 核心亮点 5：成本工程（推理成本 -71%）

成本模型： `单次成本 = Σ(路由模型单价 × 该层 token 数) × (1 - 缓存命中率)`。三招：

1. **模型路由**：80% 简单流量走 7B，仅 20% 走 70B → 单价 -80%。
2. **KV Cache 复用**：相同 System Prompt / 长文档前缀走 Prefix Caching，命中省去重算。
3. **语义缓存**：相似问题直接返回历史答案，命中率 ~35%。

## 📌 二、技术难点（开发过程中的关键技术难点与解决方案）

### 2.1 多 Agent 编排的"任务发散/循环"

**现象**：Planner 反复生成相似子任务，Agent 在 A→B→A 间打转，token 爆炸、任务永不结束。

**根因**：缺乏"已完成任务"的状态约束 + 缺乏最大步数硬限。

**解决方案**：
- DAG 化：Planner 产出有依赖关系的任务图，而非自由文本列表。
- 状态机约束：每完成一个节点打 `done` 标记，禁止重复调度。
- 硬限 + 反思：超过 `max_steps=12` 强制进入 Reflector，输出"无法完成"并给出部分结果。

### 2.2 大规模推理成本 + KV Cache 显存

**现象**：百万用户并发，KV Cache 显存成为瓶颈，单卡只能跑极少并发。

**根因**：MHA 下 KV Cache 随序列长度线性增长：`KV_size = 2 × L × n_layers × n_kv_heads × d_head × T × 2(bytes)`。

**解决方案**：
- 模型侧换 GQA/MLA（KV head 数从 32→8→压缩到低秩），KV 显存 -82%。
- 服务侧 PagedAttention（显存利用率 60%→92%）+ Prefix Caching（共享前缀）。
- 业务侧上文压缩：超长文档先 LLMLingua 压到 30% 再入上下文。

### 2.3 工具调用可靠性

见 1.5。核心认知：**"让模型输出 100% 合法 JSON"靠的是约束解码（阻止错误 token 出现），而不是生成后再修**。修复通道只是兜底，不能当主路径。

### 2.4 长上下文与记忆"遗忘/污染"

**现象**：会话越长，早期关键信息被挤出窗口；或记忆库召回了错误/过时的旧记忆，造成幻觉。

**解决方案**：
- 滑动窗口 + 自动摘要：超出窗口的旧轮次先摘要再保留。
- 记忆重要性打分 + 最小阈值召回（2.4 节代码），降低噪声污染。
- 关键事实"钉死"：用户明确给定的 ID/规则，以结构化字段注入，不参与向量召回，避免被错误记忆覆盖。

### 2.5 幻觉与可控性工程化

**现象**：模型自信地编造工具不存在的返回值、或引用不存在的文档。

**解决方案（四层）**：
1. 工具返回值做 schema 校验，非法直接判失败触发重试。
2. RAG 回答强制"引用约束生成"（每个论断必须挂 citation，无引用句扣分）。
3. Guardrail 层对事实性断言做轻量一致性检查。
4. Online Eval 持续监控幻觉率，>阈值自动告警 + 回滚 Prompt。

### 2.6 多租户隔离与 SLA 保障

**难点**：数十个业务线共用底座，某业务突发流量不能拖垮其他业务；且需按租户计费。

**解决方案**：
- 配额隔离：每租户令牌桶限流 + 独立推理队列，避免头号租户占满 GPU。
- 优先级调度：付费租户优先，免费租户排队。
- 计费埋点：每请求记录 token / 模型 / 工具调用次数 → 按租户聚合出账单。

## 📌 三、常见问答（Common Interview Q&A · 深度版）

### Q1：Agent Harness 和普通 RPA / 工作流编排（如 Airflow）的本质区别？

**答（分三层）**：
1. **决策方式**：RPA/工作流是**静态图**，节点与边在编码时写死；Agent 是**动态图**，Planner 根据运行时状态实时决定下一步（LLM 充当"软控制器"）。
2. **容错粒度**：工作流失败按节点重试；Agent 能**反思并改路径**（A 失败→尝试 B 或降级），具备目标驱动的自愈。
3. **知识接口**：Agent 原生接 LLM（理解非结构化输入、自然语言规划），RPA 只能处理结构化触发。

**加分项**：能指出 Agent 的代价——不确定性（同输入不同路径）、可解释性差、调试难，所以生产上我们用"DAG 约束 + 状态机"把 Agent 的不确定收敛到可控范围。

### Q2：如何支撑百万用户的 KV Cache 与记忆？

**答**：
- **短期会话 KV**：用 PagedAttention 分页 + Prefix Caching 共享系统提示前缀，显存利用率 92%。
- **跨会话记忆**：Redis（周级，热数据）+ 向量库（永久，冷知识），异步双写 + 重要性去重（见 1.4）。
- **成本**：KV 复用 + 语义缓存把重复计算降到最低；超长文档先压缩再入上下文。

### Q3：RAG 召回率上不去，怎么系统排查？

**答（分层）**：
1. **召回层**：换更好的 Embedding（BGE-M3）、上混合检索（向量 + BM25）、加重排（Cross-Encoder）。
2. **切分层**：检查 chunk 是否切太碎/太大；用布局感知切分 + 父子文档。
3. **索引层**：检查向量库参数（IVF-PQ 的 nprobe 是否过小）。
4. **评测层**：用 nDCG@10 / Recall@10 量化，而不是直接看体感。

### Q4：如何把幻觉率压到可控范围？

**答（四层，见 2.5）**：工具 schema 校验 + RAG 引用约束 + Guardrail 事实检查 + Online Eval 监控回滚。核心心法：**幻觉不能靠"提示词让它别编"解决，必须靠"系统把编造的空间堵死"**。

### Q5：MoE 负载均衡在推理服务里怎么落地？

**答**：训练侧用 Auxiliary-Loss-Free 路由（不引入额外损失，用偏置项动态平衡）；推理侧要保证每个 expert 的 batch 均匀，否则出现"热门 expert 排队、冷门 expert 空闲"。落地手段：动态路由偏置 + 按 expert 负载做 micro-batch 重排 + 监控各 expert 命中分布。

### Q6：推理成本如何优化 70%+？

**答（成本模型驱动）**：`成本 = 路由单价 × token 数 × (1 - 缓存命中率)`。
- 模型路由（7B 承接 80% 流量）：-80%
- 语义缓存 + KV 复用：-30%~
- 量化（INT8/FP8）：吞吐 +100%，单价 -50%
- 上文压缩：长文档 -70% token
三者叠加（非简单相加，有重叠）综合 -71%。

### 🎯 模拟面试题 1：设计支撑百万用户的多 Agent 端到端系统

**参考答案要点（分层作答）**：

5. **记忆层**：工作/短期（Redis）/长期（向量库）三层，异步双写 + 重要性去重。
6. **可观测层**：全链路 Tracing + Online Eval 采样打分 + 30 分钟级告警。
7. **成本层**：语义缓存 + KV 复用 + 量化，综合 -71%。

**加分项**：主动谈"不确定性收敛"——生产 Agent 必须给 LLM 的自由度加约束（DAG/状态机/硬限），否则不可运维。

### 🎯 模拟面试题 2：Agent Harness 的调度可靠性架构如何设计，保证单点故障不影响整体？

**参考答案要点**：

1. **节点级隔离**：每个工具/Agent 节点独立超时 + 独立重试预算（3 次指数退避），失败不污染其他节点。
2. **熔断机制**：某节点连续失败 → 打开熔断，后续请求直接走 Fallback，不再打爆已故障依赖（防雪崩，见 1.3 代码 `circuit_open`）。
3. **无状态 + 幂等**：调度器无状态，任务可重放；工具调用带幂等键，重试安全。
4. **降级金字塔**：70B 挂→13B→7B→缓存结果，逐级保可用。
5. **Checkpoint**：长任务每完成一个 DAG 节点持久化进度，故障后从断点续跑而非从头。
6. **多区域**：推理集群跨可用区部署，区域级故障 DNS 60s 切换。

**加分项**：能区分"重试解决瞬时故障，熔断解决持续故障"——这是 SRE 基本功，很多人混为一谈。

### 🎯 模拟面试题 3：某天工具调用失败率从 5% 突增到 40%，你如何 30 分钟内止血并复盘？

**参考答案要点（止血→定位→根治）**：

**0-5 分钟（止血）**：
- 监控发现失败率破 P1 阈值 → 自动/手动打开该工具熔断，请求走 Fallback（缓存/简化工具），先把成功率拉回。
- 若为关键路径，临时降级到 7B 模型或返回"部分完成"。

**5-20 分钟（定位）**：
- 按 `trace_id` 下钻：是某一类工具全挂，还是特定租户？
- 看错误分布：超时（下游 RT 升高）？JSON 解析失败（模型版本回退）？鉴权 403（密钥过期）？
- 对比变更：最近是否上了新 Prompt / 新模型版本 / 新工具 Schema。

**20-30 分钟（初步根因）**：
- 常见三类：①下游 API 故障/限流 ②模型升级导致输出格式漂移 ③Schema 改动未同步。

**根治 + 防复发**：
- 工具调用加约束解码 + 自愈通道（见 1.5），降低对模型格式的脆弱依赖。
- 外部环境加熔断 + 降级 + 重试预算。
- 上线"Schema 变更联动回归测试"，防止格式漂移悄悄上线。

**加分项**：强调"可观测性是一切的前提"——没有全链路 trace，30 分钟定位是不可能的；以及"Fallback 不是偷懒，是生产系统的必备安全网"。

## 📌 五、今日速记卡（Flashcards）

| 考点 | 一句话答案 |
|------|-----------|
| Agent vs RPA | Agent 是动态图+LLM软控制+可反思改路；RPA 是静态图+固定路径 |
| 防 Agent 循环 | DAG 约束 + 状态机 done 标记 + max_steps 硬限 + Reflector |
| 100% 合法 JSON | 靠约束解码阻止错误 token，不是生成后修 |
| KV 显存公式 | `2·L·n_layers·n_kv_heads·d_head·T·2`，GQA/MLA 压 n_kv_heads |
| 成本模型 | `路由单价 × token × (1-缓存命中率)` |
| 幻觉治理 | 堵死编造空间：schema校验+引用约束+Guardrail+Online Eval |
| 重试 vs 熔断 | 重试治瞬时故障，熔断治持续故障，防雪崩 |
| 故障止血 | 先熔断+Fallback 拉回成功率，再 trace 下钻定位 |
