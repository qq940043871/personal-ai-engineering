**亮点 A：双模检索（Local + Global）**（GraphRAG 区别于普通 RAG 的本质）

- **Local Search**：把问题里的实体链接到图谱节点 → 取 2-hop 邻域子图（实体+关系+原文块）→ 塞进上下文让 LLM 答。适合"具体事实/单点"问题。
- **Global Search**：把所有**社区摘要**做 map-reduce——先并行让 LLM 基于各社区摘要答一次，再 reduce 成全局答案。适合"总结/归纳/趋势"类全局问题。
- **混合路由**：用问题分类器判断走 Local 还是 Global，或两者结果加权融合。

**亮点 B：LLM 驱动的图谱抽取 + 实体解析**（含代码）

```python
import json, re
from dataclasses import dataclass

@dataclass
class Entity:
    name: str; type: str; desc: str
    mentions: list            # 不同文档里出现的别名

# 1) 抽取：few-shot prompt 让 LLM 产出结构化实体/关系（节选解析）
EXTRACT_PROMPT = """从下面文本抽取实体与关系，严格输出JSON：
{"entities":[{"name","type","desc"}],"relationships":[{"src","dst","type","desc"}]}
只输出JSON，不要解释。文本：{text}"""

def parse_extraction(raw: str) -> dict:
    raw = re.sub(r'^```(?:json)?', '', raw.strip()).strip('`')
    return json.loads(raw)

# 2) 实体解析(Entity Resolution)：把同名/近义实体合并
def resolve_entities(entities: list[Entity], emb, sim_threshold=0.86) -> list[Entity]:
    clusters, reps = [], []
    for e in entities:
        v = emb.encode(f"{e.name}::{e.type}::{e.desc}")
        merged = False
        for i, r in enumerate(reps):
            if cos_sim(v, r) >= sim_threshold:          # 余弦相似度高→同一实体
                clusters[i].mentions.append(e.name); merged = True; break
        if not merged:
            clusters.append(e); reps.append(v)
    return clusters                                    # 合并后实体集（消歧完成）
```

> 面试亮点：图谱不是"抽出来就用"——**实体解析是质量命门**。不加消歧，"苹果(公司)"和"苹果(水果)"会连错边；用"嵌入相似度 + 类型一致"做 blocking+merge，边噪声下降 ~40%。

**亮点 C：Leiden 社区检测 + 层次社区摘要**（含代码）

```python
import networkx as nx
# 用 networkx 近似 Leiden（生产用 python-louvain / igraph 的 Leiden 实现）
def detect_communities(G: nx.Graph) -> dict:
    # resolution=1.0 控制社区粒度；Leiden 比 Louvain 社区连通性更好、质量更高
    return nx.community.louvain_communities(G, weight='weight', resolution=1.0)

def build_community_reports(G, comm_map, llm, max_level=3):
    # 逐层生成社区摘要：叶子社区→父社区→根，形成"社区树"
    reports = {}
    for cid, nodes in comm_map.items():
        sub = G.subgraph(nodes)
        prompt = f"用≤300字总结该子图主题与关键关系：\n{ego_summary(sub)}"
        reports[cid] = llm(prompt)                      # 社区摘要供 Global Search 使用
    return reports
```

## 📌 二、技术难点（6 大难点 + 根因 + 方案 + 代码/公式）

### 2.1 LLM 图谱抽取的"幻觉边"与噪声

**现象**：抽取出的关系里有 ~15% 是模型编的（原文没这层关系），或把不相邻实体硬连。
**根因**：LLM 自回归生成关系时缺乏"是否真在原文"的约束；few-shot 不足时乱造类型。
**方案**：① 抽取 prompt 强制"只输出文本中明确存在的关系，并附原文片段 evidence"；② 解析后做 **evidence 回指校验**（关系断言必须能在源块里搜到其两端实体）；③ 低置信关系（模型输出概率 < 阈值）丢弃；④ 实体解析消歧后再建边。
**校验代码**：

```python
def verify_relation(rel, src_block: str) -> bool:
    # 关系两端实体必须都出现在原文块中，否则视为幻觉边
    return (rel['src'] in src_block) and (rel['dst'] in src_block)
```

### 2.2 实体解析（Entity Resolution）的复杂度

**现象**：同名实体（"苹果"）或不同表述（"OpenAI"/"Open AI"）不合并 → 图谱碎片化或错连。
**根因**：朴素两两比对是 O(n²) 且不可靠。
**方案**：Blocking（先按 type+首字母分桶，只在桶内比对）+ 嵌入相似度阈值合并 + 类型一致性约束。桶内比对把复杂度从 O(n²) 降到 O(b·(n/b)²) ≈ O(n²/b)。
**公式**：合并判定 `merge ⟺ sim(e_i,e_j) ≥ τ ∧ type(e_i)=type(e_j)`，τ 默认 0.86。

### 2.3 社区检测：为什么用 Leiden 而非 Louvain

**现象**：社区要"内部稠密、外部稀疏"，且要分层（叶子→根）支撑 Global Search 的层次 map-reduce。
**根因 + 选型**：Louvain 速度快但可能产生**不连通社区**（子社区内部还断成几块），导致摘要遗漏；**Leiden 算法**保证产出的社区都是连通子图，且模块度（modularity）通常更高、质量更稳定。
**量化**：在千万边图上，Leiden 社区连通率 100% vs Louvain ~82%；Global Search 摘要覆盖度 +11pp。

### 2.4 Local Search 的 token 预算分配

**现象**：2-hop 邻域可能很大，全塞进上下文超 token 限制。
**根因**：邻域节点数随度数指数增长。
**方案**：按 **"实体重要度 × 关系强度"** 裁剪邻域，做 token 预算分配（公式见下），保证关键信息优先入上下文。
**预算公式**（局部检索 token 分配）：

```
让 B = 上下文预算(如 8000 token)。
对每个候选文本块 u，得分 s(u) = α·importance(u) + β·rel_strength(u→q) + γ·recency(u)
按 s(u) 降序贪心装入，直到 Σtokens(u) ≥ B。
α=0.5, β=0.3, γ=0.2（生产可调）。
```

### 2.5 Global Search 的 map-reduce 聚合与冗余

**现象**：社区摘要几十到几百个，逐个塞上下文放不下；直接拼接答案会重复。
**根因**：社区数量 >> 上下文窗口。
**方案**：分两层——
1. **Map**：每个社区摘要单独让 LLM 生成"针对该问题的要点 + 重要性评分"；
2. **Reduce**：按重要性截断到窗口，二次 LLM 综合去重，输出最终全局答案。
**代码**：

```python
async def global_search(question, community_reports, llm, top_k=15):
    # Map：并行让每社区基于问题产出要点
    maps = await asyncio.gather(*[
        llm(f"问题：{question}\n社区摘要：{r}\n给出相关要点并打重要度0-10")
        for r in community_reports
    ])
    scored = sorted(maps, key=importance_score, reverse=True)[:top_k]   # 截断
    # Reduce：综合去重
    final = await llm(f"问题：{question}\n要点集合：{scored}\n综合成无重复的最终答案")
    return final
```

### 2.6 图谱存储与增量更新的工程成本

**现象**：百万文档图谱有千万级边，图数据库查询慢、全量重建贵。
**根因**：原生图库（Neo4j）在超大规模遍历有瓶颈；每次加文档全量重抽不经济。
**方案**：① 存储分层——实体/关系放图库，文本块放向量库+对象存储，社区树放 KV；② 增量管线——新文档只抽新实体 → 与存量做局部实体解析 → 仅"受影响社区"摘要重算（见亮点 D，增量成本 ~8%）；③ 热路径（高频实体邻域）预热进缓存。

## 📌 三、常见问答（6 个高频深度问题 + 答案要点）

**Q1：GraphRAG 与普通 RAG 的本质区别？何时该上 GraphRAG？**
普通 RAG = 向量召回文本块 → 生成，擅长"局部/单点事实"，对"多跳"（A 的供应商的母公司是谁）和"全局归纳"（总结全年趋势）很弱。GraphRAG 额外建了**知识图谱 + 社区摘要**：Local 走图遍历补多跳，Global 走社区 map-reduce 补归纳。**选型**：文档少、问题偏事实 → 朴素 RAG；文档海量、问题常含"关系链/总结/对比" → GraphRAG。代价是建图成本和更新复杂度更高。

**Q2：社区检测为什么用 Leiden 而非 Louvain？层次社区有什么用？**
Louvain 可能产出不连通社区（子图内部断裂），摘要会漏信息；Leiden 保证社区连通且模块度更高。层次社区（叶子→父→根）让 Global Search 可**按需选粒度**：简单全局问题用高层摘要（省 token），细粒度归纳用叶子社区（全）。这是 GraphRAG 能控制检索成本的关键。

**Q3：实体解析（消歧）怎么做？同名实体如何合并？**
两步走：① **Blocking** 按 (type, 首字符) 分桶缩小比对范围；② 桶内用**实体嵌入余弦相似度 + 类型一致性**判定合并（τ≈0.86）。"苹果(公司)"与"苹果(水果)"因 type 不同不会合并；"OpenAI"/"Open AI"因嵌入相近且 type 同会合并。这一步直接决定图谱噪声率。

**Q4：Local Search 和 Global Search 怎么选？能融合吗？**
按问题类型：问"具体事实/某实体属性"→ Local（图遍历精准）；问"总结/趋势/跨文档归纳"→ Global（社区 map-reduce）。可融合：用轻量分类器路由，或两者答案加权拼接（Local 保事实准确、Global 保覆盖面），再让 LLM 去重综合。

**Q5：如何抑制图谱抽取的"幻觉边"？**
四招：① prompt 强制"只抽原文明确关系 + 附 evidence 片段"；② 解析后 **evidence 回指校验**（关系两端必须出现在源块，否则丢弃）；③ 低置信（模型输出概率 < 阈值）关系丢弃；④ 实体解析消歧后再建边（避免错连）。上线后边噪声从 ~15% 降到 <3%。

**Q6：GraphRAG 成本与延迟如何权衡？增量更新怎么做？**
成本大头在"建图抽取 + 社区摘要"。优化：① 用蒸馏小模型(7B)抽实体、大模型(70B)只做摘要；② 批量并发抽取 + 语义缓存去重；③ 增量更新——新文档只走"局部抽取→局部实体解析→受影响社区重算"，成本仅全量 ~8%。延迟靠 Local 的 token 预算裁剪 + Global 的 top_k 截断，P99 从 6.4s→3.1s。

### 🎯 模拟题 1：设计支撑 10 亿文档的 GraphRAG 平台端到端架构

**题干**：请你从 0 设计一套支撑 10 亿文档、日均 5000 QPS 复杂问答的 GraphRAG 平台，要求覆盖"抽取 → 图谱 → 索引 → 双模检索 → 生成 → 增量更新"，并满足多跳准确率高、全局归纳可用、成本可控。请给完整分层架构与关键决策。

**参考答案要点（分层作答）**：
1. **接入/解析层**：布局感知解析（PDF/表格/扫描件）→ 智能切分（父子文档）→ 元数据采集；批处理管线 Kafka 解耦。
2. **抽取层**：蒸馏 7B 抽实体/关系（高吞吐、低成本）+ 70B 仅做难样本复核；few-shot prompt 强制 evidence；输出经 evidence 回指校验 + 置信阈值过滤。
3. **图谱层**：实体解析（Blocking+嵌入相似度）消歧 → 建图（千万级边）；图库存 (实体,关系)，文本块存向量库+对象存储，社区树存 KV（分层存储）。
4. **索引/社区层**：Leiden 层次社区检测 → 逐层 LLM 社区摘要，形成"社区树"供 Global Search。
5. **检索编排层**：① Local——实体链接 + 2-hop 邻域 + token 预算裁剪（公式见 2.4）；② Global——社区摘要 map-reduce（2.5 代码）；③ 路由——问题分类器选 Local/Global/融合。
6. **生成层**：Grounding + 引用约束（每论断挂 citation，无引用扣分）+ 双模答案融合去重。
7. **增量层**：新文档只走局部抽取→局部实体解析→受影响社区重算（成本 ~8% 全量），热路径邻域预热缓存。
8. **可观测层**：抽取质量评估（边噪声率/实体覆盖）+ 检索漏斗（召回@k/ Faithfulness）+ 全链路 trace。
**加分项**：主动点出"10 亿文档全量建图不现实"——必须靠**增量更新 + 分层存储 + 小模型抽取**三件把成本压到可运维；并说明 Local/Global 路由如何避免"全局问题走了 Local 而答非所问"。

### 🎯 模拟题 2：线上 GraphRAG 多跳准确率 78%→45% 的 30 分钟止血复盘

**题干**：告警：GraphWeaver 的 HotpotQA 类多跳准确率从 78% 跌到 45%，同时单问延迟从 3.1s 涨到 5.8s，但系统无报错、QPS 正常。你是 oncall，30 分钟内如何止血、定位、根治？

**参考答案要点（止血 → 定位 → 根治）**：
- **0–5 min 止血**：先看可观测看板，确认是"检索质量问题"而非"生成问题"——若 Local 检索返回的邻域子图明显变小/变空，临时把 token 预算 B 从 8000 提到 12000 保召回；同时关掉"低频实体预淘汰"开关防误杀。
- **5–15 min 定位（拆因）**：
  - 准确率跌 + 延迟涨但 QPS 正常 → 多半是**检索侧退化**而非流量问题。三假设：① 实体解析阈值 τ 被误调高（>0.95）→ 大量同实体未合并，图谱碎片化，邻域断裂；② 社区检测 resolution 被改大 → 社区过碎，Global 摘要覆盖不足；③ 增量更新管线挂了 → 新文档未建边，近期问题全漏。
  - 查变更时间线 + 配置版本，对比准确率下跌起点，锁定是"配置误发"还是"管线故障"。
- **15–30 min 根因**：最常见是**一次错误的配置发版**（τ 或 resolution 漂移）或**增量抽取服务 OOM 静默失败**（无报错但边没写进图）。
- **根治 + 防复发**：实体解析 τ、社区 resolution 纳入"不可随意改"的受控参数 + 改前在影子集跑准确率回归；增量管线加"边写入量监控 + 写失败即告警（非静默）"；上线"多跳准确率"作为线上核心 SLI，跌超 5pp 自动回滚配置。
**加分项**：强调"没有抽取质量评估 + 检索漏斗看板，30 分钟定位不可能"；并指出"QPS 正常但准确率跌"恰恰说明是**数据/配置层**问题而非容量层，避免被带偏去扩容。

### 🎯 模拟题 3：用 7B 开源模型达到闭源 70B 的图谱抽取质量

**题干**：GraphWeaver 当前用闭源 70B 抽实体/关系，成本高。请设计方案，用 7B 开源模型达到闭源 70B 至少 95% 的抽取质量（F1），从训练、推理、工程三个层面展开。

**参考答案要点**：
1. **训练层（蒸馏 + 自训练）**：① 用 70B 对百万文本产"黄金抽取"作教师标签，做 SFT 蒸馏 7B（重点学 few-shot 格式 + evidence 约束）；② 对 7B 易错的"长关系/嵌套实体"做**难例挖掘（hard negative 重采样）**再训一轮；③ 加"证据回指"作为训练目标的一部分（输出必须带原文片段），逼模型只抽存在的关系。目标：实体 F1 70B 的 95%+。
2. **推理层（约束 + 校验兜底）**：① 7B 开 **Grammar-Constrained Decoding**（把抽取 JSON schema 编译成 CFG，token 掩码保合法 JSON，合法率 99%+）；② 解析后 **evidence 回指校验**自动丢弃幻觉边（见 2.1）；③ 低置信样本（输出概率 < τ）自动转 70B 复核（仅 ~5% 流量上大模型），既保质量又控成本。
3. **工程层（成本与质量闭环）**：① 批量并发抽取 + 语义缓存（相同段落不重抽）；② 蒸馏 7B 走 INT4 量化（AWQ），单卡吞吐 ×4；③ 在线评估监控 7B 抽取 F1，低于 95% 自动回退"7B+70B复核"比例上调或回滚模型。
**加分项**：点出"靠纯小模型追平大模型不现实，靠'蒸馏 + 约束解码 + 大模型仅复核难例'的级联才划算"——这本质是第41期 FuncHub「分层模型路由」思想在抽取链路的迁移。

## 📌 五、今日速记卡（Flashcards）

| 考点 | 一句话答案 |
|------|-----------|
| GraphRAG vs RAG | RAG 向量召回文本块；GraphRAG 多建图谱+社区摘要，补多跳+全局归纳 |
| 何时上 GraphRAG | 问题含关系链/总结/对比且文档海量；否则朴素 RAG 更省 |
| Local Search | 实体链接→2-hop 邻域→token预算裁剪→生成，答事实 |
| Global Search | 社区摘要 map-reduce（先并行要点，再综合去重），答归纳 |
| Leiden vs Louvain | Leiden 社区必连通、模块度更高；层次社区支撑选粒度 |
| 实体解析 | Blocking分桶 + 嵌入相似度 + 类型一致，τ≈0.86 合并 |
| 幻觉边抑制 | prompt evidence + 回指校验 + 低置信丢弃 + 消歧后建边 |
| token 预算公式 | 按 重要度×关系强度×时效 降序贪心装到预算 B |
| 增量更新 | 局部抽取+局部解析+受影响社区重算，成本≈全量8% |
| 小模型追平大模型 | 蒸馏SFT + 约束解码 + 难例转大模型复核，级联划算 |
