### 1.1 Agent Harness 架构设计——多LLM Provider统一编排引擎

#### **为什么需要一个 Agent Harness？**

```
直接裸调 LLM API 的问题：
  1. Vendor Lock-in：绑死一家 Provider（如只接 DeepSeek），切换成本极高
  2. 工具调用不统一：OpenAI 的 FC、DeepSeek 的 FC、火山引擎的 FC 格式各异
     → 同一个 Agent 应用要对接 3 个 Provider 就要写 3 套适配代码
  3. 流式输出协议不同：SSE / WebSocket / 自定义格式 → 前端适配噩梦
  4. 会话状态管理缺失：多轮对话、上下文压缩、会话中断恢复 → 全靠手动实现
  5. 可观测性空白：Token 计费、延迟监控、错误追踪 → 无法运维

Agent Harness 的核心价值主张：
  → 一套代码，N 个 LLM 后端无缝切换
  → 统一的工具调用协议 + 执行引擎
  → 生产级的可观测性 + 会话管理
  → FastAPI 后端 + Vue3 前端 + PyQt6 桌面端 三端架构
```

#### **Provider 抽象层核心设计（最核心的工程亮点）**

```python
# ========================================
# Agent Harness Provider 抽象层核心设计
# 关键思想：策略模式 + 工厂模式 + 适配器模式
# ========================================

from abc import ABC, abstractmethod
from typing import AsyncIterator, List, Dict, Any, Optional
from dataclasses import dataclass, field
from enum import Enum

# ── 统一数据模型（所有 Provider 共用）──

class MessageRole(Enum):
    SYSTEM = "system"
    USER = "user"
    ASSISTANT = "assistant"
    TOOL = "tool"

@dataclass
class Message:
    role: MessageRole
    content: str
    name: Optional[str] = None        # 工具调用时标识调用方
    tool_calls: Optional[List] = None  # 模型发起的工具调用
    tool_call_id: Optional[str] = None # 工具返回时关联调用

@dataclass
class ToolDefinition:
    """统一工具定义格式（兼容 OpenAI/DeepSeek/Doubao）"""
    name: str
    description: str
    parameters: Dict[str, Any]        # JSON Schema
    handler: Optional[callable] = None # 工具执行函数

@dataclass
class CompletionResponse:
    """统一的生成响应"""
    content: str
    tool_calls: List[Dict[str, Any]] = field(default_factory=list)
    usage: Dict[str, int] = field(default_factory=dict)  # token统计
    finish_reason: str = "stop"
    provider: str = ""  # 来源Provider标识

# ── Provider 抽象基类（策略模式）──

class BaseLLMProvider(ABC):
    """
    所有 LLM Provider 的统一接口
    核心设计：每个 Provider 只需实现两个方法
    """

    def __init__(self, api_key: str, base_url: str, model: str, **kwargs):
        self.api_key = api_key
        self.base_url = base_url
        self.model = model
        self.config = kwargs

    @abstractmethod
    async def complete(
        self,
        messages: List[Message],
        tools: Optional[List[ToolDefinition]] = None,
        temperature: float = 0.7,
        max_tokens: int = 4096,
        **kwargs
    ) -> CompletionResponse:
        """非流式生成"""
        ...

    @abstractmethod
    async def stream(
        self,
        messages: List[Message],
        tools: Optional[List[ToolDefinition]] = None,
        temperature: float = 0.7,
        **kwargs
    ) -> AsyncIterator[str]:
        """流式生成（逐 Token 返回）"""
        ...

    # ── 公共能力（子类共享）──

    async def retry_with_fallback(
        self,
        messages: List[Message],
        fallback_providers: List["BaseLLMProvider"],
        max_retries: int = 3,
        **kwargs
    ) -> CompletionResponse:
        """
        自动重试 + 降级机制
        主 Provider 失败 → 重试 → 降级到备用 Provider
        """
        last_error = None
        providers = [self] + fallback_providers

        for provider in providers:
            for attempt in range(max_retries):
                try:
                    return await provider.complete(messages, **kwargs)
                except (RateLimitError, TimeoutError, APIError) as e:
                    last_error = e
                    await asyncio.sleep(2 ** attempt)  # 指数退避

        raise ProviderExhaustedError(
            f"All providers failed. Last error: {last_error}"
        )

# ── 工厂模式：Provider 注册与实例化 ──

class ProviderFactory:
    """Provider 工厂——根据配置自动实例化正确的 Provider"""

    _registry: Dict[str, type] = {}

    @classmethod
    def register(cls, name: str):
        """装饰器注册 Provider"""
        def decorator(provider_cls):
            cls._registry[name] = provider_cls
            return provider_cls
        return decorator

    @classmethod
    def create(cls, name: str, **config) -> BaseLLMProvider:
        """根据名称创建 Provider 实例"""
        if name not in cls._registry:
            raise ValueError(f"Unknown provider: {name}")
        return cls._registry[name](**config)

# ── Doubao Provider 适配器（兼容性处理的典型场景）──

@ProviderFactory.register("doubao")
class DoubaoProvider(BaseLLMProvider):
    """
    火山引擎 Doubao Provider 适配器
    核心挑战：Doubao 的 API 格式与 OpenAI 不完全兼容
    需要做大量的字段映射和格式转换
    """

    # Doubao 特有的兼容性处理
    async def complete(self, messages, tools=None, **kwargs):
        # 1. 消息格式转换
        formatted_messages = self._convert_messages(messages)

        # 2. 工具定义转换（Doubao 的 JSON Schema 格式略有不同）
        formatted_tools = self._convert_tools(tools) if tools else None

        # 3. API 调用
        response = await self._call_api(formatted_messages, formatted_tools, **kwargs)

        # 4. 响应格式统一化（把 Doubao 格式 → CompletionResponse）
        return self._normalize_response(response)

    def _convert_messages(self, messages: List[Message]) -> List[Dict]:
        """
        消息格式转换
        核心差异：
        - OpenAI: tool_calls 在 assistant message 的顶层字段
        - Doubao: tool_calls 嵌套在 content 的 JSON 中
        """
        converted = []
        for msg in messages:
            if msg.role == MessageRole.TOOL:
                # Doubao 对 tool response 的要求不同
                converted.append({
                    "role": "tool",
                    "content": msg.content,
                    "tool_call_id": msg.tool_call_id
                })
            elif msg.tool_calls:
                # 转换 tool_calls 格式
                converted.append({
                    "role": "assistant",
                    "content": msg.content,
                    "tool_calls": [
                        self._convert_tool_call(tc) for tc in msg.tool_calls
                    ]
                })
            else:
                converted.append({"role": msg.role.value, "content": msg.content})
        return converted

# ── MainLoop 核心循环（Agent 执行引擎）──

class AgentMainLoop:
    """
    Agent Harness 的核心执行循环
    Think → Act → Observe → Reflect 四阶段循环
    """

    def __init__(self, provider: BaseLLMProvider, tools: List[ToolDefinition],
                 max_iterations: int = 20):
        self.provider = provider
        self.tools = {t.name: t for t in tools}
        self.max_iterations = max_iterations
        self.memory = []  # 对话历史

    async def run(self, user_input: str) -> str:
        """执行 Agent 主循环"""
        self.memory.append(Message(role=MessageRole.USER, content=user_input))

        for iteration in range(self.max_iterations):
            # ── Think：LLM 决定下一步 ──
            response = await self.provider.complete(
                messages=self.memory,
                tools=list(self.tools.values())
            )

            # 记录 assistant 回复
            self.memory.append(Message(
                role=MessageRole.ASSISTANT,
                content=response.content,
                tool_calls=response.tool_calls
            ))

            # ── 如果没有工具调用，直接返回最终回复 ──
            if not response.tool_calls:
                return response.content

            # ── Act：执行工具调用 ──
            for tool_call in response.tool_calls:
                tool_name = tool_call["function"]["name"]
                tool_args = json.loads(tool_call["function"]["arguments"])

                if tool_name in self.tools:
                    try:
                        # Observe：获取工具执行结果
                        result = await self.tools[tool_name].handler(**tool_args)
                        self.memory.append(Message(
                            role=MessageRole.TOOL,
                            content=str(result),
                            tool_call_id=tool_call["id"]
                        ))
                    except Exception as e:
                        # 工具执行失败的优雅处理
                        self.memory.append(Message(
                            role=MessageRole.TOOL,
                            content=f"Error: {str(e)}",
                            tool_call_id=tool_call["id"]
                        ))

        return "[Agent 达到最大迭代次数，任务可能未完成]"
```

### 1.2 推理范式演进——从 CoT 到 Reflexion 的完整技术栈

#### **推理范式的演进路线图**

```
推理能力是 LLM 应用的核心竞争力，面试必考。完整演进路线：

Zero-Shot（2020）→ Few-Shot（2021）→ CoT（2022）→ CoT-SC / Self-Consistency（2023）
     → ToT（2023）→ GoT（2023）→ ReAct（2022）→ Reflexion（2023）→ o1/o3（2024）

每一代解决上一代的核心缺陷：
  Zero-Shot → 无法处理多步推理 → CoT
  CoT → 单条推理路径，错误无法自我纠正 → CoT-SC
  CoT-SC → 无法回溯/探索不同分支 → ToT
  ToT → 无法与外部工具交互 → ReAct
  ReAct → 无法从失败中学习 → Reflexion
  Reflexion → 思考链路太短，缺乏深度推理 → o1 Test-Time Compute
```

#### **各推理范式核心原理与代码实现**

```python
# =============================================
# 1. Chain-of-Thought (CoT) —— 最基本的推理范式
# =============================================

# Zero-Shot CoT Prompt：
#   "请一步一步地思考。"
# Few-Shot CoT Prompt：
#   给出几个「问题 → 推理过程 → 答案」的示例，让模型模仿

# 核心思想：让模型「显式地写出推理过程」
# 为什么有效？
#   1. 把复杂问题分解为多个简单子问题（分治策略）
#   2. 推理过程可被验证（中间步骤错误可以被发现）
#   3. 更多 Token → 更多的计算量（Test-Time Compute）

cot_prompt = """
问题：小明有 23 个苹果，给了小红一半，又买了 5 个，然后又给了小华 1/3，
     请问他最后有多少个苹果？

请一步一步地思考。

推理过程：
1. 小明初始有 23 个苹果
2. 给小红一半：23 / 2 = 11.5，剩下 11.5 个
3. 又买了 5 个：11.5 + 5 = 16.5 个
4. 给小华 1/3：16.5 × (1/3) = 5.5，剩下 16.5 - 5.5 = 11 个
答案：小明最后有 11 个苹果。
"""

# =============================================
# 2. Self-Consistency (CoT-SC) —— 多路径投票
# =============================================

# 核心思想：同一个问题，用高温采样生成 N 条推理路径
# → 如果多条路径得到相同答案，说明答案更可靠

async def self_consistency(llm, question, n_samples=10, temperature=0.8):
    """
    Self-Consistency 推理（Wang et al., 2022）

    Step1: 生成 N 条独立推理路径
    Step2: 提取每条路径的「最终答案」
    Step3: 多数投票（Majority Vote）
    """
    answers = []
    for _ in range(n_samples):
        response = await llm.generate(
            question + "\n请一步一步地思考。",
            temperature=temperature
        )
        # 用正则提取最终答案
        final_answer = extract_answer(response)  # 如 "11 个苹果" → 11
        answers.append(final_answer)

    # 多数投票
    from collections import Counter
    most_common = Counter(answers).most_common(1)[0]
    confidence = most_common[1] / len(answers)  # 一致性 = 投票比例

    return most_common[0], confidence

# 效果（GSM8K 数学推理）：
#   CoT（单路径）：58.8%
#   CoT-SC（10 路径投票）：67.5%（+8.7%）
#   但代价：推理成本 ×10

# =============================================
# 3. Tree-of-Thought (ToT) —— 树状搜索推理
# =============================================

# 核心思想：把推理过程建模为「树搜索」问题
#   - 每个推理步骤是一个「节点」
#   - 每个节点可以展开多个「候选下一步」
#   - 用 LLM 评估每个节点的「前景」
#   - 用 BFS/DFS 搜索最优推理路径

from dataclasses import dataclass
from typing import List, Optional
import heapq

@dataclass
class ThoughtNode:
    """ToT 树中的一个推理节点"""
    state: str          # 当前推理状态（问题描述 + 已有推理链）
    thought: str        # 本步的推理内容
    evaluation: float   # LLM 评估的分数（0-10）
    parent: Optional['ThoughtNode'] = None
    depth: int = 0

    def __lt__(self, other):
        return self.evaluation > other.evaluation  # 最大堆

class TreeOfThought:
    """
    ToT 推理引擎（Yao et al., 2023）
    用 Best-First Search（最佳优先搜索）
    """

    def __init__(self, llm, max_depth=5, branching_factor=3, beam_size=5):
        self.llm = llm
        self.max_depth = max_depth
        self.branching_factor = branching_factor
        self.beam_size = beam_size  # 保留的最佳节点数

    async def solve(self, problem: str) -> str:
        # 初始化根节点
        root = ThoughtNode(
            state=problem,
            thought="",
            evaluation=0.0,
            depth=0
        )

        # Best-First Search（用优先队列）
        open_set = [root]

        while open_set:
            # 取出评估分数最高的节点
            current = heapq.heappop(open_set)

            # 终止条件：达到最大深度或找到答案
            if current.depth >= self.max_depth:
                return self._extract_solution(current)

            # 展开：生成 branching_factor 个候选下一步
            candidates = await self._generate_thoughts(
                current.state, n=self.branching_factor
            )

            for candidate_thought in candidates:
                new_state = current.state + f"\n推理步骤{current.depth+1}: {candidate_thought}"
                evaluation = await self._evaluate_state(new_state)

                child = ThoughtNode(
                    state=new_state,
                    thought=candidate_thought,
                    evaluation=evaluation,
                    parent=current,
                    depth=current.depth + 1
                )
                heapq.heappush(open_set, child)

            # 裁剪：只保留 beam_size 个最佳节点
            open_set = heapq.nsmallest(self.beam_size, open_set)

        return self._extract_solution(root)

    async def _generate_thoughts(self, state: str, n: int) -> List[str]:
        """让 LLM 生成 n 个候选推理步骤"""
        prompt = f"""
        已知推理状态：{state}
        请提出 {n} 个可能的下一步推理方向。
        每个方向一行，不要编号。
        """
        response = await self.llm.generate(prompt, temperature=0.9)
        return response.strip().split('\n')[:n]

    async def _evaluate_state(self, state: str) -> float:
        """让 LLM 评估当前推理状态的前景"""
        prompt = f"""
        评估以下推理状态的「正确性」和「距离最终答案的进度」。
        给出 0-10 的分数。

        推理状态：{state}
        分数：
        """
        response = await self.llm.generate(prompt, temperature=0.1)
        return float(response.strip())

# ToT vs CoT vs CoT-SC 对比：
#   CoT：单路径，无法回溯
#   CoT-SC：多路径并行，但无回溯（一次性采样）
#   ToT：真正的搜索——可以回溯、剪枝、探索不同分支
#   代价：推理成本 ×30~50（每个节点都要 LLM 评估）

# =============================================
# 4. ReAct —— 推理 + 行动交替
# =============================================

# 核心思想：Agent 不仅「思考」还「行动」
#   Thought → Action → Observation → Thought → Action → ... → Answer
#   与纯 CoT 的区别：可以调用外部工具（搜索/计算/API）

async def react_agent(llm, tools, question, max_steps=10):
    """
    ReAct Agent 循环（Yao et al., 2022）
    关键：Thought 和 Action 交替执行
    """
    scratchpad = f"问题：{question}\n"

    for step in range(max_steps):
        # ── Thought + Action（LLM 决定下一步）──
        prompt = f"""
        {scratchpad}
        可用工具：{json.dumps({t.name: t.description for t in tools}, ensure_ascii=False)}

        请选择下一步（格式：Thought: ... Action: ...[arg1, arg2]）
        如果已有足够信息回答问题，输出：Thought: ... Answer: ...
        """
        response = await llm.generate(prompt)

        # 解析 LLM 的输出
        if "Answer:" in response:
            return extract_between(response, "Answer:", "\n")

        thought = extract_between(response, "Thought:", "Action:")
        action_name = extract_between(response, "Action:", "(")
        action_args = extract_between(response, "(", ")")

        # ── Observation（执行工具，观察结果）──
        if action_name in tools:
            result = await tools[action_name].execute(action_args)
            scratchpad += f"Thought: {thought}\nAction: {action_name}({action_args})\nObservation: {result}\n"
        else:
            scratchpad += f"Error: 工具 {action_name} 不存在\n"

    return "达到最大步数，无法回答"

# =============================================
# 5. Reflexion —— 从失败中学习的 Agent
# =============================================

# 核心思想：Agent 执行失败后，把「失败原因」写入记忆
#   下次遇到类似任务时，先读取「失败记忆」→ 避免重复错误

async def reflexion_agent(llm, evaluator, task, max_trials=3):
    """
    Reflexion Agent（Shinn et al., 2023）
    关键创新：自我反思 + 记忆增强
    """
    memory = []  # 存储历次失败反思

    for trial in range(max_trials):
        # ── 生成（如果有历史反思，注入 Prompt）──
        context = ""
        if memory:
            context = f"\n你之前在这个任务上犯过以下错误，请避免：\n"
            for reflection in memory:
                context += f"- {reflection}\n"

        response = await llm.generate(task + context)

        # ── 评估 ──
        score, feedback = await evaluator.evaluate(task, response)

        if score >= 0.8:  # 达标
            return response

        # ── 反思（让 LLM 分析失败原因）──
        reflection_prompt = f"""
        任务：{task}
        你的回答：{response}
        评估反馈：{feedback}

        请反思：你的回答哪里出错了？下次应该如何改进？
        用一句话总结失败原因。
        """
        reflection = await llm.generate(reflection_prompt)
        memory.append(reflection)

    return response  # 返回最后一次尝试的结果（即使未达标）

# Reflexion 关键洞察：
#   - 不需要更新模型权重（在线学习）
#   - 用「自然语言记忆」替代「梯度更新」
#   - 实验表明：3 轮 Reflexion 在 HumanEval 上从 67% → 80%
```

#### **推理范式选型决策树**

```
需要 LLM 做复杂推理？
  ├── 任务是纯文本推理（数学/逻辑/分析）？
  │     ├── 简单（1-2步）→ Zero-Shot CoT（"请一步一步思考"）
  │     ├── 中等（3-5步）→ CoT-SC（10 路径投票）
  │     └── 复杂（5+步，需要回溯）→ ToT（树搜索）
  ├── 任务需要外部信息（搜索/计算/API）？
  │     └── ReAct（推理 + 行动交替）
  ├── 任务需要从失败中学习？
  │     └── Reflexion（反思 + 记忆增强）
  └── 任务需要极深度推理（竞赛级数学/代码）？
        └── o1/o3 Test-Time Compute（MCTS + 强化学习）
```

## 🔧 二、技术难点与解决方案（Technical Challenges）

### 2.1 多 LLM Provider 的 Tool Calling 标准化——Agent Harness 的最大工程挑战

#### **问题：三大 Provider 的 Tool Calling 格式完全不兼容**

```
核心矛盾：
  OpenAI、DeepSeek、Doubao 都支持 Function Calling，
  但请求/响应的 JSON 格式存在微妙差异：

差异1：tool_calls 字段位置
  OpenAI:   response.choices[0].message.tool_calls → 顶层字段
  DeepSeek:  与 OpenAI 兼容（90%），但参数校验更严格
  Doubao:   tool_calls 嵌套在 content 字段的 JSON 中 → 结构不同

差异2：工具定义的 JSON Schema 格式
  OpenAI:   支持完整的 JSON Schema Draft 2020-12
  DeepSeek:  支持子集（不支持 $ref、allOf 等）
  Doubao:   只支持简单的 properties 定义 → 复杂类型需要展平

差异3：并行工具调用
  OpenAI:   原生支持（一次返回多个 tool_calls）
  DeepSeek:  部分支持（model 参数需指定 parallel_tool_calls=true）
  Doubao:   不支持并行 → 需要串行化处理

差异4：流式输出中的 tool_calls
  OpenAI:   用 delta 格式增量推送（类似打字机效果）
  Doubao:   流式模式不支持 tool_calls → 必须用非流式模式
```

#### **解决方案：四层标准化架构**

```python
class ToolCallNormalizer:
    """
    Tool Calling 标准化器
    处理三大 Provider 的格式差异
    """

    # ── Layer1: Schema 简化（统一降维到最小公共集）──
    @staticmethod
    def normalize_schema(tool_def: ToolDefinition) -> Dict:
        """
        把复杂 JSON Schema 简化为所有 Provider 都支持的最小集
        核心原则：嵌套对象 → 展平为一层
        """
        schema = tool_def.parameters.copy()

        # Doubao 不支持嵌套对象 → 展平
        if is_nested(schema):
            schema = flatten_schema(schema)
            # 例：{"address": {"city": "str", "zip": "str"}}
            #   → {"address_city": "str", "address_zip": "str"}

        # DeepSeek 不支持 enum → 移除
        schema.pop("enum", None)
        # DeepSeek 不支持 $ref → 解引用
        schema = resolve_refs(schema)

        return schema

    # ── Layer2: 请求转换（统一 → Provider 特定格式）──
    @staticmethod
    def to_provider_format(
        messages: List[Message],
        tools: List[ToolDefinition],
        target_provider: str
    ) -> Dict:
        """转换为特定 Provider 的 API 格式"""
        if target_provider == "openai":
            return _to_openai_format(messages, tools)
        elif target_provider == "deepseek":
            return _to_deepseek_format(messages, tools)
        elif target_provider == "doubao":
            return _to_doubao_format(messages, tools)  # 最复杂的转换

    # ── Layer3: 响应解析（Provider 特定格式 → 统一格式）──
    @staticmethod
    def parse_response(raw_response: Dict, provider: str) -> CompletionResponse:
        """把不同 Provider 的响应统一为 CompletionResponse"""
        if provider == "doubao":
            # Doubao: tool_calls 可能在 content 的 JSON 中
            return _parse_doubao_response(raw_response)
        else:
            # OpenAI/DeepSeek: 标准格式
            return _parse_standard_response(raw_response)

    # ── Layer4: 并行化适配（处理不支持并行的 Provider）──
    @staticmethod
    async def execute_tool_calls(
        tool_calls: List[Dict],
        tools: Dict[str, ToolDefinition],
        provider: str,
        parallel_capable: bool = True
    ) -> List[Message]:
        """
        执行工具调用
        - 支持并行的 Provider: 并行执行所有工具
        - 不支持并行的 Provider: 串行执行（每次只返回一个结果）
        """
        if parallel_capable:
            # 并行执行
            tasks = [
                tools[tc["function"]["name"]].handler(
                    **json.loads(tc["function"]["arguments"])
                )
                for tc in tool_calls
            ]
            results = await asyncio.gather(*tasks, return_exceptions=True)
        else:
            # 串行执行（Doubao 场景）
            results = []
            for tc in tool_calls:
                try:
                    result = await tools[tc["function"]["name"]].handler(
                        **json.loads(tc["function"]["arguments"])
                    )
                    results.append(result)
                except Exception as e:
                    results.append(f"Error: {e}")

        return [
            Message(role=MessageRole.TOOL, content=str(r), tool_call_id=tc["id"])
            for r, tc in zip(results, tool_calls)
        ]
```

```python
class DataCleaner:
    """
    数据清洗 Pipeline
    目标：从 Common Crawl 中过滤掉 ~95% 的低质量数据
    """

    def clean(self, raw_text: str) -> bool:
        """
        清洗流程（按顺序执行，任一规则不通过即丢弃）：
        """
        # Rule 1: 语言过滤
        if not self._is_chinese_or_english(raw_text):
            return False

        # Rule 2: 长度过滤
        if len(raw_text) < 100 or len(raw_text) > 100000:
            return False

        # Rule 3: 符号密度过滤（网页广告/导航栏/乱码）
        symbol_ratio = len(re.findall(r'[^\w\u4e00-\u9fff]', raw_text)) / len(raw_text)
        if symbol_ratio > 0.5:  # 非文字符号占比 > 50%
            return False

        # Rule 4: 重复行过滤
        lines = raw_text.split('\n')
        unique_lines = len(set(lines))
        if unique_lines / len(lines) < 0.5:  # 重复行 > 50%
            return False

        # Rule 5: N-gram 重复度过滤（跨文档去重的前置步骤）
        ngram_overlap = self._compute_ngram_overlap(raw_text, self.corpus_ngrams)
        if ngram_overlap > 0.7:  # 和语料库 N-gram 重叠 > 70%
            return False

        # Rule 6: 命名实体比率（人名/地名过多的文本可能是通讯录/目录）
        ner_ratio = self._compute_ner_ratio(raw_text)
        if ner_ratio > 0.3:
            return False

        # Rule 7: 困惑度过滤（用轻量级语言模型打分）
        perplexity = self._compute_perplexity(raw_text)
        if perplexity > 1000:  # PPL 过高 → 乱码/低质量文本
            return False

        return True

# LLaMA 的清洗统计数据（参考）：
#   Common Crawl 原始：~8.0T Token
#   语言过滤后：~5.0T（淘汰 37.5%）
#   质量过滤后：~1.4T（淘汰 72%）
#   最终保留率：~17.5%

# ── Stage 3: 去重（Deduplication）──

"""
去重是数据工程中最关键的步骤之一！

为什么去重如此重要？
  1. 训练数据中的重复 → 模型「记住」重复模式 → 降低泛化能力
  2. MinHash 论文（Lee et al., 2022）：
     - 50% 重复率的数据训练出的模型，困惑度高 15%
     - 去重后训练出的模型，同等规模下性能提升 2-5%
"""

class Deduplicator:
    """
    两级去重策略
    Level 1: 精确去重（文档级）—— O(1) 查找
    Level 2: 模糊去重（N-gram MinHash）—— O(N) 查找
    """

    def __init__(self, ngram_size=10, num_hashes=256, threshold=0.7):
        self.ngram_size = ngram_size
        self.num_hashes = num_hashes
        self.threshold = threshold
        self.exact_hashes = set()  # 精确去重哈希集合

    def exact_dedup(self, document: str) -> bool:
        """Level 1: 文档级精确去重"""
        doc_hash = hash(document)
        if doc_hash in self.exact_hashes:
            return False  # 精确重复，丢弃
        self.exact_hashes.add(doc_hash)
        return True  # 保留

    def fuzzy_dedup(self, document: str) -> bool:
        """
        Level 2: N-gram MinHash 模糊去重

        MinHash 原理：
          1. 把文档分解为 N-gram（连续 N 个 Token）
          2. 对每个 N-gram 做 hash
          3. 用 num_hashes 个不同的 hash 函数
          4. 取每个 hash 函数的最小值 → 构成 MinHash 签名
          5. 两个文档的 Jaccard 相似度 ≈ MinHash 签名的重合度

        时间复杂度：O(N) per document（N = 文档 N-gram 数）
        空间复杂度：O(num_hashes) per document（固定 256 维签名）
        """
        # 生成 N-gram
        tokens = document.split()
        ngrams = set()
        for i in range(len(tokens) - self.ngram_size + 1):
            ngram = ' '.join(tokens[i:i+self.ngram_size])
            ngrams.add(hash(ngram))

        # 计算 MinHash 签名
        minhash_sig = []
        for i in range(self.num_hashes):
            # 使用不同的 hash 种子
            h = min(hash_func(n, seed=i) for n in ngrams)
            minhash_sig.append(h)

        # 估算 Jaccard 相似度
        if hasattr(self, 'existing_signatures'):
            for existing_sig in self.existing_signatures:
                jaccard = sum(1 for a, b in zip(minhash_sig, existing_sig) if a == b) / self.num_hashes
                if jaccard > self.threshold:
                    return False  # 模糊重复，丢弃

        self.existing_signatures.append(minhash_sig)
        return True

# 去重效果（CCNet 论文数据）：
#   精确去重：淘汰 ~20%
#   模糊去重（阈值=0.7）：再淘汰 ~15%
#   总淘汰率：~35%（显著提升训练效率）
```

### 2.3 Agent 的会话记忆系统——短期/长期/工作三层记忆架构

#### **为什么 Agent 需要「记忆系统」？**

```
没有记忆的 Agent 的问题：
  1. 上下文窗口限制（128K Token 用完就忘）
  2. 无法积累经验（每次对话从零开始）
  3. 无法个性化（不记得用户偏好和历史）
  4. 成本浪费（每次都发送完整历史，Token 计费飙升）

Agent Harness 的三层记忆设计：

  Layer 1: 工作记忆（Working Memory）
    → 当前会话的消息列表
    → 存储在内存中，实时读写
    → 容量：当前上下文窗口（~128K Token）

  Layer 2: 短期记忆（Short-term Memory）
    → 过去几天的对话摘要
    → 存储在 Redis / 本地文件
    → 用 LLM 生成摘要，压缩 10K Token → 500 Token

  Layer 3: 长期记忆（Long-term Memory）
    → 用户偏好、重要事实、项目上下文
    → 存储在向量数据库（语义检索）
    → 永久保留，跨会话持久化
```

```python
class AgentMemorySystem:
    """
    Agent Harness 三层记忆系统
    """

    def __init__(self, llm, vector_db, working_memory_limit=100000):
        self.llm = llm
        self.vector_db = vector_db
        self.working_memory = []  # 当前会话消息
        self.working_memory_limit = working_memory_limit
        self.short_term_memory = []  # 会话摘要列表
        self.long_term_memory = vector_db  # 用户长期记忆

    def add_message(self, message: Message):
        """添加消息到工作记忆"""
        self.working_memory.append(message)

        # 检查是否需要压缩（上下文窗口快满了）
        current_tokens = sum(len(str(m)) for m in self.working_memory)
        if current_tokens > self.working_memory_limit * 0.8:
            self._compress_working_memory()

    async def _compress_working_memory(self):
        """
        压缩工作记忆：把旧消息生成摘要 → 移入短期记忆
        保留：最近 20% 的消息 + System Prompt
        """
        # 保留最近消息
        keep_count = max(10, len(self.working_memory) // 5)
        old_messages = self.working_memory[:-keep_count]
        new_messages = self.working_memory[-keep_count:]

        # 生成摘要
        conversation_text = "\n".join(str(m) for m in old_messages)
        summary = await self.llm.generate(
            f"请用 200 字以内总结以下对话的关键信息：\n{conversation_text}"
        )

        # 移入短期记忆
        self.short_term_memory.append({
            "summary": summary,
            "timestamp": datetime.now().isoformat(),
            "message_count": len(old_messages)
        })

        # 更新工作记忆
        self.working_memory = new_messages

    async def recall(self, query: str, top_k: int = 5) -> List[str]:
        """
        检索长期记忆：用向量相似度找到相关记忆
        """
        query_embedding = await self.llm.embed(query)
        results = await self.vector_db.search(query_embedding, top_k=top_k)
        return results

    def get_context_for_llm(self) -> List[Message]:
        """
        构造给 LLM 的完整上下文
        优先级：System Prompt < 长期记忆 < 短期记忆 < 工作记忆
        """
        context = []

        # 如果有短期记忆摘要，添加到 context 开头
        if self.short_term_memory:
            latest_summary = self.short_term_memory[-1]
            context.append(Message(
                role=MessageRole.SYSTEM,
                content=f"[历史对话摘要] {latest_summary['summary']}"
            ))

        # 添加当前工作记忆
        context.extend(self.working_memory)

        return context
```

## 📝 三、常见面试问答（FAQ）

### Q1：请详细解释 Agent Harness 的 MainLoop 设计，为什么要用 Think-Act-Observe 循环？

**答**：

```
MainLoop 是 Agent 系统的「心跳」，核心是 Think → Act → Observe 的闭环：

【Think 阶段】
  LLM 接收当前上下文（用户问题 + 历史消息 + 工具执行结果），
  决定下一步行动：
    - 直接回答（没有工具调用 → 任务结束）
    - 调用工具（有 tool_calls → 进入 Act 阶段）

【Act 阶段】
  解析 LLM 返回的 tool_calls：
    - 提取工具名称和参数
    - 通过 Tool Registry 查找并执行对应工具
    - 支持并行工具调用（OpenAI 原生支持）
    - 不支持并行的 Provider（如 Doubao）→ 自动串行化

【Observe 阶段】
  工具执行结果写入消息历史（role=tool），
  然后回到 Think 阶段，LLM 根据工具结果决定下一步。

设计这个循环的原因：
  1. LLM 本身没有「行动能力」，只能通过 API 间接操作外部世界
  2. 单轮调用无法完成复杂任务（需要多步推理 + 多次工具调用）
  3. 工具调用可能失败 → 需要循环机制让 LLM「看到」错误并自我修正
  4. 最大迭代次数限制（如 20 次）→ 防止无限循环（Token 计费失控）

面试加分：
  "这本质上是 ReAct 范式的工程实现。
   更高级的演进是加入 Reflect 阶段（如 Reflexion），
   在任务完成后让 LLM 反思执行过程，把经验写入长期记忆。"
```

### Q2：CoT、ToT、ReAct 的核心区别是什么？分别适用什么场景？

**答**：

```
核心区别（一句话）：
  CoT = 只「想」不「做」
  ToT = 想，且可以「回溯」（树搜索）
  ReAct = 想 + 做（推理 + 行动交替）

详细对比：

维度              CoT              ToT              ReAct
───────────────────────────────────────────────────────────
推理方式          线性推理链        树状搜索          推理 + 行动交替
能否回溯          ❌ 不能            ✅ 可以回溯       ✅ 可以回溯
```

### Q3：大模型预训练数据工程中，去重为什么如此重要？MinHash 的原理是什么？

**答**：

```
去重的重要性（三个维度）：

维度1：训练效率
  重复数据 = 无效计算。训练一个 70B 模型，1000 万美元的算力
  → 如果 30% 数据重复 = 浪费 300 万美元

维度2：模型质量
  Lee et al., 2022 实验结果：
    - 重复率 50% 的数据 → 模型困惑度高 15%
    - 去重后 → 同等规模下，MMLU 提升 2.5%，HumanEval 提升 4%

维度3：隐私安全
  重复的个人隐私数据（如身份证号、地址）→ 模型「记住」并可能泄露

MinHash 原理（5 步理解）：

Step1：N-gram 分解
  文档 "A B C D E"（ngram_size=3）→ {"A B C", "B C D", "C D E"}

Step2：Hash 函数族
  用 K 个不同的 hash 函数 h1, h2, ..., hK（如 K=256）

Step3：MinHash 签名
  对每个 hash 函数，取所有 N-gram 的最小 hash 值
  签名 = [min(h1(ngrams)), min(h2(ngrams)), ..., min(hK(ngrams))]

Step4：Jaccard 相似度估算
  两个文档的 MinHash 签名中，相同位置值相等的比例
  ≈ 这两个文档的 Jaccard 相似度

Step5：近似最近邻查找
  用 LSH（Locality-Sensitive Hashing）把签名分成若干 band
  同一 band 内签名完全相同的文档 → 可能相似 → 精确计算确认

时间复杂度分析：
  N-gram 生成：O(L) per document（L = 文档长度）
  MinHash 签名：O(K × N) per document（K=256, N=ngram数）
  LSH 查找：O(1) per document（近似）
  总体：O(K × N) per document → 可扩展到十亿级文档

工程优化：
  SimHash（Google 用于网页去重）：O(L) per document，固定 64-bit 签名
  但精度不如 MinHash（适合海量数据的第一轮粗筛）
```

### Q4：如何设计一个生产级的 Agent 记忆系统？

**答**：

```
三层记忆架构（已在 Agent Harness 中实现）：

Layer1：工作记忆（Working Memory）
  存储：内存（Python List）
  内容：当前会话的完整消息历史
  容量：受上下文窗口限制（~128K Token）
  压缩策略：
    - Token 接近窗口上限 80% → 触发压缩
    - 保留最近 20% 消息 + System Prompt
    - 旧消息 → LLM 生成摘要 → 移入短期记忆
  访问速度：O(1)（直接读内存）

Layer2：短期记忆（Short-term Memory）
  存储：Redis / SQLite
  内容：过去 N 天的对话摘要（每轮对话一个摘要）
  容量：~1000 条摘要（约 500K Token）
  检索：最近 N 条摘要 + 关键词过滤
  过期策略：30 天后自动删除

Layer3：长期记忆（Long-term Memory）
  存储：向量数据库（Milvus / Qdrant / FAISS）
  内容：用户偏好、项目知识、重要决策
  容量：无限制（取决于向量库容量）
  检索：语义相似度检索（Embedding → 余弦相似度）
  写入策略：
    - 显式记忆：用户明确要求记住的信息 → 直接写入
    - 隐式记忆：从对话中提取「值得长期保留」的信息 → LLM 判断

写入长期记忆的判断逻辑：
  prompt = "以下信息是否值得长期记住？（用户偏好/重要事实/项目上下文）
    如果是，请提取关键信息。
    信息：{message}"

关键设计决策：
  1. 什么时候触发记忆写入？
     → 每轮对话结束后，让 LLM 判断是否有值得长期保留的信息
  2. 记忆冲突怎么办？
     → 新信息覆盖旧信息（Last-Write-Wins），但记录修改历史
  3. 记忆检索的时机？
     → 每次 Think 阶段前，用当前 Query 检索 Top-5 相关记忆
     → 注入 System Prompt 的 [记忆] 部分

面试加分：
  "更高级的方案是 MemGPT 的虚拟上下文管理——
   把 Agent 的记忆分成「主上下文」和「外部存储」，
   Agent 像操作系统管理内存一样管理自己的上下文（Page In/Out）。
   这本质上是给 LLM 加了一层「虚拟内存」。"
```

### Q5：LLM 推理中的 Test-Time Compute 是什么？o1 模型的核心创新在哪里？

**答**：

```
传统 LLM 推理：输入 → 一次前向传播 → 输出
  → 推理计算量固定（和输入长度线性相关）

Test-Time Compute（测试时计算）：
  输入 → 多次推理/搜索/自我验证 → 输出
  → 推理计算量动态可变（简单问题少算，复杂问题多算）

核心洞察：
  "Scaling Law 不只适用于训练阶段。
   推理阶段增加计算量也能提升性能。
   对于困难的数学/代码问题，让模型'多想几步'比训练更大的模型更高效。"

o1/o3 的具体技术（基于公开信息和逆向工程推测）：

技术1：Process Reward Model (PRM)
  传统 ORM（Outcome RM）：只看最终答案对不对
  PRM：对推理过程的每一步都打分
  → 更细粒度的信号 → 更好的搜索引导

技术2：MCTS（蒙特卡洛树搜索）
  在推理空间中搜索最优推理路径：
    - 每个节点 = 一步推理
    - PRM 给每个节点打分
    - 用 UCB 公式平衡「探索」和「利用」
    - 搜索深度和广度根据问题难度动态调整

技术3：自我验证（Self-Verification）
  模型生成答案后，再生成一个「验证器」：
    - "我的答案是 42，让我验证一下..."
    - 如果验证不通过 → 回溯搜索其他路径
  → 显著减少数学推理的最终错误率

效果数据（竞赛级数学）：
  GPT-4 CoT：AIMO 竞赛正确率 ~5%
  o1 Test-Time Compute：AIMO 竞赛正确率 ~36%（+7×）
  推理成本：比 GPT-4 高 10-100 倍

面试加分：
  "Test-Time Compute 的本质是把'推理能力'从训练阶段
   延迟到推理阶段。这和 ToT 的思想一致，但 o1 的关键突破是：
   用 PRM（Process Reward Model）替代 LLM-as-Judge 来评估推理质量，
   PRM 是专门训练的，评估准确率远高于通用 LLM 打分。"
```

### 模拟题 3：Doubao Provider 的兼容性问题的完整排查思路

**题目**：
> 在 Agent Harness 项目中，Doubao Provider 集成时遇到以下问题：
> (1) 工具调用在流式模式下完全不触发
> (2) 某些复杂参数结构（嵌套对象）导致 API 报错
> (3) 并行工具调用不支持，但 Agent 业务逻辑依赖并行
> 请给出完整的排查思路和解决方案。

**参考答案要点**：

```
【1】问题1：流式模式下 Tool Calling 不触发

  排查步骤：
    Step1：阅读 Doubao API 文档 → 确认是否支持流式 Tool Calling
      发现：Doubao 的流式模式（stream=True）不支持 tool_calls
    Step2：对比 OpenAI 的流式 Tool Calling 机制
      OpenAI: stream 模式下 tool_calls 通过 delta 事件增量推送
      Doubao: 不支持 → 必须用非流式模式
    Step3：确定解决方案

  解决方案：双模式切换
    - 有工具定义时 → 强制使用非流式模式（stream=False）
    - 无工具定义时 → 使用流式模式（stream=True）
    - 对用户透明：在 Provider 抽象层自动切换，上层无感知

  代码设计：
    async def stream(self, messages, tools=None, **kwargs):
      if tools and len(tools) > 0:
        # 有工具 → 非流式（保证 tool_calls 可用）
        response = await self.complete(messages, tools=tools, **kwargs)
        yield response.content  # 模拟流式（一次性输出）
      else:
        # 无工具 → 真正流式
        async for chunk in self._real_stream(messages, **kwargs):
          yield chunk

【2】问题2：复杂参数结构导致 API 报错

  排查步骤：
    Step1：复现问题 → 构造一个嵌套对象参数（如 address: {city: str, zip: str}）
    Step2：查看 API 错误信息 → 400 Bad Request, "Invalid parameter schema"
    Step3：对比 OpenAI 的 Schema 支持 vs Doubao 的 Schema 支持
      OpenAI: 支持 JSON Schema Draft 2020-12 全集
      Doubao: 只支持简单的 properties + type + description

  解决方案：Schema 自动降级
    - 在 ToolCallNormalizer.normalize_schema() 中检测嵌套结构
    - 嵌套对象 → 展平为一层（用下划线连接）
    - 枚举类型 → 转为 string + description 中注明可选值
    - $ref / allOf / anyOf → 解引用/合并为简单结构

  展平示例：
    原始: {"address": {"city": "string", "zip": "string"}}
    展平: {"address_city": "string", "address_zip": "string"}

    工具 handler 侧：在执行前，把展平的参数重构为嵌套结构
    def reconstruct_args(flat_args, original_schema):
      """把展平参数还原为嵌套结构"""
      ...

【3】问题3：不支持并行工具调用

  排查步骤：
    Step1：确认 Doubao API 是否支持 parallel_tool_calls
      结果：不支持，一次只能返回一个 tool_call
    Step2：分析影响：Agent Harness 的 MainLoop 假设可以并行执行工具

  解决方案：Provider 层串行化 + 并行化透明封装
    - Doubao Provider：一次请求只发送一个工具定义（最重要的那个）
      → 或者：发送所有工具定义，但只处理返回的第一个 tool_call
    - Provider 层内部循环：
      while has_pending_tool_calls:
        response = await doubao.complete(messages)
        execute(response.tool_calls[0])  # 只处理第一个
        messages.append(tool_result)
    - 上层 Agent 完全不知道底层是串行的

  架构层面的考量：
    - 这个问题暴露了「统一抽象」的代价：底层能力差异被隐藏了
    - 工程权衡：
      ✅ 统一接口（上层简单）
      ✅ 底层自动适配（减少重复代码）
      ⚠️ 性能损失（串行化 → 延迟增加）
      ⚠️ 行为差异（某些 Provider 的工具选择可能不同）

    建议：在监控中记录每个 Provider 的「工具调用次数」和「延迟」
    → 长期来看，可以引导用户选择最合适的 Provider

【4】面试加分：这类兼容性问题的通用解决方法论

  通用排查框架：
    1. 先查文档 → 确认 API 的「能力边界」（什么支持/什么不支持）
    2. 构造最小复现用例 → 隔离问题（不要一次排查所有问题）
    3. 对比「标准实现」（OpenAI）和「目标实现」（Doubao）的差异
    4. 设计适配层（不要修改业务逻辑，在 Provider 层做转换）
    5. 加回归测试（每个 Provider 的每个能力点都有自动化测试）
```
