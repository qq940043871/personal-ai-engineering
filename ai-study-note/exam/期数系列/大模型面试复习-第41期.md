## 一、项目亮点：FuncHub 函数调用中台

### 1.1 项目背景与业务价值

**FuncHub** 是公司内部统一的函数调用中台，支撑 Agent Harness（第35期）下所有"调用外部能力"的需求：查数据库、调内部 RPC、搜网页、发消息、跑代码、操作 SaaS。它面对三个硬约束：

- **工具规模爆炸**：从 30 个增长到 1200+ 个，单次请求不可能把所有工具 schema 全塞进上下文；
- **可靠性要求**：工具调用失败不能让整个 Agent 崩，必须结构化重试、降级、兜底；
- **成本与延迟**：每次多塞一个工具 schema 就多吃几百 token，错误调用一次就是一次真实副作用（发错消息/扣错款）。

**量化成果：**

| 指标 | 上线前（裸 prompt + 手工 JSON.parse） | 上线后（FuncHub 中台） | 提升 |
|------|------------------------------------|---------------------|------|
| 工具调用首次成功率 | 55% | 92% | +37pp |
| 结构化输出合法率（JSON 可解析） | 71% | 99.6% | +28.6pp |
| 平均每次请求工具描述 token 数 | 11,200（全量塞入） | 1,340（按需路由） | -88% |
| 单次工具调用平均成本 | ¥0.018 | ¥0.0067 | -63% |
| 无效/错误工具调用占比 | 14% | 2.1% | -85% |
| P95 端到端延迟（多工具编排） | 8.4s | 3.1s | -63% |

### 1.3 三大核心亮点

**亮点一：工具注册中心（Registry）—— 把"散落的 API"变成"受控资产"**

每个工具不只是 `name + description + parameters(JSON Schema)`，还带元数据：

```yaml
tool:
  id: order_query_v3
  name: query_order
  version: 3
  description: "查询用户订单，支持按订单号/手机号/时间范围检索"
  parameters:   # JSON Schema
    type: object
    properties:
      user_id: { type: string, description: "用户ID" }
      start:   { type: string, format: date, description: "起始日期" }
    required: [user_id]
  tags: [ecommerce, read]
  risk: low          # low/medium/high -> 决定是否需要二次确认
  owner: trade-team
  timeout_ms: 800
  cost_token: 0      # 工具自身无 token 成本，schema 才有
  enabled: true
```

治理价值：版本灰度（v2/v3 并存）、权限（risk=high 工具需 human-in-the-loop）、埋点（每个调用的延迟/失败率/参数分布）全部可观测。

**亮点二：强约束结构化输出 —— 让"合法 JSON"成为硬保证，而非概率事件**

业界裸 `JSON.parse(model_output)` 的失败率高得吓人（尤其小模型）：换行、多余逗号、未闭合引号、解释性前缀（"Here is the JSON:"）。FuncHub 用 **Grammar-Constrained Decoding**：在解码每一步，把"合法 JSON / 合法工具 schema"编译成上下文无关文法（CFG），用 token 级掩码强制模型只能输出语法合法的序列。

核心公式（约束解码的概率重标定）：
$$P_{masked}(x_t|x_{<t}) = \frac{P(x_t|x_{<t}) \cdot \mathbb{1}[x_{<t}x_t \in \mathcal{L}(G)]}{\sum_{x'} P(x'|x_{<t}) \cdot \mathbb{1}[x_{<t}x' \in \mathcal{L}(G)]}$$

即：凡是会让前缀脱离文法 $G$ 的语言集的词，概率被直接**置 0**。最终输出必然可解析，且分布仅在合法空间内重归一化。

**亮点三：并行依赖编排 —— 一次回复里调 5 个工具，按依赖关系 DAG 并发**

模型一次可返回多个 tool_call（OpenAI 的 `tool_calls[]`）。FuncHub 解析出调用集合后，按参数依赖构建 DAG：

- A 的输出是 B 的输入 → B 等 A；
- 无依赖的 C、D、E → 并发执行；
- 任一节点失败 → 按策略重试 / 跳过 / 回退到"让模型重新规划"。

## 二、技术难点与解决方案

### 难点 1：结构化输出可靠性 —— 模型就是不吐合法 JSON

**问题本质：** 自回归模型按 token 采样，天然可能输出残缺 JSON。小模型（7B/13B）尤为严重，且"思考链 + JSON"混排会让解析崩溃。

**我们的方案（三层防御）：**

1. **第一层（首选）：Grammar-Constrained Decoding（服务端保证）**
   在推理引擎侧集成约束解码（如 vLLM 的 ` guided_decoding` / outlines / lm-format-enforcer）。把工具 JSON Schema 编译成 CFG，解码时做 token 掩码。合法率 99.6%，且不损失语义质量（只在语法空间内重归一化）。

2. **第二层：双通道输出（prompt 侧兜底）**
   要求模型把"推理过程"与"最终 JSON"用明确分隔符分开（`<reason>...</reason><json>...</json>`），再用宽松解析器（修复未闭合、去前缀、去尾注）兜底第一层缺失的场景。

3. **第三层：自愈重试**
   解析失败时，把错误回灌给模型（`你上一轮的 JSON 缺少闭合括号，请只输出修正后的 JSON`），最多 2 次。

**关键代码（JSON 修复兜底解析器）：**

```python
import json, re

def robust_json_parse(raw: str):
    """三档兜底：直接解析 -> 截取到最后一个合法括号 -> 错误回灌"""
    raw = raw.strip()
    # 1) 去掉常见噪声前缀/后缀
    raw = re.sub(r'^```(?:json)?', '', raw).strip()
    raw = re.sub(r'```$', '', raw).strip()
    try:
        return json.loads(raw), None
    except json.JSONDecodeError as e:
        pass
    # 2) 截取到最后一个平衡的 } 或 ]
    for end in (raw.rfind('}'), raw.rfind(']')):
        if end > 0:
            cand = raw[:end+1]
            try:
                return json.loads(cand), "truncated_to_balanced"
            except json.JSONDecodeError:
                continue
    # 3) 失败，返回可回的新 prompt 片段
    return None, f"JSONDecodeError: {e.msg} at pos {e.pos}"
```

### 难点 2：工具路由与选择 —— 1200 个工具不能全塞上下文

**问题本质：** 工具 schema 是 token 黑洞。1200 个工具平均每个 380 token，全量 = 456K token，远超上下文且浪费钱。必须"先路由，再注入"。

**方案：两级路由**

- **离线建索引**：每个工具的 `name + description + tags` 做 Embedding，存向量库；
- **在线召回**：当前对话最近 K 轮 + 用户 query 拼成检索句，召回 Top-N（N=8~16）最相关工具；
- **LLM 精排（可选）**：召回 Top-32 后让小模型打分选 Top-12，平衡召回与精度。

**关键代码（语义路由）：**

```python
def route_tools(query: str, history: list, registry, top_n: int = 12):
    ctx = query + " " + " ".join(h["content"] for h in history[-3:])
    q_vec = embed(ctx)                       # [D]
    # 向量库 ANN 检索（IVF-PQ 或 HNSW）
    hits = registry.ann.search(q_vec, k=top_n * 3)
    # 用工具 risk/owner 做轻量规则过滤（如当前租户无权限则剔除）
    hits = [h for h in hits if can_use(h)]
    # 必要时 LLM 精排
    if len(hits) > top_n:
        hits = llm_rerank(ctx, hits, top_n)
    return hits[:top_n]
```

**效果：** 单次注入 token 11.2K → 1.34K（-88%），无效调用 14% → 2.1%。

### 难点 3：并行工具调用的依赖编排

**问题本质：** 模型一次返回 `tool_calls: [A, B, C]`，但 B 的入参依赖 A 的返回值。若并发执行 B 会拿不到参数。必须把调用集合编译成有依赖的 DAG。

**方案：参数占位符解析。** 若某调用的参数值命中"另一调用的输出槽位"（如 `B.input = ${A.output.order_id}`），则建立边。否则视为可并行的独立节点。

**关键代码（DAG 调度器）：**

```python
from collections import defaultdict, deque

def build_dag(calls: list):
    """calls: [{id, fn, args}]，args 中可能引用 ${other_id.field}"""
    graph = {c['id']: [] for c in calls}      # id -> 依赖(前置)列表
    producers = {c['id']: c for c in calls}
    for c in calls:
        for dep_id in extract_refs(c['args']):   # 解析 ${dep_id.xxx}
            if dep_id in graph:
                graph[c['id']].append(dep_id)
    return graph

def topo_layers(graph):
    indeg = {k: len(v) for k, v in graph.items()}
    layers, ready = [], deque([k for k, d in indeg.items() if d == 0])
    while ready:
        layer, nxt = [], deque()
        while ready:
            node = ready.popleft(); layer.append(node)
            for n, deps in graph.items():
                if node in deps and n not in layer:
                    indeg[n] -= 1
                    if indeg[n] == 0: nxt.append(n)
        layers.append(layer); ready = nxt
    return layers   # 同层内并发，跨层串行

# 执行：逐层并发，结果回填占位符
for layer in topo_layers(build_dag(calls)):
    results = parallel_execute(layer)        # asyncio.gather
    fill_refs(calls, results)
```

### 难点 4：参数校验与类型安全 —— 模型填的参数经常非法

**问题本质：** 模型可能传 `"user_id": 12345`（应为字符串）、`"start": "昨天"`（应为 ISO 日期）、漏掉 required 字段。直接拿来调接口 = 报错或脏数据。

**方案：JSON Schema 运行时校验 + 自愈。** 用 `jsonschema` 校验，失败时把 `ValidationError` 结构化回灌模型修正；对"可推测"的错误做轻量强制转换（int↔string），对"不可推测"的报错并中止该调用。

**关键代码：**

```python
from jsonschema import Draft202012Validator

def validate_args(tool, args: dict):
    v = Draft202012Validator(tool['parameters'])
    errs = sorted(v.iter_errors(args), key=lambda e: e.path)
    if not errs:
        return args, []
    repaired = dict(args)
    for e in errs:
        # 可自愈：类型轻微不匹配（int/str 互转）
        if e.validator in ('type',) and _coercible(e):
            repaired[e.path[-1]] = _coerce(e)
        else:
            return None, [f"{'/'.join(map(str,e.path))}: {e.message}"]
    return repaired, []
```

### 难点 5：长上下文工具描述压缩

**问题本质：** 即便路由到 12 个工具，每个工具的 `description + parameters` 仍占 4~5K token。多轮对话累积，工具描述很快吃掉上下文预算。

**方案：schema 外部化 + 动态裁剪。**

- **外部化**：上下文里只放 `name + 一句话 description + required 字段名`；完整 JSON Schema 存在中台，执行前再补全；
- **动态裁剪**：按当前 query 与历史，用 LLM 把不相关参数从 schema 中删掉（如"查订单"不需要"export_format"参数）；
- **增量更新**：只在工具集合变化时重算 embedding，不每轮重算。

```python
def slim_schema(tool, ctx):
    """用 LLM 把与当前任务无关的 optional 参数裁掉，降低 schema token"""
    keep = llm_select_params(tool['parameters'], ctx)   # 返回需保留参数字典
    return {**tool, 'parameters': shrink(tool['parameters'], keep)}
```

### 难点 6：工具调用成本控制 —— 错误调用 = 真金白银 + 真副作用

**问题本质：** 每多注入一个工具 schema 都吃 token；更糟的是错误调用会触发真实 API 费用或副作用（发消息、下单）。需要"预算 + 短路 + 缓存"。

**成本数学模型：** 单次对话的工具相关成本

$$C = \underbrace{\sum_{i} n_i \cdot c_{tok}}_{\text{schema 注入}} + \underbrace{\sum_{j} f_j \cdot c_{call}}_{\text{真实调用}} + \underbrace{\sum_{k} m_k \cdot c_{tok}}_{\text{回灌修正}}$$

其中 $n_i$ 为第 $i$ 个工具的注入 token 数，$f_j$ 为第 $j$ 次真实调用。FuncHub 的治理手段：

- **预算闸门**：单次对话工具调用次数 / 总费用设上限，超限触发 human-in-the-loop；
- **短路缓存**：对 `risk=low` 且幂等的读工具（如"查天气"），对相同入参做语义缓存（embedding 相似度 > 0.96 直接命中），省去一次真实调用；
- **幂等键**：写工具强制带 `idempotency_key`，重复调用不重复副作用。

## 三、常见面试问答（6 个深度问题）

### Q1：ReAct 和 Function Calling 的本质区别是什么？什么时候用哪个？

**核心答点：**

- **ReAct** 是 *prompting 范式*：在 prompt 里写"Thought → Action → Observation"的少样本，让模型用**自然语言**写出要调用的工具名和参数（如 `Action: search("北京天气")`）。解析靠正则/脆弱的字符串匹配。
- **Function Calling** 是 *模型原生能力*：模型被专门训练成输出**结构化** `tool_calls`（含 `name` + 合法 JSON `arguments`），由 API 层解析后执行。
- **本质差异**：① 输出格式（自然语言 vs 机器可解析结构）；② 是否进训练（FC 需 SFT 数据训练，ReAct 仅靠 prompt）；③ 可靠性（FC 可配合约束解码 99.6% 合法，ReAct 解析失败率高）；④ 多工具并行（FC 原生支持 `tool_calls[]` 数组，ReAct 需额外解析）。
- **选型**：生产级 Agent 一律用 Function Calling（可靠、可控、可并行）；ReAct 适合快速原型、小模型、或没有 FC 训练数据的开源模型（此时用"类 ReAct + 宽松解析"兜底）。

### Q2：如何保证大模型输出 100% 合法的 JSON / 工具参数？

**核心答点（由浅入深）：**

1. **prompt 约束**（最弱）："只输出 JSON，不要解释" —— 仍会失败（尤其小模型/长输出）。
2. **后处理修复**（兜底）：截断到平衡括号、去前缀、错误回灌重试（见难点1代码）—— 覆盖率有限且耗 token。
3. **约束解码 / Grammar-guided decoding（根本解）**：把目标结构（JSON Schema 或工具 schema）编译成 CFG，解码时对非法 token 概率置 0（见 1.3 公式）。合法率可到 99.6%+，且不改语义分布。代表实现：Outlines、lm-format-enforcer、vLLM `guided_decoding`、xGrammars。
4. **小技巧**：要求模型用分隔符隔离推理与 JSON；对必填字段缺失用 schema 校验 + 回灌；低 risk 类型错误做强制转换。

**加分点**：约束解码的代价是每次 step 要遍历文法状态、token 掩码有少量开销；可用"前缀缓存 + 文法状态缓存"摊薄。

### Q3：模型一次返回多个 tool_call，其中 B 依赖 A 的结果，怎么编排？

**核心答点：** 见难点3。核心是把 `tool_calls[]` 编译成 DAG：

- 解析每个调用的 `arguments`，识别对其它调用输出的引用（如 `${A.order_id}`）；
- 建立依赖边，拓扑排序成"层"；
- **同层并发**（asyncio.gather），**跨层串行**；
- 失败节点按策略（重试 / 降级 / 让模型重新规划）处理。
- 加分点：循环依赖检测（A 依赖 B 且 B 依赖 A → 报错让模型重规划）；"可并行的独立调用"必须并发才满足延迟 SLA。

### Q4：Function Calling 的训练数据是怎么构造的？

**核心答点（SFT 数据构造范式）：**

- **数据格式**：每条样本 = `system(工具定义) + 多轮对话 + assistant 的 tool_call(结构化) + tool 的 observation + assistant 最终答案`。
- **来源**：
  1. **人工标注**：标注员写 query → 标注正确 tool + 参数（高质量但贵）；
  2. **模型蒸馏**：用强模型（GPT-4 级）生成 tool_call 轨迹，过滤后蒸馏给小模型；
  3. **合成数据**：给定工具集，用 LLM 生成多样 query 与对应调用（注意覆盖"无需调用""需并行""需多步"等模式）；
  4. **拒绝/负样本**：加入"不属于任何工具"的 query，训练模型输出 `no_tool_call`，避免幻觉调用。
- **关键陷阱**：训练数据必须包含"多轮 + 工具返回后继续推理"的样本，否则模型不会利用 observation；必须包含并行调用样本；必须平衡"调用/不调用"比例防止过调用。

### Q5：线上工具调用失败率从 90% 飙到 60%，你怎么排查？

**核心答点（系统化排查，体现工程素养）：**

1. **分层定位**：是"模型没调用"（结构化失败/路由错）还是"调用了但执行失败"（参数非法/接口 5xx/超时/权限）？看埋点拆因。
2. **结构化失败**：合法 JSON 率是否下降 → 查是否换了小模型/没开约束解码/上下文被截断导致 schema 不全。
3. **路由错**：召回的 Top-N 是否不含正确工具 → 查 embedding 漂移 / 工具改名未同步索引。
4. **参数非法**：`required` 字段缺失或类型错 → 查 schema 变更是否向后兼容。
5. **执行失败**：接口超时/限流/鉴权过期 → 查依赖服务 SLO、token 过期、突发流量。
6. **回归**：是否刚发版（工具 schema 改了描述/字段）→ 灰度回滚。
- 加分点：用"漏斗看板"（召回率→选对率→合法率→执行成功率）一眼定位掉在哪个环节。

### Q6：JSON Mode 和 Tool Calls 怎么选？二者关系是什么？

**核心答点：**

- **JSON Mode**：强制输出合法 JSON，但**不绑定任何工具 schema**——模型自己决定结构。适合"只要结构化输出"（如抽取、分类），但结构是否对、字段是否齐，模型自己说了算。
- **Tool Calls**：输出 `{name, arguments}`，`arguments` 必须匹配某个已注册工具的 JSON Schema，且由 API 解析、可执行。适合"要让模型调具体工具"。
- **关系**：Tool Calls 是"带 schema 约束 + 可路由 + 可执行"的 JSON Mode 超集。能用 Tool Calls 就别用裸 JSON Mode 做工具调用——前者把"结构正确性"交给约束解码和 schema 校验，可靠性更高。
- **选型**：要调工具 → Tool Calls；要自由结构（如把文本转成自定义 JSON）→ JSON Mode；两者都可叠加约束解码。

## 四、模拟面试（3 个深度题 + 参考答案要点）

### 模拟题 1：从零设计支持 1200+ 工具、百万 QPS 的函数调用中台

**题干：** 假设你要为公司的 Agent 平台设计函数调用中台 FuncHub，面对 1200+ 工具、日均百万级 QPS、模型从小模型到旗舰模型混合。请设计完整架构，重点回答：①工具 schema 怎么管理才不会撑爆上下文；②如何保证结构化输出合法；③多工具并行怎么编排；④如何控制成本与副作用。

**参考答案要点：**

1. **分层架构（见 1.2 六层）**：治理层(Registry) → 路由层 → 约束层 → 执行层 → 编排层 → 应用层。每层单一职责、可独立扩容。
2. **schema 治理（难点2/5）**：工具注册中心存完整 schema + 元数据（version/risk/owner/timeout）；**不把 schema 全塞上下文**，改为"语义路由召回 Top-12 + LLM 精排 + 外部化/动态裁剪"。1200 工具 → 注入 ~1.3K token。
3. **结构化保证（难点1）**：推理引擎侧 **Grammar-Constrained Decoding**（把工具 schema 编译成 CFG，token 掩码强制合法），合法率 99.6%；prompt 侧分隔符 + 修复解析 + 错误回灌做兜底。
4. **并行编排（难点3）**：解析 `tool_calls[]` → 引用解析建 DAG → 拓扑分层 → 同层 asyncio 并发、跨层串行；失败节点重试/降级/重规划；循环依赖检测。
5. **成本与副作用（难点6）**：预算闸门（次数/费用上限 → human-in-the-loop）、语义缓存（幂等读工具去重）、幂等键（写工具防重复副作用）、风险分级（high-risk 强制二次确认）。
6. **可观测**：每个工具埋点（延迟/失败率/参数分布/合法率），漏斗看板（召回→选对→合法→执行），异常自动告警 + 灰度回滚。
7. **纵深防御**：约束解码(服务端) + schema 校验(中台) + 权限/预算(执行前) + 审计(执行后)，任一层漏了下一层兜。

### 模拟题 2：工具调用成功率从 92% 跌到 30% 的 30 分钟止血复盘

**题干：** 凌晨 FuncHub 报警：工具调用首次成功率从 92% 暴跌到 30%，用户大面积反馈 Agent"调不动工具"。你是 oncall，如何在 30 分钟内止血并定位根因？请给出现场动作序列与可能的根因。

**参考答案要点：**

1. **0~5 分钟 · 止损先撇流量**：看漏斗看板拆因——是"合法 JSON 率"掉（约束解码挂了？模型回退到旧版？）还是"执行成功率"掉（依赖服务挂了？）。若执行失败，先对 high-risk 之外开启**降级**（失败转"让模型说明无法调用"），保住主链路不雪崩。
2. **5~10 分钟 · 看变更**：查近 1 小时发版/配置变更。极可能：**工具 schema 刚批量改了字段/改名**但 embedding 索引未同步 → 路由召回错工具；或**约束解码开关被误关** → 小模型裸输出 JSON 合法率骤降。确认即回滚。
3. **10~20 分钟 · 看依赖与容量**：若执行失败，查下游 RPC/DB 的 SLO、限流、鉴权 token 是否过期、是否突发流量把下游打挂（限流兜底）。查 FuncHub 自身是否 OOM（路由层 embedding 服务被打满）。
4. **20~30 分钟 · 定位 + 固化为规则**：确认根因（如"索引未同步导致召回错误工具"），强制"schema 变更必须触发索引重建 + 灰度校验召回率"的发布卡点；补告警（召回正确率跌破阈值即告警，而非等最终成功率）。
5. **加分点**：用"失败样本聚类"快速看错误类型分布（是 `ValidationError` 多还是 `Timeout` 多），比逐条看日志快 10 倍；事后写复盘把"召回率"纳入 SLI。

### 模拟题 3：让开源 7B 模型具备可靠的 Function Calling 能力

**题干：** 你只有开源 7B 基座（无原生 FC 训练），但业务要求它在 200 个工具上达到可用调用准确率，且输出必须可解析。请设计"训练 + 推理"的完整方案，并讲清如何评测。

**参考答案要点：**

1. **训练侧（Q4 范式）**：构造 SFT 数据——系统提示含工具 schema + 多轮 `(query, tool_call, observation, answer)` 轨迹；用强模型蒸馏 + 合成数据覆盖"单工具/并行/多步/无需调用/拒绝"五类；加入负样本训练"无匹配工具时输出 no_tool_call"。LoRA/QLoRA 微调（成本可控）。
2. **推理侧（双保险）**：
   - 必开 **约束解码**（xGrammars/outlines），把工具 schema 当文法，7B 也能 99%+ 合法——这是小模型可靠的关键；
   - 路由层把 200 工具召回 Top-12，降低小模型"选错工具"的概率；
   - schema 校验 + 类型自愈 + 错误回灌兜底。
3. **评测侧**：建 **BFCL（Berkeley Function Calling Leaderboard）风格** 基准——覆盖：① 抽象参数准确性（类型/必填）；② 多工具选择；③ 并行调用；④ 多步依赖；⑤ 无关查询拒绝。指标用 `AST 匹配率`（解析出结构与 ground-truth 是否语义等价，而非字符串相等）+ 执行成功率 + 合法率。
4. **加分点**：小模型常"过度调用"（啥都想调），用"无工具样本"强化 + 温度调低 + 拒绝类 SFT 抑制；长尾工具用"路由召回"比"全量塞入"对小模型更友好（注意力不被噪声 schema 稀释）。

## 五、速记卡 / 一页纸总结

```
【函数调用工程化 FuncHub 一句话】
Agent 的"手" = 路由(找对工具) + 约束解码(吐合法JSON) + 编排(并行DAG) + 校验(参数安全) + 治理(成本/副作用)

【六层架构】
治理(Registry/版本/权限) → 路由(Embedding召回+精排) → 约束(语法解码+Schema校验)
→ 执行(执行器/审计/预算) → 编排(DAG/重试/降级) → 应用(Agent/工作流)

【结构化输出三道防线】
1) Grammar-Constrained Decoding（服务端，99.6%，概率置0非法token）
2) prompt 分隔符 + 宽松修复解析（兜底）
3) 错误回灌自愈（≤2次）

【约束解码公式】
P_masked(xt|x<t) = P(xt|x<t)·1[x<t xt∈L(G)] / Σ P(x'|x<t)·1[x<t x'∈L(G)]

【1200 工具不撑爆上下文】
全量 456K token → 语义路由 Top-12 + 外部化/动态裁剪 → ~1.3K token（-88%）

【并行编排】
tool_calls[] → 引用解析建 DAG → 拓扑分层 → 同层并发/跨层串行 → 失败重试/降级/重规划

【成本控制】
预算闸门(次数/费用上限) + 语义缓存(幂等读) + 幂等键(写防重复) + 风险分级(high需确认)

【高频考点速记】
- ReAct vs FC：自然语言prompt范式 vs 训练出的结构化能力（可靠/可并行/可控）
- JSON Mode vs FC：FC = 带schema约束+可执行 的 JSON Mode 超集
- 合法JSON保证：约束解码是根本解，prompt/修复只是兜底
- 失败率暴跌排查：漏斗看板(召回→选对→合法→执行) 先撇流量再查变更
- 小模型FC：必开约束解码 + 路由召回 + 拒绝类SFT 抑制过调用
```
