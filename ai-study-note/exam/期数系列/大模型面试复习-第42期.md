### 1.3 六大核心亮点

**① 仓库级上下文工程（Repo Context Engineering）**
不是把整个仓库塞进 prompt，而是构建"向量索引 + 调用图（Call Graph）+ 符号表"三位一体的语义检索：先按 AST 切分为函数/类/方法级 chunk，再用 CodeBERT 类 embedding 做语义检索，并用调用图做"拓扑邻居扩展"（被调用方 + 调用方），最后按预算动态裁剪。召回 @10 从 64% → 91%。

**② AST 约束解码（Grammar-Constrained Decoding）保证 100% 合法代码**
在解码每一步对 vocab 做语法掩码：维护一个增量式解析器（Earley / Lark），只保留能让当前前缀继续扩展为合法语法树的 token（类似 Outlines / 谷lm-constraints）。生成结果**结构性合法率 99.7%**，彻底消除"括号不匹配 / 缩进错乱"类错误。

**③ FIM（Fill-In-the-Middle）中间补全**
训练与推理均支持 `<|fim_begin|> prefix <|fim_hole|> suffix <|fim_end|> middle` 格式，让模型学会"给定前后文补全中间"，完美适配 IDE 光标处补全（而非总是从左往右生成）。配合 Repo-Level Prefix Cache，跨补全共享 prefix KV，首 token -77%。

**④ SWE Agent 多文件自动修复**
把"修 bug / 加功能"建模为工具调用循环：读文件 → 编辑 → 跑测试 → 看报错 → 再改。支持跨文件一致性（AST diff 最小化补丁），在内部 SWE-bench 风格基准上 resolve rate 达 41%（从 18% 起步），接近大模型直接给答案难以企及的可执行质量。

**⑤ 可执行评测体系（Execution-based Eval）**
不靠 BLEU/困惑度，而靠"编译通过率、单测通过率、SWE-bench resolve rate、静态分析报告、人类评审通过率"多维客观指标；离线跑 SWE-bench 风格任务，在线用 A/B 看补全接受率与漏洞红灯率。

**⑥ 安全合规内建（Security-by-Design）**
生成后链入 SAST（静态应用安全测试）+ SCA（软件成分分析 / 许可证）+ 敏感信息扫描：高危漏洞误生成率 -87%，许可证合规率 99.2%，避免"模型生成 GPL 代码 / 硬编码密钥 / SQL 注入"。

## 二、技术难点与解决方案

### 难点 1：代码结构化输出 100% 合法——AST 约束解码

**问题**：自由采样生成的代码经常括号不匹配、缩进错乱、关键字拼错。传统"生成后 `ast.parse` 校验 + 重试"成功率低且浪费 token。

**方案**：Token 级语法掩码（Grammar-Guided Generation）。每一步解码前，用增量解析器算出"当前前缀下，哪些 token 是合法的"，把不合法 token 的 logit 置为 `-inf`，模型只能从合法集合里采样。

下面给出一个**最小可运行的 CFG 掩码骨架**（真实实现用 Earley/Lark 的状态栈做增量推导，这里用简化版表达核心思想）：

```python
import torch
from lark import Lark, Transformer  # 真实项目用 lark 解析语法

class GrammarConstrainedDecoder:
    def __init__(self, grammar, tokenizer, model):
        self.grammar = grammar
        self.tokenizer = tokenizer
        self.model = model
        # 构建 token -> 是否为"合法接续"的增量校验器
        self.parser = IncrementalParser(grammar)

    def step(self, prefix_ids, logits):
        # 1) 用增量解析器得到"在 prefix 之后能接的字符前缀集合"
        allowed_chars = self.parser.allowed_continuations(prefix_ids)
        # 2) 对每个候选 token，检查它 decode 出的首字符是否落在 allowed 集合
        mask = torch.full_like(logits, float('-inf'))
        for tok_id, score in enumerate(logits):
            tok_str = self.tokenizer.decode([tok_id])
            if self.parser.is_valid_next(prefix_ids, tok_str):
                mask[tok_id] = score
        return mask  # 只允许合法 token

# 调用：每一步 model(input_ids).logits -> decoder.step(input_ids, logits) -> softmax -> 采样
# 复杂度：每次 O(vocab) 校验，配合 trie/状态缓存可降到近乎 O(1)
```

**关键数学**：设模型 vocab 大小 V，约束解码把采样空间从 V 收缩为合法子集 $V_{valid} \subset V$（通常 $|V_{valid}| \ll V$），等价于对分布做硬约束：
$$p'(w_t|w_{<t}) = \begin{cases} \dfrac{p(w_t|w_{<t})}{\sum_{w\in V_{valid}} p(w|w_{<t})}, & w_t\in V_{valid}\\ 0, & otherwise\end{cases}$$

**收益**：合法率 82% → 99.7%；因为不再需要反复重试，端到端 token 消耗反而下降。

### 难点 2：仓库级上下文工程——把百万文件"塞"进上下文

**问题**：补全一个函数，真正有用的上下文是"它的签名、被谁调用、调用了谁、相关类型定义"，而非整个仓库。整文件塞入既超长又稀释注意力。

**方案**：三层索引 + 调用图扩展。

```python
import ast, networkx as nx
from sentence_transformers import SentenceTransformer

# 1) AST 切分：函数/类级 chunk，保留符号名与 docstring 作为检索锚点
def ast_chunk(path, source):
    tree = ast.parse(source)
    chunks = []
    for node in ast.walk(tree):
        if isinstance(node, (ast.FunctionDef, ast.ClassDef)):
            chunks.append({
                "symbol": node.name,
                "lineno": node.lineno,
                "text": ast.get_source_segment(source, node),
            })
    return chunks

# 2) 调用图：用 NetworkX 建图，查询时做 k 跳拓扑邻居扩展
G = nx.DiGraph()
for caller, callee in extract_calls(tree):  # 自己实现的调用抽取
    G.add_edge(caller, callee)

def repo_context(query, k=2):
    hits = embed_retrieve(query, top_n=8)          # 向量语义召回
    expanded = set(hits)
    for h in hits:
        neighbors = set(nx.ego_graph(G, h, radius=k).nodes())  # 拓扑邻居
        expanded |= neighbors
    return rank_and_trim(expanded, budget_tokens=4000)  # 按预算裁剪
```

**要点**：向量检索负责"语义相关"，调用图负责"结构相关（谁依赖谁）"，二者互补。纯向量检索在"修一个被 20 处调用的公共函数"场景会漏掉调用方，调用图补齐。

### 难点 3：SWE Agent 多文件编辑与测试驱动迭代

**问题**：真实任务（如"修复空指针异常"）往往横跨多个文件；一次性生成整文件 patch 极易不一致，且无法自证正确。

**方案**：把修复建模为"读-改-测"工具循环，用最小化 AST diff 表达补丁，以"测试是否变绿"作为奖励信号。

```python
def swe_agent_loop(issue, repo, max_steps=12):
    ctx = build_issue_context(issue, repo)   # 检索相关文件/报错栈
    for step in range(max_steps):
        plan = llm.plan(ctx)                  # 推理"该看哪个文件、怎么改"
        files = llm.pick_files(ctx)           # 工具：read_file
        edits = llm.propose_edits(files, ctx) # 工具：edit_file（AST diff 最小补丁）
        apply_patch(repo, edits)
        result = run_tests(repo)              # 工具：run_tests（真实执行）
        if result.passed:
            return format_pr(edits)           # 成功：产出 PR
        ctx = append(ctx, result.failure_log) # 失败：把报错喂回模型迭代
    return None
```

**Why it works**：把"生成正确代码"的不可验证问题，转化为"生成能让测试通过的补丁"的可验证问题。每一步都有可执行反馈，避免幻觉漂移。

### 难点 4：执行式评测体系——怎么客观知道代码好不好

**问题**：代码质量不能用困惑度衡量；BLEU 对代码几乎无意义（局部 token 相似 ≠ 语义正确）。

**方案**：多层级可执行评测。

| 层级 | 指标 | 说明 |
|------|------|------|
| L0 语法 | parse 通过率 / 类型检查通过率 | 是否合法 |
| L1 单元 | 单测通过率 (pass@k) | $pass@k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}$，n=样本数, c=通过数, k=候选数 |
| L2 任务 | SWE-bench resolve rate | 实例经自动修复后全部测试通过的比例 |
| L3 静态 | SAST 高危数 / 圈复杂度 | 安全与可维护性 |
| L4 人工 | 评审通过率 / 接受率 | 主观但关键 |

**pass@k 公式推导直觉**：从 n 个采样里取 k 个，至少一个通过的概率。当 k=1 即单次通过率；k>1 代表"生成多个候选、跑测试筛最优"的策略收益。

**SWE-bench resolve rate 定义**：
$$\text{resolve\_rate} = \frac{|\{i : \text{instance } i \text{ 修复后 FAIL_TO_PASS 全绿 且 PASS_TO_PASS 仍绿}\}|}{|\text{total instances}|}$$

### 难点 5：推理加速——FIM、Repo Prefix Cache 与代码投机解码

**问题**：IDE 补全对首 token 延迟极度敏感（>300ms 用户就觉得"卡"）；同时仓库级上下文在多次补全间大量重复。

**方案三件套**：

**(a) FIM 训练与推理格式**。标准自回归只建模 $P(x)$。FIM 把序列重排为：
$$\text{PSM（Prefix-Suffix-Middle）}:\; P(x_{mid}|x_{pre},x_{suf}) = \frac{P(x_{pre},x_{mid},x_{suf})}{P(x_{pre},x_{suf})}$$
$$\text{SPM（Suffix-Prefix-Middle）}:\; P(x_{mid}|x_{suf},x_{pre}) = \frac{P(x_{suf},x_{mid},x_{pre})}{P(x_{suf},x_{pre})}$$
训练时按概率 $\gamma$（如 0.5）把样本从 PSM 转 SPM，使模型同时学会"前后文→中间"。推理时按光标位置拼 `<fim_begin>prefix<fim_hole>suffix<fim_end>`。

**(b) Repo-Level Prefix Cache**：同一文件的 import 头、公共类型定义在多次补全间完全一致，将其 KV Cache 按文件 hash 缓存复用，跨补全/跨用户共享 → 首 token -77%。

**(c) 代码投机解码（Speculative Decoding）**：代码具有强规律（模板/样板/import），用小 draft 模型一次猜 8 token，target 模型一次验证，接受率显著高于自由文本，吞吐 +2~3x。

### 难点 6：安全合规——不被模型"投毒"出漏洞/侵权代码

**问题**：代码大模型可能在训练数据里学到 GPL 许可片段、硬编码密钥、SQL 注入写法，直接输出会引入合规与安全风险。

**方案**：生成前过滤 + 生成后扫描双保险。

```python
def safe_generate(prompt, repo):
    draft = code_llm(prompt)                 # 生成草稿
    report = sca_scan(draft)                 # 软件成分分析：许可证/已知 CVE
    vulns  = sast_scan(draft)                # 静态扫描：注入/XSS/硬编码密钥
    if report.license in {"GPL","AGPL"} or vulns.high > 0:
        draft = regenerate_with_constraint(  # 带约束重生成
            prompt, forbid_licenses={"GPL"}, forbid_patterns=vulns.patterns)
    return draft
```

**效果**：高危漏洞误生成率 -87%，许可证合规率 99.2%。

## 三、常见面试问答（6 个深度问题）

### Q1：为什么代码大模型要用 FIM（Fill-In-the-Middle），而不是纯左到右（left-to-right）？

**答**：IDE 补全的核心场景是"光标在中间，前后都有代码"——用户是在一段函数体中间、或两行之间补全。纯左到右 $P(x)$ 只能从左往右生成，无法利用**后缀（suffix）**信息，而补全质量高度依赖后缀（例如后面有个 `}` 决定了当前要补的是 `return` 还是 `pass`）。

FIM 通过把训练样本重排为 `(prefix, suffix, middle)` 三元组，让模型显式学习条件概率 $P(x_{mid}|x_{pre},x_{suf})$。两种排列（PSM / SPM）在数学上等价（联合分布分解，只是条件顺序不同），训练时按概率混用二者，使模型对"光标任意位置"都鲁棒。GPT-2/Codex/StarCoder 系列均验证：FIM 在中间补全任务上相对纯 left-to-right 提升显著（StarCoder 报告中间补全 HumanEval 提升约 10+ 点）。

**辨析**：FIM 不改变模型结构，只改变训练数据的序列化格式与推理时的拼接方式，是"数据/推理技巧"而非"架构改动"。

---

### Q2：如何保证生成的代码 100% 语法合法？约束解码 vs 生成后修复，怎么选？

**答**：两条路线：

- **(A) 约束解码（Grammar-Constrained Decoding）**：解码时逐 token 做语法掩码（见难点 1），模型**只能在合法 token 集合内采样**，天然输出合法序列。优点：零重试、零浪费；缺点：需维护增量语法解析器、与采样策略耦合、对超长生成有状态维护成本。代表：Outlines、 guidance、lm-format-enforcer。
- **(B) 生成后修复（Parse-then-Repair）**：先自由生成再 `ast.parse` / 类型检查，失败则把报错回灌模型重生成或做括号自动闭合。优点：实现简单、不侵入解码；缺点：重试浪费 token、复杂错误（缩进/跨行）修复率低。

**选型**：生产环境**首选约束解码**（合法率 99.7% 且更省 token）；仅在语法规则难以用 CFG 表达（如动态 DSL）或模型不支持 token 级掩码时，退化为"约束解码 + 轻量修复兜底"混合方案。注意：语法合法 ≠ 语义正确，约束解码只解决"能编译"，不解决"逻辑对"，仍需评测体系把关。

---

### Q3：仓库级代码检索为什么需要"调用图"，单纯向量检索不够吗？

**答**：不够，二者解决不同问题。

- **向量检索**回答"语义相关"：例如 query "处理支付的超时逻辑" 能召回名字不叫 timeout 但语义相近的函数。但它是**扁平**的，不知道结构关系。
- **调用图（Call Graph）**回答"结构相关"：修一个被 20 处调用的公共函数 `validateOrder()`，真正要联动看的是它的**调用方**（20 个上层函数），而非只是语义相似的一段代码。纯向量检索会漏掉调用方，因为调用方文本可能和 `validateOrder` 语义不近。

**最佳实践**：向量召回 top-k 做"种子"，再用调用图做 k 跳拓扑扩展（调用方 + 被调用方 + 共享类型定义），最后按 token 预算重排裁剪。这把召回 @10 从 64% 拉到 91%——因为代码任务的"相关性"本质是**结构依赖**而非纯语义。

---

### Q4：SWE-bench 是怎么评测代码模型的？为什么它比 BLEU / 单测通过率更难也更可信？

**答**：SWE-bench 用**真实 GitHub issue + PR** 构建：每个实例给出仓库快照、issue 描述（自然语言需求），gold patch（人类 PR）。评测时让模型生成 patch 并应用到仓库，运行两套测试：

- **FAIL_TO_PASS（F2P）**：被该 issue 修复后由红变绿的测试——衡量"是否真修好了"；
- **PASS_TO_PASS（P2P）**：修复前后都绿的测试——衡量"有没有引入回归"。

只有 **F2P 全绿 且 P2P 仍绿** 才算 resolve。

**为什么更难更可信**：
1. 它要求**多文件、跨上下文、可执行**的正确，而非单函数补全；
2. 用"测试是否通过"做标签，杜绝了 BLEU（token 相似≠正确）和单测通过率（可能只是恰好蒙对）的弊端；
3. resolve rate 直接对应"模型能否替代初级工程师做真实 PR"，是最贴近落地的指标。

---

### Q5：代码生成怎么做到推理加速？FIM 和投机解码在代码场景为什么特别有效？

**答**：三板斧（见难点 5）：

1. **Repo-Level Prefix Cache**：补全时 import 头、公共类型定义等前缀在多次请求间高度重复，按文件 hash 缓存 KV，跨补全复用 → 首 token 从 800ms→180ms（-77%）。
2. **FIM + 光标感知**：只在光标处算一次 middle 解码，prefix/suffix 部分可缓存，避免每次重算整文件。
3. **投机解码（Speculative Decoding）**：代码（尤其样板/import/模板）具有**强局部规律与低熵**，draft 小模型一次猜 8 token 的接受率远高于自由文本（自由文本接受率常 <0.6，代码可达 0.8+），target 模型一次并行验证，吞吐 +2~3x 且不损质量。

**补**：还可叠加 INT4/INT8 量化（代码任务对精度损失更不敏感）、tensor parallelism 横向扩展。

---

### Q6：代码大模型怎么防止生成"有漏洞 / 侵权"的代码？

**答**：双保险（见难点 6）：

- **生成前（训练/数据侧）**：清洗训练语料中的高危片段、剔除 GPL/AGPL 强 copyleft 许可证代码、过滤含硬编码密钥的样本；可用 SCA（软件成分分析）对训练源做许可证画像。
- **生成后（推理侧）**：流水线接入 SAST（静态应用安全测试，扫注入/XSS/硬编码密钥）、SCA（扫开源许可证与已知 CVE）、敏感信息扫描；命中高危则带约束重生成（禁止 GPL 许可、禁止特定漏洞 pattern）。

**本质**：代码生成的"安全"不能靠模型自觉，必须**工程化闭环**——因为漏洞/侵权是确定的、可机器判定的规则，正好适合用确定性扫描器兜底，而不是交给概率模型去"别写错"。这也是 Code LLM 比聊天 LLM 更"可治理"的优势：反馈信号客观。

## 四、模拟面试（3 个深度题 + 参考答案要点）

### 模拟题 1：端到端架构设计

> **面试官**：请设计一个支撑 10 万开发者、托管 100 万仓库的代码智能平台（类似 CodeWeaver）。要求覆盖：IDE 补全、Repo 级问答、SWE 自动修复三类场景；说明仓库索引怎么建、上下文怎么裁剪、代码怎么保证合法、推理怎么加速、质量怎么评、安全怎么管。

**参考答案要点（建议 8 分钟讲清楚）：**

1. **分层架构**（对应六层）：应用层（插件/Bot/CI）→ 编排层（Repo Agent / SWE Agent）→ 生成层（AST 约束解码 + FIM + 候选筛选）→ 检索层（向量 + 调用图 + 裁剪重排）→ 模型层（路由 + Repo Prefix Cache + 投机解码 + 量化）→ 治理层（索引/权限/合规/埋点）。
2. **仓库索引**：CI 触发时异步跑 AST 切分（函数/类级 chunk）+ embedding 入库（向量库 IVF-PQ）+ 构建调用图（NetworkX / 图数据库）；增量更新只重算改动文件。
3. **上下文裁剪**：向量召回 top-k 作种子 → 调用图 k 跳拓扑扩展 → 按 token 预算（如 4k）重排（调用方优先于被调用方、报错栈相关优先）。
4. **合法保证**：解码期 AST 约束解码（token 级语法掩码），99.7% 合法；辅以生成后 `ast.parse` 兜底。
5. **推理加速**：Repo-Level Prefix Cache（按文件 hash 跨用户共享 KV）、FIM 光标感知、投机解码（+2~3x）、INT4 量化。
6. **质量评测**：离线 SWE-bench 风格 + pass@k；在线 A/B 看接受率/首 token/漏洞红灯率。
7. **安全合规**：生成后 SAST+SCA+敏感扫描，命中高危带约束重生成；训练侧许可证过滤。
8. **伸缩性**：索引与生成解耦，生成用弹性 GPU 池 + 队列削峰；检索走向量库副本。

### 模拟题 2：线上故障复盘

> **面试官**：线上代码补全突然出问题——首 token 延迟从 800ms 暴涨到 5s，补全接受率从 62% 掉到 12%，15 分钟内工单雪崩。请你做 30 分钟止血复盘：怎么定位、怎么止血、怎么根治？

**参考答案要点：**

1. **先止血（5 分钟）**：
   - 看网关指标：延迟 5s 多半是**下游模型/缓存**问题而非 IDE。确认 Prefix Cache 命中率是否骤降（命中率掉 → 每次重算整文件 → 延迟↑且因上下文变长/截断导致接受率↓）。
   - 临时降级：关闭 Repo 级上下文扩展（退回"仅当前文件 + 轻量向量召回"），首 token 立刻回落；接受率因上下文变少短期略降但稳定。
2. **再定位（10 分钟）**：
   - 查 Prefix Cache 服务：很可能缓存集群**内存打满被逐出**或 hash 策略变更导致 key 不一致（命中率 95%→3%）。
   - 查检索层：调用图服务是否超时（上游一次补全要等图扩展 4s）→ 触发熔断后上下文为空 → 模型盲生成 → 接受率崩。
3. **根因（举例）**：一次"调用图服务扩容"改了序列化协议，旧客户端读到空图，检索层返回空 → 模型无上下文 + 重试风暴打满 KV → 延迟与接受率双崩。
4. **根治（15 分钟+）**：恢复缓存/图服务兼容；给检索层加**超时熔断 + 降级空上下文**；给 Prefix Cache 加命中率告警；把"接受率 + 首 token"设为 SLO 红区，低于阈值自动切降级通道（呼应第39期 LLMOps 观测）。

### 模拟题 3：从零训练一个"小而强"的代码模型

> **面试官**：公司算力有限，只能用 7B 开源底座。目标是让它在补全质量上逼近 34B 代码模型（HumanEval 风格 60%+），并能在 IDE 里低延迟服役。请给出数据工程 + 训练 + 推理的完整方案，重点讲 FIM、语法约束、仓库检索怎么组合。

**参考答案要点：**

1. **数据工程（质量 > 规模）**：
   - 语料：The Stack / 内部仓库，按**许可证白名单**筛选（排除 GPL/AGPL），去重（MinHash/SSDE），按语言配比（Python/TS/Java/Go 加权）。
   - **FIM 化**：按概率 0.5 把样本转 PSM/SPM 三元组，使 7B 学到中间补全能力——这是小模型追平大模型的关键技巧之一。
   - 加入**仓库级构造样本**：把"函数 + 它的调用方/被调用方"拼成训练样本，让小模型隐式学到结构依赖。
2. **训练**：
   - 继续预训练（continued pretrain）在代码混合物上，再 SFT 在 (指令, 代码) 对 + 单元测试通过的 (问题, patch) 对。
   - 用 **pass@k 做验证集筛选**，而非困惑度；早停在 SWE-bench-lite 上。
3. **推理侧补齐差距**：
   - **AST 约束解码**：小模型语法更易出错，约束解码把合法率拉到 99%+，直接抹平与 34B 的"低级错误"差距。
   - **Repo 检索增强**：7B 记不住仓库约定，靠检索把"项目 own 的写法/类型"喂进去，逼近大模型参数里记住的先验。
   - **多候选 + 单测筛选**：小模型用 pass@k（生成 8 个、跑测试留最优）以算力换质量，成本仍远低于 34B 单次。
   - **量化 + Prefix Cache + 投机解码**：INT4 + 仓库前缀缓存 + 投机解码，把首 token 压到 200ms 内、成本压到 34B 的 1/5。
4. **结论**：小模型追平大模型 = **更好的数据（FIM/许可证/去重）+ 解码期约束（AST）+ 检索增强（Repo 上下文）+ 评测筛选（pass@k）**，而非纯堆参数。
