## 二、技术难点

### 难点 1：端侧权重量化（INT4 / INT2）与反量化内核

**问题**：移动端总内存仅 4–8GB，LLM 一般只分到 1/4；FP16 7B 要 14GB，根本放不下。必须压到 2–4GB 且精度损失小。

**方案**
- **权重量化（Weight-only Quantization）**：只量化静止的权重，激活保持 FP16。反量化在推理时做：
  `W = s · q`（INT4 对称量化，per-group，group_size=64/128）
- 推理 GEMM：`X @ W = X @ (s · q) = s · (X @ q)`，量化核心用 INT4/INT8 GEMM + 反量化。
- **混合精度**：敏感层（embedding / lm_head / 部分 up_proj）保留 FP16/INT8，其余 INT4，注意力相关可用 INT2。
- **校准**：端侧算力有限，跑不了 GPTQ 的二阶逆，常用 **AWQ（激活感知）** 做单步校准；QQQ / SpQR 进一步做混合精度。

**代码：group-wise INT4 量化 + 反量化**

```python
import torch

def quantize_weight_int4(w: torch.Tensor, group_size: int = 128):
    """Group-wise INT4 权重量化。返回量化值(int8 打包语义)与每组 scale。"""
    assert w.dim() == 2
    out_features, in_features = w.shape
    assert in_features % group_size == 0
    w = w.float()
    w_g = w.reshape(out_features, in_features // group_size, group_size)
    qmax, qmin = 7.0, -8.0            # INT4 对称区间 [-8, 7]
    scale = w_g.abs().max(dim=-1, keepdim=True).values / qmax
    scale = scale.clamp(min=1e-8)    # 对称量化，zero = 0
    q = torch.round(w_g / scale).clamp(qmin, qmax)
    return q.to(torch.int8), scale    # scale: [out, in//g, 1]

def dequantize_weight_int4(q_int, scale, group_size: int = 128):
    return (q_int.float() * scale).reshape(q_int.shape[0], -1)

def matmul_quant(x: torch.Tensor, q_int, scale, group_size: int = 128):
    """推理：INT4 权重 × FP16 激活 → FP16 输出（实际由 NPU/INT4 GEMM 内核完成）。"""
    w_deq = dequantize_weight_int4(q_int, scale, group_size)   # [out, in] fp16
    return x @ w_deq.T
```

**深层要点**：纯权重量化时激活保持 FP16，所以 GEMM 内核要支持「FP16 激活 × INT4 权重 → FP16 输出」。端侧 NPU（高通 HTP / 苹果 ANE）提供 native `matmul_4bit` 指令；若 NPU 不支持需退化为「两个 INT4 打包进一个 INT8」模拟。lm_head 的 vocab 维度巨大（32000×hidden），不能用 INT2 否则崩，常用 INT4/INT8 + 离线缓存 logits。`per-group` 比 `per-tensor` 误差小，因为权重在组内分布更均匀。

### 难点 2：端侧 KV Cache 显存压缩（GQA + KV 量化）

**问题**：解码阶段 KV Cache 增长公式：

```
KV_bytes = 2 × n_layers × n_kv_heads × seq_len × head_dim × bytes_per_elem
```

7B（MHA：32 层、32 KV head、head_dim 128、FP16）在 seq=4K 时：
`2 × 32 × 32 × 4096 × 128 × 2 ≈ 2.1 GB` —— 手机根本不够。

**方案**
- **GQA（Grouped-Query Attention）**：KV head 从 32 降到 8（极端 MQA 降到 1），KV 显存直接 ÷4~÷32。**端侧小模型首选 GQA/MQA**。
- **KV 量化**：KV 从 FP16 → INT8（per-token / per-channel 对称），显存再 ÷2；极限 INT4（配敏感度分析）。实践：**Key 用 INT8、Value 用 INT4**（Key 决定注意力分布，Value 被平均稀释）。
- **端侧 PagedAttention**：KV 分页管理避免碎片（block_size=16，思路同 vLLM 第27期）。
- **长上下文淘汰**：sliding window 或 H2O（按累计注意力得分淘汰 70–90% KV）。

**代码：GQA 注意力 + KV 量化（简化）**

```python
import torch

def gqa_attention(x, wq, wk, wv, n_kv_heads=8, n_q_heads=32, head_dim=128, kv_quant=True):
    B, T, _ = x.shape
    q = (x @ wq.T).view(B, T, n_q_heads, head_dim).transpose(1, 2)
    k = (x @ wk.T).view(B, T, n_kv_heads, head_dim).transpose(1, 2)
    v = (x @ wv.T).view(B, T, n_kv_heads, head_dim).transpose(1, 2)
    # GQA：多个 Q head 共享一组 KV head
    n_rep = n_q_heads // n_kv_heads
    k = k.repeat_interleave(n_rep, dim=1)
    v = v.repeat_interleave(n_rep, dim=1)
    # KV 量化（per-token 对称 INT8，实际与 GEMM 融合）
    if kv_quant:
        k_scale = k.abs().amax(dim=-1, keepdim=True) / 127 + 1e-8
        k = (k / k_scale).round().clamp(-128, 127).to(torch.int8).float() * k_scale
    return k, v   # 拼接历史 KV 后做 scaled dot-product attention
```

**深层要点**：KV 量化误差主要来自 softmax 前的 logits 被压缩导致注意力分布偏移；**逐 token 量化**比逐层稳健（不同位置分布差大），**逐 channel 量化**更省显存。H2O 类方法按累计注意力得分淘汰 KV，端侧 4K 上下文可压到 200–400MB。

### 难点 3：算子融合与 NPU 异构部署

**问题**：拆成大量小算子（Linear / RoPE / Attention / SiLU）在端侧 CPU 上导致大量内存读写（kernel launch + 访存瓶颈），NPU 利用率低。

**方案**
- **算子融合**：Linear+RoPE、QKV 投影合并、SwiGLU（MatMul+SiLU+Mul）、RMSNorm+后续算子融合，减少中间 tensor 落地。
- **端侧 FlashAttention**：分块计算，避免 materialize `[T×T]` 注意力矩阵。
- **异构调度**：NPU 跑大 MatMul，CPU 跑不规则控制流（采样 / top-k）。
- **编译优化**：executorch / MNN / TFLite / NCNN 编译为端侧 executor；苹果 Core ML/ANE，高通 QNN/HTP，联发科 Neuron。

**代码：融合 SwiGLU（激活融合进 GEMM epilogue）**

```python
# 标准拆分：两个 Linear + SiLU + Mul（多次 [seq, hidden] 中间写）
# 融合后：两次大 GEMM + 在 GEMM 后融合激活，省一次中间 tensor 落地
def swiglu_fused(x, w_gate, w_up, w_down):
    g = x @ w_gate.T                 # [B, T, H]
    u = x @ w_up.T                   # [B, T, H]
    g = g * torch.sigmoid(g)         # silu(g) = g * sigmoid(g)，融合进 epilogue
    return (g * u) @ w_down.T
```

**深层要点**：(1) 融合收益多在 **memory-bound** 算子（RMSNorm、激活、偏置加）；大 MatMul 是 compute-bound，融合收益小但能省中间 materialization。(2) 端侧编译器通过 **delegate** 把子图 offload 给 NPU backend，未覆盖算子回退 CPU。(3) RoPE 融合进 QKV GEMM 的 epilogue 可省一次全序列遍历。

### 难点 4：端云协同路由（质量 / 延迟 / 成本三维）

**问题**：纯端侧能力有限（7B 答不准复杂问题），纯云端成本高且隐私差；需动态路由。

**方案**
- **路由维度**：①能力（任务复杂度预估）②延迟（实时性）③隐私（是否含 PII/私有文档）④成本（预算）。
- **路由策略**：
  - 规则路由：含私有文档 / PII → 端侧；简单闲聊 / 补全 → 端侧；复杂推理 / 长文档 → 云端。
  - 模型路由：轻量分类器（小模型 / 启发式）预测难度，难→云端大模型，易→端侧小模型（RouteLLM / MoE routing 思路）。
  - 语义缓存：高频问题命中本地缓存直接返回（命中率 30%+ 可省大量云端调用）。
  - 降级兜底：云端超时 / 限流 → 自动回退端侧并提示「答案可能不那么精确」。
- **数学**：期望成本 `C = p_cloud·(c_cloud + l_cloud) + p_edge·(c_edge + l_edge)`，目标是在约束 `Q ≥ Q_min` 下最小化 C。

**代码：路由决策（隐私优先 + 难度预估 + 缓存）**

```python
import re
PII_RE = re.compile(r'(身份证|手机号|(\d{3}-){2}\d{4}|secret|密码)')

def route(query: str, has_private_doc: bool, latency_budget_ms: int, cache):
    if has_private_doc or PII_RE.search(query):     # 1) 隐私优先 → 端侧
        return "edge"
    if cache.get(query):                            # 2) 语义缓存命中
        return "cache"
    complexity = estimate_complexity(query)         # 3) 轻量难度预估 0..1
    if complexity > 0.7 or latency_budget_ms > 800: # 4) 难/长文 → 云端
        return "cloud"
    return "edge"
```

**深层要点**：路由器的「难度预估」本身是个小模型 / 分类器，需用云端大模型输出质量做标签训练。RouteLLM 用「偏好对 + 强/弱模型」训练路由，可在质量不变下省 ~50% 云端调用。路由错误导致质量下降的代价大——可用**置信度阈值 + 云端兜底**。

### 难点 5：端侧 RAG 与隐私保护（本地向量库 + 差分隐私）

**问题**：用户想让端侧模型用私有文档（合同 / 病历）问答，但不能把文档上传云端。

**方案**
- **本地向量库**：端侧 embedding（bge-small / all-MiniLM 量化版）+ 本地索引（FAISS-CPU / 轻量 HNSW）。
- **端侧重排**：小 cross-encoder 或本地 LLM 重排 top-k。
- **隐私护栏**：PII 端侧检测；文档只在本地切分 / 向量化 / 检索；必要时差分隐私（embedding 加噪）。
- **端云协同 RAG**：检索在端侧，生成可端侧可云端（见难点4）。

**代码：本地检索 + 隐私脱敏**

```python
import re

def local_retrieve(q_emb, tree, chunks, top_k=3):
    _, idx = tree.query(q_emb.reshape(1, -1), k=top_k)
    return [chunks[i] for i in idx[0]]

PII = re.compile(r'(\d{17}[\dX]|\d{11}|账号[:：]\s*\S+)')
def redact(text: str) -> str:
    return PII.sub('[REDACTED]', text)
```

**深层要点**：端侧 embedding 要量化到 INT8 以免拖慢检索。差分隐私 ε 控制隐私预算，ε 越小隐私越强但检索质量降；**日常推理靠「本地化（数据根本不出端）」已强于 DP**，DP 只在需把本地数据用于训练 / 上报时才用。

### 难点 6：端侧投机解码（Speculative Decoding on Device）

**问题**：端侧小模型自回归逐 token 慢（每步只算一个 token 的 MatMul，NPU 算力浪费）。

**方案**
- **投机解码**：端侧更小的 draft 模型（如 0.5B）并行猜 K 个 token，target（7B）一次前向验证，接受率 α 则提速。
- **数学**：加速比 ≈ `1 / (1 − α·γ)`（α 接受率，γ draft 长度）；端侧典型 α = 0.7–0.85。
- **端侧特化**：**n-gram 投机**（基于历史 bigram/trigram 表）零额外显存，最适合端侧；或更小 draft 模型。

**代码：投机解码验证步（简化）**

```python
import torch, random
from torch.softmax import softmax  # 示意

def speculative_step(x, draft_model, target_model, gamma=4):
    candidates = draft_model.generate(x, gamma)     # draft 并行生成 gamma 个
    logits = target_model(x, candidates)            # target 一次前向算所有位置
    n_accept = 0
    for i in range(gamma):
        p = softmax(logits[i])[candidates[i]]
        if random.random() < p:                     # 接受
            n_accept += 1
        else:                                        # 按 target 分布重采样并停止
            x = resample(logits[i]); break
    return n_accept
```

**深层要点**：端侧投机解码瓶颈在 draft 模型也要跑 NPU；**n-gram 投机几乎零成本**，最适合端侧。目标模型验证是单步大 batch，比自回归逐步算更高效。端侧 KV cache 要能容纳 draft + target 拼接。

## 三、常见问答（6 个深度问题）

**Q1：端侧部署为什么要优先用权重量化（weight-only）而不是训练后全量化（W8A8）？**
> ① 端侧激活方差大、离群值多，激活量化（W8A8）误差显著，尤其 attention 的 softmax 前 logits；② 权重量化只压静止权重、激活保持 FP16，误差可控且 GEMM 内核易实现（INT4 权重 × FP16 激活）；③ 端侧内存瓶颈主要是权重存储（14GB→3.8GB），激活是瞬态小；④ 现代端侧 NPU 支持 `matmul_4bit` 指令，权重量化性价比最高。极致场景才上 W4A8（LLM.int4），但要小心 outlier 处理。

**Q2：GQA 相比 MQA 和 MHA，为什么是端侧最佳折中？**
> MHA 每个 Q head 一个 KV head → KV 最大；MQA 所有 Q 共享 1 个 KV head → KV 最小但质量下降（表达力受限）；GQA 把 Q head 分组共享 KV（如 32Q:8KV）→ KV 是 MHA 的 1/4，质量接近 MHA。端侧要压 KV 显存又不想牺牲太多质量 → GQA 是甜点（LLaMA-3 / Mistral / Qwen2 都用 GQA）。MQA 适合极致端侧（如 1B 手机模型），但需更多训练补偿。

**Q3：端云协同路由，如何避免「路由错误导致质量崩塌」？**
> ① 路由器用有标签数据训练（云端大模型质量做 label），不是拍脑袋；② 设置信度阈值，低于阈值一律走云端；③ 云端兜底：端侧答完置信度低 / 用户点「不满意」→ 云端二次答；④ 在线评估（第39期 LLMOps）监控路由后质量，下降自动回退「全云端」或调高阈值；⑤ A/B + 满意度验证。RouteLLM 实测质量不变下省 ~50% 云端调用。

**Q4：端侧 KV Cache 量化为什么 Key 和 Value 常用不同精度（K INT8 / V INT4）？**
> 注意力输出 = `softmax(QKᵀ)V`。Key 决定注意力分布（分布偏移对结果影响大）→ 需高精度 INT8；Value 是加权求和的「值」，单个误差被平均稀释 → 可更低精度 INT4。量化敏感性分析（逐层 / 逐 head 测 perplexity）确认该结论。另外逐 token 量化 Key 比逐层更稳（不同位置分布差大）。

**Q5：端侧推理为什么「算子融合」收益大？融合的原则是什么？**
> 端侧（尤其 CPU / NPU 小核）带宽受限，拆成小算子每个都要把中间张量写回内存再读，访存成瓶颈（roofline 落在 memory-bound 区）。融合把多算子合并为一个 kernel，中间结果留寄存器 / 共享内存，省访存。原则：① 融合 memory-bound 算子（RMSNorm、激活、偏置加）收益最大；② compute-bound 大 MatMul 融合收益小但能省中间 materialization；③ 不规则控制流（采样 / top-k）难融合，留 CPU。

**Q6：端侧大模型如何兼顾「隐私」和「能力」？数据不出端会不会答不准？**
> 隐私靠「本地处理优先」——私有文档本地向量化检索（难点5），PII 端侧脱敏，敏感 query 强制端侧。能力靠「端云协同」——难的 / 长文走云端（难点4 路由），端侧只做简单 / 隐私任务。即「隐私数据不出端，复杂计算上云」。完全离线（飞行模式）则接受端侧 7B 能力上限，用本地 RAG + 工具弥补。差分隐私只在需把本地数据用于训练 / 上报时才用，日常推理靠本地化已足够。

## 四、模拟面试（3 题 + 参考答案要点）

### 模拟题 1：设计支持 10 亿终端的端侧大模型部署平台（端到端架构）

**参考答案要点**
- **分层**：模型压缩层（INT4/INT2、GQA、LoRA 热插拔）→ 端侧引擎（异构 NPU/CPU、算子融合、端侧 PagedAttention、KV 量化）→ 端云路由（三维路由 + 语义缓存 + 降级）→ 隐私护栏（本地优先 / PII 脱敏 / DP）→ 端侧 RAG（本地向量库）→ 应用编排（端侧 Agent）。
- **终端侧**：机型适配（安卓 NNAPI / 高通 QNN / 苹果 Core ML / MTK Neuron）；模型分片下发（按需下载 LoRA / 量化变体）；OTA 热更新。
- **服务端**：模型压缩流水线（AWQ 校准 + 量化 + 稀疏，自动评估精度损失）、路由策略训练与下发、端云协同网关、脱敏埋点回传。
- **关键指标**：端侧首 token、token/s、内存峰值、功耗、云端成本占比、隐私合规率。
- **难点**：机型碎片化（几百种 SoC）→ 统一 IR（executorch / TFLite）+ backend delegate；老机型无 NPU → CPU 量化回退。

### 模拟题 2：端侧 7B 模型首 token 延迟从 280ms 暴涨到 2s，如何 30 分钟止血并定位根因？

**参考答案要点**
- **止血（前 10min）**：① 看监控（第39期 LLMOps）确认是机型 / 版本 / query 分布变化；② 新版本 → 回滚端侧引擎；③ 云端路由异常 → 切「全端侧」降级；④ 某机型 NPU delegate 失败 → 回退 CPU 路径；⑤ 限流 / 熔断保护。
- **根因（20min）**：① NPU delegate 注册失败 → 所有算子回退 CPU，MatMul 慢 10×；② KV 反量化 bug 未融合、逐 token 在 CPU 循环 materialize 2GB；③ 新 query 含超长上下文触发未优化的 sliding window；④ 算子融合失效（图未匹配融合 pattern）。
- **修复**：固定 delegate 回退逻辑 + KV 反量化融合进 kernel + 长上下文走 H2O 淘汰 + 加 delegate 状态 assertion 监控。
- **预防**：端侧引擎启动自检（e2e latency 探针）+ 灰度发布 + 回滚开关。

### 模拟题 3：如何在 4GB 内存的手机上跑起 7B 模型并保证可接受质量？

**参考答案要点**
- **内存预算**：系统 + 其他 App 留 2GB，LLM 可用 ~2GB。
- **权重**：INT4（per-group 128）→ 3.8GB 仍超；混合 INT2（非敏感层）+ INT4（敏感层 up_proj / lm_head）→ ~2.1GB；用 **AWQ** 做激活感知校准减损。
- **KV cache**：GQA（8 KV heads）+ KV INT8 → 2K 上下文约 300MB；加 H2O 淘汰 → 150MB。
- **激活**：batch=1、seq 受限，FP16 临时 ~200–400MB，用**重算（recomputation）**换内存（不存中间激活）。
- **调度**：NPU 跑权重 GEMM（INT4 matmul 指令），CPU 跑采样；PagedAttention 管理 KV 避免碎片。
- **质量兜底**：端云协同（难点4），4GB 机型复杂任务走云端；或上 MoE（激活少数专家，总参大但推理参小）——但 MoE 端侧实现复杂，需权衡。
- **结论**：INT4 + GQA + KV 量化 + 重算 + 端云协同，可在 4GB 跑 7B（质量略降，复杂走云）。

## 速记卡

- 端侧瓶颈 = 内存（权重）+ 访存（算子）→ **权重量化 + 算子融合**
- 权重 INT4 per-group 128；敏感层保 FP16/INT8；**AWQ 校准**
- KV 显存 = `2·L·n_kv·T·hd·2`；GQA ÷4、KV INT8 ÷2、H2O 淘汰 ↓
- GQA(32:8) 甜点；MQA(32:1) 极致；MHA 最贵
- **K INT8 / V INT4**（Key 定分布，Value 被平均）
- 路由三维度：能力 / 隐私 / 成本；隐私优先端侧；难 / 长文走云；语义缓存省 50%
- NPU 跑大 GEMM，CPU 跑控制流；executorch / QNN / Core ML delegate
- 投机解码：**n-gram 零成本最适合端侧**；加速比 ≈ `1/(1−αγ)`
- 隐私靠**本地化（数据不出端）**，强于差分隐私
