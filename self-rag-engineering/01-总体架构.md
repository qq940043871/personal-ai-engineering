# 01 · 总体架构

> 定位：ownrag 的**架构总图**——分层职责、与 Dify 的能力对照、部署形态、一条 PDF 从上传到答案的完整数据流。
> 口径：个人实战工程，Python + FastAPI，**不使用 Dify、不引入 LangChain**（框架层自研，即选型复盘 §3.1 的路线）。

---

## 一、设计原则（六条，后面所有模块都从这几条推）

| # | 原则 | 一句话 | 来源 / 同构 |
|---|---|---|---|
| 1 | **协议先行** | 解析器、向量库、模型、rerank 全部藏在接口后面，可替换 | 公司项目"统一 Markdown 中间态"同构：用一层协议解耦两侧 |
| 2 | **配置驱动** | 新数据源 / 新应用 = 加 YAML 配置，不加代码 | 低代码中台口径：参数配置→场景化 |
| 3 | **本地优先** | Ollama / MinerU / ASR / 向量库全可离线；远程模型只是配置项 | 数据敏感度三通道的同款判断：本地可跑是底线 |
| 4 | **失败可见** | 任何一步失败都进任务待办表，**绝不静默丢文档** | 公司项目解析兜底口径的方法论同构 |
| 5 | **评测先行** | 没有评测集的调参是盲人摸象；召回测试脚本与管道同批交付 | `03-项目叙事-AI.md` §4"重新做会怎么改" |
| 6 | **模型中立** | 所有模型调用走统一端点抽象（Ollama native / OpenAI 兼容双协议） | 复盘"模型完全中立"条目的自研版 |

## 二、五层架构

```
┌─────────────────────────────────────────────────────────────┐
│ L1 接入层  FastAPI                                           │
│   /docs 上传与解析任务   /chat 问答(SSE流式)   /admin 管理    │
├─────────────────────────────────────────────────────────────┤
│ L2 编排层  管道 DSL + 步骤注册表 + 执行器                      │
│   YAML 声明"接入→解析→切分→索引"  执行器管重试/降级/检查点      │
│   应用模板:模型+检索参数+Prompt+闸门开关                       │
│   (承接 Harness 六机制——见 02 文档 §五)                       │
├─────────────────────────────────────────────────────────────┤
│ L3 管道层  四段模块                                           │
│   ingest: pdf_mineru / av_asr / excel_staging                │
│   index : chunker / embedder / store(向量+BM25)              │
│   retrieve: hybrid(向量+BM25→RRF) / rerank / 直击库命中       │
│   generate: ollama_client / prompts / gates(两道纯代码闸门)   │
├─────────────────────────────────────────────────────────────┤
│ L4 模型层  Ollama(本地) + 端点注册表(可挂远程OpenAI兼容)        │
│   chat: qwen 系   embedding: bge-m3   rerank: 外部服务(可选)  │
│   ASR: faster-whisper / FunASR(本地,独立进程)                 │
├─────────────────────────────────────────────────────────────┤
│ L5 存储层                                                     │
│   SQLite: 任务表/trace/评测集/staging临时表/直击库             │
│   Chroma(嵌入式): 向量   原始文件与解析产物: 本地对象目录        │
└─────────────────────────────────────────────────────────────┘
        ▲ 中台四件套横切：工具网关 / 权限分级 / 审计留痕 / 计量观测
```

**分层规则**：

- 依赖只能自上而下：L2 编排 L3，L3 调 L4，任何层读写 L5。**L3 之间不互相 import**（generate 不直接调 index，检索结果作为数据传入）。
- 中台四件套是**横切面**不是层：网关在 L1 拦，权限在检索与工具调用前查，审计随 trace 落，计量随每次模型调用记。
- 换任何一层实现，其他层不动：换 MinerU → 只换 `ingest.pdf_mineru`；换向量库 → 只换 `index.store`；换模型 → 只改配置。

## 三、Dify 能力对照表（★核心表：自研不是重写，是逐项认领）

> 这张表就是"用 Dify 到底省了什么"的答案——每一行都是 ownrag 里一个真实存在的模块。

| Dify 提供的能力 | ownrag 落点模块 | 自研要点 / 难点 |
|---|---|---|
| Workflow 可视化编排 | `core/pipeline.py` + 管道 DSL（YAML） | 放弃可视化换**可 Git 版本化**；步骤图简单为线性+分支，暂不需要画布 |
| RAG 分块 / 清洗 | `index/chunker.py` | Markdown 结构感知切分（标题树 / 表格不切 / 锚点保留）——Dify 的通用切分不看结构 |
| 混合检索 / Rerank | `retrieve/hybrid.py` + `rerank.py` | 向量+BM25→RRF 融合自己写（百行级）；rerank 需外部服务（Ollama 不支持） |
| 召回测试（命中测试） | `scripts/eval_recall.py` + 评测集表 | Dify 是界面点选；自研是脚本+固定问答集，**可进 CI 回归**——这是反超点 |
| 模型配置 / 多模型 | `core/registry.py` 端点注册表 + `configs/models.yaml` | Ollama native 与 OpenAI 兼容双协议适配；本地并发受显存约束，需队列化 |
| Prompt 管理（控制台改/AB） | `generate/prompts.py` + `configs/prompts/*.yaml` | Prompt 文件化进 Git；AB 用两份模板+评测集对比——没有界面但**有版本史** |
| 应用发布为 API（含流式） | `api/routes_chat.py`（SSE） | FastAPI StreamingResponse 自实现 SSE；Dify 一键发布换来的代价是编排黑盒 |
| 日志 / 标注 / 用量统计 | `core/trace.py` + SQLite trace 表 | trace_id 串上传→解析→检索→生成；标注表只做"答案对错+纠错文本"最小闭环 |
| 知识库管理界面 | `api/routes_admin.py`（JSON API） | **无界面**是最大让步；页面壳后置，配置驱动的表单方案可承接 |
| 知识库文档上传 / 索引状态 | 任务表 + `/admin/tasks` | 解析状态机（pending→parsing→done/failed→重试）自己建——Dify 替你藏了这些状态 |
| 直击库 / QA 对模式 | `retrieve/` 直击库命中 + SQLite | L0/L1/L2 三层口径复用公司设计（指针见 04 文档 §四） |

**代价写实**（与复盘 §3.1 判断一致，但现在能量化到模块）：编排界面、知识库界面、权限企业级（SSO/多租户）三项**不做**，其余能力总量约等于 8-10 个紧凑模块——单人可维护，但每个都要自己扛坑。

## 四、部署拓扑与资源预算

**单机形态（默认）**：

```
Windows/Linux 单机
├── uvicorn ownrag.main:app          # FastAPI 进程（CPU 即可）
├── ollama serve                     # 本地推理，模型按需加载
│     ├── chat 模型（qwen 系，按显存选规格）
│     └── embedding 模型（bge-m3，常驻）
├── mineru 服务化（可选常驻）/ CLI 拉起（省显存）
├── ffmpeg（CLI 子进程，按任务拉起）
├── faster-whisper / FunASR（ASR 子进程，CPU 可跑，GPU 加速可选）
└── 数据目录 ./data/
      ├── ownrag.db        # SQLite：任务/trace/评测集/staging/直击库
      ├── chroma/          # 向量库
      ├── files/           # 原始文件（按 doc_id 归档，可重跑）
      └── parsed/          # 解析产物（Markdown + 元数据 JSON + 图片）
```

**显存预算（`【设计】`口径，以 8GB 显存为基准档，须实测校正）**：

| 组件 | 规格 | 预算 | 说明 |
|---|---|---|---|
| chat 主模型 | qwen 7B-8B 量化（Q4） | ~5-6 GB | 14B 档需 12GB+，走模型矩阵切换 |
| embedding | bge-m3 | ~1-2 GB | 常驻（`OLLAMA_KEEP_ALIVE`），高频小请求 |
| ASR | faster-whisper small/medium int8 | CPU 2-4GB 内存或 GPU ~2GB | 长音频按段喂，不整段进显存 |
| MinerU | pipeline 后端 | CPU 可跑；VLM 后端另需显存 | 页级路由：电子版走 pipeline，扫描/复杂版式才进 VLM |

**并发现实**：本地单卡跑不齐"chat + rerank + VLM"三件套同时满载——**队列化是架构的一部分**（L2 执行器带任务队列与并发上限），不是事后优化。这正对应公司叙事里"批量解析调度、按页数估时长控并发"的同构方法论。

## 五、一条 PDF 从上传到答案（全链路时序）

```
1. POST /docs/upload (PDF 文件)
   → 存 files/{doc_id}/source.pdf，任务表建行(pending)，返回 doc_id + trace_id
2. 编排层按 doc 类型查管道 DSL：pdf_v1
   步骤: detect_pages → parse_mineru → validate → chunk → embed → index
3. parse_mineru：页级路由（电子版→pipeline / 复杂版式→VLM）
   → 统一中间态 ParsedDoc：Markdown 正文 + 元数据(文号/章节路径/页码锚点)
   + 结构清单(表格/图片/公式位置) ；产物落 parsed/{doc_id}/
4. validate：空 Markdown / 表格破损 / 页数缺失 → 失败入待办表 + 告警钩子
   降级链：换后端 → 转 OCR → 人工队列（绝不静默丢）
5. chunk：结构感知切分，块带 元数据 + 锚点；embed：bge-m3 批量向量化
6. index：向量入 Chroma，正文入 SQLite FTS5（BM25 用），同 doc_id 原子替换
7. 用户 POST /chat："这份文件的报销口径是什么？"
   → 检索：元数据过滤(知识库/时间) → 向量+BM25 双路 → RRF → rerank → 候选池
   → ★闸门一(生成前)：候选充分性判定——不足则直接"未找到有效依据"+检索路径
   → ollama chat 流式生成，Prompt 强制"只用资料、逐条带来源"
   → ★闸门二(生成后)：引用真实性校验——每个引用块必须在候选池中，否则剔除重答或降级
   → SSE 推流给前端，trace 全程落表
```

**这条链上每个失败点都有出口**：2 失败→任务表 failed+待办；3 失败→降级链；5 失败→块级跳过+标记；7 检索空→如实说不知道（不进模型）；7 生成超时→降级短答+提示重试。**"失败可见"原则落到每一格。**

## 六、技术栈清单（与选型理由）

| 组件 | 选型 | 为什么 / 否决了谁 |
|---|---|---|
| Web 框架 | FastAPI + uvicorn | 与 Harness 同栈；原生 SSE/后台任务；否决 Flask（异步与类型化弱） |
| 编排 | 自研 DSL + 注册表 | 复盘口径：框架层自研。否决 LangChain（版本漂移 + 黑盒链）、Celery（重，单人维护不起）、Temporal（要额外集群） |
| 本地推理 | Ollama | 模型中立 + OpenAI 兼容 + 量化管理省心；否决 vLLM（重、面向吞吐而非单机）、llama.cpp 直连（自管量化太琐碎） |
| PDF 解析 | MinerU | 公司项目主责环节的工具，个人复刻同一选型；否决 PyMuPDF 直取（复杂版式还原差，但保留为降级链一环） |
| ASR | faster-whisper（主）/ FunASR paraformer（中文备选） | CTranslate2 int8、CPU 可跑、词级时间戳；FunASR 中文标点与热词更强——按语料类型配置化选择 |
| 音视频处理 | ffmpeg（CLI 子进程） | 事实标准；只做抽流/重采样/抽帧，转码策略在 DSL 里配 |
| Excel | pandas + openpyxl → SQLite staging | 零部署成本；否决 DuckDB（好，但 SQLite 已覆盖 staging 需求且是运维常识内）；生产换 PostgreSQL 只动连接串 |
| 向量库 | Chroma（嵌入式） | 单机零部署；生产档 pgvector 可选（同为接口后实现） |
| BM25 | SQLite FTS5 | 与主库同引擎零额外组件；否决 Elasticsearch（单机场景过重） |
| Rerank | bge-reranker-v2-m3（外部服务，可选） | Ollama 不支持 rerank——诚实承认并接口化；无 rerank 时 RRF 顺序兜底 |
| 存储 | SQLite + 本地目录 | 单机定位；字段设计按可平迁 PostgreSQL 写 |

**版本纪律**：所有依赖锁在 `pyproject.toml`，升级 = 独立分支跑评测集回归后合入——这条本身就是自研路线的代价演示（复盘 §3.1"版本漂移成本高"的亲身体感）。
